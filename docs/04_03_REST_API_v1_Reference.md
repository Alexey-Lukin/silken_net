# 04_03: Довідник REST API v1

## 🎯 Мета

Зафіксувати повний контракт REST API v1 як Єдине Джерело Істини (SSOT). Документ описує всі **ендпоінти** обох контурів — браузерний (кореневі шляхи) і машинний (`/api/v1`), розведені за тим, ХТО відвантажує клієнта [ARCH.77] — а також механізми автентифікації, ролеву модель доступу, формати запитів/відповідей та типовий lifecycle взаємодії прошивки Gateway з бекендом.

⛔ **Цей документ не замінюється machine-readable схемою, і це вимір, а не смак** ([`00_07`](00_07_Action_Plan_Tracker) ARCH.63, 2026-08-23). Більшість його ваги — доктрина, ратифіковані присуди й підстави відкинутих альтернатив, які в OpenAPI представлення не мають узагалі; schema-представна частина є меншістю. ⊕ **Друга нога виміру важливіша за першу:** планований `openapi.yaml` є **транскрипцією з `§4`/`§5`**, отже джерело транскрипції зрізати не можна за побудовою — інакше наступна регенерація нізвідки. Схема, якщо її колись напишуть, буде ДРУГИМ, негейтованим домом тієї самої множини; ⛔ не перевідкривати під приводом «документ великий».

- **Базовий URL:** браузерний контур — `https://<host>` (корінь); машинний контур — `https://<host>/api/v1`.
- **Формат відповідей:** JSON (якщо не вказано інше)

## 1. Автентифікація

API підтримує **два паралельні механізми** автентифікації, реалізованих у `BaseController`:

> **Архітектура контролера:** `Api::V1::BaseController` успадковує `ActionController::Base` (не `ActionController::API`),
> оскільки контролер обслуговує як JSON API (Bearer token), так і HTML Dashboard (Phlex + Session Cookie).
> `ActionController::Base` надає `ActionView::Rendering` з `view_context`, необхідним для Phlex `render_in`.
> Рейковий layout вимкнено (`layout false`) — Phlex-компоненти (`DashboardLayout`, `AuthLayout`) генерують
> повний HTML-документ самостійно. CSRF захист: `protect_from_forgery with: :exception` (найсуворіша стратегія).
> Bearer-token запити обходять CSRF через `handle_unverified_request` — браузери ніколи не прикріплюють
> `Authorization` header автоматично при cross-origin запитах, тому Bearer-token запити імунні до CSRF за дизайном.

> **[ARCH.77] Два контури, один `BaseController`.** Маршрутизація розведена на браузерний контур
> (кореневі шляхи — `/login`, `/dashboard`, `/trees/:id`…) і машинний контур (`/api/v1` — рівно
> п'ять маршрутів: M2M auth + refresh, `oracle_callbacks`, Helium SOS webhook, HTTP-uplink телеметрії).
> Критерій поділу — **ХТО відвантажує клієнта**, не формат відповіді (браузерний контур теж рясно
> віддає JSON): браузерний клієнт приходить із кожною відповіддю сервера — синхронізований за
> побудовою, версія в шляху нічого не версіонує; машинний клієнт — прошивка в полі або чужа
> консоль/оракул, що НЕ оновлюється разом із деплоєм, тож версія реальна. Контролери обох контурів
> фізично лишаються в `app/controllers/api/v1/**` (`scope module: "api/v1"`) — це внутрішня
> організація файлів, не адреса. `v2` тут не планується (⚖️ founder 2026-08-01, won't-do): за
> потреби версіонується ФОРМАТ (як у CoAP-тракті — `QATT_VERSION_2`, `wire-rev2.1`), а не
> переписується дерево маршрутів.
>
> ⚠️ **Чому won't-do, а не «поки що ні»** — щоб наступний прохід не перевідкривав питання:
> монолітний URL-бамп `/v1`→`/v2` — це форма, від якої відмовились усі, хто тримає реальні
> зовнішні інтеграції (дата-версія в заголовку у Stripe/GitHub/Shopify; Microsoft REST
> guidelines забороняють версійний сегмент у шляху прямо; Zalando — так само; Fielding для
> справді несумісної системи пропонує новий ДОМЕН, а не `/v2`). Протилежна настанова
> (Google AIP-185, MAJOR у шляху) адресує публічний multi-tenant продукт із зовнішніми
> клієнтами — не наш профіль, доки їх нуль. Найближчий прецедент нашої форми — Discourse:
> server-rendered Rails, HTML і JSON з тих самих екшенів, без `/api/v1`, і при цьому власний
> нативний мобільний застосунок.

### 1.1 Bearer Token (для API-клієнтів та прошивки Gateway)

```
Authorization: Bearer <token>
```

- Токен генерується при успішному POST `/login` (поле `token` у відповіді).
- Реалізація: `User.find_by_token_for(:api_access, token)` — Rails 8 `generates_token_for`. ⚠️ **[SEC.16] Purposes ДВА, і резолвер пробує обидва:** `:api_access` (людина) ⊥ `:m2m_access` (машина, §1.4). Вони ізольовані криптографічно — токен одного не резолвиться іншим, — і саме цим `authenticate_user!` знає, кого автентифікував; наслідок для scope тримає allowlist у §1.4.
- Токен має термін дії 30 днів.
- **Обмеження на вхід:** rate limit — 5 спроб за 1 хвилину (HTTP 429 при перевищенні).
- **M2M Auth (Gateway):** прошивка шлюзу не може інтерактивно оновити токен. Для цього використовується `POST /api/v1/auth/m2m_token` — Ed25519-підпис DID без логіна/пароля (§1.4 та §5.15).

### 1.2 Session Cookie (для браузерного Dashboard)

- Встановлюється автоматично при вході через форму `POST /login` (формат HTML).
- Cookie-based session — ставиться єдиною точкою логіну `establish_session` (**[S6.21] дім — `BaseController`**, бо шляхів входу два: пароль · MFA-челендж — а формула одна, і друга рукописна копія salt-формули вже раз непомітно розширила периметр звіряльників; `/sidekiq`-constraint ARCH.61 реюзить READ-бік salt-stamp'а): `session[:user_id]` + **[SEC.16]** salt-stamp `session[:ps]` = `password_salt.last(10)`; `authenticate_user!` звіряє stamp — зміна пароля миттєво гасить усі інші cookie-сесії (дзеркало salt-bound `api_access`-токена; раніше викрадений cookie переживав password-reset до 14 днів).
- **[S6.21] Другий фактор (TOTP)**: акаунт із `mfa_enabled?` після пароля сесії НЕ дістає — `sessions#create` кладе pending-мітку (`session[:mfa_pending_user_id]` + timestamp, TTL 5 хв) у ЧИСТУ сесію й шле на `/login/mfa` (row 113-114), де TOTP (анти-replay через `otp_last_used_at`) або одноразовий recovery-код завершує вхід тим самим `establish_session`. «Наполовину зайшов» не є станом; JSON-логін дістає 401 `code: "mfa_required"` без токена. Прапорець піднімається лише setup-флоу (row 115-117: провижн → QR → verify → rotation recovery-набору); набір показується РІВНО РАЗ (row 118, PRG + одноразовий session-маркер — секрети в cookie не їдуть), повторний показ існує лише як ротація НОВОГО набору зі step-up (row 119).
- Захист від Session Fixation: `reset_session` перед встановленням нової сесії — **і симетрично на виході** [SEC.16, 2026-08-15]. Логаут доти знімав рівно `session[:user_id]`, тобто ОДИН ключ із трьох: `:ps` і `:acting_org_id` переживали вихід і лежали в cookie до наступного логіну. Доступу це не давало (`authenticate_user!` вимагає `:user_id`), тож клас — не діра, а **залишковий слід**, і найдорожчий із трьох саме `:acting_org_id`: на спільному пристрої в браузері лишалась організація, в контексті якої працював попередній оператор.
- 🔴 **Звіряльників salt-stamp'а ЧОТИРИ, спільного предка в них немає, і саме тому предикат живе на МОДЕЛІ** (`User#session_salt_matches?` / `#session_salt_stamp`, [SEC.16] 2026-08-15): `BaseController#authenticate_user!` · `LocalesController` (успадковує сестру `ApplicationController`, власного `current_user` не має) · `ApplicationCable::Connection#verified_user` (ActionCable, не ActionController) · route-constraint `/sidekiq` у `config/routes.rb`. **Розходження між ними означало б, що один шлях переживає ревокацію, яку інший уже застосував** — тож форма звірки мусить бути ОДНА, і тепер вона фізично одна. ⚠️ Найтихіша частина периметра — четвертий сайт: він живе в `config/`, тому рецепт «`rg password_salt app/`» його не бачить ЗА ПОБУДОВОЮ.
  **Форма fail-CLOSED, і це не оборонність:** `password_salt` віддає `nil`, поки нема `password_digest`, а попереднє порівняння `session[:ps].to_s == user.password_salt.to_s.last(10)` згортало ОБИДВА боки в `""` — тобто для акаунта без пароля перевірка ставала **істинною** в усіх чотирьох місцях одразу. Сьогодні недосяжно (валідація вимагає пароль) і лишиться недосяжним за побудовою — акаунт без пароля не створюється. Форма лишається (коштує один предикат) як захист без запланованого пускача, а не як конструкція, що чекає свого тригера. Носій — `spec/models/user_spec.rb` (мутація на стару форму червонить рівно fail-CLOSED-приклади, позитивні лишаються зеленими).
- Rack::Attack `account_security/ip` (10/хв на PATCH/DELETE `/account_security*`) — step-up brute-force guard підбору `current_password` **[SEC.16]**.
- 🔴 **Обмежувачів на auth-шляху ДВА, вони незалежні, і safelist ОДНОГО не звільняє від другого — це присуд, не недогляд** [SEC.32, ратифіковано 2026-08-14]. Rack::Attack (ініціалізатор, IP-keyed, має safelist на loopback і приватні мережі) ⊥ **Rails-нативний `rate_limit` у контролері** (`sessions#create` 5/хв · `passwords#create` 3/5хв; `passwords#update` не має). Виміряно: `safelists["allow-localhost"].matched_by?` віддає `true` для `127.0.0.1`, а шостий `POST /login` із тієї ж адреси все одно дістає **429**.
  **Підстава розділення — різні предмети захисту.** Edge-шар боронить від ОБСЯГУ (скани, DoS), і там «внутрішня адреса» є осмисленим винятком. Контролерний ліміт боронить КОНКРЕТНИЙ обліковий запис від перебору пароля — а внутрішній брутфорс є таким самим брутфорсом, тож скомпрометований внутрішній хост це рівно той сценарій, проти якого ліміт і стоїть. **Тому safelist лишається поняттям edge-шару й на auth-ліміт не поширюється.**
  ⚠️ **Наслідок, який треба знати, плануючи throttle:** правило `logins/ip` (10/хв) **заступлене на двох шляхах із трьох** — Rails спрацьовує раніше (5 і 3 проти 10), і живим `logins/ip` лишається тільки `PATCH /reset_password`. Питай не «який ліміт», а «який ЩЕ механізм на цьому шляху відповість раніше»; контролер тут є таким механізмом нарівні з middleware. Носій межі — `spec/initializers/rack_attack_spec.rb` (пін червоніє, щойно в auth-контролері зʼявиться посилання на edge-шар: у Rails `rate_limit` є `by:`-лямбда, тобто спільний safelist коштує один рядок, і саме тому рішення потребує сторожа, а не коментаря).
- ⚖️ **Життєвого циклу члена організації НЕ ІСНУЄ — і це РАТИФІКОВАНА стеля TRL, не діра** [SEC.16, ⚖️ founder 2026-08-20]. Заведення · переведення · виключення людей живуть поза застосунком (сіди/консоль): `User.create` в `app/` — нуль, деактивації в моделі немає, тож звільнений співробітник із живою сесією тримає доступ до першої зміни пароля. Присуд: offboarding відкладено з named-тригером — **перший B2B-онбординг зовнішньої організації**; доти відкликань **три**, і найсильніше з них зʼявилось того САМОГО дня, що й цей присуд, тож перелік устиг протухнути за години: смерть salt-stamp'а на зміні пароля (вище) · ручна ротація `stream_epoch` · **`Gdpr::AnonymizeUserService(user, actor:)` з консолі** (SEC.18, 2026-08-20) — він занулює `password_digest`, тобто робить вхід неможливим ЗА ПОБУДОВОЮ для обох шляхів. ⚠️ Це **не** життєвий цикл: anonymize СТИРАЄ (він писався під Art.17), тож придатний там, де зберігати нема чого — порожній акаунт, помилково заведений рядок; для звільненого співробітника з наробком потрібна саме деактивація зі збереженням історії, і вона й далі відсутня свідомо. Додаючи будь-який auth-шлях, НЕ закладайся на існування деактивації — її немає свідомо, і читач цього параграфа є єдиним попередженням.
- 🔌 **Той самий cookie обслуговує ТРЕТІЙ шлях, і він живе поза `BaseController`** (SEC.25 Ф1, 2026-07-28): WebSocket-зʼєднання на `/cable` автентифікується в `ApplicationCable::Connection#connect`, який читає ту саму сесію й звіряє **той самий** salt-stamp — тобто зміна пароля гасить і відкритий сокет, а не лише HTTP-сесію. ⚠️ Дзеркальність тут несуча: розходження цих двох перевірок означало б, що вебсокет переживає ревокацію, яку HTTP уже застосував. Bearer-шляху там **немає** свідомо (WebSocket-handshake із браузера не несе `Authorization`), і зʼєднання встановлює лише ОСОБУ — авторизації підписки на конкретний стрім воно не робить. Механіка, гранулярність відкликання (per-device) і чому subscribe-авторизація не будувалась — [`04_04 §8.1`](04_04_Phlex_UI_and_Tailwind).

Відтоді `config/application.rb` перелічує railtie поіменно (порядок збережено — він несучий: argon2id мусить зайти до vips), і зміряно прямо: **161 → 147 маршрутів**, тобто зникло рівно 14. 🔴 **Клас окремий і найтихіший: поверхня, що існує без рішення когось її створити** — її не бачить ані аудит «чи всі наші ендпоінти захищені» (вона не наша), ані аудит мертвого коду (коду нема). Носій проти повернення (`rails app:update` переписує `application.rb` мовчки) — `spec/security/unmounted_engine_surface_spec.rb`, і він пінить ПОВЕРХНЮ, а не текст конфігу; ⚠️ його названа стеля — судить завантаження engine, ніколи Gemfile.

> **Примітка:** `/api/v1/oracle_callbacks` виключено з `authenticate_user!`, але захищено `before_action :verify_chainlink_signature!` — HMAC-SHA256 валідація заголовку `X-Chainlink-Signature` (ENV `CHAINLINK_HMAC_SECRET`). Якщо змінна не встановлена — HMAC пропускається з попередженням (dev/test). **При `WEB3_STRICT_MODE=true` (production) — відсутність `CHAINLINK_HMAC_SECRET` викликає `SecurityError` (fail-fast).**

#### 1.3а Машинний вхід = ДВА зняття, не одне [SEC.30]

> 🧱 **Інваріант: `skip_before_action :authenticate_user!` без `skip_forgery_protection` робить машинний ендпоінт мертвим у production.**

`protect_from_forgery with: :exception` оголошено в `Api::V1::BaseController`, тож `verify_authenticity_token` лишається в ланцюгу навіть тоді, коли автентифікацію знято, а `handle_unverified_request` пропускає **лише** Bearer. Машинний клієнт свій доказ несе в заголовку (HMAC) або в тілі (Ed25519), отже запит падає `InvalidAuthenticityToken` → `rescue_from StandardError` → **500, ще до власного крипто-гарда**. Симптом читається як «інтеграція не працює», а не як помилка авторизації.

Правило походить із того, **що саме стереже CSRF** — ambient authority, тобто повноваження, які браузер додає до запиту САМ (cookie). Машинний вхід її не має за побудовою: доказ там явний і в кожному запиті. Дзеркально — там, де ambient authority є, захист лишається, тому зняття мусить бути **вужчим за контролер**, якщо в ньому є хоч одна cookie-досяжна дія (`m2m_auth`: `skip_forgery_protection only: :create`, бо `refresh` іде через `authenticate_user!`, який приймає й сесію).

🔴 **Ця вісь невидима для сюїти СТРУКТУРНО:** `config/environments/test.rb` вимикає `allow_forgery_protection` — рівно той прапорець, що створює дефект. Тому спека, яка доводить HMAC-логіку, зелена й одночасно неправдива про production. Пін мусить **сам вмикати** прапорець — дім доказу `spec/requests/api/v1/csrf_machine_contour_spec.rb`, і його форма: «запит дійшов до СВОГО гарда» (401/404), а не «не 500» — друге лишилося б зеленим на будь-якій іншій поломці. Стан і перелік уражених — [`00_07`](00_07_Action_Plan_Tracker) SEC.30.

#### 1.3б Час із недовіреного входу — `Time.zone.iso8601`, ніколи `Time.iso8601` [ARCH.92]

> 🧱 **Інваріант: голий `Time.iso8601` ігнорує `config.time_zone` і читає зону ПРОЦЕСУ.**

На рядку без суфікса зони (`"2026-05-23T10:00:00"`) обидві форми дають РІЗНИЙ момент: виміряно на хості в EEST проти UTC-застосунку — **розходження 10800 с**. Вхід із `Z` чи офсетом розходження не дає, і саме тому клас непомітний.

🔴 **Сюїта до цієї осі сліпа ЗА ПОБУДОВОЮ, і причина не в недбалості:** усі наші фікстури згенеровані нашими ж серіалізаторами (`Time.current.iso8601`, `record.created_at.iso8601`), тобто ЗАВЖДИ несуть `Z` — тож розходження недосяжне для будь-якого наявного прикладу. Це вісь ПРОВЕНАНСУ ([`04_06 §B.2`](04_06_Testing_Guide_and_Coverage) BP #14): фікстуру виробляє не той, хто виробляє вхід у проді.

🔴 **Дискримінатор приклада мусить бути стійким до ХОСТА — зсувай зону ЗАСТОСУНКУ, не процесу.** `ENV["TZ"]` не зрушить уже закешовану зону процесу, а на CI вона й так UTC, тож пін на ній зелений там і не доводить нічого. Робоча форма — `Time.use_zone("Asia/Tokyo") { … }`: виміряно, що вона розрізняє форми **і** на EEST-хості, **і** під UTC.

⚠️ **Заміна форми міняє ще й поведінку ВІДМОВИ, і це вирішується посайтово:** `Time.zone.iso8601` **приймає** дату-без-часу (`2026-05-23` → північ), тоді як `Time.iso8601` на ній кидає. Тому:

| Сайт | Дата-без-часу | Чому |
|---|---|---|
| `maintenance_records#index` (фільтр) | **приймається** | фільтр за днем — легітимний намір; його коментар обіцяв це роками, а код не вмів |
| `m2m_auth#create` (timestamp) | **явний 400** | інакше відмова вироджується з «невалідний формат» у «прострочений» (401), і клієнт шукає розсинхрон годинника |
| `TelemetryLog.partition_pruned` · `BlockchainTransaction.find_with_partition_pruning` | **явний raise → fallback** | інакше секундне вікно навколо 00:00:00 віддає ТИХУ порожнечу замість чесного лукапу без прунінгу |

### 1.4 M2M Auth (для прошивки Gateway)

Gateway-пристрої використовують **Ed25519-підпис** для отримання та оновлення Bearer-токену без логіна/пароля. **[ARCH.77]** Один із п'яти машинних маршрутів — лишається під `/api/v1` (клієнт тут прошивка в полі, не браузер):

```
POST /api/v1/auth/m2m_token
{
  "did": "SNET-A1B2C3D4",
  "timestamp": "2026-03-29T12:00:00Z",
  "signature": "<Ed25519 sig of 'SNET-A1B2C3D4:2026-03-29T12:00:00Z'>"
}
```

- Ed25519 public key реєструється під час provisioning (поле `ed25519_public_key`) і зберігається в `hardware_keys.ed25519_public_key_hex`.
- Бекенд перевіряє підпис та timestamp (±5 хвилин) перед видачею токена.
- **Replay-захист (nonce):** SHA256-дайджест підпису зберігається в Redis із TTL 10 хв (`SET NX`). Повторне використання тієї ж `signature` повертає `401 Unauthorized` із повідомленням `"Replay attack detected"`. **[S6.1]** При Redis outage: fallback на Solid Cache (DB) — шлюзи не отримують `503`.
- Токен дійсний 30 днів. Для оновлення: `POST /api/v1/auth/m2m_token/refresh` з поточним Bearer token (§5.15.1), або повторний `POST /api/v1/auth/m2m_token` з Ed25519-підписом.
- ✅ **[SEC.16] Scope звужено 2026-08-15.** Доти виданий токен був `:api_access` першого org-admin'а — **нерозрізнимий від людського** admin-Bearer, тобто компрометована польова Королева відкривала повний admin-API організації (2-га ланка cross-tenant-takeover з аудиту §04). Тепер видається окремий purpose **`:m2m_access`**, а `BaseController::M2M_ALLOWED_ACTIONS` тримає стелю поверхні: `m2m_auth#refresh` + `telemetry#gateway_uplink` — і це **весь** Bearer-периметр машини, бо решта машинних маршрутів автентифікується не токеном (`m2m_auth#create` — Ed25519 у тілі; `oracle_callbacks` і `helium_sos` — HMAC). Поза allowlist'ом — **403 `code: "m2m_scope"`, свідомо не 401**: токен валідний, просто не для цих дверей, а 401 послав би прошивку крутити Ed25519-цикл перевидачі проти дверей, які не відчиняться ніколи.
  🔴 **Purpose мусить перевидаватись ТОЙ САМИЙ, інакше звуження живе рівно один refresh-цикл:** `refresh` стоїть у машинному allowlist'і, тож видача звідти `:api_access` дозволила б машині **підвищити саму себе** до повного scope одним запитом. Форма — **allowlist, ніколи denylist**: нових admin-екшенів зʼявляється більше, ніж машинних, тож denylist роздавав би доступ кожному, кого забули дописати; тут забудькуватість коштує гучного 403 на машинному шляху.
  ⚠️ **Виміряна межа, яку варто знати, плануючи цей тракт:** прошивка сьогодні **не робить HTTP узагалі** — увесь трафік Королеви це CoAP/UDP :5683 повз Rails (`telemetry/batch`, `device/event`, `poll`, `ota`), автентифікований підписом у payload'і, а не Bearer'ом; описаний тут refresh-цикл у `firmware/queen/` не реалізований. Тобто allowlist сьогодні описує **потенційну** поверхню машини, а не спостережуваний трафік — і саме тому його звуження нічого в полі не ламає.
- Детальний опис: §5.15.

> **Примітка:** у `development` середовищі `StandardError` не перехоплюється — Rails показує детальний backtrace.

> 🔴 **Ця таблиця описує ЛИШЕ JSON-контракт, а більшість рендерерів помилок HTML-випадку не розглядає — тож на дашборді користувач бачить JSON-блоб замість сторінки помилки.** Шість із семи хелперів `BaseController` (`render_forbidden` · `render_forbidden_pundit` · `render_not_found` · `render_parameter_missing` · `render_validation_error` · `render_internal_server_error`) — це голий `render json:` без жодного `respond_to`. ⚠️ Тут доти стояло «п'ять» **над переліком із шести**, тоді як абзац нижче вже казав «шести»: частковий фікс оновив одне число й лишив сусіднє, і блок суперечив сам собі. Форму, яку треба повторити, показують ДВА: `render_no_organization` (`Errors::NoOrganization`) і — з 2026-07-30 — **`render_unauthorized`**, найширший гард застосунку. ✅ **Станом на 2026-07-31 голими лишились ТРИ, і жоден із них не борг:** `render_not_found` · `render_forbidden_pundit` · `render_internal_server_error` дістали HTML-гілки (дім тексту — `Errors::Page`); `render_parameter_missing` і `render_validation_error` — свідоме won't-do (перший суто API-шлях, у другого всі сім прямих викликів уже всередині `format.json`); `render_forbidden` лишається страховкою після того, як роле-фільтр дій зняв його штатні шляхи ([`04_04 §6.4`](04_04_Phlex_UI_and_Tailwind)). ✅ **Клас ЗАКРИТО 2026-08-01 [UI.9] — голих не лишилось жодного:** `render_forbidden` дістав власний `respond_to`, а `render_parameter_missing` і `render_validation_error` — спільний `render_error_page`, тобто won't-do-присуди про них нижче описують **підставу рішення на той момент**, а не чинний стан коду.
>
> ✅ **`render_unauthorized` полагоджено [SEC.25]: HTML-гілка рендерить сторінку логіну (`Sessions::New`) НА МІСЦІ, зберігаючи статус 401.** Вибір між «редирект на логін» і «сторінка на місці» вирішено виміром, і воно інвертувало початкове припущення трекера: шість request-прикладів, які «мали б почервоніти» від редиректу, виявились не недбалими API-тестами, а сигналом — два роблять справжній cookie-логін через `POST /login`, а один б'є в дію (`telemetry#live`), що взагалі не має `format.json`, тож «забути `as: :json`» там неможливо. Плюс редирект без `return_to` (механізму в дереві немає — `sessions#create` завжди веде на дашборд) викинув би користувача зі сторінки, яку він відкривав. Рішення узгоджене з власним прецедентом: `render_login_failure` уже відповідає на невдалу автентифікацію саме так — сторінка на місці, 401 в обох форматах. Наслідок для сумісності: **статус не змінився**, тож жоден наявний приклад не зрушив.
>
> Клас ширший за винятки, і на той момент лишався відкритим для решти **шести** (⚠️ тут доти стояло «п'яти» — арифметична помилка, що перекочувала з commit-меседжа й тиражувалась як цитата себе; перерахунок по коду 2026-07-31): `render_forbidden` досяжний зі звичайних before-action RBAC-гардів, `render_not_found` — з будь-якого `find`, а `render_internal_server_error` ловить `StandardError` на всьому дашборді. ⚠️ І ціна їхнього полагодження **не в самих рендерерах**: `base_controller_spec` будує контролер через `described_class.new` без Rails-диспетчера й стабить лише `render`, а `respond_to` лізе в `request.formats` — тож додавання HTML-гілки впаде там `NoMethodError` на nil, тобто вісім прикладів треба переписати на справжній HTTP. `render_unauthorized` закрився дешево саме тому, що прямого приклада в тому харнесі не мав узагалі. ✅ Обсяг закрито повністю — ✅-нота вище.
>
> ⚖️ **Обсяг звужено до ДВОХ гілок (founder 2026-07-31) — і вирішальним був не сам рендерер, а те, ЯК до нього доходять.** `render_forbidden`/`render_forbidden_pundit` мали **штатний** шлях: сайдбар показував усім ролям одинадцять гейтованих пунктів ⚠️ (це вимір ДО-стану, і він **не відтворюваний за побудовою**: роле-фільтр, який цей присуд і завів, той стан прибрав — тобто число є провенансом, не живою величиною; DOC-T.84 третя категорія), тож 403-блоб діставався одним кліком по видимому меню. Роле-фільтр ([`04_04 §6.4`](04_04_Phlex_UI_and_Tailwind), UI.5) зняв його з МЕНЮ. ⚠️ **Тут доти стояло «тепер обидва досяжні хіба URL-хакінгом» — спростовано adversarial-виміром того ж дня:** гарди з `only:` сидять ГЛИБШЕ за дію пункту меню, тож видима сторінка й далі пропонує дію, недосяжну цій ролі. Штатні кліки цього класу живі — admin → Species DNA → «Define DNA»/«Edit» (`authorize_super_admin!, only:` — блоб дістає навіть адмін) ⚠️ **а два інші приклади того самого речення вже НЕ живі, і це знайдено 2026-08-29:** subscriber → «Acknowledge» закрито ще `e426f8f9` (2026-07-31, UI.6) — `Alerts::Row` приймає `current_user:` з fail-closed `nil` і ховає кнопку взагалі; forester → «Simulate» зник разом із дією 2026-08-15 ([UI.7]). 🔑 **Механізм протухання варто знати: правка 08-15 оновила ТРЕТІЙ приклад у реченні й не перечитала два сусідні** — тобто речення старіло поелементно, а не цілком. Обидва лишаються як ФОРМА класу, не як живі шляхи, — і корінь у них той самий, що був у меню: компонент сторінки не приймає користувача, тож фільтрувати дію нема чим. Лік теж той самий (сховати дію від ролі, якій вона недоступна), а не HTML-гілка — тож звуження до двох гілок лишається чинним, але його підстава ВУЖЧА, ніж записано: `render_forbidden` не став недосяжним, він став наступною ітерацією того самого фільтра → [`00_07`](00_07_Action_Plan_Tracker) UI.6. `render_validation_error` виміряно **живим** (сім прямих викликів у чотирьох контролерах), і всі вже всередині `format.json` — HTML-гілка йому не потрібна; ✅ його МЕРТВИЙ `rescue_from ActiveModel::ValidationError` знято 2026-08-01 (джерел винятку нуль — `validate!` у дереві не зустрічається; сам виняток несе `model`, а не `record`, тож хендлер упав би `NoMethodError` ще до рендера). ⚠️ **Сусіда `ActiveRecord::RecordInvalid` СВІДОМО не підвішено на цей хендлер**, хоч сигнатура збіглася б ідеально: він летить у `StandardError` → 500, і це правильно — контролери гардять користувацький ввід явно ДО bang-мутації, тож `RecordInvalid`, що долетів до бази, означає пропущений гард (наш баг), а мʼяка 422 замаскувала б його під помилку людини. `render_parameter_missing` — суто API-шлях. Лишаються **три** (⚖️ 2026-07-31, обсяг переглянуто після перевиміру): **`render_not_found`** (протухлий лінк), **`render_internal_server_error`** (будь-який прод-баг) і **`render_forbidden_pundit`** — останній додано саме виміром: `wallets`/`users` мають `authorize` І `format.html` на тих самих екшенах, тобто це money-поверхня з буденним тригером «super_admin відкрив гаманець org-A → перемкнув контекст → «назад» у браузері». `render_forbidden` тоді відкладено за [`UI.6`](00_07_Action_Plan_Tracker): він найдорожчий (7 прикладів проти 2–3 у решти), а його штатні шляхи знімає роле-фільтр самих дій — ✅ і закрито [UI.9] 2026-08-01, коли вимір показав, що асиметрія з pundit-близнюком жила для дванадцяти контролерів із класовим гардом. ⚠️ Ціна тут **пофайлова, не гуртова** — кожен рендерер має власний ізольований `describe`, і прецедент переписування на справжній HTTP уже стоїть у цьому ж файлі спеки (`коли організації немає`, `коли автентифікації немає`); усереднене «~8 крихких прикладів» ховало розкид у кілька разів і саме воно робило обсяг більшим, ніж робота. ✅ **ТРИ гілки шипнуто 2026-07-31, і остаточний перевимір ціни знову дав ВНИЗ: переписати довелось три приклади, не вісім** (у `base_controller_spec` кожен із цих рендерерів має рівно один, а «сімка» для `render_forbidden` — це чужий `describe "RBAC helpers"`). 🔴 Односторонність трьох перевимірювань поспіль важливіша за самі числа: щоразу завищена ціна ставала підставою відкласти. **Форма розводить рендерери по ШАБЛОНАХ, і це вимір, не смак:** `render_not_found` (31 із 43 `find`-сайтів досяжні з браузера) і `render_forbidden_pundit` (17 із 29 `authorize`-викликів) → `render_dashboard`, бо там глядач гарантовано автентифікований і навігація йому чесна; `render_internal_server_error` → `render_auth_page`, бо це ЄДИНИЙ, до якого є відтворюваний шлях із `current_user = nil` (CSRF-виняток летить ДО `authenticate_user!`), і його blast-radius — уся поверхня. ⚠️ **Компонент помилки свідомо не має власних `t()`:** він рендериться зсередини `rescue_from`, а `raise_on_missing_translations` робить забутий ключ винятком, якого Rails там уже не переловить — тобто сторінка помилки впала б від власної.

### 2.2а Контракт відповіді на МУТАЦІЮ (браузерний контур) [SEC.25]

> 🧱 **Інваріант: non-safe дія відповідає редиректом, `4xx`/`5xx` або `turbo_stream` — але НІКОЛИ `200` без редиректу.**

Це не стильова вимога, а умова роботи Turbo Drive, і причина названа в його ж handbook: браузер має вбудований діалог «надіслати форму ще раз?» для перезавантаження POST-URL, який Turbo відтворити не може, тому відповідальності за такий URL не бере. Механіка в джерелі гема (`turbo.js`, `requestSucceededWithResponse`): на `statusCode == 200 && !redirected` кидається `Error("Form responses must redirect to another location")` → `console.error`, і **сторінка не оновлюється взагалі**.

| Ситуація | Відповідь | Нотатка |
|---|---|---|
| успіх мутації | `redirect_to …, status: :see_other` | 🔴 **303 треба ставити ЯВНО**; flash переживає редирект |
| валідація впала | `render …, status: :unprocessable_content` (**422**) | дзеркалить JSON-гілку того ж `respond_to` |
| часткове оновлення | `text/vnd.turbo-stream.html`, **200 законний** | це не навігація |

🔴 **Тут доти стояло «Rails сам віддає 303 для non-GET» — це НЕПРАВДА, виміряно рантаймом 2026-08-01** (`PATCH /settings` без явного статусу → **302**). Заява була несуча в найгіршому сенсі: на неї спиралось ціле сімейство редиректів, які через це лишались 302 після PATCH/DELETE. 🔴 **А ось МЕХАНІЗМ, який тут стояв поруч, виявився хибним — спростовано браузерним виміром 2026-08-10.** Доти було записано: «Turbo читає `_method` і шле **справжній** PATCH/DELETE (`turbo.js`, `determineFetchMethod`), а Fetch-спека конвертує 3xx у GET лише для POST, тож браузер перевидає той самий метод на адресу редиректу — де зареєстровано лише `get`». Насправді `turbo-rails` вішає **глобальний** слухач `encodeMethodIntoRequestBody` (`turbo.js`, глобальна підписка на `encodeMethodIntoRequestBody`), який для КОЖНОГО не-GET сабміту форми кладе дієслово в тіло як `_method` і виставляє `fetchOptions.method = "post"` — тобто `determineFetchMethod` викликається саме ЗВІДТИ, і на дріт PATCH/DELETE не виходить **ніколи**. Отже описаний симптом («дія відбулась, а користувач бачить 404») у цьому застосунку **недосяжний за побудовою**; шляху `data-turbo="false"`, який міг би його відкрити, у дереві теж не лишилось ([`UI.11`](00_07_Action_Plan_Tracker) крок 3). ⚠️ **Правило `status: :see_other` лишається чинним — але як КОНВЕНЦІЯ, а не як лік від бага:** 303 є семантично правильною відповіддю на не-GET (RFC 9110 §15.4.4) і не залежить від того, чи Turbo колись перестане кодувати метод у тіло. Тому відвантажені 303 (`account_security` ×11, `maintenance_records`) правильні — впала ПІДСТАВА, не вердикт. 🔴 **Урок, ширший за випадок: обидва попередні проходи міряли ПЕРЕДУМОВУ (що `redirect_to` віддає 302) і жоден не міряв ВИСНОВОК (що робить браузер), а речення про поведінку фреймворка читається як довідка, тож перевіряти його не спадає на думку.** Носій тепер поведінковий, не текстовий — `spec/features/turbo_wire_method_spec.rb`, mutation-verified (очікування `PATCH` червонить його з `got: "POST"`). ✅ Виправлено 2026-08-01 [SEC.25 Ф4].

🔴 **Гард Turbo перевіряє РІВНО `200`, тож `2xx`-рендер сторінки його минає — і ламає не оновлення, а АДРЕСУ** [SEC.25, 2026-08-03]. `responseSucceededWithoutRedirect` — це буквально `statusCode == 200 && !redirected`, отже відповідь `:created` (201) із повною сторінкою проходить як успіх, і Turbo далі робить `proposeVisit(fetchResponse.location)`, де `location` = `expandURL(response.url)` — тобто **адреса самого POST'а**. Якщо маршрут зареєстровано як `only: [:new, :create]`, адресний рядок після кожної дії вказує на URL, де GET не існує, і Reload (або «Назад»→«Вперед») дає `RoutingError`. Дефект тихий двічі: сторінка оновлюється нормально, а поламане виявляється лише перезавантаженням; і сам він тримається на випадковості — заміна 201 на 200 «для акуратності» мовчки вимикає оновлення взагалі, лишаючи слід тільки в консолі. **Тому правило читається без винятку для 2xx: мутація відповідає редиректом, 4xx/5xx або `turbo_stream` — рендер сторінки не є легальною відповіддю на мутацію навіть зі «схвальним» статусом.**

🔴 **Симптом порушення найпідступніший з можливих: «дія вдалась, і про це не сказано».** Побічний ефект уже стався (запис створено, ключ записано, воркер полетів), а сторінка не ворухнулась — тобто це не схоже на помилку ні для користувача, ні для тесту. Саме так `provisioning#register` показував лісникові порожнечу на **успішній** провізії пристрою.

⚠️ **Асиметрія всередині одного `respond_to` — найчастіша форма дефекту, і вона сама себе викриває:** `format.json` віддає 422, а `format.html` мовчки бере дефолт `status: :ok` з `render_dashboard`. Тобто автор знав правильний статус — просто HTML-гілка його не отримала. Шукати треба саме цю пару, а не «місця без `status:`» взагалі: у GET-екшенах `200` законний.

🔴 **`respond_to` без збігу формату НЕ дає чистої 406 — він спершу проходить через наш ВЛАСНИЙ обробник, і саме тому «яку помилку побачить людина» залежить від того, чи вміє error-рендерер віддати запитаний формат.** `UnknownFormat` — це `StandardError`, тож його першим ловить `rescue_from StandardError` (§2.2) і кличе `render_internal_server_error`; а той сам робить `respond_to`. Якщо запитаний формат рендерер уміє (`text/html`) — людина дістає нашу сторінку 500. Якщо ні (екзотичний `application/xml`) — хендлер падає вдруге вже зсередини себе, виняток виходить у middleware, і Rails мапить його на **406** (виміряно рантаймом; `Accept: */*`, тобто всі реальні клієнти, негоціює нормально). ⚠️ Практичний наслідок для браузерного контуру: гілка `respond_to` без `format.html` на дії, яку тисне `button_to`, дає не «чесний 406», а помилку ЗАСТОСУНКУ — тобто відсутність html-гілки маскується під збій сервера.

⚠️ **Ціна невидимості на рівні тестів:** request-спека бачить статус і тіло, але не бачить, що з тим тілом зробив браузер — тож `have_http_status(:ok)` на мутації **цементує** дефект замість ловити його. Доказ цього класу належить browser-шару ([`04_06 §B.1.4`](04_06_Testing_Guide_and_Coverage)).

#### 2.2б Голий `render json:` у браузерному контурі [SEC.25 Ф4]

> 🧱 **Інваріант: дія, чий маршрут зареєстровано ПОЗА `namespace :api/:v1`, не сміє мати гілки відмови без `respond_to`.**

Контур вирішує **хто відвантажує клієнта** (§1, ARCH.77), а не формат успішної відповіді. Голий `render json:` у браузерній дії означає, що людина бачить сирий блоб замість сторінки — і найчастіше саме в момент відмови, тобто коли пояснення потрібне найбільше.

✅ **Шість гілок закрито 2026-08-01**, усі досяжні кліком по наявному елементу: `provisioning#register` ×4 (невалідний UID · повторна провізія 409 · чужий кластер 404 · метод-рівневий `rescue StandardError`) · `actuators#execute` 409 · `maintenance_record_photos` 404 на знятому фото.

- 🔴 **Локальний `rescue StandardError` у тілі екшена перехоплює РАНІШЕ за класовий `rescue_from`** — тобто локально відтворює дефект, який глобально вже закрито. Лік — не дублювати `respond_to`, а делегувати в `render_internal_server_error(e)`, лишивши доменне логування.
- ⚠️ **Форма посадки залежить від того, чи може людина виправити ввід.** Де може — назад у форму з помилкою в тому ж місці, де показується модельна валідація (інакше та сама помилка виглядає для користувача іншим класом події); де ні — редирект на сторінку, де живе кнопка. Сторінка відмови — інше **дієслово**, і для цих гілок вона хибна.
- 🔴 **Фікс тут невидимий для сюїти в ОБИДВА боки без нового приклада:** наявні приклади цих гілок форсують `as: :json` і асертять лише статус, а статуси не змінювались. Пін мусить бути на **`media_type`**, не на статус — інакше він лишається зеленим і на зламаній поверхні.
- ⚠️ **Порядок гілок усередині `respond_to` — `format.json` ПЕРШИМ.** На `Accept: */*` (тобто всі реальні машинні клієнти) Rails віддає ПЕРШИЙ оголошений формат, тож перестановка гілок «для читабельності» мовчки перемкнула б їх на HTML. Правило видно лише в діфі, а зламане — лише в проді.
- ⚠️ **Периметр ≠ грубий лічильник `render json:`.** ⚠️ **Числа тут свідомо немає, і це куплено трьома промахами поспіль** — останній був не в арифметиці, а в ІНСТРУМЕНТІ: греп за цілим виразом не бачить форми `render(json:` без пробілу, тож будь-який рукописний лічильник тут занижений за побудовою. Єдиний чесний вимірювач периметра — екстрактор гейта (↓), не греп. Самих викликів у контролерах багато, але переважна більшість законна: JSON-only-за-задумом периметр — це машинний контур (`m2m_auth`, `oracle_callbacks`, `helium_sos`, `gateway_uplink`), і він лишається як є.

✅ **Обидва інваріанти §2.2 дістали регресійного сторожа 2026-08-03: `spec/security/browser_contour_json_spec.rb` + екстрактор `lib/browser_contour_inventory.rb` + реєстр `spec/support/browser_contour_registry.rb`.** Доти сім гілок було закрито вручну, і **жодна з них не могла почервоніти** — периметр міряли грепом тричі й тричі помилялись, тож наступний голий `render json:` приїхав би так само тихо.

- 🔴 **Чому AST, а не греп: відрізняє порушення від норми не сам виклик, а його ПОЛОЖЕННЯ в дереві.** `render json:` усередині `format.json` — законний і становить більшість із тих ~170; той самий виклик поза `respond_to` — дефект. Грепом ця різниця невиразна в принципі, і саме тому лічильник тут падав щоразу.
- 🧱 **Форма — курована мапа, що ЛИШЕ СКОРОЧУЄТЬСЯ**, і вона обрана проти двох гірших: skip-list, який дозволяє дописувати винятки, гниє тихо й за півроку стає фактичною політикою (та сама підстава, за якою відхилено `verify_authorized` — §3); а «полагодити всі» купувало б вакуумні піни й з'їдений coverage-слек проти промаху, якого ніхто не побачить, бо гілки недосяжні з UI. Кожен запис реєстру несе **підставу (`why`) і УМОВУ ПОВЕРНЕННЯ (`back`)** — подію, після якої рядок зникає, а гілка стає must-fix («з'явиться лінк», «у формі з'явиться це поле»). 🔴 **Обидві половини гейтуються ОКРЕМИМИ прикладами лише з 2026-08-03 [SEC.31]: доти двобічна заява мала однобічного сторожа** (він міряв довжину рядка підстави), і **17 із 37 записів умови повернення не несли взагалі** (за словом їх 16 — різниця рівно в рядку, де слово «повернення» присутнє, а події немає, і саме вона доводить, що лексичний гейт міряв би словник) — тобто конвенцію було заявлено в трьох домах і не виконано в майже половині корпусу. Лік — не лексичний: пошук слова червонів би на чесній DRY-прозі («той самий клас query-гарда») і задовольнявся б порожнім реченням, тож `back` став **окремим полем**, а `:none` — явною декларацією «браузерного двійника не існує», дозволеною лише машинним входам і приватним хелперам.
- **Ключ реєстру — `файл#екшен`, свідомо без номера рядка:** реєстр, ключований рядками, червонів би на переміщенні коду, тобто навчав би себе ігнорувати.
- ✅ **Друга вісь того самого питання живе там же [SEC.30]** — «хто відвантажує клієнта» вирішує не лише формат, а й наявність ambient authority, тож гейт заразом тримає CSRF-інваріант §1.3а. Двобічно: машинний вхід мусить бути звільнений (інакше 500 до крипто-гарда), браузерний — ні; **друга половина важливіша, бо її промах тихий** — зайва дірка не валить жодного тесту.
- 🔴 **І саме та важливіша половина міряла ІМʼЯ колбека, а не його дію — виправлено 2026-08-03 [SEC.31].** `skip_callback` з умовою не видаляє колбек, а підміняє його умовним близнюком **із тим самим символом у `filter`**, тож предикат на `filter.include?(:verify_authenticity_token)` читав як «гард на місці» ЧОТИРИ різні способи зняти захист: `only:` · `except:` · `skip_before_action :verify_authenticity_token` зі скоупом · `protect_from_forgery with: :null_session`. Наслідок був гірший за пропуск: приклад «частково звільнений контролер ЗБЕРІГАЄ гард» ставав **тавтологією, нездатною почервоніти**, бо для скоупленого зняття предикат завжди істинний. 🔴 **І перший лік був півкроком, який adversarial зняв:** розрізняти «умовне/безумовне» не досить, бо вердикт виходить про ФОРМУ зняття, а важить його ОБСЯГ — інверсія `only: :refresh` (машинну дію закрито, cookie-дію відкрито), `except:` і розширення на обидві дії дають однакове «умовне» і проходять зеленим. Чинна форма — **поведінковий вимір**: `ActionFilter#match?` відповідає, на яких саме діях колбек спрацює, тож реєстр декларує `unguarded` (точний перелік звільнених дій або `:all`), а гейт звіряє множини й падає ДВОМА окремими прикладами — недо-зняття (машинна дія лишилась під гардом → 500 до крипто-гарда) і пере-зняття (звільнено те, чого реєстр не оголошував). Стратегія — третя, незалежна вісь (`with: :null_session` лишає колбек на всіх діях і однаково нічого не боронить). Мутація-верифіковано кожною формою окремо; вимір поведінковий, бо `only:` кладе фільтр у `@unless`, а `except:` — у `@if`, і структурний розбір розсипався б.
- 🔴 **Корені ієрархії деривуються, а не перелічуються.** Літерал знав два (`ApplicationController`, `Api::V1::BaseController`), а їх ТРИ — `ReadinessController` успадковує `ActionController::Base` напряму. Клас відтворювався щоразу, коли корінь дописували руками (перша редакція знала один і міряла порожню множину), тому множина береться від `ActionController::Metal` — спільного предка `Base` і `API` — з фільтром за походженням файла. Ліхтар при цьому міряє **повноту, а не обвал**: поріг на розмір стеріг лише зникнення множини (45 контролерів при порозі 20 — запас на втрату більш ніж половини), тоді як промах цієї осі виглядає як ОДИН відсутній елемент, тож звірка йде проти незалежного джерела — **файлів**. ⚠️ Роутер для цієї ролі спокушає й НЕ годиться: маршрутизований контролер є нащадком `Metal` за побудовою диспетча і проходить той самий фільтр походження, тож «маршрутизовані мінус деривовані» — порожня множина завжди, а не сьогодні. Перша редакція фіксу саме так і зробила, тобто замінила поріг на тавтологію; спіймано adversarial-проходом, доведено звуженням фільтра (гейт лишався зеленим, хоч `ReadinessController` випадав з нагляду).
- ✅ **CSRF-вісь дістала третій вимір — ВЛАСНІСТЬ рішення [SEC.31, закрито]**, і перелік перемикачів по дорозі виявився неповним. Обсяг колбека й стратегія обидва сліпі до того, **хто ВИРІШУЄ**: `protect_from_forgery` лише маршрутизує неперевірений запит у `handle_unverified_request`, тож перевизначення того методу в НАЩАДКУ знімає захист цілком, не рухаючи ні колбека, ні стратегії. Тепер міряється `.owner` — множина, що лише скорочується (сьогодні рівно два власники: сам Rails і `Api::V1::BaseController`). 🔴 **І знайшовся ЧЕТВЕРТИЙ перемикач, якого пункт не називав, — він обходить обидва наявні виміри за побудовою:** `self.allow_forgery_protection = false` на самому контролері. `config` контролера — `InheritableOptions` з `default_proc` у батька, тож запис на нащадку **затіняє** глобальний, а отже й `csrf_machine_contour_spec`, який вмикає прапорець на `ActionController::Base`. ⚠️ Дискримінатор мусить міряти КОД, а не СЕРЕДОВИЩЕ: у `test` глобальний прапорець `false`, тож пряме читання червоніло б на всіх 45 контролерах — гейт піднімає глобальний і лишає рівно тих, хто записав власне. ⊕ Заразом виявлено, що перевірка **стратегії** була ХИБНО-ПОЗИТИВНОЮ для нащадків `BaseController`: той кидає сам і в стратегію не делегує, тож `with: :null_session` червонив би гейт, нічого не зламавши — тепер вона питає стратегію лише там, де стратегія й вирішує.
- 🔒 Стелі названі в самому файлі; головна: гейт бачить СИНТАКСИС, не намір — чи маршрут браузерний, вирішує `routes.rb` (ARCH.77), тому реєстр є декларацією людини, а не висновком екстрактора. **З 2026-08-03 їх сім, і чотири нові куплені виміром [SEC.31]:** периметр — ЕКШЕНИ, не САЙТИ (багатосайтових ключів у реєстрі більшість, тож другий голий виклик у вже зареєстрованому екшені невидимий) · форма виклику лишається значущою і на рівні AST (хеш у дужках як позиційний аргумент, подвійний сплат і рядковий ключ — інші вузли) · усе всередині `respond_to` благословенне за побудовою, включно з `format.html { render json: }` · CSRF-половина не бачить `handle_unverified_request`, хоч саме його тіло і є реальною політикою для переважної більшості контролерів. ⚠️ Живих екземплярів у другої й третьої — **нуль**, і це «порожньо», а не «безпечно»: різниця несуча, бо перший же сайт такої форми приїде мовчки.
- ⚠️ **Лічильник сайтів на екшен відхилено виміром, а не смаком.** переважна більшість багатосайтових ключів не називає числа в прозі, тож пін став би реєстром неперевірених чисел, а машинне додавання гілки, гейтованої `request.format.json?`, червонило б чесний рефактор. Натомість стелю названо явно.
- 🔴 **Нерозпарсений контролер більше не зникає зі скану мовчки** (`BrowserContourInventory::ParseFailure`). Доти `next unless result.success?` викидав файл без сліду, а обидві JSON-перевірки лишались зеленими: множина «нових сайтів» від зникнення файла лише порожніє, а перевірка на протухлий реєстр червоніє тільки для файлів, що вже мають у ньому рядок.

### 2.3 Пагінація

Всі list-ендпоінти підтримують стандартну пагінацію Pagy:

| Query-параметр | Тип | За замовчуванням | Опис |
|---|---|---|---|
| `page` | Integer | 1 | Номер сторінки |
| `limit` | Integer | 20 | Кількість записів на сторінку |

> **Виключення розміру сторінки:** `maintenance_records#index` використовує `items: 50` (не 20); `maintenance_records#photos` використовує `items: 6`.

Відповідь містить об'єкт `pagy`:

```json
{
  "page": 1,
  "limit": 20,
  "count": 142,
  "pages": 8
}
```

> ⚠️ **Оголошена стеля дашбордної JSON-гілки — offset, і більше нічого** ([`00_07`](00_07_Action_Plan_Tracker) ARCH.63 · E.20, виміряно 2026-08-23). Немає курсорної пагінації, немає `since`/delta-запитів, немає `ETag`/умовних GET, немає bulk-вибірки. Для власного дашборда це прийнятно — сторінка перечитує вибірку цілком, — але має наслідок ЗА МЕЖАМИ UI: **будь-яка зміна серіалізатора під потреби дашборда була б breaking change для зовнішнього платного споживача.** Саме тому продаваний Tier A розглядається як ОКРЕМИЙ версіонований контракт у звільненому `/api/v1` ([`ARCH.77`](00_07_Action_Plan_Tracker)), а не як експорт цих самих серіалізаторів; форма мобільного клієнта впирається в ту саму стелю з іншого кінця.

## 3. Ролева Модель Доступу (RBAC)

> 🔴 **Зовнішній стейкхолдер `super_admin` не отримує НІКОЛИ** — ані держслужбовець за контрактом, ані партнер-ВНЗ, ані підрядник. Доступ до вивантажень обмежується договором про нерозкриття, а не роллю; потреба «подивитись усе» закривається експортом, не ескалацією. ⚠️ Інваріант відновлено 2026-08-22 з git: він жив у розчиненому реєстрі зовнішніх стейкхолдерів і зник разом із ним при прунінгу 07-23, не переїхавши нікуди — рівно клас [`00_07` DOC-T.85](00_07_Action_Plan_Tracker) («підставу зрізали разом із хронікою»). Тут його дім, бо це властивість РОЛІ, не партнерства.

| Роль | Опис | Доступ |
|---|---|---|
| `subscriber` | Замовник послуги (роль за замовчуванням) | Читання фінансових даних своєї організації |
| `forester` | Лісник | + Provisioning, Actuators, Maintenance Records, Oracle Visions. Метод `forest_commander?` (User) охоплює `forester` + `admin` + `super_admin` |
| `admin` | Адміністратор організації | + Firmwares, TreeFamilies, Settings, AuditLogs, SystemHealth, Users |
| `super_admin` | Суперадміністратор | + Organizations (реєстр усіх організацій) + перемикання acting-організації + системний аудит-ланцюг. **Дані бачить рівно тієї організації, в контексті якої працює** — як і всі. |

Формула «`admin` ∪ `super_admin`» має ОДИН дім — `User#admin_or_above?`. Її читають три
споживачі: `authorize_admin!` (`BaseController`), приватні предикати `ApplicationPolicy`
(+ `Scope`) і роле-фільтр сайдбара ([`04_04 §6.4`](04_04_Phlex_UI_and_Tailwind), [UI.5]);
доти вона стояла **пʼятьма** дослівними копіями, і меню додало б шосту. ⚠️ Тут спершу
стояло «трьома» — мій греп не побачив двох, бо між операндами стоїть отримувач
(`user&.role_admin? || user&.role_super_admin?` у `Scope` і `current_user.`-форма в
`authorize_record_mutation!`); знайшов їх adversarial-прохід, і обидві теж переведено.
Мораль ширша за рядок: **лічильник копій, зібраний грепом за однією формою написання,
занижує систематично** — шукай за ОПЕРАНДАМИ, не за цілим виразом. ⚠️ НЕ плутати з
`User#organization_admin?` (`role_admin? && organization_id.present?`) — super_admin під
неї не підпадає, тож вона НЕ взаємозамінна з гардом `authorize_admin!`.

**Дефолт `ApplicationPolicy` — DENY [SEC.16, 2026-07-30].** `index?`/`show?` віддають
`false`, `Scope#resolve` — `scope.none`. Політика, що забула визначити читання, тепер
нічого не пускає; доти дефолт віддавав `true`/`scope.all`, тобто «база нічого не
вирішує» насправді вирішувала найширше можливе. Носій дефекту був саме в базі, а не в
політиках: `rails g pundit:policy` генерує від неї, тож fail-open відтворювався б у
кожній майбутній політиці. ⚠️ Межа несуча. Це робить безпечним
**дефолт**, а не політики: жива-але-хибна політика цим не лікується — її тримають пари
`Scope`+предикат і крос-org піни. 🔴 **І «пара» означає ОДНАКОВУ відповідь, не просто наявність обох — розходження буває в ДВА боки, і другий не є діркою безпеки, тому й живе довше** ([ARCH.87], 2026-08-12). Небезпечний бік відомий: `Scope` вужчий за предикат = ілюзія ізоляції (список свій, а пряма адреса чужа). Тихий бік — дзеркальний: `WalletPolicy#show?` приймав ДВІ гілки (денормалізована колонка АБО ланцюг `tree → cluster → organization`), а `Scope` — лише першу, тож гаманець із порожньою колонкою зникав зі списку **й із суми ліквідності**, лишаючись відкритим за прямою адресою. Це не витік, а **діра видимості й обліку**, і жоден крос-org пін її не бачить за побудовою — він перевіряє, що ЧУЖЕ не видно, а не що СВОЄ видно. **Рефлекс: пару перевіряй симетрично — і «чуже не показується», і «своє не зникає»; друге вимагає субʼєкта, який резолвиться лише ДРУГОЮ гілкою.**

⚠️ **Pundit тут — не єдиний і не основний носій тенант-ізоляції.** `authorize`/
`policy_scope` кличуть три контролери; решта скоуплять асоціацією від
`acting_organization!` (`acting_organization!.trees.find(...)`), і це **сильніша**
форма: тенант-предикат живе всередині запиту, тож чужий запис не матеріалізується
взагалі, а промах дає 404 без existence-оракула — тоді як предикат виконується вже
ПІСЛЯ завантаження і може мовчки сказати `true`. Читай співіснування двох ідіомів як
свідоме: Pundit — де питання предикатне (роль × авторство), асоціація — де питання про
приналежність. Клас, який не виражає жоден із них, — FK з ТІЛА запиту
([SEC.26](00_07_Action_Plan_Tracker)); там потрібен per-site скоуплений резолвер.

⚖️ **Ратифіковано 2026-07-31: асоціативний скоуп — АРХІТЕКТУРА, не борг.** З цього
випливають два висновки, і обидва раніше щоразу відроджувались як пропозиції.
(1) **`verify_authorized`-backstop не будуємо** — хук вимагає, щоб КОЖЕН екшен кликав
Pundit, тобто або skip-list на всю асоціативну частину (реєстр, що гниє тихо й стає
фактичною політикою), або церемоніальні виклики поверх справжнього гарда; жодна з
історичних знахідок цієї осі ним не ловилась. (2) **Policy-клас, якого не кличе жоден
контролер, — не «готова інфраструктура на майбутнє», а залишок відкинутого підходу.**
Його `show?` = `true` не діра сьогодні (мертвий код), але стає нею від першого ж
`authorize`, і саме тому такі класи знімають, а не лагодять. Дзеркально й на власну
шкоду: пін на сам асоціативний скоуп доводив би поведінку ActiveRecord, а не нашу — те,
що вимагає доказу, це **резолвер контексту** (`acting_organization`), і його пінить
[`§3.1`](04_03_REST_API_v1_Reference).

### 3.1 Acting-organization — скоуп даних відв'язано від ролі [SEC.25 Ф2]

**Одна організація за раз — для всіх, включно з super_admin.** Роль дає ПОВНОВАЖЕННЯ
(які дії доступні), організація запиту дає СКОУП (які дані видно). Це різні осі, і
жодна роль більше не розширює другу.

| Що | Де живе |
|---|---|
| Організація запиту | `BaseController#acting_organization` — `session[:acting_org_id]`, per-device, гине з логаутом |
| Для не-super_admin | Завжди власна організація; сесія **ігнорується** — інакше переведення користувача в іншу організацію лишало б його сесію дивитись на стару |
| Передача в Pundit | `pundit_user` → `UserContext` (пара «користувач + організація»); `ApplicationPolicy` розпаковує й тримає `user` справжнім `User` |
| Гард відсутньої організації | `acting_organization!` кидає в ТОЧЦІ ЧИТАННЯ → 422 `code: "no_organization"` (JSON) або Phlex-сторінка (HTML) |
| Перемикання | `POST /organizations/:id/switch` — super_admin-only, сесійний запит (Bearer → 403) |

🔴 **Чому контекст несе ЛИШЕ організацію, а `user` лишається справжнім `User`.** Природна
форма обгортки — `delegate_missing_to :user` — виміряна як **шкідлива** і відкинута до коду:
`present?`/`blank?`/`nil?` означені на `Object`, тобто для обгортки вони не «missing», і
делегування їх не перехоплює. Обгортка навколо `nil`-користувача відповідала б
`present? == true` — а на цьому предикаті стоїть базовий RBAC-примітив
(`return scope.none unless user`), тож дефолт перевернувся б на **fail-OPEN** у найширшому
місці дерева. Тому `ApplicationPolicy::ContextUnpacking` розпаковує пару явно й приймає
**обидва** входи — `UserContext` і голий `User` (так політику конструюють спеки, і так вона
поводилась до Ф2).

**Гард — у точці читання, а не `before_action`.** Класовий гард вимагав би
`skip_before_action` у кожного, хто організації не має за побудовою (обидва
webhook'и, обидва auth-шляхи, `m2m_auth`, платформені) — тобто однорідне правило,
зібране зі списку винятків, який мусить рости й який хтось забуде поповнити.
Це заразом прибрало три різні поведінки одного сімейства сторінок, що були до Ф2:
422 з HTML · 200 з фальшивим порожнім станом · 500 з JSON-блобом у браузері (§2.2).

🔴 **Периметр самого контракту — тобто РЕСУРСИ, до яких він не застосовний** (виміряно
перебором 2026-08-13, [ARCH.83](00_07_Action_Plan_Tracker) — усі виклики
`acting_organization!` у дереві; ⚠️ живий лічильник бери грепом, не звідси: присуд того ж
дня перевів дві поверхні на не-bang форму). Власну колонку `organization_id` несуть **сім** таблиць
(`actuator_commands` · `audit_logs` · `clusters` · `naas_contracts` · `parametric_insurances`

`acting_organization!` кликати НЕ повинен** — зразок форми: `tree_families#index`

🔴 **Політику (1) виконують ОБИДВА контури — але Pundit-половина прийшла пізніше, і її вимір
показує, як виглядає НЕВИКОНАНА ратифікована політика [UI.7].** Асоціативний контур кличе
`acting_organization!` у точці читання від дня ратифікації; контролери, що взагалі кличуть
Pundit (`users` · `wallets` · `contracts`), не проходив ніхто — і на одному й тому самому
порожньому контексті вони давали **чотири** різні відповіді: `users#index` → 200 зі списком
org-less користувачів, кожен рядок якого `show?` далі відхиляв (**список, який неможливо
відкрити**) · `wallets#index`/`contracts#index` → 200 із порожнім реєстром над живим фондом ·
`contracts#show` → 404 · `contracts#stats` → чесні 422. Тобто саме ті «три різні поведінки
одного сімейства сторінок», які цей розділ оголосив знятими, вижили на сусідньому контурі.

**Корінь спільний і ширший за Pundit: `where(organization_id: nil)` Rails перекладає в
`IS NULL`, тобто у ФІЛЬТР, що ЗБІГАЄТЬСЯ з org-less рядками, тоді як `same_organization?` на
тому самому вході ВІДМОВЛЯЄ** (він починається з `organization_id.present?`). Один токен —
два домени: «немає контексту» ⊥ «організація `NULL`», рівно та конфляція, яку [ARCH.83]
назвав своїм виміром (1). ⚠️ Сусіди мовчали з ВИПАДКОВИХ причин, не з правила:
`Wallet.for_organization` будує сирий `= :org`, не істинний на `NULL`, а
`naas_contracts.organization_id` — `NOT NULL`; тобто fail-closed там був властивістю схеми й
форми запиту, а не оголошеного рішення, і перша ж переписка ланцюга на хеш-форму відкрила б
його мовчки. Тому половин дві й обидві оголошені: **гард у точці читання** (форма цього
розділу) + **`ApplicationPolicy::Scope#no_acting_organization?`** як fail-closed backstop для
майбутньої політики. Носій — `spec/requests/api/v1/acting_organization_contract_spec.rb`, і
він тримає ОБИДВІ половини доказу: відмова на кожній тенантній поверхні контуру ⊥ той самий
super_admin **з** організацією далі дістає 200 (інакше «гейт реагує на брак контексту» не
відрізнити від «гейт реагує на роль»). `users#me` — оголошений НЕ-член класу: питання «хто я»
тенанта не потребує, і саме звідси [UI.6] веде super_admin'а в реєстр кланів.

⚠️ **Межа цього переліку куплена виміром.** FK-ребро не завжди означає власність:
`system_parameters.updated_by_id` — це **провенанс**, і сама модель оголошує протилежне
(`organization_id: nil` → глобальний ланцюг, [ARCH.57]). Тож схема дає множину кандидатів,
а присуд ухвалює семантика — **перебором отримують периметр, не вердикт**.

**Перемикання — привілейована дія**, тож лишає слід **синхронно й до мутації сесії**
(`AuditLog.create!`, не `record_async!`: черга дала б лише порядок виклику), у журналі
тієї організації, **куди** входять. Дії, виконані з перемкнутого контексту, несуть
мітку `acting_organization_id` + `actor_home_organization_id` у `metadata` — її ставить
`Auditable` за `Current.switched_context?` ([`04_01 §5`](04_01_Data_Models_and_Entities)).

⚠️ **Що acting-org НЕ закриває — і чого епоха тут свідомо НЕ робить.** Підписане ім'я
Turbo-стріму детерміноване й без TTL, а ActionCable підписку не ре-авторизує, тож
збережений токен переживає перемикання; `targeted-disconnect` рве відкриті сокети
пристрою, але імені недійсним не робить. Механізм відкликання **існує** —
`Organization#rotate_stream_epoch!` міняє адресу цілком ([`04_04 §8.1`](04_04_Phlex_UI_and_Tailwind)),
— але перемикач його **не смикає**, і це присуд, а не недогляд: ротація — подія рівня
організації, тож switch одного адміна перезавантажив би всіх її глядачів заради гігієни
одного, а межа привілею тут і не перетинається (super_admin має легітимний доступ до
обох організацій і може перемкнутись назад). Тобто це **context-hygiene, а не витік**;
епоха закриває інший тригер — втрату членства й підозру на злив.

🔴 **Скоуп читання має ТРИ половини, і сайдбар-бейдж коштував нам двох із них [SEC.16, 2026-07-28].** `BaseController#ews_alert_count_cached` рахує нерозв'язані тривоги для бейджа, який `DashboardLayout` рендерить на **кожній** сторінці — тобто це найширше розповсюджений тенант-факт у застосунку. Доти він робив `EwsAlert.unresolved.count` **без org-скоупу** під **org-сліпим ключем кешу**, тож інцидентну активність усієї платформи (а отже й конкурента) бачив кожен автентифікований глядач — виміряно рантаймом: власних тривог 1, у бейджі 4. ⚠️ **Ключ — окрема половина дефекту, не менша за запит:** навіть зі скоупленим запитом перший, хто прогріє кеш, роздав би своє число всім іншим на весь TTL (доведено окремою мутацією). Тому обидві половини скоуплені явно (`…/org/#{org.id}` + `org.ews_alerts`), а без організації повертається **0, не глобальна сума** (fail-closed). ⚠️ Третя половина — ті, хто ключ **скидає**: перейменування ключа сиротить свої інвалідатори мовчки, і нічого не червоніє (той самий клас уже кусав на прогнозі Оракула — три деletери гасили доскоупне ім'я). 🔴 І окремо про доказ: попередня спека **цементувала дефект як норму** — вона стабила `EwsAlert.unresolved` на `double(count: 7)` і стверджувала 7, тобто перевіряла, що хелпер повертає те, що повертає його ж реалізація. Тавтологія робила відсутність скоупу невиразною в принципі; замінено двоглядацьким прикладом, де другий тенант **мусить** дістати інше число.

### 5.2 POST `/provisioning/register` — Реєстрація Вузла (Ключовий для Gateway)

**Призначення:** Ініціація нового Soldier (дерева) або Queen (шлюзу). Повертає DID для прошивки.
**[ARCH.77]** Браузерний ендпоінт попри апаратну тему — форма форестера (`authorize_forester!` +
`format.html`); машинного клієнта немає, фабричний тракт ([`03_06`](03_06_Factory_Flashing_and_Key_Provisioning)) ходить rake-задачами у власному
процесі, поза HTTP.

**Доступ:** `Authorization: Bearer <token>` з роллю `forester` або вище.

**Request Body:**

```json
{
  "provisioning": {
    "hardware_uid": "0039002F3138511538323634",
    "device_type": "tree",
    "cluster_id": 7,
    "family_id": 3,
    "latitude": 50.4501,
    "longitude": 30.5234
  }
}
```

Для реєстрації Gateway (`device_type: "gateway"`):

```json
{
  "provisioning": {
    "hardware_uid": "GW-UID-E5F6G7H8",
    "device_type": "gateway",
    "cluster_id": 7,
    "latitude": 50.4510,
    "longitude": 30.5245
  }
}
```

| Параметр | Тип | Обов'язковий | Опис |
|---|---|---|---|
| `hardware_uid` | String | ✅ | Tree: **24-hex кремнієвий UID** (три %08X-слова регістрів `0x1FFF7590/94/98`) — DID деривується murmur3-fmix32 ([`03_01 §7`](03_01_Firmware_Lifecycle_and_DMA)), не-24-hex → `422 invalid_uid`; Gateway: uid як є (`SNET-Q-…`) |
| `device_type` | String | ✅ | `"tree"` або `"gateway"` |
| `cluster_id` | Integer | ✅ | ID кластера для прив'язки |
| `family_id` | Integer | Лише для `tree` | ID породи дерева (TreeFamily) |
| `latitude` | Float | ✅ | Широта GPS |
| `longitude` | Float | ✅ | Довгота GPS |
| `ed25519_public_key` | String (HEX) | Опційно | Ed25519 public key Gateway: M2M Auth + [L1 QATT] верифікація batch-підпису (wire-дім [`03_05 §2.2`](03_05_Hardware_Symmetric_Crypto_and_Security)) |

**Success Response `201 Created` (єдиний режим — HKDF, hard cutover):**

```json
{
  "did": "SNET-80B12004",
  "key_derivation": "hkdf-sha256",
  "device": {
    "id": 156,
    "did": "SNET-80B12004",
    "status": "active",
    "cluster_id": 7
  }
}
```

> `did` — **деривований** (murmur3-fmix32 від `hardware_uid`; golden-пара
> `0039002F3138511538323634 → SNET-80B12004`): плата порахує собі той самий
> DID на кожному boot (`did_derive.h`). Сирий UID зберігається у
> `trees.silicon_uid_hex` (re-flash vs DID-колізія).

> **Zero-Trust: жодних секретів у відповіді.** Бекенд та прошивка незалежно деривують однаковий 32-байтний AES-ключ через `HKDF-SHA256(ikm: PROVISIONING_MASTER_KEY, salt: device_uid, info: "silken-aes-256-device-key")` (cross-ref: [`03_06 §2`](03_06_Factory_Flashing_and_Key_Provisioning)) **та** 32-байтний `K_seed` для атрактора Лоренца через `HKDF-SHA256(ikm: PROVISIONING_MASTER_KEY, salt: "silken-lorenz-v1", info: "silken-lorenz-seed|<DID>")` ([SEC.11], cross-ref: [`03_06 §3`](03_06_Factory_Flashing_and_Key_Provisioning)). Обидва секрети зберігаються в `HardwareKey` (AR Encryption non-deterministic) і **ніколи не передаються** через HTTP/мережу. `PROVISIONING_MASTER_KEY` повинен бути встановлений у ENV — інакше endpoint повертає `503 Service Unavailable` (no fallback). Прошивка отримує обидва секрети під час physical Factory Flashing через окремий захищений канал (UART/JTAG, поза цим API).

> **Побічний ефект:** у тій самій транзакції створюється `MaintenanceRecord(action_type: :installation, system_generated: true)` — фіксація монтажу. Ознака провенансу тут несуча, бо `installation` вимагає фотодоказів, а провізія йде без камери; деталь і перелік машинних писачів — [`04_01 §7`](04_01_Data_Models_and_Entities). Запис народжується `hardware_verified: false`; підняти прапорець — окрема дія `PATCH /maintenance_records/:id/verify` (ендпоінт 64 у §4).

**Conflict Response `409 Conflict`:**

```json
{
  "error": "Пристрій з UID STM32-UID-A1B2C3D4 вже зареєстрований в системі."
}
```

| Поле | Опис |

| `z_value` | Координата атрактора Лоренца — **безрозмірна**, одиниці немає й бути не може |
| `temperature` | Температура (°C) — внутрішній сенсор MCU у капсулі анкера + per-device офсет; це НЕ температура ксилеми |

🔴 **[ARCH.86] Що цей ендпоінт СВІДОМО не віддає — і чому.** До 2026-08-13 він друкував `unit: "kOhm"` і ключ `impedance:`, куди клав `z_value`; поруч їхав `stress_index = 1 − z_value/baseline_impedance`. Імпедансу як величини не існує: пристрій його не міряє, поля немає в жодній ері wire-формату, у BOM немає компонента. Похідний «індекс стресу» при цьому був стиснутий у ~2 % шкали (ніколи не нижче 0.955) і **спадав** зі зростанням Z — тобто дерево біля стелі «зовнішнє втручання» читалось як найменш стресоване. Обидва поля знято; підстава — [`00_07 §🗄️`](00_07_Action_Plan_Tracker) ARCH.86.

⚠️ **Як читати `z_value` — межа заявленого.** Z виконує ДВІ санкціоновані ролі: категорійний status-гейт і **DCI/anti-fraud** (парність device-Z ≡ server-Z, [`05_02`](05_02_Proof_of_Growth_Pipeline)). Мапінг «Z → здоров'я дерева» — **недоведена гіпотеза**, і рішення про роль Z ухвалює ground-truth-протокол [`05_05 §8`](05_05_Slashing_and_Risk_Policy); можливий вихід — «Z = лише DCI». **Не будуйте на `z_value` health- чи цінову аналітику.** Смуга двобічна (падіння = втрата тургору/посуха; стрибок = аномальний стрес/зовнішнє втручання), а верхня межа **ρ-відносна**, тобто рухається з температурою — тому статичного коридору відповідь не несе.

📌 **Індексу стресу тут немає за задумом.** Справжня метрика — `AiInsight#stress_index` (0..1, багатосигнальна) — має **добове** зерно, а телеметрія приходить кілька разів на добу; розмазати добове число по телеметричних мітках означало б виготовити роздільність, якої модель не має. Вона доступна на insight-поверхні ([`§5.9b`](04_03_REST_API_v1_Reference)) разом зі своїм `target_date`.

✅ **Чому `z_value` лишається публічним, попри все вище:** він входить у Merkle-лист (`TelemetryLog::LEAF_PAYLOAD_COLUMNS` = `z_value · bio_status · created_at · tree_id`), тож без нього зовнішній аудитор не перерахує `archive_root` і не перевірить наш L1-якір — це нога «**відтворювано**» критерію місії [`00_01 §1.1`](00_01_Vision_Mission_and_Roadmap).

> **[ARCH.58] Override-команди 409 НЕ отримують.** `STOP` / `EMERGENCY_SHUTDOWN` / `EMERGENCY_STOP` (`ActuatorCommand::OVERRIDE_COMMANDS`, розпізнаються за базовою частиною до `:`) проходять in-flight гард навіть коли черга зайнята — інакше оператор не подасть аварійну зупинку рівно тоді, коли вона потрібна. `sap × (1 − stress)` і бере ЛИШЕ дерева з виміряним стресом: у дерева, якого нічний
прохід ще не бачив, множника здоровʼя не існує. Доти `current_stress` віддавав `0.0`
(колонка мала `DEFAULT 0.0`), тобто множник `(1.0 − 0)` = **повна вага** — щойно
розгорнутий вузол, який уже в ефірі, віддавав у прогноз увесь свій sap як ідеально
здоровий. Після зняття підстановки ([`04_01 §2`](04_01_Data_Models_and_Entities))
мовчазний пропуск був би не полегшенням, а **відбором**, який критерій місії
забороняє словом «невідбирано» ([`00_01 §1.1`](00_01_Vision_Mission_and_Roadmap)) —
тож число віддається разом із тим, про яку частку флоту воно стверджує. Форма
дзеркалить `Cluster.health_coverage`; HTML-гілка друкує підпис лише при
ЧАСТКОВОМУ покритті (`ApplicationComponent#measurement_coverage`).

### 5.15 POST `/api/v1/auth/m2m_token` — M2M Автентифікація Gateway (Ed25519)

**Призначення:** Gateway-пристрої отримують та оновлюють Bearer-токен без логіна/пароля через Ed25519-підпис.

**Доступ:** 🌐 Публічний (без Bearer token), але верифікується Ed25519-підпис.

**Передумови:**
- Ed25519 public key зареєстровано під час provisioning (поле `ed25519_public_key` в `POST /provisioning/register`).
- Збережено в `hardware_keys.ed25519_public_key_hex`.

**Request Body:**

```json
{
  "did": "SNET-A1B2C3D4",
  "timestamp": "2026-03-29T12:00:00Z",
  "signature": "a3f2b1c4d5e6..."
}
```

| Параметр | Тип | Обов'язковий | Опис |
|---|---|---|---|
| `did` | String | ✅ | Device ID (реєструється при provisioning) |
| `timestamp` | ISO8601 | ✅ | Поточний час UTC (максимальне відхилення ±5 хв від серверного часу) |
| `signature` | String (HEX) | ✅ | Ed25519 підпис рядка `"#{did}:#{timestamp}"` приватним ключем пристрою |

**Replay-захист:**

SHA256-дайджест значення `signature` зберігається в Redis як nonce (`SET NX`, TTL 10 хв). Перший запит проходить — всі наступні з тією ж підписом повертають `401 Unauthorized` (`"Replay attack detected"`). **[S6.1]** Якщо Redis недоступний — fallback на Solid Cache (DB-backed): nonce зберігається в БД з TTL 10 хв. Шлюзи залишаються активними замість отримання `503 Service Unavailable`.

**TTL = 10 хв — обґрунтування:**
- **Timestamp validity window**: ±5 хв (компенсує clock drift gateway RTC vs server).
- **Maximum signature lifetime**: 10 хв = 5 хв (минулий timestamp на trailing edge) + 5 хв (margin для server-side processing delay).
- **Чому не 5 хв (рівно window):** підпис, створений на trailing edge timestamp window (наприклад, 5 хвилин тому, ще валідний за timestamp check), й одразу повторно надісланий — пройде nonce check якщо TTL == window. 10 хв = window + margin гарантує покриття всього періоду, протягом якого підпис вважається валідним.
- **Чому не 15+ хв:** довший TTL збільшує Redis memory footprint per gateway (індивідуально незначно, але на 100k+ пристроях та burst auth flows накопичується) без додаткової security користі — timestamps старші 5 хв вже відхиляються timestamp check'ом.

**Спостережуваність:** Prometheus counter `silkennet_m2m_nonce_fallback_total` інкрементується щоразу, коли запит падає з Redis на DB-backed fallback. Grafana-алерт `sn-alert-m2m-nonce-fallback` (p2-info): `increase[1h] > 0` — M2M-auth надто рідкісний (~1/30 днів на шлюз) для відсоткового порогу, тому фіксується БУДЬ-ЯКИЙ fallback; разове спрацювання = зафіксований Redis-blip, повторюваність день-у-день → escalate до multi-zone Upstash (Global DB) — ⚖️ рішення за прод-даними. Парний `sn-alert-qatt-nonce-fallback` окремо покриває QATT-батч-nonce (той самий S6.1-патерн; окремий counter, щоб щогодинний батч-стрім не маскував рідкісний auth-сигнал). Парність метрика↔алерт стереже `spec/deploy/grafana_alerts_spec.rb`.

**Підпис на прошивці (псевдокод):**

```c
// message = "SNET-A1B2C3D4:2026-03-29T12:00:00Z"
uint8_t sig[64];
ed25519_sign(sig, message, strlen(message), private_key);
// hex-encode sig → signature field
```

**Success Response `201 Created`:**

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "device_uid": "SNET-A1B2C3D4",
  "expires_in": "30 days",
  "token_type": "Bearer"
}
```

**Error Responses:**

| Статус | Причина |
|---|---|
| 404 Not Found | `did` не знайдено в `hardware_keys` |
| 422 Unprocessable | Ed25519 public key не зареєстровано для пристрою |
| 400 Bad Request | Невалідний формат `timestamp` |
| 401 Unauthorized | `timestamp` прострочено (>5 хв) або підпис не валідний або повтор nonce (Replay attack) |
| 503 Service Unavailable | Redis недоступний ТА Solid Cache fallback також відмовив |

### 5.15.1 POST `/api/v1/auth/m2m_token/refresh` — M2M Token Refresh (Sliding Window)

**Призначення:** Оновлення Bearer-токена без повторної Ed25519 автентифікації. Gateway надсилає поточний валідний токен і отримує новий 30-денний токен.

**Доступ:** 🔑 Автентифікований (Bearer token обов'язковий).

**Мотивація (S3.4):** 30-денний M2M token може протухнути під час тривалого uplink. Цей ендпоінт дозволяє Gateway автоматично оновити токен без Ed25519 криптографії (яка потребує CPU + часу).

**Request:**

```
POST /api/v1/auth/m2m_token/refresh
Authorization: Bearer <current_valid_token>
```

Тіло запиту не потрібне — автентифікація відбувається через Bearer header.

**Success Response `201 Created`:**

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "expires_in": "30 days",
  "token_type": "Bearer",
  "refreshed_at": "2026-04-18T13:00:00Z"
}
```

**Error Responses:**

| Статус | Причина |
|---|---|
| 401 Unauthorized | Токен прострочений, невалідний або відсутній |

**Firmware flow (псевдокод):**

```c
// Перевірка перед кожним CoAP flush:
if (days_until_token_expiry() < 7) {
    http_post("/api/v1/auth/m2m_token/refresh",
              headers: {"Authorization": "Bearer " + current_token});
    // Зберегти новий token + timestamp
}
```

### 5.16 POST `/api/v1/gateways/:id/telemetry` — HTTP Telemetry Uplink

**Призначення:** HTTP fallback для передачі зашифрованого батчу телеметрії від Gateway до бекенду. Основний канал — CoAP/UDP порт 5683 (daemon).

**Сценарії використання HTTP uplink:**
1. CoAP/UDP заблоковано корпоративним фаєрволом або LTE-обмеженнями
2. Phase 3 Starlink Mini з TCP/IP мостом (ESP32-S3 — рішення HW.18)
3. Ручне завантаження телеметрії через Dashboard (forester upload)

**Доступ:** `Authorization: Bearer <token>` (будь-який автентифікований користувач організації).

**Request Body:**

```json
{
  "payload": "base64_encoded_binary_batch..."
}
```

| Параметр | Тип | Обов'язковий | Опис |
|---|---|---|---|
| `payload` | String (Base64) | ✅ | Base64-encoded бінарний батч: legacy `[IV:16][AES-256-CBC encrypted records]` або підписаний L1 QATT конверт — обидві форми, формат ідентичний CoAP uplink (wire-дім [`03_05 §2.2`](03_05_Hardware_Symmetric_Crypto_and_Security); верифікація — у спільному `UnpackTelemetryWorker`). Розмір обмежено до `MAX_UPLINK_PAYLOAD_SIZE = 16 KiB` (~16× headroom над реальним flush'ем 45 entries). Перевищення → `413 Payload Too Large` (`flash.telemetry.payload_too_large`). Запобігає DoS через Redis-Sidekiq queue. |

**Success Response `202 Accepted`:**

```json
{
  "status": "accepted",
  "gateway_uid": "GW-UID-E5F6G7H8"
}
```

> **Обробка:** `UnpackTelemetryWorker.perform_async(payload, request.remote_ip, gateway_uid, Time.current.utc.iso8601)` — сигнатура ідентична виклику з CoAP-демона ([`lib/coap_gate.rb`](../lib/coap_gate.rb)). 🔴 **[ARCH.62→ARCH.41] Четвертий аргумент несучий:** це момент ПРИЙОМУ, зафіксований на межі й серіалізований у job. Він єдиний у тракті не рухається між Sidekiq-спробами, тож із нього береться доба cold-derive Лоренца — без нього ретрай через межу півночі UTC дає інший `epoch_day` і категоричний DCI-мисматч на ЧЕСНОМУ дереві. Gateway також оновлює `last_seen_at` та IP-адресу.

## 6. Приклад Взаємодії Gateway (Queen) з API

Нижче наведено типовий lifecycle запитів від прошивки Gateway.

> **Примітка:** Основний канал **передачі телеметрії** від Queen до Backend — **CoAP/UDP на порт 5683** (CoAP listener daemon). HTTP API використовується для управління, реєстрації та звітності. HTTP fallback uplink реалізовано як `POST /api/v1/gateways/:id/telemetry`.

```text
1. [Одноразово] POST /provisioning/register (браузерний контур, форма форестера — [ARCH.77])
   → Передає STM32 UID + Ed25519 public key (опційно).
   → Відповідь містить DID та key_derivation: "hkdf-sha256".
   → Обидві сторони математично деривують AES-ключ через HKDF без передачі по мережі.
   → Встановіть PROVISIONING_MASTER_KEY в ENV для Production режиму.

2. [За потреби] POST /api/v1/auth/m2m_token
   → Шлюз підписує "did:timestamp" Ed25519 private key.
   → Отримує 30-денний Bearer token без логіна/пароля.
   → Повторювати перед закінченням терміну дії.

3. [Регулярно] CoAP PUT → порт 5683 (основний канал uplink)
   → AES-256-CBC-зашифрований CoAP-батч від Queen (агреговані записи Soldier'ів; самі LoRa-фрейми Soldier→Queen — 21-байт AES-128-ECB) → бекенд.

   [Fallback] POST /api/v1/gateways/:id/telemetry
   → Base64-encoded бінарний батч у тілі запиту (якщо CoAP/UDP недоступний).
   → НЕ використовувати GET для передачі телеметрії.

4. [Автоматично] POST /api/v1/oracle_callbacks
   → Chainlink викликає цей endpoint після on-chain верифікації.
   → Авторизація через HMAC-SHA256 підпис в заголовку X-Chainlink-Signature.
   → Встановіть CHAINLINK_HMAC_SECRET в ENV для Production режиму.
```

## 7. Заголовки Запитів

| Заголовок | Обов'язковий | Значення |
|---|---|---|
| `Authorization` | ✅ (для захищених ендпоінтів) | `Bearer <token>` |
| `Content-Type` | ✅ (для POST/PATCH з body) | `application/json` або `multipart/form-data` |
| `Accept` | Опційно | `application/json` (за замовчуванням) |
| `X-Chainlink-Signature` | ✅ (Production) для `/api/v1/oracle_callbacks` (машинний контур) | `HMAC-SHA256(raw_body, CHAINLINK_HMAC_SECRET)` — підпис від Chainlink DON |
| `Idempotency-Key` | ✅ (JSON) для `POST /actuators/:id/execute` **і** `POST /maintenance_records` | Унікальний клієнтський ключ (UUID рекомендовано). Запобігає дублюванню фізичних команд та доменних мутацій при retry. Replay JSON-запиту з тим самим ключем повертає закешовану відповідь (TTL 24 год). Турбо-стрім і **браузерний HTML-контур виключені** — форма дашборда заголовка не шле й слати не може, тож гард звужено до `request.format.json?`. ⚠️ **Статус повтору РІЗНИЙ, і це присуд, а не недогляд:** актуатор віддає `202 Accepted` (наказ виконується асинхронно, робота ще ТРИВАЄ), запис обслуговування — `200 OK` (робота вже завершена; `201 Created` брехав би, бо цим запитом не створено нічого). Протокол — один дім, `IdempotentRequest`; різняться лише скоуп ключа, текст відмови й цей статус. |
