### B.13 Data Protection Officer (DPO)

### D.1 Мапа ролей: хто controller, хто processor

Три окремі потоки даних, з РІЗНОЮ роллю SilkenNet у кожному (R6 §3.2 — не плутати між ними):

1. **SilkenNet = CONTROLLER власних B2C/облікових даних** (email/OAuth/wallet/сесія, Документ B §B.3) — сам визначає мету й засоби обробки → на нас лежить lawful basis, privacy notice, DSR-процес, 72-годинний breach-notification обов'язок (Art. 33) щодо ЦИХ даних.
2. **SilkenNet = CONTROLLER (НЕ processor) щодо персональних даних, вбудованих у B2B-проданий «verified fact» data-продукт** (D-MRV-дані моніторингу та фіксації подій) — це продаж ВЛАСНОГО верифікованого output, не «обробка за інструкцією» покупця → **окремий Art. 28 DPA від нас до B2B-покупця тут юридично НЕ потрібен** (не плутати з DPA-логікою для облікових даних покупцевих співробітників, які логіняться у застосунок — та частина підпадає під потік #1, як для будь-якого користувача).
3. **SilkenNet = CONTROLLER відносно ВЛАСНИХ інфраструктурних вендорів** (GCP, Akash, Alchemy, Upstash, Grafana, Sentry), котрі виступають **processors/sub-processors** обробки наших користувацьких даних → **ми потребуємо DPA ВІД кожного з них** (реєстр — D.3).

OAuth-провайдери (Google/Facebook/LinkedIn/X) — НЕ входять у реєстр D.3: вони НЕ processors у сенсі Art. 28, а незалежні окремі контролери (R6 §3.2, Документ B §B.5).

### D.2 Модель авторизації субпроцесорів

Рекомендація R6 §3.1 — **загальна авторизація (general authorization)**: публічний список субпроцесорів (цей реєстр, опублікований як частина Privacy Policy/DPA-сторінки) + вікно заперечення 14–30 днів при зміні/додаванні нового субпроцесора. Це стандарт для SaaS-масштабу (на противагу поіменній авторизації кожного окремо).

## Compliance-gaps, що вже мають дім у `00_07`

Ці три пункти прямо запитані завданням цієї чернетки; тепер вони канонізовані в `00_07` (не потребують нового запису) — тут лишається лише суть, для контексту читача цього файлу.

**1–2. Akash permissionless-хостинг + Alchemy RPC — Art.28 processor-діра (`00_07` SEC.23).** `config/deploy.yml` фіксує, що сам Rails-застосунок (не лише допоміжний сервіс) переїжджає з GCP на Akash Network — permissionless-маркетплейс без підтвердженого GDPR-DPA-механізму рівня AWS/GCP (Art.28 вимагає ідентифікованого законтрактованого processor'а; mainnet-деплой ще не відбувся — вікно відкрите). Друга нога того самого треку: Alchemy (RPC-провайдер, канон [`06_02`](../../06_02_Akash_Network_Integration.md)) фіксує IP+wallet-адресу при кожному RPC-запиті (CJEU Breyer: IP = персональні дані) — недекларований субпроцесор без верифікованого DPA.

**3. Anchor-геолокація × кадастр → re-identification власника (`00_07` SEC.18).** `Tree.latitude/longitude` + `Cluster.geo_boundary` — реальні поля ([`04_01 §2/§3`](../../04_01_Data_Models_and_Entities.md)). Гранулярна geo-локація ділянки, поєднана з кадастровими/земельно-реєстровими записами, теоретично може пере-ідентифікувати малого/сімейного власника (EDPB WP248 3/9-критерії → DPIA Art.35 до обробки).
