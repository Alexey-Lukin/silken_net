# 02_03: BQ25570 MPPT та Нано-Менеджмент Живлення

---

## 🎯 Мета

Зафіксувати електричну схему, налаштування резистивних дільників та логіку роботи мікросхеми **BQ25570 MPPT** — єдиного менеджера живлення поточної архітектури. Документ описує конфігурацію восьми SMD-резисторів (VBAT_OV / VBAT_UV / VBAT_OK), відстежує виявлені проблеми з заводськими налаштуваннями Li-Po і встановлює цільові пороги для суперконденсатора 0.47F / 5.5V. Включає також специфікацію самого **EDLC-буфера** (фізика іоністора, його подвійна роль як метаболічного біо-сенсора через `delta_t` заряду, розглянуті альтернативи накопичувача) — §12.

> **Архітектурна нотатка:** Step-up конвертер LTC3108 був **повністю виключений** із BOM під час ключового піво-ту (v2). Причина: EBFC вже генерує >500 мВ, що перевищує поріг Cold Start BQ25570 (330 мВ) — каскадний перетворювач LTC3108 більше не потрібен і видаляє 2 компоненти з плати.

Цей модуль є "травною системою" Солдата: він перетворює нестабільні мілівольти від біопаливного елемента (EBFC) на чисті 3.3V для STM32WLE5JC та LoRa-антени.

## ⚡ 1. Архітектурне Обґрунтування: Cold-Start та Прямий Запуск від EBFC

### 1.1. Проблема Холодного Старту

Мікросхема BQ25570 — це надпотужний менеджер живлення, але вона має **фундаментальне обмеження**: для самостійного запуску (Cold Start) їй необхідна вхідна напруга не менше **330 мВ** та струм не менше 15 мкА.

> 📦 **Історична нота (44мВ-стенд → [`02_04 §5`](02_04_Bench_Build_Guide)):** рання версія припускала, що ксилемний потоковий потенціал дає лише ~**44 мВ** (макет з імітатором — дільник 3.3 кОм/100 Ом від AA), ~7.5× менше за поріг cold-start. Гіпотеза 44мВ **як джерело енергії відкинута з EBFC Gen 2.0**; сам 44мВ-harvester живе як навчальний bench-фронт ([`02_04 §5`](02_04_Bench_Build_Guide)), тут не дублюється.

### 1.2. Первісне Рішення: Каскад LTC3108 → BQ25570 (bench-harvester → 02_04 §5)

> 📦 Рання архітектура долала cold-start каскадом **LTC3108** (осцилятор Майснера: трансформатор 1:100 + C1/C2 обв'язка, старт від ~20 мВ) перед BQ25570. Повний опис того breadboard-каскаду — схема, піни трансформатора, недоліки — живе у bench-guide [`02_04 §5`](02_04_Bench_Build_Guide); тут **не дублюється** (Ruthless Pruning, [`00_06 §4`](00_06_SSOT_Documentation_Standard)). Стисло про мотивацію пів'оту: +2 компоненти (трансформатор + LTC3108), нижчий загальний ККД, +~40% площі плати, складніша збірка.

### 1.3. Архітектурний Пів'от

**Ключове відкриття:** Повноцінний EBFC Gen 2.0 на основі ферментів dgrFAD-GDH / Laccase + ZIF-nanozyme, іммобілізованих на гіроїдній поверхні Ti-6Al-4V, генерує **понад 500 мВ** — значно більше, ніж 44 мВ від простого ксилемного потокового потенціалу на металевих електродах без ферментів.

500 мВ > 330 мВ (поріг Cold-Start BQ25570) → **LTC3108 не потрібен як первинний каскад** (виживає лише як DNP cold-start fallback при високому R_int EBFC — §1.5).

```
Поточна архітектура (Post-Pivot):

Tree EBFC (>500mV)
      │
      ▼  VIN_DC (>500mV, типово 500–800mV)
┌──────────────────────────────────────────────┐
│  BQ25570 (Power Management IC)               │
│  CJMCU-2557 breakout module                 │
│  - Cold Start: OK (330mV порог перекрито)    │
│  - MPPT: VOC sampling / 16s                  │
│  - Boost Charger → VSTOR (до 5.5V)          │
│  - Buck Converter → VOUT (3.3V стабілізовано)│
│  - VBAT_OK → GPIO STM32 (гейт живлення — HW)│
└───────────────────┬──────────────────────────┘
                    │
                    ▼  VSTOR (накопичення)
           [ Supercapacitor 0.47F / 5.5V ]
                    │
                    ▼  VOUT (3.3V, до 100 mA)
           [ STM32WLE5JC + SX1262 LoRa ]
```

**Результат пів'оту:**
- Видалено LTC3108, трансформатор 1:100 та його C1/C2 конденсаторну обв'язку (+ 499к bleeder)
- Зменшення BOM (видалено весь cold-start каскад)
- Зменшення площі плати ~40%
- Підвищення загального ККД (один каскад замість двох)
- Спрощення налагодження

### 1.5. Cold-Start під Навантаженням: Ризик R_int EBFC (та мітигація)

> Перенесено з колишнього BLOCKER-3 (трекінг — [`00_07` — HW.13](00_07_Action_Plan_Tracker)). Видалення LTC3108 (вище) спирається на V_OC ≥ 500 мВ — але cold-start charge pump BQ25570 тягне ≥ 15 µA, і під навантаженням V просідає за R_int.

EBFC має значний внутрішній опір (dgrFAD-GDH on Ti gyroid Gen 2.0 у синтетичному соку: R_int ≈ 5–20 кΩ). V_drop = I_load × R_int:

```
R_int = 10 кΩ → V_drop = 150 мВ → V_actual = 350 мВ (вузько над 330)
R_int = 15 кΩ → V_drop = 225 мВ → V_actual = 275 мВ ❌
R_int = 20 кΩ → V_drop = 300 мВ → V_actual = 200 мВ ❌
```

**Threshold:** charge pump ≈ R_load_eq = 350мВ/15µA = 23.3 кΩ. Умова `V_OC × R_load_eq/(R_int+R_load_eq) ≥ 330 мВ` → **R_int ≤ 12.0 кΩ** для гарантованого cold-start. Половина діапазону 5–20 кΩ провалюється → **oscillation loop** (charge pump вмикається@500мВ → просідає <330 → вимикається → відновлюється → …; supercap ніколи не сягає 1.8 В MPPT-boost).

**Мітигація (пріоритизовано):**
- **Lab (обов'язково):** виміряти R_int двома точками — V_OC та V@15µA (резистор 23.3 кΩ); R_int = (V_OC − V_loaded)·23.3/V_loaded. Запит у [`00_02 §1.4`](00_02_Academic_Integration_and_IP).
- **A (рекоменд., якщо R_int > 12 кΩ):** 2 анкери **паралельно** → R_int /2 (аноди на одному потенціалі → shunt-free; потребує узгоджених V_OC). Дім — anchor stacking ([`01_03 §6.1`](01_03_EBFC_Enzymatic_Bio_Fuel_Cell)). +1 анкер.
- **B (⚠️ лише між РІЗНИМИ деревами):** серійний стек 2× EBFC → V_OC = 1.0 В → R_int_max ≤ 47.3 кΩ, **АЛЕ** серія у спільному ксилемному соку = **ionic shunting → електроліз → емболія** ([`01_03 §6.1`](01_03_EBFC_Enzymatic_Bio_Fuel_Cell)); within-tree ЗНЯТО, допустиме лише між стовбурами (дроти).
- **C:** LTC3108 cold-start preboost у **DNP footprint** (pads лишити, паяти лише для проблемних анкерів).

⚠️ До lab-перевірки R_int — **не замовляти 100 шт. PCBA без DNP-footprint LTC3108**.

## 🔌 2. Опис Пінів BQ25570

### VSTOR

**Призначення:** Підключення до суперконденсатора (накопичувач енергії).

```
VSTOR ── [0.47F / 5.5V Supercapacitor] ── GND
```

- **Діапазон:** 0V (повний розряд) до 5.5V (максимум суперконденсатора)
- **Логіка:** Boost-конвертер "перекачує" заряд з EBFC до VSTOR, поступово піднімаючи напругу від 0V
- **Захист:** VBAT_OV (Overvoltage) = 5.5V — при досягненні мікросхема зупиняє заряд
- **Firmware relevance:** `vcap_voltage` в 21-байтному пакеті (bytes 5–6) — сьогодні це **VDDA-проксі** у чесних мВ (FW.50, [`03_01 §1.4`](03_01_Firmware_Lifecycle_and_DMA)); цільовий тракт вимірювання заряду — VBAT_SEC через дільник ([`02_01 §7.1`](02_01_Hardware_Architecture_and_BOM) — канон-власник вибору вузла). Номінали дільника — відкрите питання цього документа (FW.50 👤): дільник через EDLC мусить або жити в десятках МОм (зведений bleed проти nA-бюджету), або сидіти за TPS22860-гейтом як BME280

### VOUT

**Призначення:** Стабілізований вихід для живлення мікроконтролера та LoRa-трансивера.

```
VSTOR ──[Internal Buck]──▶ VOUT (3.3V) ──▶ STM32WLE5JC VDD
                                       ──▶ SX1262 LoRa Radio
```

- **Значення:** 3.3V (програмується резисторами ROUT1/ROUT2)
- **Максимальний струм:** 100 mA (постійний)
- **Пікове навантаження:** LoRa TX +22 dBm потребує до 118 mA → необхідний Buffer Cap (розділ 5)
- **Увімкнення:** Тільки коли VSTOR > VBAT_OK threshold (3.4V) → VBAT_OK = HIGH
- **Quiescent Current Buck:** входить до загального IQ = 488 nA (в режимі очікування)

### VBAT_OK

**Призначення:** Апаратний buck-enable / brownout-**гейт живлення** STM32WLE5JC — дозволяє buck подавати 3.3 В, коли VSTOR достатній. Це **НЕ** джерело періодичного пробудження (канон wake-source — нижче, «У Firmware»).

```
BQ25570 VBAT_OK ──▶ STM32 GPIO (status/gate-вхід)
```

**Логіка спрацьовування (гістерезис):**

| Умова | Напруга VSTOR | VBAT_OK | Живлення MCU (buck) |
|---|---|---|---|
| Іоністор заряджається | < 3.4V | LOW (0V) | Знеструмлений (buck OFF) |
| Іоністор досяг порогу | ≥ 3.4V | HIGH (3.3V) | Buck ON → 3.3 В на MCU |
| Іоністор розряджається | > 3.32V | HIGH | Живлення тримається |
| Іоністор критично сів | < 3.32V (~97% від 3.4V) | HIGH → LOW (гіст.) | Buck OFF → MCU знеструмлений |

**Гістерезис:** пороги VBAT_OK **програмовані** ROK-резисторами (VBAT_OK_PROG — спад; VBAT_OK_HYST — підйом, ≈ PROG + 100 мВ; TI SLUSBH2), а **не** «вбудовані 3%». Запобігають дрижанню (chatter) при граничній напрузі. Значення 3.4 / 3.32 В у таблиці — поточна **ціль дизайну** (фінал — bench).

**У Firmware:** VBAT_OK — апаратний buck/brownout-**гейт**, НЕ періодичний wake. Канон wake-source (RTC WUT + Vcap-енергогейт + RTC-календар timebase) — [`03_01 §1.10`](03_01_Firmware_Lifecycle_and_DMA) (FW.49): при буфері 4.39 Дж VBAT_OK залипає HIGH → rising-edge не дає heartbeat; cold-start після глибокого розряду = power-on-reset (нижче порогу MCU знеструмлений).

## 🏗️ 3. Внутрішня Архітектура BQ25570

BQ25570 об'єднує три незалежні підсистеми в одному чіпі:

### 3.1. Cold Start Circuit (Система Холодного Старту)

**Умова активації:** VIN > 330 мВ та IIN > 15 мкА (наш EBFC: VIN ≈ 500–800 мВ → ✅)

- Спрощена "накачувальна помпа" (charge pump) з низьким пороговим струмом
- Заряджає VSTOR від 0V до ~1.8V (без MPPT, просто "накачує")
- При VSTOR ≥ 1.8V — вмикається основний Boost-конвертер (MPPT)

**Для нашої системи:** після місяців зберігання на складі або після повного розряду, достатньо буде навіть мінімального зимового EBFC-струму для запуску Cold Start.

### 3.2. Boost Charger з MPPT (Підвищуючий Зарядний Конвертер)

**Принцип роботи MPPT (Maximum Power Point Tracking):**
- Кожні **16 секунд** BQ25570 на **256 мс** від'єднує навантаження (EBFC "дихає")
- Вимірює VOC (Open Circuit Voltage) — напругу без навантаження
- Встановлює робочу точку: V_MPP = ROC_fraction × VOC
- Для нашого 65% налаштування (§4.А): V_MPP = 0.65 × VOC

**Чому важливий MPPT для EBFC:** EBFC має нелінійну характеристику P-V (потужність-напруга). Без MPPT система може "пристрілятися" в неоптимальній точці і видавати в 2–3 рази менше потужності.

### 3.3. Buck Converter (Понижуючий Стабілізатор)

- **Вхід:** VSTOR (0–5.5V, нестабільна)
- **Вихід:** VOUT = 3.3V (стабілізована, до 100 mA)
- **Quiescent Current:** 488 нА (в режимі без навантаження — критично для бюджету)
- **Увімкнення:** Тільки при VSTOR > VBAT_OK threshold

## 🧮 4. Розрахунок Програмуючих Резисторів

BQ25570 програмується виключно апаратно через SMD-резистори (допуск **1%**, рекомендований розмір **0402**).

**Базова формула (V_REF = 1.21V, внутрішній опорний):**

```
V_threshold = V_REF × (1 + R_upper / R_lower)
```

### А. MPPT Sampling Fraction

**Ціль:** 65% від VOC (рекомендована початкова точка для EBFC Gen 2.0 на базі dgrFAD-GDH / Laccase+ZIF-nanozyme, трекінг [`00_07` — HW.13](00_07_Action_Plan_Tracker))

> **Попередня конфігурація (50%)** наведена нижче для порівняння. Для лабораторних тестів починати з 65%.

#### 🔒 SSOT Convention — узгоджено з TI BQ25570 datasheet (SLUSBH2G, березень 2019, §8.2.3.2, Figure 42)

| Позначення | Розташування у схемі | Призначення |
|---|---|---|
| **R_OC1** | Резистор від піна **VOC_SAMP до GND** (нижнє плече) | Задає фракцію MPPT |
| **R_OC2** | Резистор від **CSTOR/VSTOR до піна VOC_SAMP** (верхнє плече) | Доповнення до RSUM |

```
MPPT_fraction = V_MPP / V_OC = R_OC1 / (R_OC1 + R_OC2)
```

> ⚠️ **Anti-Footgun:** Імена R_OC1/R_OC2 у деяких неофіційних tutorials та EE-форумах інвертовані. Якщо інженер запаяє значення за зворотньою конвенцією — **фракція стане 35% замість 65%**. Це загнало б ферментативну MPP у зону масо-транспортних обмежень (літ. Vargaftik для FAD-GDH/Laccase: P_drop до 60% при V < V_MPP). Завжди звіряти з TI datasheet Figure 42 та зведеною таблицею §5 цього документа.

**Конфігурація 65% (рекомендована для EBFC):**

| Компонент | Розташування | Значення | Допуск | Корпус |
|---|---|---|---|---|
| **R_OC1** | VOC_SAMP → GND | **10.0 MΩ** | 1% | 0402 |
| **R_OC2** | VSTOR → VOC_SAMP | **5.36 MΩ** | 1% | 0402 |
| MPPT fraction (actual) | — | 10.0 / (10.0 + 5.36) = **65.1%** | — | — |

**Перевірка за TI worked example (datasheet стор. 31):**

```
TI example: MPP = 40%, RSUM = 20 MΩ
  R_OC1 = (V_MPP/V_OC) × RSUM = 0.40 × 20 = 8.0  MΩ  ← нижній (до GND)
  R_OC2 = RSUM × (1 - V_MPP/V_OC) = 20 × 0.60 = 12.0 MΩ ← верхній (від VSTOR)
  Перевірка: 8 / (8+12) = 0.40 ✓

Наш випадок: MPP = 65%, RSUM = 15.36 MΩ
  R_OC1 = 0.65 × 15.36 = 9.98 MΩ → 10.0 MΩ standard 1%
  R_OC2 = 15.36 × 0.35 = 5.38 MΩ → 5.36 MΩ standard 1%
  Перевірка: 10 / (10+5.36) = 0.651 ✓ (65.1%)
```

**Конфігурація 50% (поточна, для порівняння/TEG):**

| Компонент | Розташування | Значення | Допуск | Корпус |
|---|---|---|---|---|
| R_OC1 | VOC_SAMP → GND | **10.0 MΩ** | 1% | 0402 |
| R_OC2 | VSTOR → VOC_SAMP | **10.0 MΩ** | 1% | 0402 |
| MPPT fraction (actual) | — | **50.0%** | — | — |

## 🛡️ 6. Апаратний Хак: Buffer Cap для Піку LoRa TX

**Проблема:** Buck-конвертер BQ25570 видає максимум **100 mA** постійного струму. Під час відправки пакету LoRa на максимальній потужності (+22 dBm) трансивер SX1262 споживає **118 mA** (пік ~100 мс). Різниця 18 мА може спричинити просадку напруги (Brownout) та скидання STM32.

> **⚠️ Залежить від рішення TX power у §9.** Якщо в §9 буде закріплено TX-power +14 dBm (рекомендовано для позитивного енергобалансу), то I_TX ≈ 40 mA < 100 mA buck max → **buffer cap не потрібен для brownout protection**, але залишається корисним для PSRR і фільтрації. У такому разі — 47µF 16V X7R 1210.

### 6.1. Реалістичний DC Bias Derating (виправлено)

> **⚠️ DC bias derating — реалістичні дані:** наївна оцінка «~20% для X5R при 3.3V/6.3V» сильно недооцінює просадку ємності. Реальні дані з Murata GRM32 series datasheet (1210 corpus):

| Part | C@0V | C@3.3V | Derating | Eff. capacitance |
|---|---|---|---|---|
| 100µF, **6.3V**, X5R, 0603 (GRM188R60J107M) | 100 µF | ~15-25 µF | **-75 to -85%** | ❌ Brownout risk |
| 100µF, **6.3V**, X5R, 0805 | 100 µF | ~30-40 µF | -60 to -70% | ❌ Marginal |
| 100µF, **6.3V**, X5R, 1210 (GRM32ER60J107M) | 100 µF | ~45-55 µF | -45 to -55% | ⚠️ На межі |
| 100µF, **25V**, X7R, 1210 (GRM32ER71E107M) | 100 µF | ~85-90 µF | **-10 to -15%** | ✅ **Recommended** |
| 47µF, **25V**, X7R, 1210 | 47 µF | ~38-42 µF | -10 to -15% | ✅ Достатньо для +14 dBm |

**Корінь проблеми:** DC bias derating нелінійно залежить від (а) корпусу (товщина діелектрика — більший корпус = більша товщина = менший field), (б) voltage rating (25V part при 3.3V працює у 13% від номінальної напруги — мінімальний derating), (в) діелектрика (X7R стабільніший за X5R).

### 6.2. Специфікація (2 конфігурації залежно від TX power)

**Конфігурація A — TX +22 dBm (118 mA pulse):**

```
VOUT (3.3V) ──┬── [STM32WLE5JC 3V3 pin]
              │
              ├── [100 µF, 25V, X7R, 1210, low-ESR]
              │       Murata GRM32ER71E107M або аналог
              │       C_eff @ 3.3V ≈ 85 µF
              ├── [10 µF, 25V, X7R, 0805]     ← мід-частотний фільтр
              ├── [100 nF, 50V, X7R, 0402]    ← HF decoupling біля STM32 VDD pin
              │
             GND
```

ΔV during 100ms TX: ΔV = (118-100)mA × 100ms / 85µF = **21 мВ** ✓ (< 50 мВ tolerance)

**Конфігурація B — TX +14 dBm (40 mA, рекомендована, див. §9):**

```
VOUT (3.3V) ──┬── [STM32WLE5JC 3V3 pin]
              ├── [47 µF, 25V, X7R, 1210]    C_eff ≈ 40 µF
              ├── [10 µF, 25V, X7R, 0805]
              ├── [100 nF, 50V, X7R, 0402]
              │
             GND
```

При I_TX = 40 mA < 100 mA buck max → конденсатор не покриває пік, а лише фільтрує. ΔV пренебрежимо.

### 6.3. Жорсткі правила

- ✅ **MLCC X7R** (не X5R) — кращі температурна стабільність та DC bias performance
- ✅ **Voltage rating ≥ 4× робочої напруги** (для 3.3V → 25V part). Це найдешевший спосіб зменшити DC bias derating до прийнятних -15%.
- ✅ **Корпус 1210** для основного бункерного cap (більший корпус = тонший field at 3.3V)
- ❌ **6.3V parts заборонені** незалежно від корпусу — DC bias знищує половину ємності
- ❌ **Корпус 0603/0805 для основного buffer cap заборонений** — derating -65 до -85%
- ❌ **Танталові капи** — leakage 1-10 µA знищує енергобюджет (`/per §9`)

> **Чому НЕ просто 2× 47µF паралельно замість 100µF:** Це OK варіант (нижчий ESR, redundancy), але займає 2× місця на PCB і не дає виграшу в effective capacitance — два 47µF 25V X7R 1210 дають ~80 µF при 3.3V, що еквівалентно одному 100 µF 25V X7R 1210 (~85 µF). Залишити як option для high-reliability batches.

## 🔋 7. Логіка VBAT_OK: апаратний живлення-гейт (cold-start + brownout)

Сигнал `VBAT_OK` від BQ25570 — апаратний **гейт живлення**: він вирішує, чи buck взагалі подає 3.3 В на STM32, а **не** коли вузол прокидається. «Нульовий лаг» тут — у тому, що MCU не опитує напругу: BQ25570 сам тримає живлення лише коли VSTOR достатній. **Періодичне пробудження** (heartbeat) робить RTC-WUT, а корисність циклу гейтить Vcap-енергогейт — канон wake-source [`03_01 §1.10`](03_01_Firmware_Lifecycle_and_DMA) (FW.49). VBAT_OK фігурує лише на двох краях: **cold-start** (перший boot) і **brownout** (втрата/відновлення живлення).

```
Часовий графік (типовий цикл):

0 год      0.5 год     0.75 год    1+ год
│          │           │           │
│ Холодний ▼ VSTOR     ▼ VBAT_OK   ▼ LoRa TX
│  старт   зростає     стає HIGH   цикл починається
│ (EBFC)   (0→3.4V)   (MCU BOOT)   (через 15-30 хв першого заряду)
│
└── VBAT_OK ──LOW (MCU = STOP2) ──────────────▶ HIGH ──── MCU активний
                                                       (VSTOR ≥ 3.4V)
```

**Поведінка на краях (cold-start + brownout):**
- **Після монтажу (свіжий супер-кап, 0V):** BQ25570 Cold-Start → VSTOR повільно зростає → через 15–30 хвилин досягає 3.4V → VBAT_OK = HIGH → STM32 завантажується вперше
- **Глибокий розряд (зимовий дефіцит / тривала ніч):** якщо VSTOR падає < 3.31V → VBAT_OK = LOW → buck off → MCU **знеструмлений** (brownout), стан — у RTC Backup. ⚠️ Це **brownout**, не штатний сон: у нормі вузол STOP2-спить між RTC-WUT-циклами ([`03_01 §1.10`](03_01_Firmware_Lifecycle_and_DMA)), а не тому, що VBAT_OK впав.
- **Відновлення:** EBFC підіймає VSTOR ≥ 3.4V → VBAT_OK = HIGH → buck ON → STM32 стартує заново (power-on-reset), `delta_t`-continuity з RTC.

**Граничний ланцюжок живлення (cold-start / brownout-recovery):**
```
EBFC (>500mV) → BQ25570 Boost → VSTOR ≥ 3.4V → VBAT_OK HIGH
                                              → Buck ON → VOUT = 3.3V
                                              → MCU під живленням (перший boot / brownout-recovery = power-on-reset)
                                              → штатний heartbeat далі = RTC-WUT ([`03_01 §1.10`](03_01_Firmware_Lifecycle_and_DMA)), НЕ VBAT_OK-edge
```

## ⚡ 9. Розрахунок Енергетичного Балансу (з урахуванням ККД)

> **⚠️ ККД boost+buck — вирішальний:** лінійний розрахунок без ККД дав би хибний висновок «1 TX/год = в плюсі». При реалістичних ККД per-stage система **виходить у мінус на 54 мДж/год** без мітигацій. Нижче — повний розрахунок з ККД per-stage та три рішення, що повертають баланс у плюс.

### 9.1. ККД BQ25570 — точні значення (TI datasheet SLVSBH2)

**Boost path (EBFC → VSTOR):**

| Робоча точка | I_IN | η_boost |
|---|---|---|
| P_EBFC=15 µW @ V_OP=325 мВ | ~46 µA | **~0.68** |
| P_EBFC=30 µW @ V_OP=325 мВ (2× площа) | ~92 µA | ~0.75 |
| P_EBFC=100 µW (winter peak) | ~300 µA | ~0.82 |

**Buck path (VSTOR=4.5V avg → VOUT=3.3V):**

| Режим | I_OUT | η_buck |
|---|---|---|
| Active TX/compute | 30–120 mA | **~0.88** |
| Idle (RTC + DMA) | ~1 µA | **~0.50** (quiescent overhead dominates) |

### 9.2. Генерація з урахуванням boost ККД

```
P_gen     = 15 µW   (typical Gen 2.0 EBFC, P_sapwood @ 15°C summer)
t         = 3600 s
E_gen_raw = 54 мДж  (raw на вході BQ25570)
η_boost   = 0.68
E_gen_supercap = 54 × 0.68 = 36.7 мДж/год  ← реальна енергія в supercap
```

### 9.3. Sleep Drain з ККД buck (low-load efficiency hit)

```
P_STM32_sleep_at_VOUT = I_STM32_STOP2 × V_OUT = 1.07 µA × 3.3 V = 3.531 µW
P_drawn_from_VSTOR    = P_STM32_sleep / η_buck_sleep = 3.531 / 0.50 = 7.06 µW

P_BQ_Q (з VSTOR безпосередньо, не через buck) = 488 nA × 4.5 V = 2.196 µW

P_total_VSTOR_drain   = 7.06 + 2.20 = 9.26 µW
E_sleep_supercap      = 9.26 × 3600 = 33.3 мДж/год  ← у 1.87× більше за лінійну оцінку!
```

### 9.4. Cost of Active Cycle з ККД buck active

```
E_active_at_VOUT:
  TinyML:       12 mA × 3.3 V × 0.2 s  = 7.92 мДж
  mruby Lorenz:  8 mA × 3.3 V × 0.15 s = 3.96 мДж
  LoRa TX@+22dBm: 118 mA × 3.3 V × 0.1 s = 38.94 мДж
  ─────────────────────────────────────
  Σ E_active_at_VOUT = 50.82 мДж/cycle

η_buck_active = 0.88
E_active_from_VSTOR = 50.82 / 0.88 = 57.75 мДж/cycle
```

> **Тривалості — оцінки-стелі:** `0.2 / 0.15 / 0.1 с` тут — округлені **верхні** оцінки активних під-фаз (завищені відносно виміряних → енергобюджет **консервативний**, а не точковий). Детальна latency-розкладка акустичного шляху — [`03_03 §3.3`](03_03_TinyML_Acoustic_Inference): одне inference-вікно ≈ **44–57 мс** awake (DMA-fill 32 мс + DSP + CNN), тобто добре в межах 0.2-с стелі; LoRa air-time уточнюється per-SF у §9.6 (SF9 ≈ 165 мс). Тому висновки §9.5–9.7 — **нижня межа** запасу.

### 9.5. Net Balance — поточна конфігурація (+22 dBm, 1 TX/год) ❌

```
E_net_per_hour = E_gen_supercap − E_sleep_supercap − N_TX × E_active_from_VSTOR
              = 36.7 − 33.3 − 1 × 57.75 = −54.35 мДж/год

ВИСНОВОК: система втрачає 54 мДж на кожному циклі.
Supercap розрядиться за: 7.11 Дж / 54.35 мДж = 131 цикл = 5.5 діб → reset.
```

### 9.6. Три Сценарії Виправлення

#### Сценарій A — Просто збільшити інтервал TX (не працює)
```
H = E_active / (E_gen − E_sleep) = 57.75 / (36.7 − 33.3) = 17 годин
```
17 годин між пакетами — неприйнятно для моніторингу здоров'я лісу.

#### Сценарій B — Знизити TX power з +22 до +14 dBm
SX1262 @ +14 dBm: I_TX ≈ 40 mA (datasheet, vs 118 mA @ +22 dBm).
**Trade-off:** -8 dB TX power → -8 dB link margin → знижене покриття. Компенсація: підняти SF (з SF7 на SF9-SF10) → +5 dB sensitivity на gateway, що частково компенсує. Air-time зростає (SF9 ≈ 165 ms замість 110 ms @ SF7).

```
E_TX_+14dBm = 40 mA × 3.3 V × 0.165 s = 21.78 мДж  (SF9 air-time)
E_active_at_VOUT = 7.92 + 3.96 + 21.78 = 33.66 мДж
E_active_from_VSTOR = 33.66 / 0.88 = 38.25 мДж

H = 38.25 / (36.7 − 33.3) = 11.2 години  ← все ще багато
```

#### Сценарій C — +14 dBm TX + знижений STM32 sleep current (РЕКОМЕНДОВАНО)

> ⚠️ **У цього вибору є МЕТРОЛОГІЧНА ціна, і вона порахована окремо [STK.5, 2026-08-26].** Рекомендація тут виведена з енергії; але отриманий інтервал `Δt ≈ 1.77 год` лежить БЛИЗЬКО до повільного краю метаболічного відображення `m(Δt)`, а там та сама похибка `delta_t` підсилюється сильніше. Виміряно: розширена невизначеність `U(k=2)` growth-points ≈ **18%** у цій точці проти ≈ **5%** біля швидкого краю — тобто **енергетичний і метрологічний оптимуми не збігаються**. Ціна названа, не заперечена: енергобаланс лишається несучим (без нього вузол просто не працює), а бюджет точності живе в [`05_02 §Trust-origin ladder`](05_02_Proof_of_Growth_Pipeline) і рахується моделлю `tools/firmware/uncertainty_budget.rb`. ⛔ Переглядаючи `Δt`, не оптимізуй лише енергію — прожени обидві моделі (`scc_rate.rb` для значення, `uncertainty_budget.rb` для точності).
Зменшити sleep STM32WLE5JC з 1.07 µA до ~300 nA через RTC-backup-only mode (SRAM2 retention OFF, тільки backup registers) — це підтримується LL_PWR_EnterStop2Mode з flag `STOP2_RTC_ONLY`:

```
P_STM32_sleep_at_VOUT = 300 nA × 3.3 V = 0.99 µW
P_drawn_from_VSTOR    = 0.99 / 0.50 = 1.98 µW
P_total_VSTOR_drain   = 1.98 + 2.20 = 4.18 µW
E_sleep_supercap      = 4.18 × 3600 = 15.04 мДж/год

H = E_active / (E_gen − E_sleep) = 38.25 / (36.7 − 15.04) = 1.77 години
```
✅ **1 TX кожні 1 год 46 хв** — близько до цільового 1/год циклу, позитивний баланс +1.4 мДж/год запасу.

#### Сценарій D — +14 dBm TX + 2× площа анкера (P_gen → 30 µW) + RTC-only sleep
```
E_gen_supercap = 30 × 3600 × 0.75 = 81 мДж/год
H = 38.25 / (81 − 15.04) = 0.58 години = 35 хв
```
✅ **1 TX кожні 35 хв** — оптимально для real-time моніторингу.

> Sleep тільки: 15.04 мДж/год → НЕГАТИВ навіть без TX
> ```
> → Зимовий режим: повне відключення MCU sleep current через PFET cut-off, TX лише при VSTOR ≥ 5.0V (накопичення кілька днів). Деталі — ARCH.8 "мовчання = здоров'я" та [`02_05`](02_05_Queen_Hardware_and_Starlink) HW.14.

### 9.9. Fauna Acoustic Overlay (ARCH.39 — поза baseline TX-циклом)

Енергобаланс §9.4–9.7 рахує **лише** baseline TX-цикл (sense → Lorenz → 1 TX). Fauna-акустичні сесії (TinyML biodiversity inference, [`03_03 §10.3`](03_03_TinyML_Acoustic_Inference) / ARCH.39) — **окрема активність поверх** нього:

```
E_fauna_session ≈ 78.3 мДж     (~12 мА × 1.56 с active CPU: 156 log-mel+inference вікон, через η_buck)
E_fauna_daily   ≈ 156.6 мДж/добу (~2 сесії/добу) — × 20 від застарілої оцінки 3.3 мДж/добу
```

Це **перевищує** запас Сценарію C (+1.4 мДж/год ≈ +33.6 мДж/добу), тож fauna **не може** бути гарантованою щоденною статтею бюджету. SSOT-рішення:

1. **Opportunistic-only:** fauna-сесія запускається **лише** коли `V_cap ≥ FAUNA_VCAP_MIN_MV` — guard `Fauna_Should_Sample()` (**FW.42**). Fauna споживає **профіцит**, не baseline.
2. **Транзієнт:** пік ~12 мА × 1.56 с потребує V_cap margin над `VBAT_OK ON`, інакше brownout посеред inference (звідси guard, а не просто лічильник).
3. Baseline TX-бюджет (Сценарій C) **лишається чинним без змін** — fauna не входить у H-розрахунок інтервалу TX.

Cross-ref: ARCH.39 ([`03_03 §10.3`](03_03_TinyML_Acoustic_Inference)), FW.42 (V_cap guard), ARCH.40 (монолітна 5-с сесія через SRAM2-wipe constraint).

### 9.10. CAD Sniff Overlay (ARCH.26 L3 — поза baseline TX-циклом)

Це той «окремий перегляд енергобюджету CAD», який відклала корекція у [`03_01 §1.9`](03_01_Firmware_Lifecycle_and_DMA). Як і fauna (§9.9), CAD-нюх — **окрема активність поверх** baseline TX-циклу; але тут дві зв'язані сторони: **сніфер** (Провідник, періодичний мс-«нюх» ефіру) і **PANIC-відправник** (подовжена преамбула). Гарантія зловлення — `T_pre > T_sniff`; SF-basis усіх цифр = SF9/BW125 Сценарію C (§9.8), `T_sym = 4.096 мс` (SF10-приклади airtime у [`03_05`](03_05_Hardware_Symmetric_Crypto_and_Security) — інший, LoRaWAN-DR2 контекст, тут не застосовні).

```
Сніфер:  E_cad ≈ 250 µЖ/цикл  (wake STOP2 → SPI → CAD 2-симв ≈ 8 мс @ ~5 мА → сон;
                               оцінка 03_01 §1.9 «десятки–сотні µJ» — уточнить PPK2)
         E_daily = 86400/T_sniff × E_cad:
           T_sniff =  3 с → 7.2 Дж/добу
           T_sniff = 15 с → 1.44 Дж/добу
           T_sniff = 60 с → 0.36 Дж/добу

Відправник: P_TX(+14 дБм, MCU+PA, через η_buck) ≈ 0.10–0.15 Вт
            E_pre(T_pre) = P_TX × T_pre;  EDLC usable ≈ ½·0.47·(3.3²−2.0²) ≈ 1.62 Дж
            → стеля T_pre ≈ 10–16 с (довша преамбула = brownout ДО кінця преамбули)
```

**Double-bind (чому це не «оптимізується», а вибирається):** харвест-сумісний нюх (60 с → 0.36 Дж/добу — влазить лише у Сценарій D +576 мДж/добу) вимагає `T_pre > 60 с` ≈ 9.2 Дж — **3.6× повного EDLC**, фізично неможливо. А посильна відправнику преамбула (≤ ~10 с) вимагає нюху кожні ≤ ~8 с ≥ 2.7 Дж/добу — **не тягне жоден EBFC-сценарій, включно з D**. На чистому EBFC async-зловлення PANIC **несумісне** — це чесний вердикт, не інженерний недолік.

**SSOT-рішення:**

1. **Role-gated overlay:** CAD-нюх — лише `ROLE_PROVISIONER` ([`03_01 §1.11`](03_01_Firmware_Lifecycle_and_DMA)) із **зовнішнім/надлишковим джерелом** (роль Провідника й означає «інше живлення» — сонячна підживка / mains, як у Королеви). Baseline TX-бюджет (Сценарій C) **не змінюється**; рядовий EBFC-Солдат не нюхає ніколи.
2. **Baseline-пара** (bench-tunable, обидві у `firmware/common/cad_sniff.h`): `T_sniff = 3 с` (сніфер, ~7.2 Дж/добу — surplus-джерело) ↔ `T_pre = 4 с` (973 симв @SF9, airtime 4.003 с; E ≈ 0.4–0.6 Дж ≈ 25–37% usable EDLC — «останній зойк» дерева під бензопилою). Host-тест №10 (`test_cad_sniff.c`) тримає нерівність гарантії — розсинхрон пари валить сюїту.
3. **Дворівневий V_cap-гейт відправника** (FW.42-патерн): повна преамбула лише при `V_cap ≥ 4500 мВ` (EMA-оцінка DR12), інакше — дефолтні 8 симв: brownout посеред преамбули = не вилетіло **нічого**, а короткий зойк always-on Королева (L1) у зоні ще зловить. До живого V_cap-каналу (FW.50) поріг вище стелі VREFINT-тракту → extended-half **чесно fail-closed**.
4. **Обов'язкове відновлення** преамбули до 8 симв одразу після PANIC-TX (дисципліна `Restore_ECB_Mode`): липкі 973 симв на звичайному TX = ~40× airtime мовчки.

Cross-ref: ARCH.26 L3 ([`03_01 §1.9`](03_01_Firmware_Lifecycle_and_DMA) — драбина Рандеву + політика ролей), ARCH.27 ([`03_01 §1.11`](03_01_Firmware_Lifecycle_and_DMA)), FW.42 (§9.9 — той самий гейт-патерн), Сценарії C/D (§9.6–9.8), EDLC §12; глю + константи — `firmware/common/cad_sniff.h`, bench-профіль — [`00_07` ARCH.26](00_07_Action_Plan_Tracker).

## 🔋 12. Буфер EDLC (Суперконденсатор — «Серцебиття Енергії»)

> Накопичувальний елемент power-path: суперконденсатор на VSTOR (§2). Тут — фізична специфікація іоністора, його **подвійна роль** як метаболічного біо-сенсора та розглянуті альтернативи накопичувача. **Енергетичний бюджет** (запас / робоче вікно / корисна енергія, TX-цикли) живе у §8 (зведена таблиця) + §9 (повний баланс з ККД) — тут **не дублюється**.

### 12.1. Фізична Специфікація

Ми свідомо відмовилися від літій-іонних (Li-ion/LiPo) акумуляторів. Літій деградує за 3-5 років, боїться морозів і має обмежену кількість циклів заряду-розряду. Наша система розрахована на 20+ років у лісі.

- **Тип:** EDLC (Іоністор) Radial / Coin Cell.
- **Ємність:** 0.47 Ф (Farad).
- **Максимальна напруга:** 5.5 В.
- **Робочий цикл:** Практично нескінченний (>500,000 циклів заряду-розряду).
- **Струм витоку (Leakage Current):** < 1-2 µA (Критичний параметр! Якщо струм витоку буде більшим за генерацію EBFC, система ніколи не зарядиться).
- **Енергетичний бюджет** (запас 7.11 Дж @5.5V → робоче вікно 4.39 Дж → ≈3.87 Дж корисних на VOUT після Buck; к-сть TX-циклів на заряд) — §8 (таблиця) + §9 (баланс з ККД, Сценарій C). Тут навмисно не повторюємо — One-Home.

### 12.2. Подвійне Призначення: Іоністор як Біо-Сенсор

У SilkenNet іоністор виконує дві функції одночасно:
1. **М'яз (Energy Buffer):** Накопичує мікроструми (наноампери) протягом ~1 год 46 хв, щоб віддати **40 мА** за 165 мс для пострілу LoRa-антени (§9.6 Сценарій C, TX @ +14 dBm SF9). _Попередня модель «120 мА × 100 мс @ +22 dBm» давала негативний енергобаланс — §9.5._
2. **Пульс (Metabolic Sensor):** Швидкість наповнення іоністора прямо пропорційна кількості цукру у ксилемному соку дерева.

#### Механіка "Нульового Лагу" та вимірювання `delta_t`
Замість того, щоб постійно будити процесор і міряти струм, ми використовуємо час як сенсор.
1. RTC WUT періодично будить STM32; firmware читає Vcap-енергогейт і робить повний цикл лише коли іоністор перезарядився достатньо (канон wake — [`03_01 §1.10`](03_01_Firmware_Lifecycle_and_DMA), FW.49; VBAT_OK — апаратний buck-гейт, **НЕ** wake-компаратор).
2. STM32 вимірює **wall-час** від останнього energy-sufficient циклу (`delta_t_seconds` через RTC-календар, не заморожений у STOP2 `HAL_GetTick`), записує `vcap_voltage`, відправляє пакет і знову засинає (STOP2).
3. Якщо `delta_t` мале — дерево активно "п'є" воду і фотосинтезує (високий струм від EBFC). Якщо `delta_t` велике — дерево у стресі (посуха).

### 12.3. Зв'язок з BioContract

Дані про зарядку (`delta_t` та `vcap_voltage`) упаковуються у payload і летять на сервер. Там у гру вступає **`bio_contract.rb`** (SilkenNet::Attractor) — канон логіки [`03_04`](03_04_mruby_Lorenz_Attractor).

[E.63] **Лоренц гейтить СТАТУС, метаболізм задає БАЛИ.** Час заряду іоністора (`delta_t`) формує осі атрактора, а Z-координата визначає лише статус гомеостазу:
* Z < 2.0 (`CRITICAL_Z_MIN`) → `status = 1` (стрес / посуха), `growth_points = 1` (дерево виживає).
* Z > anomaly_ceiling (ρ-відносна обвідна, ≈ 45 при ρ=28 — E.64) → `status = 2` (аномалія), `growth_points = 0` (емісія зупиняється).
* Інакше → `status = 0` (гомеостаз); `growth_points` = **метаболічна жвавість** `metabolic_health(delta_t)` ([`03_04 §4.3`](03_04_mruby_Lorenz_Attractor)) — швидший перезаряд дає більше балів, Z тут балів НЕ задає. Константи — [`03_04 §1.2`](03_04_mruby_Lorenz_Attractor).

**Висновок:** Чим швидше заряджається наш 0.47F іоністор (менший `delta_t`), тим більше токенів SCC (Silken Carbon Coin) генерує дерево. Апаратна фізика напряму карбує Web3-економіку.

### 12.4. Розглянуті Альтернативи Накопичувача Енергії

#### 12.4.1. Гібридний LIC (Lithium-Ion Capacitor) — Eaton HS1016-3R8306-R

**Характеристики:** 30 F / 3.8 V · Запасена енергія: ~216 Дж · Витік: < 1 µA.

**Аргументи «за»:**
- Величезний запас надійності: навіть при 50% деградації ємності через 20 років LIC зберігає в тисячі разів більше енергії, ніж потрібно для повного active-циклу (~38 мДж, Сценарій C +14 dBm — §9.6; НЕ плутати з deprecated «~39 мДж @ +22 dBm»).
- Стійкість до перебоїв: дозволяє сотні циклів TX поспіль навіть при тимчасовій відсутності генерації EBFC (сильний мороз, обрізка гілок).
- Зимовий запас: при -15°C ESR зростає, але 216 Дж дають достатній "тепловий буфер" для TX.

**Чому відхилено для поточної архітектури:**

1. **Знищення біо-сенсорного каналу `delta_t`.** Це головна причина. Поточний 0.47 F EDLC свідомо малий, щоб час його заряду (`delta_t`) прямо відображав метаболічну активність дерева (швидкість генерації глюкози → EBFC → мікроампери → заряд). При 30 F конденсатор заряджається **місяцями** (ΔQ = 30F × 5.5V = 165 Кл; при 20 µА: t ≈ 8.25 млн сек ≈ 95 днів), а не годинами — `delta_t` втрачає біологічну роздільну здатність і стає безглуздим входом для атрактора Лоренца.
2. **Літій-іонна хімія.** LIC містить літієву анодну вставку. Хоча це не повноцінний Li-ion акумулятор, літій деградує в циклах глибокого охолодження (-30°C/+40°C щоденно у лісі), має обмежений цикл-лайф порівняно з EDLC (500k+), і створює додаткові екологічні ризики при масовому розгортанні в лісах.
3. **Фізичний розмір.** 30 F LIC значно більший за 0.47 F coin cell, що порушує компактність капсули Soldier (PEEK-радом + анкер).
4. **Вартість.** LIC ~$8-12 vs EDLC ~$1.10 при 10k+ шт.

**Висновок:** LIC є корисним для систем, де потрібна чиста енергонезалежність (наприклад, Queen Gateway з сонячною панеллю). Для Soldier вузла, де конденсатор є одночасно сенсором, 0.47 F EDLC — єдиний правильний вибір.

#### 12.4.2. Концепт Діагностики Деградації Конденсатора (Перспективна ідея)

Корисний концепт, який не залежить від вибору накопичувача:

> **Задача:** Розрізнити "дерево хворіє" від "конденсатор деградує". Обидва стани виглядають однаково: `delta_t` зростає (повільніший заряд).

**Пропоноване рішення (TRL 8+, майбутній цикл):**
- Раз на добу STM32 вимірює **чисту напругу розімкнутого кола EBFC** ($V_{OC}$) при від'єднаному навантаженні.
- Якщо $V_{OC}$ в нормі (>500 мВ), а `delta_t` зростає — деградує конденсатор, а не дерево.
- Якщо $V_{OC}$ падає разом з `delta_t` — дерево у стресі (посуха, хвороба).
- Для точного вимірювання $V_{OC}$ можна використати зовнішній 24-бітний ADC (наприклад, **ADS1220** від TI, ~$6.00) з режимом duty cycling (споживання 120 нА у сні, пробудження за мілісекунди). Однак для поточного TRL 6 вбудований 12-бітний ADC STM32WLE5JC є достатнім.
- Ця інформація дозволяє **не «штрафувати» дерево за апаратну деградацію**.

> **⚠️ DCI-safe архітектура [HW.19, verified 2026-05-29].** Корекцію застосовувати **НЕ в Z-математиці.** `SilkenNet::Attractor` — бітове дзеркало firmware `bio_contract.rb` для **Dual Computation Integrity** (server-Z мусить == device-Z). Firmware VOC не має → якщо сервер скоригує Z (σ/ρ) за VOC, server-Z розійдеться з device-Z → `check_z_divergence!` флагне фрод на **кожному** пакеті. Тому:
> - **Z лишається ідентичним firmware** (без VOC) — DCI недоторканий.
> - VOC-корекція живе на **шарі рішення про slashing** (`ContractHealthCheckService` / degradation count): дерево зі **здоровим VOC (≥500мВ) + degraded `delta_t`/`vcap`** → *hardware-confounded* → **виключається зі slashing-підрахунку** (не false-slash інвестора за старіння заліза).
> - **VOC = рідкісний діагностичний сигнал** (кап деградує роками), НЕ per-packet (sensor payload повний) — потрібен окремий механізм доставки.

**Статус:** Концепт **верифіковано** (2026-05-29), DCI-safe дизайн зафіксовано. Реалізація gated: (1) firmware VOC-вимір (GPIO disconnect EDLC → ADC), (2) delivery-контракт, (3) slashing-layer корекція + `voc_mv` колонка. Backlog: HW.19. TRL 8+.
