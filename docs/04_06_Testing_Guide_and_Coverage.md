# Частина A — View Component Testing Guide

Всі нові та існуючі спеки ПОВИННІ слідувати цим правилам.

## A.1 Структура та конвенції (Convention over Configuration)

> 🔴 **`spec/integration/` НЕ є окремим ярусом тестування — це каталог, а не шар** (виміряно 2026-08-12, [`TEST.12`](00_07_Action_Plan_Tracker) вісь D). `rspec-rails` мапить `spec/(requests|integration|api)` в ОДИН і той самий `type: :request` (`configuration.rb`: `request: %w[spec (requests|integration|api)]`), тож обидва каталоги дістають ті самі `before(:each, type: :request)`-хуки й той самий Rack-стек. **Практичний наслідок: приклад у `spec/integration/` не має жодної властивості, якої не має його близнюк у `spec/requests/` — тож коли обидва існують, другий є ЧИСТИМ дублем, а не «дешевшою страховкою».** Доведено зняттям 22 таких дублів: покриття не зрушило ні на рядок (line 99.54 % · branch 98.01 % до і після). ⚠️ Звідси й правило для нових файлів: ярус обирають ЗА ПОВЕДІНКОЮ (браузерний приклад — `spec/features/`, критерій належності в §B нижче), а не за словом «integration» у шляху.

### 1. Один файл — один компонент
Шлях спеки дзеркалить шлях компонента:
```
app/views/components/trees/show.rb  →  spec/views/components/trees/show_spec.rb
app/views/shared/ui/stat_card.rb    →  spec/views/shared/ui/stat_card_spec.rb
app/views/layouts/dashboard_layout.rb → spec/views/layouts/dashboard_layout_spec.rb
```

### 2. Використовуй `PhlexComponentHelper` (DRY rendering)
Модуль `spec/support/phlex_component_helper.rb` автоматично підключається до
всіх файлів у `spec/views/`. Він надає:
- `render_component(**kwargs)` — автоматично обирає `.call` чи `ApplicationController.renderer.render`
- `component_class` — синонім `described_class`
- `mock_pagy(count:, page:, last:)` — **СПРАВЖНІЙ `Pagy::Offset`**, не double: `last` тут не поле, а ВХІД, з якого виводиться `limit`, тож суперечити `count` не може ⚠️ слово «double» стояло тут до 2026-08-19 і описувало знятий `OpenStruct` (носій — `spec/quality/pagy_fixture_is_real_spec.rb`)
- `mock_model(klass, id:, **attrs)` — OpenStruct з model_name/to_key/to_param
- ⛔ **Жодну з цих `mock_*`-фабрик не затінюй локальним `def`** — див. §A.2 п.7 (гейт `spec/quality/shared_fixture_home_spec.rb`)

### 3. Рендеринг: renderer vs .call
- **`.call`** — для компонентів БЕЗ route helpers, turbo tags, form builders
- **`ApplicationController.renderer.render`** — для компонентів з `_path`, `turbo_frame_tag`, `form_with`, `button_to`
- `render_component` з хелпера обирає автоматично за аналізом вихідного файлу
- Якщо перевизначаєш `render_component` у спеці — ЗАВЖДИ пиши коментар чому

### 4. Не перевизначай `render_component` без потреби
Хелпер працює для 95% випадків. Перевизначай тільки коли:
- Компонент приймає блок (DataTable)
- Потрібна кастомна логіка рендерингу (layout wrapping)
- Layout-компоненти (`DashboardLayout`, `AuthLayout`) потребують `content:` параметр
- Сигнатура `initialize` конфліктує з `**kwargs`

### 5. Не оголошуй `component_class` локально — його дає хелпер
Хелпер надає метод `component_class`. Якщо спека ще має
`let(:component_class) { described_class }` — це не помилка, але зайвий рядок.

## A.2 Моки та тестові дані

### 6. OpenStruct для моків, НЕ FactoryBot (для view спек)
View спеки тестують HTML-розмітку, не ORM. `OpenStruct` швидший за `build()`.
⚠️ **ПРАВИЛО ЗВУЖЕНО [TEST.12]: це дефолт для ДАНИХ, а не дозвіл ПІДРОБЛЯТИ модель.** Щойно компонент читає щось, що модель ДЕРИВУЄ (`alias_attribute` · `store_accessor` · метод над колонками), `OpenStruct` віддає `nil` або дозволяє задати похідне НАПРЯМУ — і фікстура оголошує світ, у якому дефекту не існує (тринадцять виміряних осей — §B.2 BP #14). Тому дерево системно переведене на **реальні незбережені записи** (`Klass.new`, без БД); мок лишається доречним для plain-Hash даних, які й контролер будує хешем. Винятки, де AR-модель обовʼязкова структурно: `Maintenance::Form` (потребує валідну модель для `form_with`).

### 7. `mock_model(klass, id:, **attrs)` для моделей з route helpers
Якщо компонент використовує `tree_path(tree)` або `dom_id(tx)` —
mock ПОВИНЕН мати `model_name`, `to_key`, `to_param`. Використовуй `mock_model`.

🔴 **І НЕ ЗАТІНЮЙ фабрику спільного хелпера локальним `def` — це обхід гейта, а не стиль** [TEST.12/UI.17, 2026-08-19]. Фікстурні фабрики (`mock_*` у `spec/support/phlex_component_helper.rb`) тримають інваріант, і гейт на нього міряє САМЕ хелпер. Локальне визначення затінює його всередині файлу, тож обходить перевірку мовчки: `pagy_fixture_is_real_spec` роками стверджував, що `OpenStruct`-двійник `Pagy` вимер, і був зелений — поки один файл оголошував власний `def mock_pagy` рівно забороненої форми. Потрібна інша фікстура — дай їй **власне імʼя** (`build_*`). Носій — `spec/quality/shared_fixture_home_spec.rb`; його стеля названа там же (судить ЗАТІНЕННЯ, ніколи ЯКІСТЬ; `render_component` свідомо поза периметром — він віддає рендер, не фікстуру, і його локально спеціалізують це законно в десятках файлів — точну лічбу бери прогоном `grep -rln 'def render_component' spec/views | wc -l`, не звідси).

🔴 **Надгробок конверсії називає СУБʼЄКТ, бо в багатообʼєктному файлі напис про один обʼєкт читається як звіт про файл** [UI.17, виміряно 2026-08-19]. Форма `# [TEST.12] Реальний незбережений Tree…` правдива про свою фікстуру й хибна як враження: чотири файли несли такий надгробок, а за 2–6 рядків від нього стояв неконвертований СУСІД (`wallets/show` · `organizations/show` · `maintenance/index` · `trees/index`). ⚠️ Дискримінатор виміряно, і це **не** мова вердикту: надгробок, що каже «це присуд, а не недогляд», ховав дефект так само. Не вводять в оману ті, що називають **(а) межу субʼєкта** (цей РЯДОК ⊥ цей МЕТОД ⊥ цей ФАЙЛ), **(б) сам вимір** («виміряно, не вгадано»), часто **(в) чого прохід НЕ брав** — взірці: «Пін цілиться в «CSQ: 0», а НЕ в голе «0%» — і це виміряно», «`under_threat?` стабимо свідомо — єдине, що тут вимагало б БД». **Тож закривши сайт, перечитай ФАЙЛ і назви в надгробку, що саме він покриває.** ⊕ Родини, чиї надгробки межу називають (`ARCH.84` · `UI.3` · `SEC.25` · `I18N.1`), виміряні чистими — правило не універсальне, воно про **конверсію фікстур у файлі з кількома обʼєктами**.

### 8. Кожен mock-метод — іменований за domain entity
```ruby
# ✅ Добре
def mock_tree(...) end
def mock_gateway(...) end
def mock_wallet(...) end

# ❌ Погано
def make_data(...) end
def build_mock(...) end
```

### 9. Параметри mock-методів мають розумні дефолти
```ruby
def mock_tree(did: "SNET-00000042", status: "active", ...)
```
Кожен параметр — з дефолтом. Тест перевизначає тільки те, що тестує.

### 10. `define_singleton_method` для предикатів
```ruby
t = OpenStruct.new(status: status)
t.define_singleton_method(:active?) { status == "active" }
```
OpenStruct не генерує `?`-методи автоматично.

### 10а. 🔴 Стаб на РЕАЛЬНОМУ класі не сміє ВИЗНАЧАТИ метод, якого в застосунку немає

Мок на `OpenStruct` (правила 6–10) імітує **дані** — це нормально. `prepend` на живий
клас — інша річ: він змінює саму поверхню, що тестується, і якщо додає метод, якого
в продакшні не існує, спека пінить світ, у якому дефект **неможливий**.

🔴 **І та сама хвороба входить ДРУГИМИ дверима — коли `OpenStruct` імітує не дані, а МЕТАДАНІ ФРЕЙМВОРКУ** (SEC.25, 2026-08-01). `model_name` виглядає як поле мока, а насправді це контракт, з якого Rails виводить **маршрут і префікс параметрів**. `firmwares/form_spec` оголошував

```ruby
fw.define_singleton_method(:model_name) do
  OpenStruct.new(param_key: "firmware", route_key: "firmwares", …)  # ❌ обидва ВИГАДАНІ
end
```

а справжній `BioContractFirmware` дає `bio_contract_firmware` / `bio_contract_firmwares`. Тобто фікстура вигадала **рівно ті два імені, яких моделі бракує** — і це не випадковість: інакше автор спеки не змусив би її пройти. Ціна: `form_with(model:)` виводив неіснуючий `bio_contract_firmwares_path` → `GET /firmwares/new` віддавав **500 без форми**, тобто завантажити прошивку через UI було неможливо, при зеленій спеці на всіх її прикладах. **Правило:** мок, що оголошує `model_name` / `to_param` / `persisted?` / `to_model`, підміняє КОНТРАКТ, а не дані — або бери справжню модель (`.new`, БД не потрібна), або звір кожне поле рантаймом. **І перевіряй сусіда:** `TreeFamilies::Form` живий лише тому, що там `route_key` і `param_key` **випадково** збіглися з іменем маршруту й `params.require` — тобто патерн небезпечний в обох місцях, просто в одному ще не вистрелив. Питай не «чи є робочий приклад», а **«він працює за конструкцією чи за збігом»**.

🔴 **ТРЕТІ двері, і вони уточнюють саме першу клаузу цього правила («мок імітує ДАНІ — це нормально»):** `OpenStruct` + `define_singleton_method` імітує не дані, а **ПОВЕДІНКУ**, і тоді він не «мовчки віддає nil на невідоме поле» — він **виготовляє предикат, якого модель не має**. [`TEST.12`](00_07_Action_Plan_Tracker), 2026-08-10: спека компонента оголошувала предикат `…?`, якого на моделі не існувало — там був лише однойменний СКОУП; компонент кликав його в циклі, гілка досяжна за штатного стану, і сторінка віддавала **500**, доки спека лишалась зеленою саме тому, що метод для неї існував. ⚠️ **І `verify_partial_doubles` тут сліпий ЗА ПОБУДОВОЮ** — він перевіряє `instance_double` і `allow(real).to receive(…)`, а `OpenStruct`/`define_singleton_method` не проходять через RSpec mock-API взагалі, тож увімкнений прапорець створює хибне відчуття, що клас закритий. **Правило:** мок, що оголошує метод із `?`/`!` або будь-яку ПОВЕДІНКУ (а не значення поля), підміняє контракт так само, як `model_name` вище — бери справжню модель (`.new`/`build_stubbed`, БД не потрібна) або звір існування методу рантаймом. Найдешевший детектор — **асиметрія**: тут той самий намір за 80 рядків у контролері був виражений правильно (через скоуп, не через вигаданий предикат), і саме розбіжність двох сусідів указала на дефект швидше за будь-який греп.

Куплено дорого ([UI.6], 2026-07-31): чотири спеки родини `maintenance` робили

```ruby
Views::Shared::UI::PhotoCard.prepend(Module.new do
  def maintenance_record_photo_path(*, **) = "/…/photos/1"   # ❌ метод НЕ існував
end)
```

Хелпер не існував (зайвий `as:` у вкладеному `resources` подвоював префікс), тож
сторінка запису **з будь-яким фото віддавала 500** — а сюїта лишалась зеленою роками.
Сусідній стаб у тому ж файлі підміняв хелпер, який **існує**, і його коментар
стверджував протилежне («routes do not expose an `:edit` action») — тобто був stale-
дзеркалом ери до фіксу маршруту.

**Правило.** `prepend`/`allow_any_instance_of` на продакшн-клас дозволені лише для
того, що в тому класі **вже є**. Перед тим як стабити маршрут-хелпер — перевір його
в рантаймі (`Rails.application.routes.url_helpers.respond_to?(:name)`), а не на око.

🔴 **І друга половина того самого правила — про ОБСЯГ дії, а не про предмет: `prepend` на клас діє ГЛОБАЛЬНО з моменту завантаження будь-якого файлу, що його виконав.** Той самий blob-carve-out (`prepend` зі стабами `rails_blob_path`/`rails_representation_path`) стоїть у кількох спек-файлах однієї родини, тож у ПОВНОМУ прогоні він накриває й request-спеки, які прикріплюють РЕАЛЬНІ блоби. Сьогодні це нікого не турбує (виміряно ізольовано й разом — обидва зелені, бо жоден приклад не пінить blob-URL), але вада латентна: щойно хтось запінить URL у request-спеці, результат почне залежати від ПОРЯДКУ завантаження файлів.
⛔ **Спільний винос такого carve-out'а в `spec/support/` — НЕ робити** (винесено з [`00_07`](00_07_Action_Plan_Tracker) UI.4 при архівації 2026-08-18): той каталог автозавантажується, тож глобальний `prepend` став би безумовним для ВСІЄЇ сюїти, включно зі спеками на реальний ActiveStorage. Чесна форма — **явний хелпер-метод, який файли кличуть самі**: обсяг тоді оголошений викликом, а не побічним ефектом розташування файлу.

### 10б. 🔴 Компонент, що диспетчеризує за ТИПОМ, вимагає справжнього класу — `is_a?` тут не працює за побудовою

Коли компонент розрізняє події через `case @event when EwsAlert … end`, Ruby йде через
`Module#===`, а той **не диспетчеризується** через Ruby-рівневий `is_a?`. Тобто мок із
`define_singleton_method(:is_a?)` віддає `true` на прямий виклик і все одно падає в `else`
(виміряно рантаймом, не прочитано). Наслідок класовий: усі «типізовані» сценарії тихо
рендерять нейтральну гілку, а приклад, що пінить лише присутність тексту, лишається зеленим.

**Лік — `Klass.allocate`:** він обходить ініціалізацію ActiveRecord (БД не потрібна), але
зберігає класову ідентичність, тож `case/when` працює. Поля добираються
`define_singleton_method`.

⚠️ **Ціна `.allocate` реальна й на користь:** запис не має `@attributes`, тож **кожне**
поле, яке читає компонент, мусить бути застабленим — інакше рендер падає
`fetch_value for nil`. Мовчазний `nil` (як у `OpenStruct`) заміняється гучним падінням,
і саме воно показує, що компонент читає більше, ніж думала фікстура.

🔴 **І дефекти тут ВКЛАДЕНІ: зовнішній маскує внутрішній.** У `dashboard_event_row_preview`
під диспетчеризацією ховалось значення поза enum'ом (`alert_type: "Thermal Anomaly"`) —
полагодивши лише перше, превʼю поїхало б fail-open гілкою `humanize`. **Полагодивши
диспетчеризацію, перевір рендер ЩЕ РАЗ, а не постав галочку** ([`TEST.12`](00_07_Action_Plan_Tracker), 2026-08-12).

🔴 **І окремо про побічний ефект САМОЇ конверсії, бо вона тут рекомендований хід: мок буває носієм НАВМИСНОГО захисту, і заміна на реальну модель знімає його мовчки** ([`TEST.12`](00_07_Action_Plan_Tracker), 2026-08-14). `actuators/card_spec` подавав `commands` об'єктом, чий `last` **кидає виняток** — це був не недогляд фікстури, а пастка, що пінить «картка не сміє добирати команди сама» (заборона запиту в Phlex-`initialize`, [`04_04 §6.4`](04_04_Phlex_UI_and_Tailwind)). На реальному `Actuator` це жива асоціація, тож наївна конверсія перетворила б вибух на тихий `nil` і зняла б захист, лишивши всі приклади зеленими. **Правило: перед конверсією інвентаризуй, що мок робив НАВМИСНО — вибух, відсутність поля, свідомо порожня колекція — і відтвори це стабом на реальному записі. Фікстура, яка виглядає недбалою, буває єдиним носієм інваріанта, і жоден приклад не назве його вголос.**

**Межа проходить по КОНТРАКТУ АРГУМЕНТІВ, не по «маршрут ⊥ зовнішній ресурс».**
`rails_blob_path` теж маршрут-хелпер; стабити його доводиться тому, що він вимагає від
мока `signed_id`, а не тому, що він «зовнішній». `…_photo_path` вимагає лише
`to_param`, який `Object` дає безкоштовно, — тому й працює без стабу. Питання завжди
одне: **чи задовольняє мок контракт аргументів цього хелпера**.

🔴 **І половина, якої це правило не покривало: заміна мока на СПРАВЖНЮ модель закриває РЕНДЕР і лишається сліпою до САБМІТУ.** `firmwares/form_spec` перевели на реальний `BioContractFirmware.new` саме за цим правилом — і він лишався зеленим, поки форма слала два поля без колонок (`target_hardware`, `notes`) і кожен `POST /firmwares` віддавав **500**. Причина структурна, не недбала: `form_with` виставляє `allow_method_names_outside_object`, тож `Tags::Base#value` читає неіснуюче поле під `respond_to?`-гардом і повертає `nil`. Реальна модель доводить, що компонент РЕНДЕРИТЬСЯ, і не здатна сказати нічого про те, чи контролер прийме те, що зрендерилось — а мас-присвоєння в `create` кидає `ActiveModel::UnknownAttributeError` саме на цих полях. **Єдиний пін, який це бачить, — round-trip:** `GET` форми → зішкребти `name="<scope>[…]"` із живої розмітки → `POST` тим самим складом. Рукописний перелік полів атестує те, що надрукував автор, а не те, що форма шле, тож наступний дрейф пройде зеленим; форма піна тут і є вся його цінність.

⚠️ **І ціна самої конверсії, яку треба закладати наперед: реальний запис ЗАКРИВАЄ гілки, які мок тримав відкритими через `nil`.** Після переходу `firmwares/index_spec` на `build_stubbed` перестала виконуватись гілка `binary_sha256&.first(16) || t(".not_available")` — мок не оголошував того поля взагалі, тож рендер завжди йшов у фолбек. Одна гілка тут коштує ≈0.02 pp, тобто рівно ту дельту, що розводить локальний прогін і CI (98.01 ⊥ 97.99 на підлозі 98.00) — тож зелене локально не є свідченням про CI. **Конвертуючи мок, грепни компонент на `&.` · `||` · `presence` і додай приклад на кожну гілку, яку доти тримав nil** — інакше конверсія, зроблена заради чесності фікстури, зсуває підлогу покриття.

⚠️ **Що саме купує зняття стабу — ІМ'Я, а не URL.** Хелпер із голим `OpenStruct`
резолвиться, але підставляє `inspect`-рядок у сегмент:
`/maintenance_records/7/photos/%23%3COpenStruct%20id=99%3E`. Тобто спека
доводить «метод існує», а не «шлях правильний». Наслідок для пінів: перевіряй
**повний** шлях (`include(maintenance_record_photo_path(record, photo))`),
ніколи не префікс на кшталт `include("/photos/")` — префікс істинний при будь-якому
сміттєвому аргументі.

⚠️ І наслідок для покриття: компонентна спека рендерить повз маршрутизатор, тож
непіднятий хелпер вона не побачить у принципі. Кожна сторінка, що рендерить дію,
потребує **одного** request-приклада на справжньому HTTP — саме він ловить цей клас.

🔴 **Той самий сліпий кут має ДРУГУ форму, і вона тихіша: хелпер резолвиться, а ціль
не приймає ДІЄСЛОВО** ([UI.7], 2026-07-31). Засновковий інстанс слав un-toggle
на колекційний шлях, зареєстрований лише під `POST` — рядок HTML виглядав бездоганно,
компонентна спека рендерила його роками зеленою, а кнопка вела в 404 у всіх. Тому пінь
**ЦІЛЬ, а не дієслово**: `include(%(action="#{шлях}"))` плюс `not_to include` на сусідній
шлях, коли дві дії не сміють ділити адресу. І **сам стаб може звузити світ до дефекту**:
той спек визначав рівно ОДИН із двох потрібних хелперів — той, яким компонент помилково
слав обидві дії. Це не порушення правила вище (метод існував), а його сусід: стаб покривав
**підмножину** реальної поверхні, тож правильний маршрут не міг зʼявитись у рендері навіть
теоретично. Рефлекс: стабиш маршрут-хелпер — спитай, **скільки їх у цієї сторінки**.

⚠️ **Виміряна стеля, яку не закрити спекою взагалі:** `allow_forgery_protection = false`
у test-env, а `ApplicationController.renderer` не має сесії — тож `authenticity_token`
не рендериться навіть при примусово ввімкненому захисті (перевірено). Уся сюїта сліпа
до відсутнього CSRF-токена, і саме так рукописна `<form>` без нього прожила поруч із
`button_to`-сусідами. Не вдавай, що покрив: використовуй `button_to`/`form_with`, які
кладуть токен самі, і не рукописний `<form>`. ✅ **Із 2026-08-15 це вже не порада, а
HARD-гейт** — `spec/security/phlex_no_handwritten_form_spec.rb` (заборона з нульовим
винятком, ⚖️ UI.7). 🔴 Форма доказу тут інша, ніж у гейта над ВЛАСТИВІСТЮ: порожня
множина є МЕТОЮ, тож живість несе не «підмет існує», а самоперевірка детектора
(позитивний ⊥ негативний контроль) плюс пін, що glob узагалі бачить дерево.

```ruby
RSpec.describe Trees::Show do

```

### 12. Перший describe-блок — базовий рендер (чи рендериться взагалі)
Мінімум 2-3 it-блоки: ключовий заголовок, структурний елемент, анімація. **Імʼя блоку вільне** — `"rendering"` · `"header section"` · будь-яке предметне. ⛔ Тут доти стояло «`describe "rendering"` — перший блок», тобто ІМʼЯ як вимога — і дерево її не виконувало: 19 спек із 88 (виміряно 2026-08-22), бо решта копіювала ✅-взірець BP 11, який починається з `describe "header section"`. Правило й власний взірець гайду вказували в різні боки, і 79% авторів пішли за взірцем — правильно, бо копіювати ✅-блок гайд і запрошує (див. застереження про цементування дефекту взірцем нижче). Несуче тут — ЩО перевіряє перший блок, не як він зветься.

### 13. `describe "edge cases"` — nil handling, empty collections, boundary values
```ruby
describe "edge cases" do
  it "handles nil gateway gracefully" do ...
  it "shows empty state when logs are empty" do ...
end
```

### 14. `describe "accessibility"` — role, aria, focus-visible
```ruby
describe "accessibility" do
  it "renders table with role=table" do ...
  it "renders th with scope=col" do ...
  it "has focus-visible ring on interactive elements" do ...
end
```

### 15. `describe "design system compliance"` — gaia tokens, custom text scale
```ruby
describe "design system compliance" do
  it "uses gaia design tokens, not raw Tailwind colors" do
    expect(html).not_to include("bg-white")
    expect(html).not_to include("text-gray-900")
  end

  it "uses custom text scale (text-tiny/mini/micro/compact)" do
    expect(html).to include("text-tiny")
  end
end
```

> 🔴 **Чесно про межу цього піна — він стверджує РЯДОК, не ефект.** `include("text-tiny")`
> зелений і тоді, коли Tailwind для `text-tiny` не генерує нічого: v4 на невідомий
> токен не лається, тож розмітка виглядає написаною, CSS мовчить, елемент успадковує
> чуже. Саме так ця секція сім місяців засвідчувала шкалу, якої в CSS не існувало
> **жодного дня** (`@theme` оголошував її в мертвому namespace `--font-size-*` замість
> v4-шного `--text-*`; 448 ужитків рендерились кореневими 16px). Той самий клас уже
> коштував фантомного `--gaia-primary-text` (кнопки 1.98:1 у темній темі) і всієї
> entrance-анімації (94 входження при нулі в білді).
>
> Тому пін тут лишається — він про **намір компонента**, і це законний предмет — але
> існування утиліти він НЕ доводить. Ту половину тримає окремий гейт із зовнішнім
> якорем: `spec/quality/design_token_existence_spec.rb`, вісь «the custom text scale
> actually reaches the built CSS». **Правило ширше за цей приклад: пін на текст класу
> ніколи не є заявою про його ефект** (§B.2 BP #14).

```ruby
expect(html).to include('<div class="p-6 border border-emerald-900 bg-black">')

# ✅ Стійкий — але ЗА ТОКЕНАМИ, не за сирою палітрою
expect(html).to include("border-gaia-border")
expect(html).to include("bg-gaia-surface-base")
# ⛔ `border-emerald-900` / `bg-black` тут стояли до 2026-08-22 і суперечили §19 нижче,

#    рівно те, від чого застерігає правило «правлячи правило, грепни ГАЙД»
```

### 18. Тестуй CSS-класи окремо, не разом
```ruby
# ✅ Кожен клас — окрема перевірка
expect(html).to include("bg-status-warning")
expect(html).to include("italic")
```
⚠️ **Приклад свідомо переписаний 2026-08-19, і причина варта рядка: тут стояли
`text-emerald-500` + `animate-pulse` — обидва тепер ЗАБОРОНЕНІ саме в цій ролі**
(сира палітра як текст ⊥ рух як носій сенсу, [`04_04 §3.5`](04_04_Phlex_UI_and_Tailwind)/§16),
і сім таких пінів довелось переносити зі спек. **Взірець у гайді — це найдешевший
спосіб зацементувати дефект: наступний контрибʼютор копіює ✅-блок, не читаючи
розділ, що його забороняє.** Тож правлячи правило, грепни ГАЙД на форму, яку воно
щойно оголосило поза законом — інакше документ навчатиме проти себе.

### 19. Тестуй наявність gaia-токенів, не hardcoded значень
```ruby
# ✅
expect(html).to include("text-gaia-text-muted")
expect(html).to include("bg-gaia-surface")
expect(html).to include("border-gaia-border")

# ❌ сира палітра — дефект теми, а не «дозволено на доменній сторінці»
expect(html).to include("text-emerald-500")
```
⚠️ **У ✅-блоці стояв `text-gaia-primary`, і його теж прибрано 2026-08-19** — токен
оголошений і леґітимний, але НЕ в ролі кольору тексту (`2.30–2.54` у світлій темі,
[`04_04 §3.5`](04_04_Phlex_UI_and_Tailwind)); для тексту йде парний `-strong`. **Взірець
«вживай токени» примірював саме той токен, який щойно став порушенням** — тобто
приклад був правильний на своїй осі (токен ⊥ сира палітра) і хибний на сусідній
(придатність до ролі), і ніщо в ньому цього не показувало. Носій — `spec/quality/text_token_contrast_spec.rb`.
Для shared UI компонентів — ТІЛЬКИ gaia-токени (HARD-гейт `gaia:lint_tokens`).

🔴 **Доти тут стояло «Для page components (Trees::Show, etc.) — допускається raw Tailwind» — дозвіл ЗНЯТО 2026-08-07** разом із його домом ([`04_04 §3.5`](04_04_Phlex_UI_and_Tailwind), ⚖️ присуд «світла тема підтримувана»). Сире палітрове значення легальне лише тем-інваріантне **й оголошене** (бренд-глоу [`04_04 §16.4`](04_04_Phlex_UI_and_Tailwind) · scrim), решта — дефект теми. ⚠️ Наслідок саме для тестового шару, і він не косметичний: доменні компоненти сьогодні цим дозволом РЯСНО користуються (борг → [`00_07`](00_07_Action_Plan_Tracker) UI.1), тож `not_to include("bg-black")` у їхніх спеках зараз почервонів би масово. Тобто пін на токен-чистоту ставиться **разом із migrate-хвилею свого домену**, не наперед — а вже наявний хіт читай як борг, не як ліцензію.

Заборона стосується **токена**, не імені. Пін на сам підписаний рядок пінив би
`secret_key_base` і серіалізатор Turbo замість НАШОГО скоупу — і мовчки порвався б
на ротації ключа. Але зупинятись на «елемент присутній» не можна: підпис
детермінований, тож імʼя **розпаковується** і є єдиним, що робить підписку
правильною чи витоком ([`04_04 §8.1`](04_04_Phlex_UI_and_Tailwind), SEC.25).

```ruby
def subscribed_streams(markup)
  markup.scan(/signed-stream-name="([^"]+)"/).flatten
        .map { |s| Turbo::StreamsChannel.verified_stream_name(s) }
end

# Скоуп несе саме ІМʼЯ → рівність множини, не `include`.
# `_e{epoch}` — покоління імені [SEC.25 Ф3]; у компонент-спеці бери епоху
# НЕ-дефолтну (тут 7), інакше зашита в код одиниця лишила б пін зеленим.
expect(subscribed_streams(html)).to eq([ "telemetry_stream_org_42_e7" ])
```

⚠️ **Голий `include("turbo-cable-stream-source")` — вакуумний пін**: він зелений і
тоді, коли сторінка підписана на чужий стрім. Саме ця редакція правила лишила
компонент-спеки телеметрії й мапи без жодного асершна на підписку — ані на ціль,
ані на факт. Форму доказу диктує **кардинальність сторінки**: одна сутність →
two-subject (двоє глядачів мусять дістати РІЗНІ імена), список → рівність множини
(дефект там виглядає як ЗАЙВИЙ стрім, а не як відсутній власний).

### 23. `ApplicationCable::Connection`: три пастки харнеса, кожна дає ФАЛЬШИВО-ЗЕЛЕНЕ

Знайдені читанням джерела `actioncable`/`rspec-rails`, не помилкою, — але кожна
коштувала б налагодження, і дві з трьох роблять приклад зеленим із хибної причини.

- 🔴 **`TestCookieJar` має `signed` і `encrypted`, але НЕ `signed_or_encrypted`.**
  Тобто дослівне дзеркало продового `CookieStore` (який читає саме через
  `signed_or_encrypted`) штатним харнесом **не пишеться взагалі** — приклад упаде
  на `NoMethodError`, а не на тому, що перевіряє.
- 🔴 **`TestCookies#[]=` бере `options.symbolize_keys[:value]`.** Хеш сесії, покладений
  без обгортки `{ value: … }`, мовчки стає `nil` — і тоді КОЖЕН приклад «доводить»
  відмову з порожнього cookie незалежно від логіки під тестом. Класика вакуумного
  зеленого: асершн правдивий, а причина не та.
- ✅ **Харнес будувати не треба:** `rspec-rails` `ChannelExampleGroup` уже підмішує
  обидва `Behavior` і дає матчер `have_rejected_connection`.

⚠️ Суміжна пастка фікстур на acting-організації: `Organization has_many :audit_logs,
dependent: :restrict_with_error`, а перемикання контексту **завжди** лишає запис
([`04_03 §3.1`](04_03_REST_API_v1_Reference)) — тож організація, в яку хтось перемкнувся,

будуй такий стан, не видаляючи вже вживану організацію.

### B.1.2 Solidity

Відкритих ризиків немає. ERC20Permit (повна EIP-712 сюїта: `permit()` + SFC `delegateBySig` + cross-chain інваріант) та Governor↔SCC integration (DAO керує/ротує `MINTER_ROLE`/`SLASHER_ROLE` через 48h-Timelock) — закрито; цемент у [`00_07`](00_07_Action_Plan_Tracker) (TEST.3).

🔴 **Тут доти стояла «чесна межа шару»: нібито в тестовому середовищі сторінки не несуть asset-тегів узагалі, і винен рендер-шлях запиту Rails. Обидві половини СПРОСТОВАНО 2026-07-31 — і винен був не Rails, а наш власний харнес.** Глушив `spec/support/layout_asset_stubs.rb`: він БЕЗУМОВНО повертав `""` замість `stylesheet_link_tag`/`javascript_importmap_tags` на `DashboardLayout`/`AuthLayout`. Рендер-шлях запиту весь цей час віддавав повний importmap — це перевірено тим самим `ActionDispatch::Integration::Session`, яким «доводили» протилежне. 🔴 **Чому діагноз тримався й чому шукали не там: контрольним виміром був `bin/rails runner`, а він НЕ вантажить `spec/support/`** — тобто найпереконливіший «доказ провини Rails» був артефактом того, що контроль не проходив через власний стаб. Клас ширший за випадок: **контраст «тут працює, там ні» доводить провину лише тоді, коли обидва середовища вантажать одні й ті самі support-шари.** Лік — глушити відсутність asset'а, а не виклик (`rescue Propshaft::MissingAssetError`).

✅ **Що це означає для нового feature-спека сьогодні:** сценарії на живий Stimulus/Turbo **можна й треба писати** — `typeof window.Stimulus` = `"object"`, `turbo:morph` відтворюється керовано (`Turbo.visit(href, {action:"replace"})`). Зразок — `spec/features/dashboard_browser_smoke_spec.rb` («boots Leaflet locally and plots a geolocated tree»: він доводить увесь ланцюг від серверної розмітки до намальованого маркера, тобто ВИКОНАННЯ нашого контролера, а не лише присутність Stimulus). ⚠️ Дві пастки лишаються чинними, і зразок обходить їх НЕ боротьбою, а зміною якоря: Capybara скоупить пошук у `/html/body` (тож `have_css("html…")` по кореню не матчить НІКОЛИ) → пінься за вузол у `body`, який мутує контролер; `evaluate_script` не чекає нічого → спершу дочекайся DOM-зміни через `have_css`, і лише ПОТІМ читай скриптом. ⚠️ Доти обома ілюстраціями був тумблер теми (`theme#toggle` + `startViewTransition`) — його знято присудом [`04_04 §1`](04_04_Phlex_UI_and_Tailwind), тож приклади й пастки перепривʼязано до живих носіїв; сам КЛАС обох пасток не змінився. ⚠️ І **не «лагодь» такий приклад моком**: замоканий Stimulus доводив би, що працює мок, а не застосунок. ✅ **Мапа (Leaflet) — закрито 2026-08-03, і причин виявилось ДВІ, обидві поза тестовим шаром.** Тут доти стояло «контролер реєструється й модуль вантажиться, але `L.map()` не викликається — причина НЕ встановлена»; насправді не було жодного стану, в якому обидві половини цього речення правдиві одночасно, бо це два різні виміри, зшиті в один опис. **(1)** `map_controller.js` робить СТАТИЧНИЙ `import L from "leaflet"` на верхньому рівні, а `leaflet` пінився на зовнішній CDN — тож недосяжний домен валив завантаження **всього модуля**, і Stimulus не реєстрував контролер узагалі (виміряно блокуванням: 8 identifiers → 7). **(2)** Головна й постійна: **`nodeTargetConnected` приходить РАНІШЕ за `connect()`** — Stimulus піднімає `targetObserver` до виклику `controller.connect()`, тож для вузлів, уже присутніх у розмітці, обробник target'а спрацьовує першим і ловить `this.markers` як `undefined`; виняток валить реєстрацію контролера. Тобто мапа ламалась саме тоді, коли їй було що показати, а «зелені» проби минулих сесій просто не мали жодного геолокованого дерева. 🔴 **Клас, ширший за випадок: розбіжність результатів МІЖ СЕСІЯМИ на тому самому дереві — це не «середовище», а невиміряна змінна; тут їх було дві (аптайм чужого домену й наявність даних у фікстурі), і кожна поодинці пояснювала симптом переконливо й неправильно.** Лік — локальний пін (JS+CSS+images) та ідемпотентна ініціалізація з обох входів; походження модулів стереже `spec/security/importmap_locality_spec.rb`, бо пін на «мапа будується» при живому CDN зелений і з зовнішнім піном.

⚠️ **Пастка харнеса, успадкована звідти й дорога в діагностиці:** локальний `public/assets/.manifest.json` перемикає Propshaft на **Static**-резолвер, тож після будь-якого нового піна ВСІ браузерні приклади падають на логіні (asset не в манифесті → stub гасить теги → сторінка без JS). Симптом брехливий — читається як зламана автентифікація, а не як asset.

🔴 **І це лише ГУЧНА половина пастки — тиха коштувала дорожче (виміряно 2026-08-17, [`UI.3`](00_07_Action_Plan_Tracker)).** Той самий Static-резолвер віддає **застарілий дайджест** CSS, і тоді приклади не падають, а **проходять**, міряючи знімок стилів довільної давнини: `bin/rails tailwindcss:build` оновлює `app/assets/builds/`, а браузер бачить `public/assets/tailwind-<старий>.css`. У виміряному випадку розрив був три доби — фікс namespace типографіки був зроблений, перевірений грепом по білду, і **не доходив до браузера взагалі**, тож прилад червонів на вже полагодженому коді. **Клас: гейт не бреше про вердикт, він судить ІНШИЙ АРТЕФАКТ, ніж той, що в дереві** — і на зеленому це не має жодного симптому.

✅ **Лік — ВИДАЛИТИ `public/assets/`, а не оновити її.** Це вирівнює локальний прогін із CI: обидві спек-джоби заходять через `./.github/actions/setup-rails-test` (крок «Build Tailwind CSS» = `bin/rails tailwindcss:build`) і **прекомпіляції не роблять свідомо** — мотив і вимір записані просто в `ci.yml` над кроком `feature-test`. Прекомпільований манифест локально повертає розбіжність із CI й гарантовано протухає при наступній правці CSS; `assets:precompile` доречний лише коли предметом є САМЕ Static-шлях. ⚠️ Каталог у `.gitignore` — тож у репо його немає, і на відвантажене це не впливає; пастка суто локальна, і саме тому невидима для будь-якого CI-гейта.

⚠️ **Гейт покриття:** `FEATURE_TEST=1` (як і `COVERAGE=0`) повністю вимикає SimpleCov-поріг — feature-специ міряються окремою CI-джобою, а їхній власний прогін дає ≈0% глобального покриття, тож гейт хибно впав би (§B.3).

⚠️ **Критерій нижче зараз БЕЗ живої демонстрації в дереві** — другий зразок шару існував і показував його в чистому вигляді, але носія більше немає. Це оголошена діра, а не забутий рядок: наступна browser-спека цього класу мусить стати сюди зразком. Дефект був такий: сервер віддавав здорову відповідь (повна сторінка, 201), а ламав її КЛІЄНТ — Turbo робить `proposeVisit(fetchResponse.location)`, де `location` є URL самого POST'а, тож адресний рядок після кожної дії вказував туди, де GET не зареєстровано. Request-пін на статус і ціль редиректу тут потрібен і вже існує; чого він не вміє — це **перезавантаження**, а саме воно й було єдиним проявом. Тобто в цей шар іде не «сценарій цілком», а рівно та одна дія, що нижче неможлива.

🔴 **Пастка цього шару, куплена в тому ж файлі й дорожча за сам приклад: браузерний клік легко влучає не туди, і приклад від цього не червоніє, а ЗЕЛЕНІШАЄ.** Перша редакція брала `first(:button)` по всій сторінці — а дашборд несе сайдбар і топбар, тож клік ішов у хром, дія не відбувалась, і приклад проходив однаково зі зламаним кодом (перевірено мутацією: повернення дефекту лишало його зеленим). Читанням це не видно взагалі. Два висновки, обидва обов'язкові: **клік скоупити** (`within("#…") { click_button(…) }`), і **пінити, що дія СТАЛАСЯ** (`change(Model, :count)`), бо сама лише навігація після кліку в порожнечу виглядає точно так само, як після успішного сабміту. Без другої половини приклад лишається вакуумним у нову форму — той самий клас, що §A.2, правило 10а, лише на браузерному шарі.

✅ **Третій зразок — `spec/features/form_error_visibility_spec.rb` (2026-08-03, [SEC.25]), і він додає до критерію одну грань: у цей шар іде не лише «дія, неможлива нижче», а й ДОКАЗ, що людина щось ПОБАЧИЛА.** Дефект був у тому, що форми, які рендеряться на 422, не показували причини відмови; request-пін доводить, що причина є в ТІЛІ відповіді, але саме тіло викидає клієнт — Turbo рендерить сабміт-відповідь лише поза 2xx, і вся ця вісь відкрилась `200`-ками, які він ковтав мовчки. Тобто пін на тіло лишається зеленим тоді, коли на екрані не змінюється нічого. ⚠️ **Прикладів тут рівно два — по одному на МЕХАНІЗМ сабміту, а не по одному на форму** (`form_with`, де Rails будує форму й CSRF сам, ⊥ рукописна `form(...)` з hidden `_method` і рукописним токеном — клас, що вже стріляв в [`UI.7`](00_07_Action_Plan_Tracker)); решта чотири поверхні доказовні нижче й сюди не дублюються.

🔴 **І друга пастка шару, спіймана там же: наше власне a11y-рішення зробило найочевидніший селектор вакуумним.** `have_css('[role="alert"]')` окремим твердженням **не падає ніколи**, бо `FlashMessages` за a11y-контрактом тримає порожній assertive-регіон у КОЖНОМУ дашборді ([`04_04 §6.1`](04_04_Phlex_UI_and_Tailwind)) — тобто селектор істинний на будь-якій сторінці незалежно від того, чи форма щось сказала. Роль і текст мусять їхати ОДНИМ матчером (`have_css('[role="alert"]', text: …)`). Клас ширший за цей випадок: **щойно якийсь елемент рендериться беззастережно заради доступності, кожен пін на його САМУ ПРИСУТНІСТЬ стає тавтологією** — перевіряй вміст, не наявність. ⚠️ **Другий носій того самого класу живе на request-шарі й виглядає ще переконливіше:** `provisioning_controller_spec` пінив `body.include?("hardware_uid")` на гілках 409/404 — рядок, що є в тілі ЗАВЖДИ, бо це `name` інпута тієї самої форми. Приклад читався як перевірка причини й не вмів упасти (виправлено 2026-08-03 на `I18n.t`-текст, mutation-verified). **Правило, що покриває обидва: пін мусить цитувати те, чого без фіксу в тілі НЕ БУЛО** — а `name` поля, `id` регіону та будь-який елемент каркаса сторінки цю умову не проходять.

🧱 **Критерій належності шару — і він НЕСУЧИЙ, бо без нього шар за півроку стане повільною копією `spec/requests/`.** Браузерний приклад коштує на два порядки дорожче (Chrome + Postgres + Redis на кожен прогін), тож правило одне:

> **приклад належить сюди лише тоді, коли нижче він неможливий У ПРИНЦИПІ.**

| Шар | Доводить | Йде повз |
|---|---|---|
| компонентна | розмітку, токени, `aria` | контролер **і** layout |
| request | статус, `media_type`, вміст тіла, тенантність | **браузер** |
| **feature** | **виконання НАШОГО JS · поведінку Turbo (морф · форм-контракт · візити) · те, що людина справді побачила** | — |

🔴 Це **продовження вже наявної сходинки, а не нове правило**: §B.2 #11 каже «policy-спека не заміняє request-спеку» (та йде повз контролер), #13 — «позитивний пін мусить жити в request-спеці» (компонентна йде повз layout). Тут той самий механізм на крок вище — і саме тому цілий клас дефектів «**відповідь правильна, а користувач її не бачить**» для нижніх шарів невидимий за побудовою: 42 німі `flash` і 11 Turbo-відповідей, проковтнутих через `200` без редиректу, прожили пів року при повністю зеленому CI ([`00_07`](00_07_Action_Plan_Tracker) SEC.25). ⚠️ **Дзеркальна половина, без якої правило однобоке:** твердження, доказовне request-спекою, сюди **не дублюється** — інакше CI дорожчає без жодного нового доказу.

🧰 **Спільний хелпер шару — `spec/support/feature_helper.rb`** (та сама конвенція, що `PhlexComponentHelper`: авто-include через `file_path: %r{spec/features/}`, окремо підключати не треба). Несе `sign_in_as(user, password:)` — логін **через справжню форму**, бо підміна сесії обійшла б `establish_session` і той самий salt-стемп (`session[:ps]`, SEC.16), від якого залежить половина сценаріїв цього шару; хелпер сам чекає завершення візиту, тож приклад не повторює `have_current_path` як ритуал. Виміряні стелі шару живуть у шапці хелпера — там, де їх зустріне автор нового спека.

## B.2 Рекомендації для нових фіч

1. **Кожен новий Service/Worker** мусить потрапити під per-group tripwire (`Services` / `Workers` у `spec/spec_helper.rb`) — непокрита гілка червонить білд. ⛔ Тут доти стояло «ratio ≥ 1.5x»: ані чисельник, ані знаменник не були названі, і виконавця в дереві не існувало (перевірено 2026-08-22 по `scripts/`, `spec/quality/`, `.github/workflows/` — нуль). Правило, яке неможливо провалити, стояло позицією №1 і читалось як найважливіше.
2. **AASM state machines** ПОВИННІ тестувати всі transitions + invalid transitions.
3. **Web3 сервіси** ПОВИННІ тестувати: stub mode, strict mode, missing credentials, RPC errors.
4. **Phlex компоненти** — слідувати Частині A цього документа (min 8 examples).
5. **Firmware** — кожна нова функція потребує host-based test у `firmware/test/`.
6. **Solidity** — naming: `test_` (happy), `testRevert_` (error), `testFuzz_` (fuzz), `check_` (Halmos symbolic proof, `test/symbolic/`), `property_` (Medusa fuzz, `test/medusa/`). Пара `test_`⊥`testRevert_` **HARD-gated** з 2026-08-09 (`scripts/solidity_test_naming_check.rb`, TEST.14): тіло з `expectRevert` під іменем `test_*` → RED. 🔴 **`.gas-snapshot` рухає БУДЬ-ЯКА правка тіла тесту — не лише «навмисна зміна газу» й не лише переіменування** (виміряно TEST.14, 2026-08-09, на трьох осях поспіль). **(1)** Ретрофіт `vm.expectRevert()` → `abi.encodeWithSelector` зсунув **16 записів понад tolerance 3%, до +16%**: аргументи — це реальні виклики в тілі. **(2)** `address(0xN)` → `makeAddr` додає ≈+1250 газу, **але лише з IN-BODY сайтів** — ініціалізатори state-змінних біжать у конструкторі тест-контракту й у число снапшота не входять (16 із 26 сайтів були саме такі). **(3)** Переіменування — не лише про ключі: імʼя тесту є 4-байтовим селектором, тож воно зсуває порядок бінарного диспетчера й змінило газ **70 СУСІДНІХ** записів на ±1.5% понад власні 22 заміни ключів. **Два наслідки:** кожен коміт, що чіпає тіла тестів, несе **власний** regen (`forge snapshot --no-match-test "invariant_|testFuzz_"`), інакше money-path baseline червоний МІЖ комітами, а не лише наприкінці; і новий ключ **hard-fail'ить незалежно від tolerance** — у нього просто немає baseline, щоб бути толерантним. CI-аудит-шари: static (Slither + Aderyn) · symbolic (Halmos — доводить інваріант для ВСІХ входів) · property-fuzz (Foundry invariant + Medusa). Інструменти/roadmap → [`05_03`](05_03_Tokenomics_SCC_and_SFC).
7. **Per-group SimpleCov tripwire** — окрім глобального гейту, прогін падає, якщо **line- або branch**-покриття групи опускається нижче порога. ⛔ Груп **ШІСТЬ**, не пʼять: `Models` · `Controllers` · `Services` · `Workers` · `Views` · **`Blueprints`** — і остання оголошена БЕЗ per-group порога, тобто tripwire на неї не стоїть. Перелік бери з `spec/spec_helper.rb`, не звідси (поріг per-group = `floor(поточне покриття)` — найтісніший цілий % нижче факту; branch — тісніший сигнал за line). Глобальні та per-group пороги живуть **тільки** у `spec/spec_helper.rb` (їхній єдиний дім — точні числа тут не дублюються, [`00_06 §1`](00_06_SSOT_Documentation_Standard)). Мета — ловити випадкове видалення спек у hot path-ах. 10. **Мережеві loopback-зонди ловлять connection-Errno, не лише timeout** (TEST.6) — UDP-тест на «мертвий порт» (щойно закритий сокет) на Linux дістає ICMP port-unreachable: `IO.select` бачить сокет readable, а `recvfrom` спливає `Errno::ECONNREFUSED` замість тиші. macOS цей ICMP на **non-connected** UDP НЕ доставляє (30/30 silent) → зелено локально, seed-залежний flake **лише в Linux CI** (гонка «ICMP встиг/не встиг за `timeout`»). Зонд/клієнт має трактувати `ECONNREFUSED`/`ENETUNREACH`/`EHOSTUNREACH` як «шлях не відповів» (тиша → ретрай → чесний false), а не пробивати голий Errno (`CoapSmoke::UNREACHABLE`). Регресію пінити **host-independent** (стаб `recvfrom` → `ECONNREFUSED` після readable-`IO.select`), бо реальний ICMP платформозалежний і на dev не відтворюється.

Доказ, що конверсія щось купила, тут прямий: мутація формули деривації червонить сім прикладів із тридцяти дев'яти, тоді як на моці не зачепила б жодного. ⊕ Той самий рід із не-AR суб'єктом: `ChainAuditService::Result` — `Struct` рівно з п'яти полів, а мок дописував `id`/`ok?`, яких на ньому немає, і розв'язував `critical` із `delta`, хоча сервіс виводить перше з другого порівнянням із порогом. 🔴 **Дев'ята вісь, виміряна тим самим проходом — і вона НЕ шоста: там брехала ЗОНА, тут ЛАГ.** Пін на **форматоване похідне від часу** нестабільний без заморозки годинника: залишок, заданий як «2 дні 9 годин», доїжджає до рендера як `2d8h`, бо розряди рахуються цілим діленням, а мікросекунда, згаяна між побудовою фікстури й `Time.current` **усередині моделі**, зрізає цілий розряд. Бʼє по КОЖНІЙ круглій межі, не лише по добі, і на некруглих значеннях приклад зелений — тобто «працює» тут чистий збіг. **Рефлекс: щойно пін торкається форматованого інтервалу, став `freeze_time`** — інакше доказ належить не коду, а швидкості машини. ⚠️ Периметр тут різальний так само, як у шостої осі: у сусідній спеці тієї ж родини заморозку легко пропустити, і показує це лише прогін, не читання. 🔴 **ТРЕТЯ пастка часу того ж роду, виміряна 2026-08-11 ([`TEST.12`](00_07_Action_Plan_Tracker)) — і вона не ЗОНА (шоста вісь) і не ЛАГ (ця), а ДВІЙКОВЕ ПРЕДСТАВЛЕННЯ самої фікстури.** Дробова секунда, задана Float-ом, зрізає розряд ще ДО рендера: `Time.zone.local(2024, 6, 15, 10, 30, 45.123)` доїжджає як `45.122999999`, бо 0.123 не представиться в binary float, а `%L` **зрізає, не округлює** — тож пін на мілісекунди мовчки чекав би «122» замість «123». Лік — задавати мікросекунди **окремим (сьомим) аргументом**: `Time.zone.local(…, 45, 123_000)`. **Спільне з ЛАГ-пасткою — цілочисельне зрізання похідного розряду; відмінне й практично важливе — що ця детермінована й відтворювана, тобто читається не як флейк, а як «спека просто не та», і автор іде правити ПІН замість фікстури.** ⊕ Периметр ширший за `%L`: те саме бʼє по будь-якому форматі, що друкує дробову частину часу (`%N`, `strftime("%6N")`, `iso8601(3)`). 🔴 **ДЕСЯТА вісь, виміряна 2026-08-11 ([`TEST.12`](00_07_Action_Plan_Tracker)) — і об'єкт підміни тут НЕ наша модель, а ЗОВНІШНЯ ЗАЛЕЖНІСТЬ: фікстура дописує API гему.** `maintenance/form_spec` підміняв `Pagy.define_singleton_method(:new) { |**_kwargs| … }`, тоді як у Pagy 43.x базовий клас конструктора не має взагалі (`Pagy.new` кидає `ArgumentError`; чинна форма — `Pagy::Offset.new(count:, page:, limit:)`). Наслідок відрізняється від усіх дев'яти осей вище **родом шкоди**: попередні ховали НАШ недогляд, а ця зробила невидимим **провал міграції залежності** — мажорний перехід оновив один call-site із двох, і компонент валив 500 на кожному записі з фото, поки спека дописувала гему метод, якого той не має. 🔑 **Дискримінатор, який відрізняє безпечну підміну від цієї: чи йде вона через RSpec mock-API.** `allow(Gem).to receive(:x)` проходить `verify_partial_doubles` і червоніє, щойно метод зникає; `define_singleton_method` на класі гема — ні, і саме тому переживає бамп мовчки (те саме, чому `OpenStruct` сліпий за побудовою, лише на рівні залежності). **Рефлекс подвійний: (а) підміняючи щось із гема, роби це ЧЕРЕЗ mock-API; (б) шукаючи наслідки мажорного бампа, грепни не лише виклики в `app/`, а й `define_singleton_method`/`define_method` на класах гема у `spec/` — саме там ховається неоновлений call-site.** ⚠️ Друга половина, без якої фікс неповний: компонентна спека рендерить повз роутер, тож HTML-гілку сторінки редагування не відкривав ЖОДЕН приклад у дереві — клас закривається лише парою «конверсія фікстури + request-приклад на ВМІСТ». ⊕ **Та сама вісь має ближчий підвид — підміна API ВЛАСНОЇ моделі в `before`-блоці**, і вона підступніша розмахом: `define_method` на класі визначає метод ГЛОБАЛЬНО й переживає весь прогін, тобто годує й сусідні файли, а субсет-прогін цього не показує за побудовою. Виміряно на `contracts_controller_spec` (2026-08-11): пʼять таких гардів під прозою «methods not yet on the model / scopes that don't exist» — чотири інертні (методи давно існують), пʼятий дописував асоціацію, якої на моделі немає й яку не кличе ніхто. **Знімати такі гарди можна лише повною сюїтою, а не файлом**, і найдешевша ознака, що гард протух, — його власний `unless`: якщо умова вже хибна, гард нічого не робить, а проза поруч і далі стверджує протилежне.

    🔴 **Стеля ПРИЛАДУ, яким цю вісь міряють: греп по `db/structure.sql` СЛІПИЙ до `store_accessor`/`delegate`/`alias_attribute`/`attribute`, тож «такої колонки немає» з нього є заявою про інструмент, а не про модель** ([`TEST.12`](00_07_Action_Plan_Tracker)). Виміряно: `TreeChronicle::TextFormatter` читає `avg_z`/`max_temp`/`deviation_from_baseline`, серед колонок `ai_insights` їх немає — і це виглядало як живий інстанс «мок вигадує поля». Один рядок моделі зняв гіпотезу: `store_accessor :reasoning, :avg_z, :max_temp, …`, тобто читачі поверх JSONB. **Питай МОДЕЛЬ, не схему**; перевіряючи «поля не існує», грепни всі чотири форми оголошення плюс `def <name>`. ⊕ Дзеркало вже записаного «наявність класу не доводить значення»: тут навпаки — ВІДСУТНІСТЬ у схемі не доводить відсутності поля, і помилка йде в дорогий бік, у бік вигаданої роботи.

🔴 **ОДИНАДЦЯТА вісь — дзеркало п'ятої, і найтихіша з усіх, бо фікстура тут не вигадує НІЧОГО: кожне значення легальне, просто ДВА РІЗНІ поля дістали ОДНАКОВЕ** (виміряно 2026-08-11 на двох сайтах поспіль, [`TEST.12`](00_07_Action_Plan_Tracker)). На першому сайті `slug` і `geo_region` обидва були тим самим рядком — тож приклад «renders geo_region» лишався зеленим через `href`, який пінить СУСІДНІЙ приклад, і зняття гілки `geo_region` він не помітив би. На другому лічильник-колонка (counter_cache) і переданий `count:` (kwarg із запиту контролера) обидва були сімкою — тож підміна одного джерела на інше проходила зеленою, хоча в проді ці шляхи наповнюються НЕЗАЛЕЖНО й розходяться першими. ⚠️ Живих носіїв обох сайтів у дереві немає; вісь від того не зникає — вона про ФОРМУ фікстури, а не про ті два компоненти. **Відмінність від п'ятої осі: там пін не міг би пройти НІКОЛИ (фікстура вигадала рядок, якого розмітка не дає), тут він проходить чесно — просто не здатен сказати, З ЯКОГО джерела прийшло надруковане.** Рефлекс дешевий і механічний: **перш ніж пінити значення, грепни його по власній фікстурі — якщо той самий літерал стоїть у двох полях, пін доводить менше, ніж здається; розведи значення.** ⚠️ Особливо часто це трапляється там, де одне з полів — денормалізований лічильник або аліас: обидва «правильні», обидва про ту саму сутність, і саме тому автор фікстури природно ставить їм однакове число.

🔴 **ДВАНАДЦЯТА вісь — і вона єдина, що питає не про ПРАВДИВІСТЬ значень, а про ПОВНОТУ набору: фікстуру ліплять із того, що компонент ЧИТАЄ, а не з того, що контролер ПЕРЕДАЄ** (виміряно 2026-08-11, [`TEST.12`](00_07_Action_Plan_Tracker)). `reports/financial_summary_spec` оголошував хеш `data:` із ЧОТИРМА ключами, тоді як `reports#financial_summary` будує його з ПʼЯТЬМА. Пʼятий (`network_emission`) виявився не забутим полем, а **цілим блоком звіту**, який CSV, PDF і JSON того самого екшена друкують, а HTML-компонент не читає взагалі й не читав ніколи (`git log -S` по каталогу компонентів порожній) — тобто фікстура ховала не хибну поведінку, а **відсутню поверхню** ([`ARCH.90`](00_07_Action_Plan_Tracker)). **Відмінність від усіх одинадцяти осей вище несуча: там пін брехав про те, що відрендерилось; тут рендериться менше, ніж контракт передбачає, і жоден пін про це не питає, бо питання не з чим поставити.** Причина структурна, а не недбала: автор спеки будує фікстуру, читаючи компонент («які поля він бере?»), і саме тому набір фікстури є ДЗЕРКАЛОМ реалізації, а не контракту — розходження між ними невидиме за побудовою. **Рефлекс механічний: звір МНОЖИНУ ключів фікстури з множиною, яку будує контролер** — правило «бери значення з рядка контролера» (вісь (а)–(в) вище) стосується ЗНАЧЕНЬ і про повноту набору мовчить. ⊕ Узагальнення за межі тестів: щойно один екшен віддає кілька форматів (`respond_to` з `html`/`json`/`csv`/`pdf`), питай не «чи правильний HTML», а **«чи однаковий ЗМІСТ у всіх гілках — і хто платить за той, що не показує»**: тут `@data` будується ДО `respond_to`, тож кожен HTML-запит виконував subgraph-раундтрип і викидав результат.

🔴 **ТРИНАДЦЯТА вісь — і всі дванадцять детекторів сліпі до неї ЗА ПОБУДОВОЮ, бо вона не робить твердження про вміст узагалі** (adversarial-вимір 2026-08-12, [`TEST.12`](00_07_Action_Plan_Tracker)). Дванадцять осей вище питають «чи міг прод виробити ЦЕ значення?»; ця питає **«хто його виробив — той, хто виробляє його в проді?»**. Дві дзеркальні половини, обидві виміряні. **(а) Позичене ОЧІКУВАННЯ:** оракул береться з коду, який приклад і мав би стерегти — константа з `described_class`, рядок із нашого ж серіалізатора, або порівняння `f(a)` з `f(b)`; приклад стає тотожністю й не може впасти. Інстанс: три HKDF-info (`silken-aes-128-lora-key` · `-broadcast-key` · `silken-ed25519-iotex-v1`) не мали ЖОДНОГО літерального піна — оракул будувався як `info: described_class::IOTEX_HKDF_INFO`, тож перейменування константи лишало сюїту зеленою, а деривація віддавала ключ, якого не має жоден прошитий Soldier і не знає W3bstream: мовчазна відмова атестацій і закритий мінт-гейт. **(б) Фікстура оминає ВИРОБНИКА:** обʼєкт справжній, поля реальні й правильно типізовані, але зібраний шляхом, яким прод не ходить. Інстанс: галерея фото будувала справжній `Pagy::Offset` із рукописним `limit:`, тоді як контролер передавав застаріле `items:`, якого Pagy 43 не знає й на яке не кидає — сторінка на 6 фото віддавала 20. 🔴 **Найгостріше — це вісь, яку РЕМЕДІАЦІЯ попередніх дванадцяти не закриває, а породжує:** заміна мока на справжній обʼєкт цементує брехню виробника саме тому, що будує обʼєкт ПРАВИЛЬНО, і робить це у вже «полагодженому» файлі. Тобто лічильник `OpenStruct` іде вниз, а сайти цієї осі ростуть — **прогрес на попередніх осях не є доказом прогресу на цій**. **Рефлекс: питай не лише «чи правдиве це значення», а «звідки воно тут узялось» — і якщо відповідь «з того самого коду» або «з конструктора, якого продовий шлях не викликає», приклад доводить нуль.**

🔴 **ЧОТИРНАДЦЯТА вісь — і вона не про значення взагалі, а про те, чи фікстура ДОСЯГАЄ порога, навколо якого механізм визначений** (виміряно 2026-08-12, [`ARCH.94`](00_07_Action_Plan_Tracker)). Тринадцять осей вище питають, чи правдиве значення і хто його виробив; ця питає, **чи розрізняються в цьому наборі дві величини, які механізм трактує по-різному**. `spec/factories/wallets.rb` дає `balance { 5000.0 }` при порозі емісії 10 000, тож у КОЖНОМУ прикладі `locked_balance = 0`, а отже `balance ≡ available_balance`. Дефект грошового шляху — сайзинг мінту від gross-`balance` при гарді по net-`available_balance` — не міг упасти **ні до фіксу, ні після**: 8704 приклади зелені обабіч, включно з усіма прикладами спеки самого воркера й наскрізною інтеграційною спекою токеноміки. **Відмінність від «у наборі немає того, що механізм ВІДКИДАЄ» (BP 21) несуча: там фільтру бракує негативного члена, тут набір узагалі не доходить до величини, навколо якої механізм визначений — нижче порога дві різні величини ЗБІГАЮТЬСЯ, і жоден пін, хоч би який точний, не здатен їх розрізнити.** Тож лік не інший ассерт, а **фікстура, що поріг перетинає**: закрив це наскрізний `credit → mint → confirm → credit → mint`, де перший цикл лишає ненульовий лок, і другий приклад уперше в історії сюїти бачить `balance ≠ available_balance`. **Рефлекс: перелічи пороги, навколо яких визначений предмет — конверсії, пагінації, свіжості, межі партиції, — і спитай, чи бодай одна фікстура стоїть по ДРУГИЙ їх бік.** ⚠️ Найтихіша ознака цієї осі — саме зелень В ОБИДВА боки: якщо фікс не червонить жодного наявного прикладу, це не «фікс безпечний», а «сюїта до класу сліпа».

🔴 **Третя половина тієї самої осі, і вона заходить повз УСІ фікстурні детектори: ТИП підміняє не мок, а СТАБ** (виміряно 2026-08-12, [`ARCH.89`](00_07_Action_Plan_Tracker) сайт 3). `allow(Rails.cache).to receive(:fetch).and_return(1.5)` — легальний, доречний стаб, який прибирає з тесту дорогий розрахунок; але він віддає **Float**, тоді як справжній розрахунок повертає **BigDecimal** (`sap_flow` типу `decimal` додається до Float-акумулятора, і сума стає BigDecimal після першого ж доданка). Наслідок був живий: показник рендериться голим блоком, а Phlex тоді не вмів друкувати BigDecimal узагалі (корінь знято 2026-08-12 → [`04_04 §2`](04_04_Phlex_UI_and_Tailwind)), тож число зникало з екрана на будь-якій організації з телеметрією — а сюїта лишалась зеленою, бо стаб підставляв правильний на вигляд тип. **Відмінність від решти осей несуча: тут фікстура НЕ бреше про значення — вона взагалі не бере участі, бо тракт обрізано на межі кешу/сервісу. Тож греп по `OpenStruct`, конверсія на реальну модель і будь-який статичний прилад сліпі до цього ЗА ПОБУДОВОЮ.** **Рефлекс: щойно стаб повертає ЧИСЛО замість обчислення, спитай, якого воно типу в проді — і принаймні один приклад проведи повз стаб.**

15. 🔴 **Приклад, що не може ВПАСТИ, — це вимкнений детектор, і породжує його не недбалість, а метрика покриття** ([`TEST.10`](00_07_Action_Plan_Tracker), 2026-08-01…03). Форма-архетип — `expect(response.status).to be_in([ 200, 500 ])`: приклад зелений і коли шлях працює, і коли сервер падає. 🔴 **Походження, без якого правило не тримає:** усі екземпляри народились у комітах, чия мета названа в заголовку («Increase coverage to 96%»). Такий приклад **оптимальний** для поставленої метрики — ходить по коду (покриття росте) і не може впасти (CI зелений). А поріг покриття тримається HARD, тож прибрати вакуумний приклад не можна, не замінивши справжнім: **тиск, що створив дефект, став його бронею.** Тому це не стильова причіпка, а вісь, на якій метрика воює проти власної мети. 🔴 **І припис «`redirect_to(exact_path)` замість `have_http_status(:redirect)`» правильний лише НАПОЛОВИНУ — його дискримінувальна сила залежить від того, чи цілі гілок РІЗНІ** (UI.7, 2026-08-15, вимір на 11 сайтах). Де вони протилежні, адреса вирішує все: `passwords` (успіх → `login_path` ⊥ битий токен → `forgot_password_path`), `sessions` (вхід → дашборд ⊥ вихід → логін), `tree_families` (create → список ⊥ update → сторінка запису) — там пін на ціль перетворює пару прикладів на взаємні мутації. **Але де обидві гілки ведуть в ОДНЕ місце** (`alerts#resolve` і `firmwares#deploy` обидві редиректять у свій список), адреса не розрізняє нічого, і справжній дискримінатор — **ключ flash**; тоді пін мусить нести й НЕГАТИВНУ половину (`expect(flash[:success]).to be_blank`), інакше «успіх» і «вже зроблено» лишаються нерозрізненними навіть із бездоганно названою адресою. **Рефлекс: перш ніж пінити ціль, спитай, чи вона взагалі ДИСКРИМІНУЄ гілки цього екшена — якщо ні, шукай, що саме їх розводить, і пінь ТЕ, парою «є ⊥ немає».**
    **Три виміряні наслідки, кожен — реальний дефект, який вакуум приховав.** (а) Сторінка завантаження прошивки віддавала `500` і не рендерила форми взагалі — приклад був зелений САМЕ тому, що шлях падав. (б) Приклад із назвою «missing family» ніколи не доходив до валідації: `hardware_uid` у фікстурі був 11 символів проти `UID_HEX_FORMAT` на 24 hex, тож спрацьовував UID-guard, а хедж на ключі відповіді (`json["errors"] || json["error"]`) не давав побачити, ЯКА гілка відповіла — тобто гілка, яку назва обіцяла стерегти, не мала піна взагалі. (в) HTML-гілка rate-limit'а: `429` там недосяжний **за дизайном** (обробник віддає 429 лише JSON), а успішний сабміт **теж** редіректить — отже сам `302` не розрізняв «ліміт спрацював» і «не спрацював»; різнить їх ЦІЛЬ редіректу плюс флеш.
    🔴 **Друга форма класу, і форма-гейт сліпий до неї ЗА ПОБУДОВОЮ** ([`SEC.31`](00_07_Action_Plan_Tracker), 2026-08-04). `no_unfalsifiable_status_expectations_spec` анкерований на очікуванні СТАТУСУ — тож він не бачить прикладу, де очікуване значення цілком змістовне, а тавтологічним є **предикат**: перевірка «частково звільнений контролер зберігає CSRF-гард» питала `_process_action_callbacks.map(&:filter).include?(:verify_authenticity_token)`, тобто чи є колбек із таким ІМЕНЕМ, — а скоуплене зняття колбек не видаляє, лише підміняє умовним близнюком із тим самим символом. Отже для єдиного контролера, який ця перевірка стерегла, вона була істинною завжди, і жодна мутація її не вбивала. **Ознака, за якою це ловиться без гейта: перевірка стверджує ПРИСУТНІСТЬ чогось, тоді як дефект — це зміна ВЛАСТИВОСТІ того, що присутнє.** Рефлекс той самий, що в #11 (пінуй аргумент, не факт виклику), піднятий на рівень вище: питай не «чи існує гард», а «чи він діє на тій множині, яку називає речення поруч» — і мутуй КОЖЕН спосіб зламати властивість, а не той, який мав на думці.
    🔴 **Смок на HTML-сторінку («get → `:ok`, і більше нічого») — НЕ однорідний клас, і критерій розділу вимірний: чи несе сторінка ДАНІ З КОНТРОЛЕРА** (присуд 2026-08-12, [`TEST.12`](00_07_Action_Plan_Tracker)). Спершу вимір, бо «200 марний» доти було міркуванням: підміна `view_template` сторінки на порожнє тіло лишає **статус 200** і прибирає з розмітки геть усе змістовне — тобто смок справді переживає повний крах вмісту. Але наслідок із цього НЕ «переписати всі». Сторінка **статична** (форма входу, «забув пароль») проводки не має взагалі: там смок чесний, а вміст тримає компонентна спека, і чіпати його — робота без предмета. Сторінка, що несе дані з контролера (**предзаповнена форма**, показ запису, дашборд із числами), смоком не покрита в тій самій точці, у якій сліпа й компонентна спека — та рендерить повз маршрутизатор і повз викликача (#14), тож проводку не бачить НІХТО. Два виміряні інстанси другої групи: форма редагування без предзаповнення віддає чесні 200 і **стирає дані на сабміті**; форма скидання пароля без прокинутого в приховане поле токена виглядає справною і робить скидання мовчки неможливим. **Тож питай не «чи є в цього смоку вміст», а «чи є на цій сторінці бодай одне значення, що прийшло з контролера» — і пінуй саме його.**
    🔴 **Третя форма, і вона не потребує ані стаба, ані мока: асерція, ЗАХИЩЕНА умовою** ([OPS.33](00_07_Action_Plan_Tracker), 2026-08-25). `expect(trace&.txs_created_from).to be_present if trace` читається як обережність, а насправді вимикає перевірку рівно тоді, коли предмет відсутній — тобто в тому єдиному випадку, який мав би червоніти. Виміряно: `trace` там був `nil` завжди, і половина прикладу, названа в його ж заголовку («обидва шляхи створення»), не виконувалась жодного разу — стаб `update_all` не спрацьовував, бо вхід не доходив до біндингу. **Рефлекс: `if`/`&.` перед `expect` — це не захист від помилки, а вимкнення асерції; якщо предмет МОЖЕ бути відсутнім, то саме його присутність і треба стверджувати першою.**

    **Правило.** Тверджуй ОДИН статус + `media_type` + **вміст**; коли два коди дає ДВА РІЗНІ механізми — різни їх ціллю, флешем або тілом, бо статус там не дискримінує. Форму стереже `spec/quality/no_unfalsifiable_status_expectations_spec.rb` (множина статусів не сміє перетинати класи 2xx/3xx/4xx/5xx), і його **стеля названа в шапці**: хедж УСЕРЕДИНІ одного класу (`be_in([ 403, 429 ])`) невидимий за побудовою, бо це семантика, не форма.
    ⚠️ **Три пастки, куплені під час зняття класу.** (1) **Більшість класу НЕ грепається:** дефект — розходження між НАЗВОЮ прикладу й тим, що він тверджує, а самі матчери (`be_a(Numeric)`, `have_http_status(:ok)`, `not_to raise_error`, `expect(html).to be_present`) в іншому місці цілком доречні. Механічний шортліст дає лише кандидатів: «усі твердження прикладу — status-only / type-only / no-raise-only, А назва містить дієслово поведінки». Другий тель, який греп не бачить, — **двійникування**: два приклади у ПРОТИЛЕЖНИХ контекстах із побайтово однаковим твердженням. (2) **Не цитуй стару форму дослівно в коментарі** — літерал у прозі тримає файл грепо-позитивним назавжди, тобто засліплює рівно ту перевірку, якою клас себе й міряє; переказуй («множина {200, 500}»). (3) **Повідомлення валідації в HTML екрановані** (`can't` → `can&#39;t`), тож порівняння з сирим `full_messages` дає ХИБНИЙ негатив і виглядає як «блок помилок не рендериться» — звідси `CGI.escapeHTML` у твердженні.

16. 🔴 **Перш ніж полювати на flake — виключи БРУДНУ test-БД; вона вміє імітувати саме ПОРЯДКОВУ залежність, і це те, чого попередні два діагнози не знали** ([`TEST.8`](00_07_Action_Plan_Tracker), виміряно 2026-08-03). Транзакційні фікстури ізолюють приклади **один від одного** й нічого не кажуть про рядки, що лежали в БД **до** прогону: `bin/rails runner` у `RAILS_ENV=test` пише повз них, і навіть впавши на валідації лишає те, що встиг записати до падіння. **Вимір трьома плечима на одному коміті й харнесі:** чиста БД, сід 11111 → `0 failures`; та сама сюїта з **чотирма** залишковими рядками → **26 падінь у 13 файлах**; той самий бруд, сід 22222 → **25**, причому **сім падінь різняться**. 🔴 **Ключ — механізмів ДВА, і саме другий будує міст до хибного діагнозу:** (а) твердження на **глобальному, нескоупленому** ліку (`BlockchainTransaction.where(…).count == 1`, `Tree.count == 0`) падає завжди, від сіда не залежить; (б) **колізія FactoryBot-послідовності** (вона стартує з 1 у КОЖНОМУ процесі) валить той приклад, що першим витягне вже зайняте значення (`Crypto public address has already been taken`), а це вирішує **порядок** — тому файл лишається зеленим в ізоляції. Отже «різні сіди дають різне число падінь» доводить брудну БД **рівно так само добре**, як витік стану між прикладами, і саме нерозрізнення цих двох пояснень відправило два проходи діагностики не туди. **Носій — не правило, а гард**: `spec/rails_helper.rb` `before(:suite)` одним `EXISTS`-запитом падає з переліком непорожніх таблиць (правило «не забруднюй» уже двічі не спрацювало — воно існує лише там, де стоїть перевірка в момент дії, [`00_03` — TRL Matrix HIL and Beyond](00_03_TRL_Matrix_HIL_and_Beyond)). **Рецепт runner'а:** обгортай тіло в `ActiveRecord::Base.transaction { …; raise ActiveRecord::Rollback }`.
    🔴 **І ДРУГА причина того ж симптому, виміряна того ж дня, виявилась ГОЛОВНОЮ: два прогони сюїти одночасно.** Транзакційні фікстури ізолюють приклади всередині ОДНОГО процесу й нічого не знають про другий, а спільного мутабельного стану між прогонами рівно два — **Redis DB 1** (`Kredis…flushdb` у `rails_helper` біжить перед КОЖНИМ прикладом, тобто чужий прогін вимиває твої ключі посеред твого ж прикладу) і сама **Postgres**. Вимір на ЧИСТІЙ БД: соло — `0 failures`; два одночасні — **17 і 19 падінь**, механізми `seed_invalid_or_consumed` (зниклий сид) та `PG::TRDeadlockDetected` на вставці. 🔴 **Вирішальне — трійка найчастіших жертв збіглася з трійкою, названою в пункті, ДО ФАЙЛА** (`batch_payout_service` · `vote_recorder_service` · `unpack_telemetry_worker_attest`), тоді як брудна БД валила ширший і інший набір. Отже конкуренція пояснює вихідне спостереження краще: «в ізоляції зелено» — бо соло; «то 0, то 5, то 8» — бо число залежить від того, наскільки прогони перекрились **у часі**, а не від сіда. Носій — другий `before(:suite)`-гард (ключ-власник у тій самій Kredis-БД, з перевіркою живості pid, самозагойний на мертвому). 🔴 **І перша його версія була НЕПРАЦЮЮЧОЮ рівно тим способом, який цей документ і описує: механізм правильний, ПУСКАЧ мертвий.** Мітка ставилась один раз у `before(:suite)` — а `flushdb` сюїти біжить у ТІЙ САМІЙ DB 1 перед КОЖНИМ прикладом, тож ключ не переживав навіть першого, і вікно детекції стискалось із «увесь прогін» до збігу двох стартів у суб-секунду. **Мутація цього не показала, бо ставила ключ РУКОЮ** — вона довела гілку `raise` й нічого не сказала про те, чи мітка доживає до приходу конкурента. Спіймав adversarial-прохід; лік — переставляти мітку в тому ж `config.before` одразу після `flushdb` (заразом освіжає TTL і робить власність самовідновною, якщо чужий `after(:suite)` її зітре). **Загальне правило: гард, чий стан живе в ресурсі, який сюїта САМА чистить, треба перевіряти живим конкурентом, а не підкладеним станом** — інакше верифікується гілка, а не тригер. 🔴 **І ТРЕТІЙ носій — для процесу, який НЕ є сюїтою:** обидва гарди вище живуть у rspec-хуку, а фактичним забруднювачем у цьому дереві двічі був `bin/rails runner` — тож `config/environments/test.rb` попереджає (WARN, не raise — разова проба буває легітимною), коли ключ-власник живий. Це не косметика: проба, запущена під час прогону, не лише бруднить БД, а й **бреше у відповідь**, бо сюїта вимиває її Redis-ключі перед кожним своїм прикладом. Периметр класу — «другий ПРОЦЕС», а не «другий rspec», і гард, поставлений лише в rspec-хук, закриває його наполовину. ⚠️ Його стеля названа інлайн і вона не косметична: гард ключиться на Redis, а ділять прогони ДВА ресурси — ізоляція лише Redis приглушить гард, лишивши дедлоки; справжня паралельність = БД на процес (`parallel_tests`-модель), тобто інша робота.
    ⚠️ Стеля першого гарда теж названа в ньому: він бачить лише стан на **старті** прогону — ні рядка, записаного повз транзакцію всередині сюїти, ні бруду в Redis. Сиблінг #12: там правильний порядок дій («спершу CI-історія»), тут — правильний перший **підозрюваний**; і обидва механізми тут — приклад того, що «симптом варіює з сідом» задовольняють ДВІ різні гіпотези, тож сама варіація нічого не доводить.

17. 🔴 **Хедж УСЕРЕДИНІ одного класу статусів невидимий формі-гейту за побудовою — і ховає найгірше: що названий механізм не спрацьовує ніколи** ([`TEST.10`](00_07_Action_Plan_Tracker), 2026-08-03). Три приклади `rack_attack_spec` тверджували `be_in([ 403, 429 ])`, і два коди там означали **два різні механізми**. Вимір: неавтентифіковані `/telemetry/live`, `/api/v1/oracle_callbacks`, `/api/v1/auth/m2m_token` віддають **401/404**, тобто годують Fail2Ban, який банить на **15**-й відмові, тоді як ліміти самих правил — 60/60/15. Отже названий throttle не досягався **жодного разу**, і `telemetry/uid` можна було зняти з ініціалізатора, лишивши сюїту зеленою (доведено мутацією). **Властивість системи, а не тесту:** throttle доводиться поведінково на **невдалому** трафіку лише якщо його ліміт **нижчий** за поріг бану (`logins/ip` 10 < 15 — тому його приклад чесний) **або** якщо він дискримінує не по IP. Звідси й критерій членства в списку «заступлених» (дискримінатор = IP **І** ліміт ≥ порогу **І** шлях на невдалій спробі віддає 401/404) — його треба застосовувати до кожного НОВОГО правила, а не вгадувати. 🔴 **І сам цей критерій НЕПОВНИЙ — виміряно 2026-08-12 ([`SEC.32`](00_07_Action_Plan_Tracker)): він знає лише ОДНОГО заступника (Fail2Ban), а їх у дереві ДВА.** Другий — Rails-нативний `rate_limit` **у самому контролері**, і сайтів у дереві **ТРИ**, не два (`sessions` · `passwords` · **`mfa_challenges`**; перелік бери прогоном `grep -rn rate_limit app/controllers/`, бо цей рядок уже одного разу недорахував саме той механізм, про недорахування якого й попереджає). Він не має жодної з трьох ознак критерію: не IP-keyed у сенсі Rack::Attack, не має «порогу бану», і спрацьовує на УСПІШНОМУ шляху так само, як на невдалому. **Тож питання до нового throttle-правила ширше за критерій: «який ЩЕ механізм на цьому шляху може відповісти раніше» — і контролер є таким механізмом нарівні з middleware.** 🔴 **І окрема пастка в самому ІНСТРУМЕНТІ: мутація, що міняє ІМʼЯ правила, а не його дію, про покриття не доводить нічого.** Ім'я в Rack::Attack — префікс кеш-ключа, а не вмикач: перейменований throttle працює далі з тим самим лімітом, тож зелена сюїта під такою мутацією означає лише «назву звіряє реєстровий приклад». Вимикає ліміт, піднятий вище за кількість запитів у прикладі — і під ним `logins/ip` виявляється живим рівно на **одному** зі своїх трьох шляхів (`PATCH /reset_password`, де контролерний ліміт стоїть `only: :create`), а на двох POST-шляхах заступленим. **Мутуй ПОВЕДІНКУ, ніколи ідентифікатор.** ⚠️ Заразом там же: safelist Rack::Attack від Rails-ного ліміту НЕ звільняє (`matched_by?` віддає `true` для `127.0.0.1`, а шостий POST усе одно дістає 429), тож «безпечна» адреса безпечна лише на одному з двох шарів: adversarial-прохід показав, що список без `helium_sos/ip` суперечив власній назві «every». ✅ Дзеркальний залишок тієї ж перевірки закрито 2026-08-03: `account_security/ip` (10 < 15) **досяжний**, тож він дістав два поведінкові приклади — по одному на КОЖНЕ дієслово свого списку (`%w[PATCH DELETE]` живуть в одному рядку, тож приклад лише на PATCH лишався б зеленим, якби DELETE звідти випав). Обидва мутація-перевірені: зняти `DELETE` → червоніє рівно DELETE-приклад, підняти ліміт → обидва. **Форма ліку — розчепити механізми їхніми ВЛАСНИМИ дискримінаторами:** для `telemetry/uid` це розгін IP при сталому `X-Gateway-UID` (кожна адреса набирає одну відмову, лічильник правила добирає свої 60) — і той самий приклад заразом стає піном на сам дискримінатор. 🔴 **А там, де правило недосяжне за побудовою, проза-пояснення мусить бути ФАЛЬСИФІКОВНОЮ:** «його заступає Fail2Ban» — це твердження про механізм, тож поруч стоїть приклад-інваріант, що падає, щойно ліміт опускається під поріг бану; без нього хтось знизить ліміт, пояснення стане хибним, і не почервоніє нічого. Дзеркало правила #15: там статус не дискримінує **гілку**, тут — **механізм**. ⚠️ І окремо про облік цього класу: рахуй його `ruby scripts/spec_claim_audit.rb --all` (advisory, on-demand), а не грепом — греп зараховує коментарі, що цитують стару форму, і саме через це обсяг класу тричі поспіль виміряли хибно.

18. 🔴 **Фабрична послідовність — це унікальність у межах ПРОЦЕСУ, і ніколи між процесами** ([`TEST.11`](00_07_Action_Plan_Tracker), 2026-08-03). `sequence(:did, 900_000)` стартує з тієї самої позиції в кожному новому процесі, тож два писачі в одну БД видають **побайтово однакові** значення на unique-колонках. Виміряно прямо (`attributes_for` × 2 процеси, без БД): до фіксу **20 із 20** значень збігались на всіх семи полях, після — **0 із 20**. Форма ліку — **sequence + випадковий суфікс**: лічильник лишається гарантією всередині процесу (чистий random дає birthday-колізії на тисячах записів), випадкова частина розводить процеси. ⚠️ Формат несучий і перевіряється валідацією, а не смаком: `did`/`uid` — рівно 8 hex у ВЕРХНЬОМУ регістрі (`DID_FORMAT`/`UID_FORMAT`), а Ethereum-адреса — 40 hex в ОДНОМУ регістрі, бо `EthAddressValidatable` пропускає всю-однорегістрову як unchecksummed, але **мішаний** регістр звіряє з EIP-55 — тобто випадковий `upcase` тут завалив би фабричний дефолт майже завжди. 🔴 **Чесна межа, без якої правило перебільшує власну користь:** у повній конкурентній сюїті це **не зменшує падінь** — виміряно два одночасні прогони до і після, 2 проти 2, і жодного `has already been taken` у жодному. Причина: транзакційні фікстури відкочують вставку раніше, ніж другий процес встигає зіткнутись, тож колізія послідовності реально стріляє лише по **закомічених** рядках (класика — `bin/rails runner` у `RAILS_ENV=test`, який пише повз фікстури). Отже це hardening класу за побудовою, а не лік живого болю — і саме так його треба цитувати, бо «падіння впали з 17-19» стосувалося зовсім іншої осі (спільний Redis, #16).

19. 🔴 **Спека, що пінить рядок про ДОСТАВКУ, цементує самосвідчення — пінь СТАН КАНАЛУ** ([`ARCH.78`](00_07_Action_Plan_Tracker), 2026-08-04). Клас ширший за тести й має дім поза каноном (памʼять, «self-attestation»): артефакт стверджує результат, якого не перевіряв, бо слово укладене в момент **спроби**, а не **підтвердження**. Тестовий бік хвороби виглядає так: спека вимагала від воркера лог-рядка з дієсловом доставки, тоді як транспорт поруч був **закоментований**, — тобто вона могла впасти лише якщо прибрати брехню, і зеленіла рівно тому, що брехня на місці. Сусідній приклад того ж файлу пінив ТИШУ на невідомий канал («does nothing») як бажану поведінку, цементуючи відсутність `else`-гілки як контракт. **Правило.** Доки транспорт не задротований, приклад стверджує **стан каналу** («не сконфігуровано → НЕ надіслано»), а не результат; на невідомий канал вимагає ГУЧНОЇ гілки, бо тиша тут невідрізненна від доставки. **Дзеркало на боці продакшену** — `spec/quality/no_self_attesting_logs_spec.rb`: ловить пару «закоментований виклик транспорту + журнальний рядок із дієсловом-результатом у межах ±3 рядків» по `app/**`, mutation-verified. 🔒 Стеля названа в його шапці й не косметична: форма-**агрегатор** (підсумковий рядок, що звітує про успіх, не спитавши жодного з підлеглих каналів) і **статус у БД** замість журналу ([`FW.63`](00_07_Action_Plan_Tracker) — стан просувається при побудові відповіді, не при її отриманні) для нього невидимі за побудовою й потребують власних детекторів. ⚠️ Форму дефекту тут переказано, а не процитовано: літерал у прозі отруїв би ручний лічильник класу (пастка 2 правила #15).

20. 🔴 **Зонд «фолбек-гілки» на РЕАЛЬНОМУ записі здатен відрендерити звичайний стан — і тоді гейт на КЛАС стає тавтологією, яка звинувачує невинного** ([`UI.4`](00_07_Action_Plan_Tracker), 2026-08-06). На моці дістати його тривіально (будь-яке невалідне значення), на реальному незбереженому записі — ні: enum кидає `ArgumentError` на неіснуючому значенні, а `Model.new(status: nil)` **не дає `nil`**, бо AASM ставить `initial: true` просто в конструкторі. Тож пін `include(адреса)` лишається зеленим при повністю знятому фолбеку — і показала це лише мутація, що ПРОЙШЛА. **Правило: щойно пін стосується ПОХІДНОГО значення, спитай, чи не друкує те саме значення сусідній вузол — і цілься у вузол разом із його класом, а не в документ.** ⊕ Клас вужчий, ніж здається, і периметр варто знати: він вимагає, щоб похідне значення могло ДОСЛІВНО збігтись із сусіднім, тобто живе майже виключно у ФОЛБЕКАХ, не у формулах (свіп дерева: рівно один такий сайт; піни `trees/index` на fail-open і `dashboard/map_node` на `data-status="removed"` уже цілять у вузол). ⚠️ І детектор фолбеку не бери ЛІТЕРАЛОМ: у рядку таблиці той самий клас може носити сусідня комірка (`text-gray-600` — і статус, і хеш), тож пін був би вакуумним — витягуй увесь клас статус-вузла з рендеру. Сиблінг BP #14 із дзеркальним знаком: там фікстура оголошує світ, у якому дефект **неможливий**, тут — світ, у якому він **уявний**. 🔴 **Третя форма того самого, і в ній фолбек НЕДІАГНОСТОВНИЙ у принципі — виміряно 2026-08-11 на `Trees::Chronicle`:** дефолтна гілка `case severity` віддає ту саму зелень, що й ЖИВИЙ `:stable` (три продюсери — `homeostasis`/`recovery`), а сама `severity` ніде не друкується. Отже жоден пін не розрізняє «фолбек спрацював» від «нормальна подія відрендерилась» — не через слабкість піна, а тому, що **розрізняльної ознаки в розмітці немає**. Це не гіпотеза: у тому ж сервісі живе `ALERT_SEVERITY_TO_CHRONICLE` саме тому, що чужі `:medium`/`:low` колись падали в цю зелень і читались як «усе гаразд». **Тож перш ніж писати пін на фолбек, спитай не «який клас він дає», а «чи існує в розмітці бодай одна ознака, якої живий стан НЕ має»** — якщо ні, пін неможливий, і чесний хід це або зробити фолбек помітним (рішення ВІЗУАЛЬНЕ, тобто не тестове), або записати неможливість там, де її прочитають.

Обидва приклади зелені роками, обидва з живим Prosopite. **Тобто дефект тут не в прозі, а у ФОРМІ носія: канон-рядок не спрацьовує в момент, коли хтось пише спискову спеку, а порожня колекція не залишає сліду ні в статусі, ні в покритті.** Доведено третьою мутацією: дефект повернуто НА МІСЦЕ й фікстуру звужено до одного дерева → **11 прикладів, 0 падінь**. Тож носієм мусить бути ЛІХТАР У САМОМУ ПРИКЛАДІ — пін, що кожен із ≥2 записів доїхав у тіло відповіді, — бо лише він робить розмір фікстури несучим і червоніє, коли її звузять. Дім класу — `spec/requests/collection_pages_query_hygiene_spec.rb`: усі колекційні сторінки контуру, кожна з ≥2 записами й ліхтарем; Prosopite судить сам (його межа — дискримінує РІЗНОМАНІТТЯ бінд-значень, тож два рядки зі спільним батьком дають ідентичні SELECT і мовчання). ⚠️ **Ліхтар пиши по тому, що сторінка СПРАВДІ друкує**, не по атрибуту запису: сітка виводить `did.last(6)`, тож пін на повний `did` падає на здоровому коді й читається як хибний дефект. ⚠️ Заразом виміряно причину того N+1, і вона узагальнюється: `.count` і `sum(:колонка)` шлють SQL **навіть по вже завантаженій через `includes` асоціації**, тож дбайливий preload поруч із ними лише додає запит; `.size` і блокова `sum` беруть завантажений масив.

    🔴 **Наслідок для ВИМІРУ класу, куплений другим проходом (2026-08-12): будь-яке число, здобуте парсером, є ПІДЛОГОЮ, а не переліком.** Інвентар цього класу знімають статично — «єдине твердження прикладу є статусом» — і саме тому він недорахує систематично: приклад із чесним на вигляд піном на вміст безсилий рівно так само, якщо у фікстурі немає того, що механізм мусить відкинути. Виміряно на одному файлі: із чотирьох зіпсованих фільтрів парсер бачив два, а `types.uniq == ["inspection"]` тримався БЕЗ фільтра, бо єдиний свій запис і був інспекцією. **Тобто форма ТВЕРДЖЕННЯ не вирішує — вирішує склад ФІКСТУРИ, а його статичний прилад не бачить за побудовою.** ⚠️ Обсяг класу знімається лише `ruby scripts/spec_claim_audit.rb --all` (його шапка: «лічильник знімай лише звідси, не грепом»); там же записано, чому HARD-гейт на цю вісь неможливий — матчери доречні, дефект семантичний, — і чому корпусний advisory-звіт відхилено виміром. **Тож лік тут — політика, а не кампанія: переписуй приклад тоді, коли в тому ж файлі шипиться контракт відповіді.**

    🔴 **Третя форма, відмінна від обох пасток вище: приклад наведений НЕ НА ТОЙ КОД — і тоді ні пін, ні фікстура ні до чого.** `describe "signed_in? helper"` робив HTTP-запит і читав статус, тоді як рішення про 401 ухвалює `authenticate_user!`, який цього хелпера не кличе ЖОДНОГО разу: повністю інвертований `signed_in?` лишав би обидва приклади зеленими. Той самий рід у throttle-спеці — «uses X-Gateway-UID as discriminator» робив 11 НЕавтентифікованих запитів, кожен 401, тож `not_to eq(429)` істинне незалежно від дискримінатора, а справжній диференціал на одній IP недосяжний за побудовою (401 годує Fail2Ban, і бан настає раніше за throttle-ліміт). **Рефлекс: перш ніж підсилювати пін, спитай, чи ВЗАГАЛІ виконується механізм, названий у заголовку — і якщо шлях до нього перекритий іншим механізмом, пінь предмет прямо** (виклик хелпера з застабленим `current_user`; блок-дискримінатор правила замість його тіні у статусі). ⊕ Сиблінг-детектор: два приклади з ПОБАЙТОВО однаковими тілами під різними назвами — це одне слабке тіло за двох, і жодна з двох обіцянок не перевірена.

    🔴 **Четверта форма, і вона єдина, чиє мовчання СТРУКТУРНЕ, а не випадкове: глобальний стаб у `before` = заява, що цієї осі не пінить ніхто** ([`ARCH.84`](00_07_Action_Plan_Tracker), 2026-08-15). `allow_any_instance_of(Tree).to receive(:broadcast_map_update)` стоїть у голові обох спек Дерева цілком правильно — інакше кожен `create(:tree)` штовхав би в Turbo, — але побічний ефект, заглушений на рівні файлу, стає **непінабельним у цьому файлі за побудовою**; не «забутий пін», а відсутність місця, де він міг би стояти. Саме тому броадкаст мапи не стріляв на зміну стресу ЖОДНОГО разу і жодна з 83 наявних прикладів цього не бачила. **Рефлекс: перш ніж повірити, що механізм покрито, грепни `before`-блок на його імʼя** — а носія будуй ШПИГУНОМ ПОВЕРХ того самого стабу (`receive(:x) { |o| seen << o.did }`), не зняттям глушника. ⚠️ І дзеркало-ліхтар тут обовʼязкове обабіч: без «на цю зміну НЕ стріляє» пін проходить на «броадкастимо все підряд» — тобто на поведінці, що вбиває той самий дашборд іншим кінцем.

    🔴 **Пʼята форма — не про пін, а про ДІАГНОСТИКУ: дві незалежні причини одного симптому МНОЖАТЬСЯ, тож правильний фікс однієї виглядає як спростування гіпотези.** Мертвий маркер тримали дві ноги одразу (множина тригерів ⊥ обхід колбеків `update_column`), і кожна поодинці лишає симптом недоторканим. Природний висновок «полагодив — не змінилось — отже причина не тут» веде рівно в протилежний бік. **Рефлекс: полічи ЛАНЦЮГ доставки цілком (умова → колбек → продюсер → стрім) і став пін на КОЖНУ ланку окремо** — спільний наскрізний приклад тут не діагностує, бо червонить однаково на будь-якій із ланок.

Питання-дискримінатор: **«якщо ця передумова тихо не спрацює, чи впаде хоч один приклад?»** — якщо ні, ти пінив поведінку системи БЕЗ передумови. ⊥ Це не дублікат `feature_helper#sign_in_as`: там браузерний шар (Capybara, `page.status_code`), тут request-шар; спільна лише ідея ліхтаря, і саме її бракувало другому. ⚠️ Оголошена стеля хелпера: акаунти з увімкненим MFA поза скоупом (там `create` редиректить на MFA-challenge — власний дім `spec/requests/api/v1/mfa_flow_spec.rb`), і ліхтар доводить, що сесію ВИДАНО, а не що запит авторизований під потрібну роль — це вже предмет самого прикладу.


31. 🔴 **Глушіння побічного ефекту, переписане від руки в кожному файлі, робить ПРИСУД про нього неможливим — і саме це, а не гігієна, є його ціною** ([TEST.16](00_07_Action_Plan_Tracker), 2026-08-23). `allow_any_instance_of` жив у **317 сайтах / 101 файлі**, і **57% allow-форми — п'ять одних і тих самих глушінь броадкасту** (`Tree#broadcast_map_update` · `Wallet#broadcast_balance_update` · три `EwsAlert`-и). Коп, що їх ловить, вимкнений із 2026-03-08 під коментарем «поступова міграція», якої ніхто не ніс: доки популяція така, ввімкнення дало б 317 червоних, тобто рішення було заблоковане САМИМ РОЗМІРОМ, а не сумнівом.
    ✅ **Носій — `spec/support/side_effect_silencer.rb`**, і три його властивості несучі. **(а) Гранулярність ПОМЕТОДНА, не по-класова:** `EwsAlert` має кілька різних ефектів, і файли глушать різні їх підмножини — ключ «весь EwsAlert» тихо додав би глушіння там, де сусідній приклад той самий ефект пінить. **(б) Конвертуються ЛИШЕ голі стаби:** сайт із хвостом (`.and_return`, `.and_raise`, блок, `.and_wrap_original`) не глушить, а ЗАДАЄ поведінку, і сховати його за іменем «silence» означало б збрехати про те, що робить рядок. ⚠️ Хвіст рахуй із урахуванням ПРОДОВЖЕННЯ: коли `.and_return` стоїть НАСТУПНИМ рядком, однорядковий греп читає сайт як голий — саме так один вимір нарахував удвічі більше конвертованого, ніж існує. **(в) ДВА методи за предметом** (`silence_broadcasts!` ⊥ `silence_side_effects!`, OPS.33 2026-08-24): реєстр виріс за межі броадкастів (LoRa-відправка, каскад по моделі), і єдине імʼя брехало б про половину ключів; перейменування ж єдиного методу коштувало б ~сотні call-site-ів. Тому перейменовано МОДУЛЬ, а методи розведено — промах ключем відповідає адресою сусіднього реєстру, тож ціна двох імен нульова для викликача. Результат заміру: **317 → 173 сайти, 101 → 51 файл**.
    ⚠️ **Найважливіше — те, що вимір СПРОСТУВАВ.** Пункт побоювався, що глобальний стаб робить вісь броадкасту непінабельною, тобто «дефект має 101 місце сховатись». Насправді вісь має власний дім і запінена якісно: `tree_spec` доводить, що броадкаст стріляє на потрібних тригерах і **НЕ стріляє** на сусідній колонці; `wallet_spec` захоплює аргументи; `maintenance_record_spec` тримає `have_received` з негативною половиною. Тож ці глушіння законні — вони мовчать про побічний ефект у файлах, що про інше. **Рефлекс: перш ніж лікувати «непінабельну вісь», знайди її ДІМ — питання не «скільки місць її глушать», а «чи є бодай одне, де вона є предметом».**
    🔑 **І в носія ДВІ половини, бо глушіння без зняття неповне** ([OPS.33](00_07_Action_Plan_Tracker), 2026-08-25). Приклад, який САМЕ цей ефект і пінить, мусить глушник свого файлу зняти — `restore_broadcasts!(:ключ)` за тим самим ключем. Доти зняття писалось від руки (`allow_any_instance_of(EwsAlert).to receive(:broadcast_alert_update).and_call_original`), тобто пара (клас, метод) дублювалась поза реєстром — а рукописна форма не має ЧИМ сказати, що глушника немає: чотири такі рядки знімали `schedule_satellite_verification!` у файлі, який глушить лише броадкасти, тож не робили нічого й читались як гарантія. Ключ червонить це одразу. ⚠️ Сіблінга `restore_side_effects!` немає свідомо — жоден приклад ще не знімав глушник не-броадкастового ефекту, і заводити його наперед означало б абстракцію без викликача.

32. 🔴 **Ритуал, чия ПРАВИЛЬНА форма неочевидна, скопійований у 2+ файли без спільного дому, дає копію, яка при помилці лишається ЗЕЛЕНОЮ — а не червоніє** ([TEST.16](00_07_Action_Plan_Tracker), 2026-08-23). Це вужчий клас, ніж «дублювання моків між файлами — ОК» (правило 27 вище): там копія або працює, або падає; тут вона мовчки виробляє байти, яких пристрій не шле. Інстанс — фікстура конверта Королеви (`[IV:16][AES-256-CBC ct]`): хибне вирівнювання **не міняє `bytesize % 16`**, тож residue-дискримінатор QATT його не бачить, а споживач в обох файлах був заглушений. Дім тепер один — `spec/support/telemetry_chunk_helper.rb`, і його шапка вже документувала ТОЙ САМИЙ діагноз про три копії, що розійшлись.
    🔑 **Лік — не переїзд, а ЛІХТАР: без нього клас лишається німим за побудовою.** Додано пін на ДОВЖИНУ конверта (ct == zero-padded plaintext), і мутація «прибрати `padding = 0`» червонить рівно його. **Рефлекс перед виносом будь-якого ритуалу в спільний дім: спитай не «чи однакові копії», а „що САМЕ почервоніє, якщо дім віддасть неправильне" — якщо відповідь «нічого», спершу пиши ліхтар, і лише потім переїзд.**

33. 🔴 **Доданий `allow(X).to receive(:m)` ПЕРЕКРИВАЄ наявний стаб і повертає `nil` — message-expectation так НЕ робить, він падає на реалізацію того, що вже стоїть** ([OPS.33](00_07_Action_Plan_Tracker), 2026-08-24). Тому переклад `expect(...).to receive` → spy-форми не є механічним: за одну кампанію (354 сайти) ця пастка спрацювала **32 рази**, двічі на money-path — мінт-сервіс, де `before` стабить клієнта через `receive_messages`, і `BurnCarbonTokensWorker`, де занілився б `.and_return(:slashed)`, лишивши пін зеленим про ІНШИЙ шлях коду. ⛔ **Зелена сюїта тут не свідок за побудовою** — вона мовчить, доки той `nil` десь не розіменують; ловиться лише інвентарем наявних стабів ПЕРЕД кожним доданим `allow`.
    ✅ **Конвенція конверсії** (коп `RSpec/MessageSpies` увімкнено, `EnforcedStyle: have_received`, дерево на нулі): лічильники (`.once/.twice/.exactly/.ordered`) переїжджають на `have_received`, а реалізація (`.and_return/.and_raise/.and_call_original`) лишається на `allow`; **обмежений `expect` вимагає дзеркалити `.with(...)` на `allow`** — без цього два виклики, з яких матчить один, тихо перетворюють RED на GREEN; **ПОЗИЦІЯ `allow` несуча** там, де вікно запису має значення (memoization-warm-up, відкритий circuit) — тримати її там, де стояв `expect`. Строгість при цьому не міняється: `have_received(:m)` дефолтиться на «рівно раз», як і message-expectation. Єдиний виняток — стаб, що вже стояв у `before`: вікно відкривається РАНІШЕ, тож негативна асерція стає трохи СУВОРІШОЮ, і це хибить у безпечний бік.
    🔬 **Клас ширший за конверсію: стаб на обʼєкті, який сервіс дістає САМ, не спостерігає нічого.** Два кредит-гарди телеметрії роками стояли вакуумними — сервіс тримає власний кеш `Tree.where(did:)` і кредитує гаманець СВОГО екземпляра, тож `allow(tree.wallet)` стабив обʼєкт, якого код не торкається, і `not_to have_received` було істинним тривіально. Доведено МУТАЦІЄЮ (зі знятими гардами приклади лишались зеленими), полагоджено спостереженням НАСЛІДКУ — баланс у БД через `reload`, стаб зник зовсім. Питай не «чи застабовано метод», а **«чи це ТОЙ САМИЙ екземпляр»**.
    📐 **Два методичні хвости, без яких кампанія міряє себе хибно:** лічи сайти **AST-ом, а не регексом** (`.*?` під `/m` перестрибує рядки — дало 421 замість 108), і **інваріант мусить НАЗИВАТИ свої виключення** — `expect_any_instance_of` коп свідомо не флагає, бо spy-форми для `any_instance` не існує, тож без явного виключення «впасти до нуля» недосяжне за побудовою, і наступний прохід спише це на власну помилку. ⊕ **Розбіжність номера рядка між твоїм лічильником і копом — це ТЕЛЛ провідної крапки-продовження** (сайт розбито на два рядки, і другий починається з крапки), а не похибка інструмента: регекс, писаний під один рядок, такий сайт або пропускає, або рахує двічі.

34. 🔴 **`any_instance_of` заявляє КЛАС, а не місце виклику — тож стаб на кореневому чи фреймворковому класі дотягується до коду, якого ти не писав, і найтихіше він стріляє на ЛІНИВОМУ завантаженні** ([OPS.33](00_07_Action_Plan_Tracker), 2026-08-25). Девʼять сайтів `allow_any_instance_of(Object).to receive(:rand).with(1..65535)` детермінізували CoAP message-id — і накривали КОЖЕН обʼєкт у процесі. Коли всередині прикладу вперше вантажився гем пошти, його тіло модуля кличе `rand` з іншим аргументом, обмежений стаб бачить неочікуваний виклик і валить приклад із ЧУЖОГО гема. ⚠️ Зелене трималось не на коректності, а на ПОРЯДКУ завантаження: файл цілком був зелений, а той самий файл під `-e` давав дві невдачі — тобто дефект видно лише тому, хто звузив прогін.
    ✅ **Рефлекс: став стаб на НАЙВУЖЧИЙ приймач, що дістає до місця виклику.** Тут це `allow(described_class)`, бо `rand` кличеться всередині `def self.put`, і заміна знімає обидві невдачі. **Дискримінатор перед тим, як писати `any_instance_of`: чи МОЖУ я назвати приймач?** Якщо екземпляр створює код під тестом і дістати його ніде (`ActiveRecord::Relation`, яку сервіс будує всередині; модель, яку створює фабрика воркера) — форма законна; якщо приймач відомий, вона просто ширша за потрібне, а ширина тут не косметична: чим вищий клас, тим більше чужого коду в радіусі.

## B.3 Скоуп покриття та гейт

**Що міряється.** Гейт покриває **продакшн-застосунок** (`app/`) + **увесь `lib/`**, окрім відфільтрованих `/lib/daemons/` і `/lib/tasks/` — профіль `rails` бере `{app,lib}/**/*.rb` з ДИСКА, не з `require`-графа. ⛔ Не читай як перелік конкретних движків: у скоупі 25 файлів (виміряно 2026-08-22), і рядок, що називав пʼять, змушував автора нового `lib/silken_net/`-файлу вважати себе поза гейтом. Пороги line/branch + per-group tripwire живуть **тільки** в `spec/spec_helper.rb` — точні числа сюди не копіюються (volatile, [`00_06 §1`](00_06_SSOT_Documentation_Standard)).

**Що відфільтровано — і чому.** `SimpleCov` фільтрує `/spec/`, `/config/`, `/db/`, `/vendor/`, `/firmware/`, `/lib/daemons/`, **`/lib/tasks/`** та **`/scripts/`**. Rake-таски — це ops/SSOT-оркестрація (file I/O + `puts`-звіти + `abort`-гейти), не running-застосунок; їхня **логіка винесена** в lib-движки зі 100% покриттям (`DocsLinter`, `DocsToc`, `DocsGraph` …), а самі таски ганяються в `docs.yml`/`ssot_guard.yml`, не в unit-сюїті. Рахувати їхні незаміряні `puts`-рядки = розводнити продакшн-гейт. Той самий принцип, що й фільтр `/firmware/` (host-mock'и): міряємо там, де факт «чи працює код» справді встановлюється (One-Home, [`00_06 §2`](00_06_SSOT_Documentation_Standard)). **`/scripts/`** (standalone CLI drift-гейти — `guard_registry_sync`/`workflow_gate_perimeter`/`docs_check`/`stan_audit`) фільтрується з тим самим rationale: pure-Ruby, ганяються `ruby scripts/*.rb` у `docs.yml`, якість-межа = власна spec+mutation, не app coverage-floor.

> ⚠️ **Стеля самого ратчета: підлога `floor(поточне)` карає не лише падіння покриття, а й ВИДАЛЕННЯ покритого коду** — але дві ці кари різняться на два порядки, і без магнітуди правило читається хибно. Арифметика однобічна: при `h/t = p < 1` зняття `k` покритих гілок дає `(h−k)/(t−k) < h/t`, тобто чистий refactor механічно опускає відсоток, не додавши жодної непокритої гілки. 🔴 **Але ціна за гілку різна:** лишена непокрита гілка коштує `1/t`, а знята покрита — лише `(1−p)/t`, тож **на `p ≈ 98%` видалення дешевше приблизно у `1/(1−p) ≈ 50` разів**. Практичний наслідок: зв'язує майже завжди **ДОДАВАННЯ** непокритої гілки (групи за дизайном сидять від нуля до кількох гілок над підлогою), а не прибирання — заява «це видалення зачервонить білд» потребує арифметики, а не інтуїції, бо в норму вкладаються десятки знятих гілок. Тому напруга з драбинкою «лінивого сеньйора» ([`CLAUDE.md §4`](../CLAUDE.md): видалення > додавання) і з §B.4 («мертву гілку прибирати, а не покривати») **реальна за знаком, але майже ніколи не зв'язує**; падіння групи після рефактора-видалення означає «перерахуй підлогу», а не «допиши тест». (Прецедент 2026-07-27 був ІНШИМ: `Workers` просів через три нові воркери зі своїми захисними гілками — тобто саме додавання. 🔴 А 2026-08-01 неперевірена інтуїція цього класу створила ФАЛЬШИВИЙ блокер: зняття мертвого `Firmwares::Row` записали як таке, що «заганяє CI під поріг», тоді як вимір дав зсув на тисячні частки відсотка — [`00_07`](00_07_Action_Plan_Tracker) TEST.9/UI.8.)

> ✅ **Друга стеля була НЕ властивістю ратчета, а дефектом покриття — і її знято в корені (2026-08-03).** Симптом: значення розходилось між платформами (CI `97.99%` проти локального `98.01%` при нулі падінь), тож локальне «вище порога» не було доказом про CI. **Корінь:** метрика включала гілки, **недосяжні на хості, що міряє** — платформний `case/when` у `lib/silken_net/load_test/coap_flood.rb` (netstat на darwin проти `/proc/net/snmp` на Linux), де кожна платформа лишала непокритою чужу половину. Лік — не вивести файл зі скоупу, а **запінити сам dispatch host-independent** (стаб `RbConfig::CONFIG["host_os"]` + джерела в обидві гілки), після чого обидві половини виконуються всюди й розбіжність зникає: непокритою лишається одна платформно-НЕЗАЛЕЖНА захисна гілка. 🔴 **Загальне правило, ширше за випадок: покриття як гейт вимагає, щоб кожна врахована гілка була досяжною на КОЖНІЙ платформі, де гейт біжить** — інакше метрика міряє хост, а не код. Вивести файл фільтром було б лікуванням симптому: фільтр за шляхом ширший за проблему й забрав би нагляд і з INF.23 honesty-детекторів, які §B.1.3 тримає в скоупі свідомо. **Діагностичні рефлекси лишаються чинними для будь-якого threshold-гейта:** червона `test`-джоба + «examples, 0 failures» → грепни `below the expected minimum` (це метрика, не тест); а покриття перед push'ем звіряй артефактом CI (`gh run download <run> -n simplecov-coverage`), не локальним числом. Присуд про сам поріг → [`00_07`](00_07_Action_Plan_Tracker) TEST.9.

> ✅ **ТРЕТЯ стеля того ж класу — і змінна тут не платформа, а НАБІР специ (виміряно 2026-08-11).** Симптом ідентичний другій: CI `97.99%` проти локального `98.01%` при нулі падінь. Але грепи на `host_os`/`RUBY_PLATFORM`/`Errno` по файлах із непокритими гілками дають **нуль**, тобто платформного dispatch'у там немає взагалі. Корінь: джоба, що МІРЯЄ поріг, ганяє сюїту з `--exclude-pattern "features/**/*_spec.rb"` — feature-специ живуть окремою джобою (див. «Зняття гейту» нижче), тож локальний «повний прогін» і CI-шній прогін-вимірювач це **різні множини прикладів**. Set-diff артефактів (`gh run download <run> -n simplecov-coverage` проти свіжого локального `coverage.json`) дав РІВНО одну розбіжність: гілка альфа-суфікса hex у `lib/silken_net/contrast.rb`, локально 85 хітів, у CI нуль — бо єдиним її споживачем був **браузерний** харнес `spec/support/contrast_audit.rb`. 🔴 **Тобто чиста арифметична функція мала «покриття» від інтеграційного тесту, а в наборі, яким міряють поріг, її не торкався жоден приклад.** Лік — власний юніт-приклад на ту гілку, не зсув порога й не розширення `--exclude-pattern`. **Правило узагальнюється поверх другої стелі: кожна врахована гілка мусить бути досяжною не лише на кожній ПЛАТФОРМІ, а й у кожному ПРОГОНІ, що міряє поріг** — інакше метрика міряє склад набору. **Рефлекс перед push'ем: звіряти покриття не «повним локальним прогоном», а відтвореною командою джоби-вимірювача** (`--exclude-pattern` включно). ⚠️ Пастка самої звірки: нормалізацію шляхів роби ЖАДІБНОЮ (`\A.*/silken_net/`) — non-greedy зріже CI-шлях `/home/runner/work/silken_net/silken_net/…` до першого входження, і кожен файл виглядатиме CI-only.
>
> 🧱 **Нульовий груповий запас безпечний ЛИШЕ доки покриття детерміноване щодо порядку тестів — і це властивість, яку треба ПЕРЕМІРЮВАТИ, а не припускати.** Групи за дизайном сидять від нуля до кількох гілок над підлогою (§B.2 #7), тож будь-який seed-залежний флоатер одразу перетворюється на червоний білд при нулі падінь — рівно та хибна тривога, яку ратчет має не давати. Перевірка коштує два fixed-seed прогони: `scripts/coverage_seed_diff.rb` (рецепт — у шапці скрипта; `.resultset.json` обов'язково чистити МІЖ прогонами). Станом на 2026-08-03 виміряно **нуль** флоатерів по обох осях, тому нульовий запас читається як «додав нетестовану гілку — гейт скаже», а не як крихкість. Прецедент, коли було інакше, і як його зняли, — §B.4 «Seed-флак покриття».

**Зняття гейту.** `FEATURE_TEST=1` та `COVERAGE=0` повністю вимикають гейт (feature-специ міряються окремим CI-job'ом; `docs.yml` ганяє лише лінтер-специ → загальне покриття ≈0, гейт хибно впав би). 🔴 **Але вимикають вони РІЗНЕ, і плутанина коштувала чотирьох украдених сесій [TEST.15]:** `FEATURE_TEST=1` знімає лише ПОРІГ (звіт збирається — окремий job його читає), а `COVERAGE=0` з 2026-08-13 не запускає SimpleCov ВЗАГАЛІ, тобто не пише у спільний `coverage/.resultset.json`. Носій — `scripts/docs_band.rb` звіряє відбиток файлу до і після своїх кроків і червоніє на регресії (сама по собі вона симптому не має: ламається НАСТУПНИЙ прогін сюїти).

> **Sweep = момент для security-лінтерів.** Gap-парсинг водить по рідко-виконуваних шляхах (guard / `&.` / regex) — там же часто сидять security-знахідки. Цей цикл закрив CodeQL-**ReDoS** у `lib/tracker/dashboard.rb` (вкладений `(?:[…]+\s*)*` з опційним роздільником → exponential backtracking), помічений саме під час coverage-sweep. Тож прогнати CodeQL / `bin/brakeman` на файлах, які чіпаєш у sweep, — дешева суміжна вигода.

## B.4 Пошук і тріаж прогалин

**Знайти** — після ПОВНОГО `bin/rspec` (цілісний `coverage/.resultset.json`; subset-прогон переписує його частково й тригерить per-group tripwire-артефакт — не реальний fail):

```ruby
require "json"
cov = JSON.parse(File.read("coverage/.resultset.json")).values.first["coverage"]
cov.filter_map { |p, d|
  next unless p =~ %r{/(app|lib)/}
  t = h = 0
  (d["branches"] || {}).each { |_, s| s.each { |_, n| t += 1; h += 1 if n.to_i > 0 } }
  t > h ? [ t - h, p.sub(%r{.*/(app|lib)/}, '\1/') ] : nil
}.sort_by { |r| -r[0] }.first(25).each { |u, f| printf "-%3d %s\n", u, f }
```

**Тріаж — НЕ покривати сліпо. Недосяжна гілка = мертвий код → спершу спитай: рефакторити геть чи лишити (і ЧОМУ).**

- **Реальна логіка** (status / empty-state / guard / error-path) → написати тест.
- **Справді мертве → РЕФАКТОРИТИ гілку** (прибрати, а не «лишати заради %»):
  - **Мертвий `&.`**: receiver short-circuit'нутий другим операндом `&&`, або літерал/константа → `&.`→`.`. ⚠️ обов'язковий `belongs_to` ≠ гарантований non-nil на READ — `dependent: :nullify` зануляє FK, і тоді `parent.child` читається nil (це захист нульованого FK, **НЕ** мертвий `&.`).
  - **Завжди-true модифікатор-`if`**, чию умову робить істинною інваріант методу (напр. `… if x.status_paid?` після `return unless triggered || paid` + AASM, де `triggered` йде ЛИШЕ в `paid`) → прибрати надлишковий `if` (якщо це не послаблює safety-guard нижче).
- **Не мертве, лише не-в-тесті:**
  - **Env-conditional** `defined?(Const)`, де `Const` — dev/test-only gem (`group :development, :test`): else — це **прод-шлях** (не мертвий). Покрити `hide_const`, АБО лишити + 1 рядок чому, якщо це ламає глобальну інтеграцію гему в харнесі (напр. `Prosopite` RSpec-хуки).
  - **Forward-looking** (ще-не-зареєстрована версія тощо) → чесно покрити `stub_const`.
- **Defensive, що ЛИШАЄМО — обов'язково задокументувати інлайн ЧОМУ:**
  - **Model-validation-dead**: гілка guard-ить стан, заборонений валідаціями самої моделі (`if tx.tx_hash.present?`-else, коли `:sent`-tx завжди має hash) → справжній guard — валідація; гілку лишити.
  - **Financial-safety-defensive**: недосяжний за поточним інваріантом, але захищає від МАЙБУТНЬОЇ зміни стейт-машини (напр. мінтинг лише для `:paid`) → прибирання послабило б захист; крихкий white-box-тест заради % суперечить §A.4, BP 16–17.
- **Баг біля непокритого коду** → виправити + тест, або занести в [`00_07`](00_07_Action_Plan_Tracker).

**Швидка матриця dead-vs-leave (довідник):**

| Гілка | Вердикт | Чому |
|-------|---------|------|
| always-true умова (інваріант / AASM) | **refactor** | прибрати надлишковий `if` — behavior-preserving |
| dead `&.` (receiver non-nil: `&&`-short-circuit / `dependent: :delete_all` / літерал) | **refactor** | `&.`→`.` |
| exhaustive `case` implicit-else (`i%3 ∈ {0,1,2}`) | **leave** | нема чого прибирати; явний `else` = новий dead-код |
| model-validation-dead (`if x.present?`-else, коли валідація гарантує present) | **leave** | справжній guard — валідація |
| financial-safety-defensive (dead за інваріантом, але захищає від зміни стейт-машини) | **leave + ЧОМУ** | прибирання послабить захист |
| env-conditional `defined?(dev/test-gem)` | **cover** (`hide_const`) / leave якщо ламає харнес | else = прод-шлях |
| nullify-FK `parent.child` (`dependent: :nullify`) | **cover / leave** | child реально nil після видалення батька |

> **Gotcha (parser vs verify).** Гап-парсер вище читає resultset лише після **повного** прогону. ✅ **[TEST.15, 2026-08-13] Субсет-verify його більше НЕ перезаписує:** `COVERAGE=0` тепер вимикає сам ЗАПИС (SimpleCov не стартує), а не лише поріг, тож `COVERAGE=0 bin/rspec <file>` лишає `coverage/.resultset.json` недоторканим. Доти часткове перезаписування давало сміття на повторному парсі, а поряд із повною сюїтою — колізію, що читається як «я зламав покриття» (`0 failures` + EXIT=2 + усі групи по 0.0 %). ⚠️ Субсет БЕЗ `COVERAGE=0` перезаписує як і раніше — це очікувано, бо там покриття свідомо збирають.

**Seed-флак покриття (точний hunt).** Коли line/branch «плавають» між прогонами (маржа гейту їх ховає), винуватець — код, що вправляється лише за певного ПОРЯДКУ тестів. Інструмент: `scripts/coverage_seed_diff.rb` — порівнює два `.resultset.json` від двох fixed-seed прогонів і друкує рядки/гілки, чия покритість різниться (рецепт зняття пари — у шапці скрипта; SimpleCov мержить у 10-хв вікні, тож `.resultset.json` обовʼязково чистити МІЖ прогонами). Тріаж знахідок: класичні корені — **незворотні `Module#prepend` у спеках** (анонімний модуль тіньовить продакшн-метод до кінця процесу — решта сюїти тестує підміну; worked example — §B.5), memoization first-test-wins, class-level стан, **ENV-витік без robust-restore** (`after { ENV.delete }` чистить стаблений Hash, якщо приклад робить `stub_const("ENV", …)` → реальна змінна тече; мітиговано глобальним ENV-snapshot, §B.2 #9). Прецедент (2026-06-12, TEST.1): єдиними флоатерами всієї сюїти були 2 рядки + 2 гілки `sessions_controller#current_session` — `around`-хук препендив підміну за хибною преміссою «методу нема»; видалення препенду зробило покриття детермінованим. View-стаби з `prepend` (asset/route-хелпери, ідемпотентні patched-once гарди) — легітимні: тіньовлять фреймворкові методи поза скоупом покриття.

**Останній викликач може жити у `spec/` — і тоді метод не мертвий, а `seam`.** Тріаж вище ключований на досяжність **гілки**; ця вісь інша — множина **викликачів** методу, і вона спрацьовує без coverage-приводу (перед будь-яким видаленням, не лише під час sweep'у). Механізм: SimpleCov фільтрує `/spec/` (§B.3), тож ані гап-парсер, ані `rubocop --only Lint/UselessMethodDefinition` спекових викликів не бачать **за побудовою** — метод виглядає без викликачів саме тому, що інструмент дивиться в один каталог. **Тож перед видаленням грепни `spec/` ОКРЕМО від `app/`/`lib/`.** Якщо єдиний уцілілий викликач — приклад, що інʼєктує через нього крах (`allow(obj).to receive(:m).and_raise(...)`), метод є **seam**: він дає тесту дістатись error-path, який інакше не відтворити (мережевий таймаут, впалий RPC, ENOSPC). Видалення забирає не код, а покриття цього error-path, і платить двічі: спека червоніє незрозумілим `does not implement`, а там, де `verify_partial_doubles` вимкнено, — **зеленіє на неіснуючому методі**, тобто мовчки перестає перевіряти будь-що.

## B.5 Worked triage examples

Конкретні рішення sweep'у — як читати «недосяжне» правильно (мапінг на матрицю §B.4):

- **`insurance #perform if status_paid?` → REFACTOR.** AASM має лише `triggered→paid`, тож після transaction-блоку статус завжди `:paid` → умова завжди-true; `tx ||=` сам short-circuit'ить → прибрання behavior-preserving (−1 гілка зі знаменника).
- **`minting_rollback log.tree&.wallet` → REFACTOR.** `Tree dependent: :delete_all` видаляє логи разом із деревом → orphaned-log не існує → `tree` non-nil → `&.` мертвий. **NB:** якби стояв `:nullify` — `&.` був би real (лишити). **Завжди перевіряй `dependent:` перед тим, як назвати `&.` мертвим.**
- **`attractor case i % 3` → LEAVE.** `i` — loop-індекс, `i % 3 ∈ {0,1,2}` завжди; implicit-else недосяжний математично. Додати явний `else` = ДОПИСАТИ dead-код заради лічильника.
- **`insurance tx.tx_hash.present?`-else → LEAVE.** `:sent`-tx завжди має hash (валідація моделі; `update!(status: :sent, tx_hash: nil)` падає — доведено тестом, що НЕ проходить). Справжній guard — валідація, не цей `if`.
- **`audit_log defined?(Prosopite)`-else → LEAVE некритим.** Prosopite — у `group :development, :test`, тож else — це прод-шлях (не мертвий); але `hide_const("Prosopite")` ламає глобальні Prosopite-RSpec-хуки (доведено фейлом `create`). Прод-only + не cleanly-testable → лишити з цим рядком-обґрунтуванням.
- **`sessions#current_session` seed-флак → REFACTOR спеки (видалити prepend).** Інтеграційна спека `around`-хуком препендила анонімний модуль із власним `current_session` за хибною преміссою «методу на контролері нема» (він є). `Module#prepend` незворотний → за сід-порядків, де ця спека бігла першою, продакшн-метод (2 рядки + 2 гілки) діставав нуль покриття, а РЕШТА сюїти тестувала підміну — інтегріті-дефект, не лише coverage-шум. Знайдено `scripts/coverage_seed_diff.rb` (§B.4); фікс = видалення хука — реальний метод робить те саме, обидві спеки зелені без нього. **Мораль: стаб «відсутнього» метода — спершу `method_defined?`-перевір премісу; prepend у спеках допустимий лише для фреймворкових хелперів поза скоупом покриття (asset/route view-стаби) і лише ідемпотентний.**
