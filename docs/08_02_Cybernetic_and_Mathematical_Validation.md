#### 🔶 Вектор 1: SPI/DMA Оптимізація — Модуль 02 (Hardware Capsule)

**Контекст: Проблема Енергетичного Блокування Процесора**

Анкери Silken Net функціонують в умовах екстремально низького енергоспоживання. Мікроконтролер STM32WLE5JC має постійно опитувати зовнішні мікросхеми: **BQ25570** (стан MPPT та `vcap`) і сенсорну периферію. Стандартний синхронний SPI-обмін **блокує CPU** на весь час транзакції — CPU простоює та марно витрачає енергію, не перебуваючи у STOP2 (2.1 мкА).

**Зв'язок з Публікаціями Ярмілка:**

Праця _«High-Speed SPI Bus Host Controller for Embedded Systems»_ (2022) та подальші дослідження апаратних SPI-експандерів (SPI-FSMC) з підтримкою **DMA (Direct Memory Access)** є прямою відповіддю на цю проблему.

**Завдання А: DMA-режим для SPI-шини STM32WLE5JC**

Впровадження DMA-режиму для SPI-шини дозволить:

1. MCU ініціює збір даних з BQ25570/сенсорів через SPI
2. MCU **негайно повертається в STOP2** (2.1 мкА) — не чекає завершення транзакції
3. DMA-контролер самостійно завантажує дані в RAM-буфер
4. Завершення DMA генерує переривання → MCU прокидається лише для обробки готових даних

```c
// Концептуальна схема (firmware/soldier/main.c — Phase 1 Enhancement):
// Поточна реалізація: блокуючий HAL_SPI_Transmit()
// Цільова реалізація після Ярмілка:
HAL_SPI_Receive_DMA(&hspi1, rx_buffer, BQ25570_REG_COUNT);
HAL_PWR_EnterSTOP2Mode(PWR_STOPENTRY_WFI);  // негайно спати
// ISR DMA_Complete: прокинутись, обробити rx_buffer
```

**Завдання Б: Запобігання Колізіям (HAL + RTOS парадигма)**

Ярмілко має досвід застосування HAL та методів RTOS для запобігання нештатним ситуаціям **множинного доступу до загальної SPI-шини**. У Silken Net на одній шині можуть конкурувати: опитування сенсорної периферії, читання сенсора температури, TinyML inference (DMA 16 кГц аудіо). Його методологія гарантує стабільність 2-пінового Pogo Pin Blind Mate інтерфейсу (→ `02_02`) при одночасному опитуванні кількох каналів без data corruption.

#### 🔶 Вектор 2: Lightweight Cryptography — Модуль 07 (Web3 Security)

**Контекст: Дилема «Безпека vs Енергія»**

Анкери Silken Net вживлені у дерева у відкритому лісі — вони фізично вразливі до перехоплення. Водночас традиційна «важка» криптографія (RSA-2048) вимагає сотень тисяч тактів процесора та занадто дорога для системи з мікроватним живленням від EBFC. Поточна реалізація:

- **Soldier → Queen (LoRa, post-ARCH.42 Variant B):** **AES-128-ECB** (`HAL_CRYP_Encrypt`, апаратний CRYP-модуль, `CRYP_KEYSIZE_128B`) — захищає тіло пакету, але **без IV** (режим ECB не забезпечує дифузію між блоками, BLOCKER-2 з 03_05). FW.2 target: **AES-128-CCM** (24B packet, 8-byte MIC, Frame Counter).
- **Queen → Rails (CoAP Batch):** AES-256-CBC + HRNG IV — батч зашифрований CBC (без змін після ARCH.42 — окремий CoAP key)
- **Відсутнє:** автентифікація повідомлень — **немає MAC/MIC** на LoRa (BLOCKER-3 з 03_05; закривається FW.2). Per-device provisioning ключів — **✅ Виправлено (FW.1, 2026-05-02)** через HKDF з різними info-strings (Tree LoRa AES-128 / Gateway CoAP AES-256).

**Зв'язок з Публікаціями Ярмілка:**

Стаття _«IoT Smart Implants: Information Security and the Implementation of Lightweight Cryptography»_ (2023, співавтори: І. Розломій, С. Науменко) є **прямим науковим фундаментом** для Silken Net. Концепція «Smart Implant» у цій роботі — це буквально те, чим є гіроїдний анкер у дереві.

**Завдання А: ECC (Curve25519) для Вирішення BLOCKER-1 — Key Exchange**

Історичний BLOCKER-1 (03_05): єдиний hardcoded AES ключ у Flash всіх вузлів — один зламаний вузол компрометує всю мережу. **✅ Закрито FW.1 (2026-05-02)** через per-device HKDF з `PROVISIONING_MASTER_KEY`. Майбутній upgrade — **ECDH (Curve25519)** для ephemeral key exchange (Perfect Forward Secrecy):

| Алгоритм | Рівень безпеки | Розмір публічного ключа | Такти CPU |
|----------|---------------|------------------------|-----------|
| RSA-2048 (key exchange) | 112 bit | 256 байт | ~1,000,000 |
| AES-256 (CoAP Queen↔Rails, current) | 256 bit (128 post-Grover) | 32 байт | ~50,000 |
| **AES-128** (LoRa Soldier↔Queen, post-ARCH.42) | **128 bit (64 post-Grover, компенсується ratchet)** | **16 байт** | **~40,000** (10 раундів vs 14) |
| **ECDH (Curve25519)** | **128 bit** | **32 байт** | **~10,000** |

ECDH не замінює AES для шифрування пакетів — він забезпечує безпечний **обмін унікальним per-device ключем** при провізіонуванні (`POST /api/v1/provisioning/register`). Після ECDH кожен вузол отримує унікальний `device_key = HKDF(master_key, device_uid)`.

> **Примітка:** При збереженні ECB-режиму для LoRa (BLOCKER-2 з 03_05) необхідно також додати per-packet nonce/counter для захисту від replay-атак. Завдання Ярмілка — обрати та обґрунтувати найбільш прийнятне рішення з урахуванням 21-байтового обмеження пакету.

**Завдання Б: MAC/MIC для LoRa-пакетів — Вирішення BLOCKER-3**

Поточний BLOCKER-3 (03_05): LoRa-пакет не містить жодного механізму перевірки цілісності або автентифікації джерела. Розробки Ярмілка щодо застосування **хеш-методів у криптографічному аналізі потоків** дають основу для додавання lightweight MAC:

```c
// Поточно: CRC-16 (2 байти, байти 19-20) — лише error detection, не автентифікація
// Цільово після Ярмілка: BLAKE2s або SipHash-2-4 (lightweight MAC — 4 байти)
//   — верифікація відправника + integrity для peaq DID pipeline
//   — замінює CRC-16 або розширює пакет до 23 байт (аналіз trade-off з Порубльовим)
uint8_t mac[4];
siphash24(payload, PAYLOAD_LEN, device_key, mac);  // device_key — унікальний (після BLOCKER-1 fix)
memcpy(packet + MAC_OFFSET, mac, 4);
```

Цей MAC верифікується Queen-шлюзом та Rails backend (MAC mismatch → дроп пакету → EwsAlert) перед передачею в peaq DID pipeline (Модуль 05_02).

> **Рекомендоване рішення (→ `03_05`, post-ARCH.42 Variant B):** **AES-128-CCM** для LoRa — апаратно підтримується STM32WLE5JC (`CRYP_AES_CCM` у HAL), узгоджено з ATECC608B Secure Element (AES-128 hardware constraint), надає одночасно confidentiality + MAC (MIC, 8 байт) + Frame Counter (захист від replay) в одній операції. Пакет розширюється до 24 байт (+ 4-байтний Frame Counter як CCM nonce + 8-байтний MIC). Альтернатива: AES-128-GCM (потребує порівняльного аналізу такти/RAM). Порівняння CCM vs GCM vs окремий BLAKE2s MAC — завдання Ярмілка (Підгрупа Б).

#### 🔶 Вектор 3: Edge AI та Стиснення — Модуль 06 (Observability / Telemetry)

**Контекст: Мінімізація LoRa TX — Головний Пріоритет**

LoRa-передача (+22 dBm ≈ 100 мВт) — найбільш енерговитратна операція. Кожна мілісекунда TX коштує енергії, накопиченої за хвилини зарядки іоністора від EBFC. Три інструменти Ярмілка атакують цю проблему з різних боків.

**Завдання А: Арифметичне Стиснення Payload (зменшення часу TX)**

Стаття _«Transforming Big Data: A Novel Arithmetic Compression Method Based on Symbol Frequency»_ (2023) пропонує **легкий арифметичний кодек**, придатний для мікроконтролерів. Застосування до 21-байтового пакету Soldier:

- Телеметричні дані (байти 4–15: `delta_t`, `vcap`, `temp`, `acoustic`, `lorenz_z`) мають **передбачувані розподіли** (здоровий ліс → більшість значень у вузькому діапазоні «норми»)
- Арифметичний кодек стискає ці поля, потенційно скорочуючи payload з 21 до ~13–15 байт
- Кожен зекономлений байт = менше символів LoRa = коротший час TX = менше енергії

```
Орієнтовна економія:
  Поточний пакет: 21 байт → SF=7, BW=125kHz → ~56 мс TX-time
  Після стиснення: ~14 байт → ~37 мс TX-time → економія ~34% енергії TX
```

**Завдання Б: Фільтрація Нечітких Дублікатів (suppress TX взагалі)**

Стаття _«General Methodology for Detecting Fuzzy Duplicates»_ (2024) адаптується для телеметрії Soldier. Якщо вектор сенсорних показників (зокрема `delta_t` — ключовий вхід рівняння Лоренца) **є «нечітким дублікатом»** попереднього вимірювання (змінився в межах статистичної похибки), Soldier **не активує LoRa-передавач** взагалі:

```c
// Phase 2.5 — перед Phase 4 TX (firmware/soldier/main.c):
// Ярмілко: загальна методологія fuzzy duplicate detection
// Порубльов: C-реалізація fuzzy_distance() для бінарних пакетів
if (!should_transmit(current_packet, last_packet, FUZZY_THRESHOLD)) {
    goto ENTER_STOP2;  // пропустити TX, зекономити ~100 мВт × TX_duration
}
```

> **Примітка:** Ярмілко надає **методологічну базу** (загальна методологія fuzzy duplicates), Порубльов — **математичну реалізацію** функції `fuzzy_distance()` (алгоритм нечіткого порівняння бінарних векторів). Обидва внески є взаємодоповнювальними.

**Завдання В: Dependability Firmware Framework (самовідновлення після brownout)**

Стаття _«Dependability of Embedded Systems in the Industrial Internet of Things»_ (2024) дає **фреймворк відмовостійкої прошивки**. Для Silken Net це критично: EBFC може тимчасово втратити вихідну напругу (хмарність, сезонне падіння метаболізму дерева) → brownout → STM32 може зависнути у невизначеному стані.

Фреймворк Ярмілка охоплює:

- **Watchdog стратегії:** правила відновлення стану після IWDG/WWDG reset без втрати накопиченої телеметрії
- **Brownout detection:** поріг на `vcap` (наприклад, < 1.8 В) → graceful shutdown → збереження стану в RTC Backup регістрах (DR0–DR10) до глибокого STOP2
- **State recovery:** після відновлення живлення — читання DR0–DR10, відновлення контексту (mesh\_relay\_flag, last\_wakeup\_timestamp, acoustic\_events) без перезавантаження firmware-стану

```c
// Концептуальна схема brownout handler (firmware/soldier/main.c):
void HAL_PWR_PVDCallback(void) {  // Power Voltage Detector IRQ
    RTC_BKP_WriteRegister(RTC, RTC_BKP_DR0, mesh_relay_flag);
    RTC_BKP_WriteRegister(RTC, RTC_BKP_DR1, (uint32_t)last_vcap);
    // ... зберегти критичний стан ...
    HAL_PWR_EnterSTOP2Mode(PWR_STOPENTRY_WFI);  // graceful shutdown
}
```

#### 🔷 Вектор 1: Обчислювальна Геометрія — Модуль 01\_01 (Коаксіальний Гіроїд)

**Контекст:**

Центральний апаратний елемент Gaia 2.0 — монолітний **120-мм коаксіальний Ti-6Al-4V анкер**, внутрішня структура якого є **TPMS-гіроїдом (Triply Periodic Minimal Surface)** із заданою пористістю **65%**. Ця пористість є наслідком закону Gibson-Ashby:

```
E_foam / E_solid ≈ C × (ρ_foam / ρ_solid)^n   [n≈2 для відкритих TPMS, C≈1.0 для гіроїда]

При 65% пористості: ρ_foam/ρ_solid = (1 − 0.65) = 0.35
  E ≈ 1.0 × (0.35)² × 110 ГПа = 0.1225 × 110 ≈ 13.5 ГПа
Діапазон деревини Pinus sylvestris: 9–16 ГПа ✓
```

Ізоеластичність 13–15 ГПа забезпечує нульовий ефект stress-shielding. CAD-модель генерується у nTop (ліцензія очікується — BLOCKER-1 в 01\_01). Після генерації STL/STEP файлу необхідна **алгоритмічна валідація** перед відправкою на DMLS-завод (Київ/Дніпро, партія 100 шт.).

**Завдання А: Алгоритмічна Валідація STL/STEP Моделей**

Розробка Python/C++ скриптів для математичної перевірки згенерованих 3D-моделей:

- Підтвердження пористості **65% ± допустима похибка** на кожному горизонтальному зрізі гіроїда
- Топологічна цілісність сітки (відсутність «дірок», самоперетинань, вироджених полігонів)
- Коректність симетрії TPMS (тричі-периодична структура не порушена при дискретизації)
- Відповідність діаметра капілярних каналів специфікації

```
Вхід:  STL/STEP файл від nTop або Rhino+Grasshopper
Вихід: Звіт валідації (porous_fraction per slice, mesh_integrity, symmetry_score)
Інструментарій: Python (numpy, trimesh, scipy) або C++ (CGAL)
```

**Завдання Б: Розрахунок Площі Поверхні для EBFC (зв'язок з Модулем 01\_03)**

EBFC Gen 2.0 генерує струм (dgrFAD-GDH на аноді, Laccase/ZIF-nanozyme на катоді) пропорційно до **ефективної площі контакту** металу з ксилемним соком. Гіроїд має дворівневу шорсткість:

1. **Макрорівень:** Самі пори гіроїда (~100–500 мкм)
2. **Мікрорівень:** Протравлені ями на Ti-6Al-4V (~1–10 мкм, HF/HNO₃ травлення — Модуль 01\_02)

Методи обчислювальної геометрії точно розраховують площу `S_eff` цієї складної дворівневої поверхні з STL-моделі. Результат передається хімікам (Школа Мінаєва, Модуль 08\_01) для розрахунку точної кількості MWCNT нанотрубок та осмієвого редокс-полімеру для іммобілізації ферментів.

```
I_max = j_surface × S_eff
  де j_surface — питома густина струму (мкА/см², від Школи Мінаєва)
      S_eff    — ефективна площа поверхні (см², обчислює Порубльов)
```

**Завдання В: Оптимізація Капілярних Каналів (Відсутність «Глухих Кутів»)**

Геометрія гіроїда як мінімальна поверхня теоретично забезпечує рівномірний капілярний транспорт рідини. Проте в реальній дискретизованій STL-сітці можуть виникати локальні «кишені» — зони де сік застоюється і викликає bio-fouling (гниття, що руйнує EBFC). #### 🔷 Вектор 2: Дискретна Математика, Надійність LoRa-Mesh та Перколяція — Модуль 07 / 03\_02

**Математичне Формулювання (Зв'язок з Дипломною Роботою)**

Дипломна робота Порубльова: _«Задача вибору варіантів при побудові систем мінімальної вартості з заданою нижньою межею надійності»_ — є **точним математичним формулюванням** задачі аналізу надійності LoRa flood relay мережі Silken Net:

| Термін дипломної роботи | Відповідник у Silken Net |
|------------------------|--------------------------|
| «Система мінімальної вартості» | TTL-flood relay з мінімальними енерговитратами на TX |
| «Вартість» | Мікровати на LoRa-TX (+22 dBm ≈ 100 мВт — найдорожча операція) |
| «Задана нижня межа надійності» | Мінімальна ймовірність доставки пакету до Queen-шлюзу |
| «Варіанти» | Конфігурації мережі (TTL, cluster density, redundancy factor) |

**Контекст: Як Реально Працює Mesh у Silken Net**

Поточна реалізація (`firmware/soldier/main.c`, Phase 4.5) — **TTL-based flood relay** з PANIC\_TTL=5 та DEFAULT_TTL=3. Кожен Soldier, отримавши чужий зашифрований пакет з TTL > 0, декрементує TTL та перепередає його всім сусідам у зоні досяжності (broadcasting). Anti-pingpong реалізовано через 8-слотовий seen-set у RTC Backup Domain (DR8..DR15). Це означає, що в мережі **немає вибору маршруту** — система виконує контрольований flooding.

Математична проблема, яка **залишається відкритою**: flood relay може втрачати пакети, якщо **всі** потенційні вузли-ретранслятори між Soldier та Queen в даний момент перебувають у STOP2 (vcap < 1.8 В). Необхідно математично встановити, при яких параметрах мережі (щільність вузлів, PANIC_TTL, DEFAULT_TTL) ймовірність доставки є прийнятною.

**Завдання А: Математична Модель Надійності Flood Relay**

```
G(V, E, P) — граф надійності мережі:

V = {v_i}  — множина анкерів-Солдатів та Queen-шлюзів
E = {e_ij} — ребра (LoRa-зв'язок між сусідами при RSSI ≥ поріг)
P(v_i, t)  — ймовірність того, що вузол v_i активний у момент t:

  P(v_i, t) = f(vcap_i(t), delta_t_i)
    де vcap_i та delta_t_i передаються у 21-байтовому пакеті від v_i

Ймовірність доставки пакету при flood relay з TTL=k:
  P_delivery(src → Queen, TTL=k) = 1 - ∏(1 - P_path_j)   [по всіх шляхах довжиною ≤ k]
```

**Завдання А2: Ланцюги Маркова для TTL-Flood Маршрутизації (Markov Chain Analysis)**

> **Контекст: Детермінований код у стохастичному середовищі.** Прошивка `firmware/soldier/main.c` є детермінованою, але ліс — стохастичне середовище (відмови вузлів через тварин, деградацію іоністора, погодні умови). Ланцюги Маркова є математичним мостом між ідеальним кодом і реальним хаосом.

```
Стани ланцюга Маркова для пакету (станів = TTL_MAX + 1 + 1):

  S_k = "пакет з TTL=k знаходиться у вузлі на відстані k стрибків від Queen"
  S_delivered = "пакет доставлено до Queen" (поглинаючий стан)
  S_lost      = "TTL=0, пакет відкинуто" (поглинаючий стан)

Матриця перехідних ймовірностей P (розмір: [TTL_MAX+2] × [TTL_MAX+2]):

  P(k → k-1)      = p_relay(k)    — вузол-ретранслятор активний та передає
  P(k → delivered) = p_queen(k)   — прямий сусід Queen активний
  P(k → lost)      = 1 - p_relay(k) - p_queen(k)  — всі сусіди у STOP2

де:
  p_relay(k) = 1 - ∏_{i ∈ neighbors(k)} (1 - P_alive(v_i))
  P_alive(v_i) = f(vcap_i, delta_t_i) — сигмоїдна функція або empirical CDF

Математичне очікування кількості стрибків:
  E[hops | delivered] = Σ_{k=1}^{TTL_MAX} k × P(S_k → S_delivered)

Ймовірність доставки (без поглинання у S_lost):
  P_delivery = P^n[S_0 → S_delivered]  (n-крокова перехідна ймовірність)
```

**Практичне Застосування:** Результат — оптимальне значення DEFAULT_TTL та PANIC_TTL у `firmware/soldier/main.c`, яке мінімізує `E[energy_per_packet]` (кількість TX-операцій) при обмеженні `P_delivery ≥ 0.99`. Надмірно великий TTL → шторм пакетів → спалення іоністорів. Надто малий → втрата телеметрії та зупинка Proof of Growth Pipeline.

**Завдання А3: Теорія Перколяції для Виживаності Мережі (Percolation Theory)**

> **Ключове питання для Web3-інвесторів та DAO:** При якому відсотку стохастичних відмов вузлів відбувається **фазовий перехід** і мережа розпадається на ізольовані кластери, що втрачають зв'язок з Queen?

```
Модель перколяції для топології лісу:

  Мережа = квадратна решітка (або random geometric graph) зі щільністю ρ вузлів/га
  Кожен вузол незалежно активний з ймовірністю p = P_alive (середнє по лісу)
  Кожне ребро (LoRa-зв'язок) існує, якщо обидва вузли активні

Критичний поріг перколяції p_c:
  - Для нескінченної квадратної решітки: p_c = 0.5927 (точне значення, Kesten 1980)
  - Для random geometric graph (реалістичніша лісова топологія):
      p_c залежить від ρ та r (LoRa-дальність ~150-200 м)
      p_c ≈ π × ρ × r² / ln(N)  (для sparse RGG)

Фазовий перехід:
  p > p_c: існує гігантська зв'язна компонента → мережа зберігає зв'язок з Queen
  p < p_c: мережа розпадається на ізольовані острівці → телеметрія втрачається

Критичний відсоток відмов:
  q_c = 1 - p_c  →  при q > q_c мережа колапсує
  (для лісу Silken Net: очікуване q_c ≈ 35-40% за початковими оцінками)
```

**Зв'язок з Parametric Insurance (Модуль 07\_01):** Поріг перколяції `q_c` є **базовим параметром** для смарт-контракту параметричного страхування: якщо відсоток вузлів у критичному стресі (vcap < 1.8V) перевищує `q_c`, автоматично спрацьовує страхова виплата — без людського арбітражу, trustless oracle. Це перетворює фізичну математику лісу на on-chain фінансовий інструмент.

**Deliverable А2+А3:** Математична модель відмовостійкості — **аудиторський документ для DAO токеноміки**: доводить Web3-інвесторам, що `PANIC_TTL=5` та `DEFAULT_TTL=3` є математично обґрунтованими, а страховий поріг q_c > 0.20 (поточний Slashing Protocol) науково валідований.

**Цільова публікація:** Спільна стаття Scopus Q1/Q2 (Порубльов + Онищенко + Архітектор): _«Оптимізація TTL-флудингу в енергонезалежних LPWAN мережах за допомогою ланцюгів Маркова та теорії перколяції»_.

**Завдання Б: Monte Carlo Симуляція Надійності Flood Relay**

На базі моделі — **кількісна оцінка надійності** існуючого flood relay та калібрування TTL-параметрів:

1. **Генерація лісових топологій:** випадкові графи G(V, E, P) з реалістичними параметрами (щільність дерев 300 шт/га, LoRa дальність 150–200 м hop)
2. **Monte Carlo симуляція:** для кожної топології запустити N=10,000 симуляцій flood relay при різних рівнях відмов (5%, 10%, 20%, 30% вузлів у STOP2)
3. **Калібрування:** визначити мінімальний DEFAULT_TTL та PANIC_TTL, що забезпечують P_delivery ≥ 0.99 при 20% відмов

**Завдання В: Аналіз Відмовостійкості та Рекомендації**

Математичне обґрунтування: при якій **мінімальній щільності** вузлів та TTL мережа гарантує доставку при 20–30% одночасних відмов. Поріг 20% узгоджується зі Slashing Protocol (автоматичне спалювання SCC, якщо >20% дерев кластеру у критичному стресі). Результат: підтвердження або перегляд поточних значень PANIC_TTL=5 і DEFAULT_TTL=3.

#### 🔷 Вектор 3: Нечіткий Пошук — Edge AI Дедуплікація Телеметрії (Модуль 03\_03)

**Контекст: LoRa TX — Найдорожча Операція**

LoRa-передача (+22 dBm) є найбільш енерговитратною операцією Soldier-вузла. Якщо показники метаболізму дерева **суттєво не змінилися** з моменту останньої передачі (знаходяться в межах «нечіткої похибки»), MCU **не вмикає LoRa-передавач** — зберігаючи критичний запас енергії в іоністорі.

**Зв'язок з Публікаціями Порубльова (2020, 2025)**

Його дослідження нечіткого пошуку та порівняння рядків (fuzzy string matching) адаптуються для порівняння векторів телеметрії:

```c
// Псевдокод для firmware/soldier/main.c (Phase 2.5 — перед Phase 4 TX):
// SENSOR_OFFSET = 4  (байти 0-3: заголовок + DID; сенсорні дані з байту 4)
// SENSOR_PAYLOAD_LEN = 12 (байти 4-15: delta_t, vcap, temp, acoustic, Lorenz)
// Повна розмітка пакету: firmware/soldier/main.c (21-байтовий формат)
bool should_transmit(uint8_t *new_pkt, uint8_t *last_pkt, uint8_t threshold) {
    uint8_t delta = fuzzy_distance(new_pkt + SENSOR_OFFSET,
                                   last_pkt + SENSOR_OFFSET,
                                   SENSOR_PAYLOAD_LEN);
    return delta > threshold; // TX лише якщо зміни суттєві
}
```

**Вимоги до алгоритму:**

- Час виконання: < 1 мс (не впливає помітно на цикл Soldier)
- RAM: < 128 байт (жорстке обмеження STM32WLE5JC)
- **Не застосовувати в PANIC-режимі** — при виявленні пилки/вогню TinyML → завжди TX

#### 🟡 Вектор 1: RF-Оптимізація SMD-Антени та PEEK-Радому (Модуль 02)

**Контекст: Архітектура RF-Deck 'Silken Net'**

Система використовує **STM32WLE5JC** з інтегрованим LoRa-трансивером та **керамічну SMD-антену** на верхньому шарі двоповерхової PCB. Плата накривається куполоподібним **PEEK-радомом** (Деталь 4, герметизація IP68), залишаючи зовні дерева лише 2–3 см «таблетку». Нижній шар (Power Deck: іоністор 0.47F + BQ25570 MPPT) та 120-мм Ti-6Al-4V анкер слугують частковим електромагнітним екраном знизу.

Ця конструкція породжує **три критичних RF-завдання**:

**Завдання А: Узгодження Імпедансу (Impedance Matching)**

Керамічні SMD-антени екстремально чутливі до змін Near-Field: міліметрові відхилення у формі PEEK-кришки, гумовий O-ring кільця, крапля води — все це викликає розлагодження (detuning) і підвищення КСВ/VSWR:

```
Мета: VSWR < 1.5 на 868 МГц (LoRa EU)  /  915 МГц (US ISM)

Метод Косенюка:
  1. VNA-вимір (Vector Network Analyzer): S11-параметр реальної зборки у
     PEEK-корпусі + O-ring + волога поверхня → комплексний імпеданс Z_measured
  2. Проектування П- або Т-подібного LC-ланцюга узгодження:
     Z_source (STM32WLE5 PA: 50 Ω) → Z_measured (реальна антена)
  3. Ітеративне тестування 5+ варіантів кришки (PEEK товщина 1.5 / 2.0 / 2.5 мм;
     діаметр 28 / 30 мм) для вибору оптимальної геометрії
  4. Верифікація: КСВ < 1.5 для 1000 серійних зразків (виробничий допуск ±5%)
```

**Завдання Б: 3D-Діаграма Спрямованості з Ti-Анкером як Ground Plane**

Титановий анкер (Ti-6Al-4V, 120 мм, діаметр 8 мм) та нижній шар PCB з іоністором діють як **нестандартний Ground Plane**, що суттєво модифікує реальну діаграму спрямованості:

```
Моделювання (FEKO / CST Microwave Studio або аналітично):
  - Циліндричний металевий об'єкт (Ti анкер): відбиття → формування вторинного
    пелюстка вниз (вглиб дерева → небажаний)
  - PEEK-радом: діелектричне навантаження → зсув резонансної частоти
  - Кора дерева (ε ≈ 10–20, σ ≈ 0.1–0.5 S/m): часткове поглинання сигналу

Мета: Горизонтальна поляризація, максимум у площині XY (горизонт лісу)
  → сигнал до сусідніх анкерів Mesh-мережі, а не вниз у ґрунт або вгору в небо
```

**Завдання В: Link Budget у Лісовому Середовищі**

Відсутність зовнішньої штирьової (whip) антени знижує Gain. Розрахунок Link Budget визначає оптимальний Spreading Factor:

```

  PEEK Radome Loss: -0.3 dB
  Path Loss (лісовий масив 200м, LoRa 868 МГц): -91 dB (worst case, волога кора)
  RX Sensitivity:  -137 dBm (SF=12, BW=125kHz)
  Margin:           +67.7 dB  → SF=7 достатньо для 200м hop

Висновок Косенюка: навіть при SF=7 запас зв'язку > +55 дБ (→ `02_01` §5.3);
  оптимальний SF=7–9 (баланс дальність/час-в-ефірі/енергія)
  при типовій відстані між анкерами 150–200м у лісі
```

#### 🟡 Вектор 2: FEC та Хеш-Захист Телеметрійних Потоків (Модуль 07)

**Контекст: Без зовнішньої антени → вища ймовірність помилок → потрібен FEC**

У густому лісі LoRa-пакети страждають від **багатопроменевого поширення (multipath fading)** — відбиття від стовбурів, гілок, листя. Частина пакетів або приходить пошкодженою, або втрачається. Повторна передача (retransmission) витрачає дорогоцінну мікроватну енергію EBFC.

**Завдання А: Forward Error Correction (FEC) для 21-байтового Пакету**

```
Поточна структура 21-байтового пакету (→ firmware/soldier/main.c):
  Незашифровані (5 байт):
    Bytes 0-3: DID (4B, uint32_t, Network byte order)
    Byte 4:    RSSI (1B, int8_t, додається Queen при ретрансляції)
  AES-128-ECB зашифровані (16 байт = 1 блок, post-ARCH.42 Variant B):
    Bytes 5-6:   Vcap (2B, uint16_t, мілівольти)
    Byte 7:      Temp (1B, int8_t, °C)
    Byte 8:      Acoustic (1B, uint8_t, TinyML клас)
    Bytes 9-10:  dT / delta_t (2B, uint16_t)
    Byte 11:     StatusByte (1B: [bio_status:2 | growth_points:6])
    Byte 12:     TTL (1B, uint8_t)
    Bytes 13-14: FW version (2B)
    Bytes 15-16: PAD (2B, зарезервовано)
  Ruby unpack: "N n c C n C C a4" (після розшифровки AES-ECB блоку)

Пропозиція FEC (Косенюк):
  Reed-Solomon(21,17) або Hamming(26,21): додати 4–5 байт контрольних символів
  → Gateway відновлює до 2 пошкоджених байт без повторного запиту
  → Загальний пакет із FEC: 25–26 байт (залишається в LoRa MTU = 242 байти SF=12)
  → Економія: 1 повторна TX = ~500 мкДж (≈ 10% добового EBFC бюджету)
```

**Завдання Б: Hash Method для Захисту Web3-Потоків**

Публікація Косенюка «Hash Method for Information Stream's Safety in Dynamic Cooperative Production System» безпосередньо застосовна до телеметрійного конвеєра:

```
Конвеєр верифікації цілісності:

MCU (STM32WLE5JC):
  hash_16 = CRC16_CCITT(sensor_bytes[5..18])  ← вже реалізовано (bytes 19-20)
  Варіант A: замінити CRC-16 на HMAC-SHA256[0..3] (4 байти, той самий розмір +2 байти)
    → пакет 21 байт зберігається; Gateway верифікує автентичність І цілісність
  Варіант Б (з FEC): пакет 25-26 байт (FEC) + HMAC-4 замість CRC-2 = 27-28 байт
    → все одно << LoRa MTU 242 байт

Gateway (Queen):
  Верифікує HMAC → відкидає фальсифіковані пакети
  Логує hash у GatewayTelemetryLog.packet_hmac (нове поле)

Rails Backend:
  UnpackTelemetryWorker верифікує HMAC перед INSERT у telemetry_logs
  Якщо HMAC invalid: зберегти у rejected_telemetry_logs + EWS alert

Blockchain (Chainlink Oracle):
  Передає лише верифіковані пакети → Polygon mint
  hash_chain: SHA256(prev_hash || current_packet) → аудитний ланцюг

Гарантія: маніпуляція delta_t (показник метаболізму) → invalidates HMAC
  → SCC/SFC не мінтяться → збережена цілісність Proof of Growth
```

#### 🟡 Вектор 3: Стохастична Фільтрація Аналогових Сигналів Edge AI (Модуль 06)

**Контекст: Pogo Pin сигнали мають "білий шум" через природні фактори**

Система зчитує **час заряду іоністора (delta\_t)** через Pogo Pins з Ti-анкера. Це — головний показник метаболізму дерева та ключовий вхід для Lorenz Attractor. Але природні вібрації стовбура, температурні флуктуації (±20°C сезонні), механічний контакт Pogo Pin → **σ\_noise ≈ 3–8% від delta\_t**.

**Завдання: Легковагові Стохастичні Фільтри на STM32WLE5JC**

```c
/* Метод Косенюка: Kalman Filter для delta_t (< 200 байт RAM, < 50 μs) */

typedef struct {
  float x_est;    // оцінка стану (delta_t фільтрований)
  float p_est;    // дисперсія оцінки
  float q;        // шум процесу (Q=0.01, налаштовується)
  float r;        // шум вимірювання (R=0.09 = σ²_noise)
} KalmanFilter_t;

float kalman_update(KalmanFilter_t *kf, float measurement) {
  // Prediction step
  kf->p_est += kf->q;
  // Update step
  float k_gain = kf->p_est / (kf->p_est + kf->r);
  kf->x_est += k_gain * (measurement - kf->x_est);
  kf->p_est *= (1.0f - k_gain);
  return kf->x_est;
}
/* 2 float32 operations per call → < 10 μs на STM32WLE5 @ 48 MHz */
```

**Альтернатива (при обмеженому RAM):** Exponential Moving Average (EMA):

```c
/* EMA: 1 float32, 1 multiply, 1 add → < 2 μs */
#define EMA_ALPHA 0.15f  // Косенюк розраховує оптимальний α для δt_noise
float ema_update(float prev, float measurement) {
  return EMA_ALPHA * measurement + (1.0f - EMA_ALPHA) * prev;
}
```

**Вплив на якість Lorenz Attractor:**

```
Без фільтрації: delta_t ± 8% → Z_lorenz флуктуації ± 12% (чутливість до IC)
З Kalman Filter: delta_t ± 1.2% → Z_lorenz флуктуації ± 2% → стабільний
  homeostasis signal для Proof of Growth верифікації
```

#### 🟠 Вектор 1: Stochastic Branch & Bound — Модуль 07 (LoRa-Mesh Reliability)

**Контекст: TTL-Flood Relay у Стохастичній Мережі**

Поточна прошивка (`firmware/soldier/main.c`) реалізує **TTL-based flood relay** з PANIC\_TTL=5. Це контрольований flooding: кожен Soldier, отримавши чужий пакет з TTL > 0, зменшує TTL та перепередає його всім сусідам без аналізу їхнього стану. Система не знає, **чи активний вузол-ретранслятор у конкретний момент** — якщо він у STOP2 (vcap < 1.8 В), пакет просто не буде перепереданий далі, і це непомітно для відправника.

Праця _«Reliability optimization of a complex system by the stochastic branch and bound method»_ (2008, Онищенко + Норкін) дає **готовий математичний апарат** для вирішення саме цієї задачі.

**Завдання А: Ймовірнісна Модель Доступності Вузла**

```
P_alive(v_i, t) — ймовірність того, що вузол v_i є активним у момент t

Входи моделі:
  vcap_i(t)    — поточна напруга суперконденсатора (передається у 21-байтовому пакеті)
  delta_t_i    — час заряду (індикатор метаболізму дерева → прогноз наступного заряду)
  weather(t)   — статистика хмарності / сезону (зовнішні дані)

Модель:
  P_alive(v_i, t + τ) = f(vcap_i(t), delta_t_i, weather(t))
    де τ — очікуваний час до наступного контакту
    f() — калібрується на реальній статистиці вузлів
```

**Завдання Б: Стохастичний Аналіз Надійності Flood Relay**

На основі моделі P_alive — **кількісна оцінка надійності існуючого TTL-flood relay** методом гілок і меж:

```
Оцінка P_delivery для flood relay з TTL=k:
  P_delivery(src, k) = P(∃ хоч один активний шлях довжиною ≤ k від src до Queen)

Метод: стохастичний B&B Онищенка-Норкіна:
  upper_bound(підграф) = ∏ max P_alive(v_i) → обрізати неперспективні гілки
  lower_bound(підграф) = ∏ min P_alive(v_i) → гарантований нижній поріг
  Результат: діапазон [P_low, P_high] для P_delivery при заданому рівні відмов
```

**Завдання В: Ідентифікація «Критичних Ретрансляторів»**

Стохастичний B&B ідентифікує **вузли, від яких найбільше залежить P_delivery** — вузькі місця flood relay в критичних зонах лісу. Ці анкери отримують рекомендацію на підвищену щільність розміщення (shorter hop distance) при розгортанні.

#### 🟠 Вектор 2: Мінорантні Методи Глобальної Оптимізації — Модуль 06 (Edge AI on-MCU)

**Контекст: Калібрування Edge AI на Дереві без Хмари**

Поріг впевненості TinyML (`confidence_threshold = 0.80`, хардкодований) та параметри Лоренца (`OPTIMAL_Z_TARGET`, зони гомеостазу) потребують **адаптації до конкретного лісу** — вологості, температури, фонового шуму. Стандартний підхід: зібрати дані → відправити до хмари → перетренувати → надіслати OTA. Але це **коштує дорого** (Starlink TX) та займає дні.

> **⚠️ Контекст TinyML (BLOCKER з 03_03):** Поточна реалізація має `Run_Inference()` **закоментованою** — TinyML inference фактично не виконується. Файл моделі `silken_net_audio_model.h` відсутній у репозиторії. Тому мінорантний метод для TinyML thresholds є **дослідницькою задачею на перспективу** після розблокування TinyML, а не поточним завданням.

Дисертаційна робота та публікація Онищенка _«Minorant methods of stochastic global optimization»_ (2005) відкривають альтернативу: **on-device глобальна оптимізація** з гарантією знаходження глобального мінімуму при мінімальній кількості обчислювальних кроків.

**Суть Мінорантних Методів (Метод Піявського):**

```
Задача: minimize f(θ)  — наприклад, f = classification_error(θ)
                           де θ — вектор порогів TinyML або params Лоренца

Класичний градієнтний спуск: може застрягти у локальному мінімумі
Мінорантний метод (Піявський):
  1. Побудувати мінорантну функцію g(θ) ≤ f(θ) (дотична знизу — конічна чи лінійна)
  2. Мінімум g(θ) дає нижню межу глобального мінімуму → пруннг неперспективних θ
  3. Ітераційно звужувати область → сходимість до глобального мінімуму

Переваги для STM32WLE5JC:
  - Кількість ітерацій: O(K log(1/ε)) замість O(1/ε²) у випадкових методах
    де K — кількість накопичених мінорантних точок, ε — необхідна точність
  - RAM: зберігати лише список мінорант (K точок × 2 числа = K×16 байт)
  - Немає автодиференціювання → немає backprop → тільки f-обчислення
```

**Завдання А: Адаптація Мінорантного Методу для STM32**

- Вибір класу мінорантних функцій для конкретної задачі: лінійні (Піявський) або конічні для гладких f
- Реалізація на C (float32, без FPU heap) — узгоджена з Ярмілком (SPI/DMA) щодо RAM-бюджету
- Першочергове завдання оптимізації: калібрування порогу `confidence_threshold` (0.80 → оптимальне значення) після розблокування TinyML inference (BLOCKER-1 з 03_03)

**Завдання Б: On-Device Калібрування `OPTIMAL_Z_TARGET` (BLOCKER-2 з 03_04)**

Мета — **on-device визначення ефективного OPTIMAL_Z_TARGET** конкретного дерева на основі накопиченої статистики Z-значень. Поточна константа (29.0) є глобальною, але реальний "здоровий" рівень Z може відрізнятися залежно від виду дерева, ґрунту та кліматичної зони.

> **⚠️ Метод — корекція (2026-05-28): для цієї задачі НЕ потрібні мінорантні методи Піявського.** Важливе уточнення: `OPTIMAL_Z_TARGET` — це **поріг інтерпретації** Z-значення, а НЕ параметр генерації хаотичної динаміки (σ/ρ/β; див. примітку BLOCKER-1 нижче). Тому над уже накопиченою (фіксованою) гістограмою `z_values[N]` цільова функція `f(θ)` є **детермінованою і Ліпшицевою** функцією однієї змінної θ — «ефект метелика» сюди не потрапляє, бо θ не подається назад у атрактор, а z-вибірка вже зафіксована. (Хаос/нескінченна Ліпшиць-константа були б проблемою лише якби ми тюнили σ/ρ/β, що змінюють траєкторію.) Отже Піявський тут **математично застосовний, але надлишковий** — для 1-D порогу над емпіричною вибіркою оптимум фактично у закритій формі (мода/медіана здорового вікна). Достатньо дешевого on-MCU оцінювача:
>   - **EMA / стохастична апроксимація (Робінса–Монро):** онлайн-оновлення θ ← θ + α·(z − θ) під час homeostasis-вікон (спадний крок α). RAM: 1 float, без зберігання гістограми.
>   - або робастна **медіана/мода** вікна `z_values[N]` (квантильна оцінка).
> Мінорантні/стохастично-глобальні методи Онищенка варто резервувати для **багатовимірних або справді мультимодальних** калібрувань Edge AI (де є кілька параметрів і локальні мінімуми), а не для 1-D порогу.

```c
// Концептуальний flow (firmware/soldier/main.c — нова Phase 3.5):
// Онлайн-оцінка здорового рівня Z через EMA / Robbins–Monro:
//   під час homeostasis-циклів: z_target += alpha * (z_val - z_target);
//   alpha — спадний крок (напр., 1/n), z_target ∈ [15.0, 45.0] clamp.
// Жодної гістограми у RAM, жодного глобального оптимізатора.
```

> **Примітка (BLOCKER-1 з 03_04):** У поточній реалізації `calculate_state(chaos_seed, temp, acoustic)` — `delta_t` та `vcap` **не передаються** у атрактор (хоча архітектурна специфікація передбачає `calculate_state(delta_t, vcap)`). Питання, який варіант математично коректніший як model of tree homeostasis, є **відкритим** і потребує аудиту Порубльова (Підгрупа Б, рядок нижче). У будь-якому варіанті `chaos_seed` як апаратна ентропія HRNG не є параметром "калібрування на конкретне дерево" — він є стохастичним початковим зерном. Завданням Б є калібрування порогів **інтерпретації Z-значення** (`OPTIMAL_Z_TARGET`), а не параметрів генерації початкових координат.

Результат: tree-specific `OPTIMAL_Z_TARGET` оновлюється в RTC Backup Domain без OTA.

#### 🟠 Вектор 3: Паралельні Алгоритми та Мережі Петрі — Модуль 08 (Akash Simulations)

**Контекст: CFD-Симуляції на Децентралізованому Суперкомп'ютері**

Гідродинаміка потокового потенціалу в порах гіроїда (Модуль 01\_01) та термодинаміка DMLS-друку вимагають **Computational Fluid Dynamics (CFD)** — задача з O(N³) складністю, яку не можна запустити на одній машині для великих N. Akash Network надає доступ до тисяч вузлів GPU/CPU за децентралізованими цінами — але **виключно для stateless compute workloads** (CFD, ML training), а не для Rails production (через BLOCKER-1: Cloud SQL ізоляція). Поточний TRL Akash: 4 (SDL існує, реального деплою не виконувалось). Для CFD обчислень Akash є першочерговим сценарієм використання — compute-only, без потреби у БД.

**Завдання А: Паралельна Декомпозиція CFD-Моделі Гіроїда для Akash**

На основі курсу «Паралельне програмування для багатопроцесорних систем» Онищенка:

```
Стратегія декомпозиції (domain decomposition):
  1. Розбиття 3D-об'єму гіроїда на N_x × N_y × N_z субдоменів
  2. Кожен субдомен → окремий Akash pod (незалежні обчислення)
  3. Граничні умови між субдоменами → halo exchange (MPI або gRPC)
  4. Мінімізація bottleneck: оптимальний розмір субдомену визначається
     як trade-off між обчислювальним часом та halo-трафіком

Onishchenko deliverable:
  - Алгоритм балансування навантаження між Akash-вузлами з неоднорідними GPU
  - Стратегія fault-tolerance: при падінні одного pod → перерозподіл його субдомену
```

**Завдання Б: Верифікація Firmware через Мережі Петрі**

Праця _«Applying a Combined Approach to Modeling of Software Functioning»_ (2023) та дослідження прихованих помилок у Petri net моделях є **критичними для прошивки STM32**. Багатопотоковий код (`RTOS tasks + DMA ISR + Watchdog`) містить потенційні **race conditions та deadlocks**, які неможливо виявити звичайним тестуванням:

```
Приклад потенційного deadlock у firmware/soldier/main.c:
  Task A (Sensing): захоплює SPI mutex → чекає DMA complete IRQ
  Task B (LoRa TX): захоплює UART mutex → чекає SPI mutex (для AES-key read)
  IRQ C (DMA):      намагається відправити результат через UART queue → заблокована Task B

  → Класичний circular wait → система зависає → IWDG reset → втрата телеметрії
```

Формальна верифікація через Petri nets дозволяє **алгоритмічно довести відсутність** таких станів до фізичного тестування:

- Побудова Petri net моделі RTOS tasks (Sensing, Compute, TX, OTA, WDT)
- Аналіз reachability graph → пошук deadlock-станів (markings без enabled transitions)
- Аналіз live transitions → перевірка що кожна задача гарантовано отримає ресурс
- Виявлення unbounded places → ідентифікація queue overflow ризиків

#### 🟣 Вектор 1: CNN + Супутникові Знімки → Digital Twin Лісу (Глобальний Моніторинг)

**Контекст: Мікро-дані без Макро-контексту не продаються на Carbon Market**

Анкер вимірює `delta_t` (час заряду EBFC) = індикатор метаболізму одного дерева. Покупець вуглецевих квот (наприклад, KlimaDAO) хоче підтвердження **на рівні всього лісу**: скільки гектарів живих, де вирубки, чи є пожежі. Без супутникових даних — це неможливо підтвердити.

Публікація Бушина (2023) _«Використання згорткових нейронних мереж для розпізнавання згорілих полів на супутникових знімках»_ дає готову архітектуру CNN, яку потрібно лише **перенавчити** на лісовий домен.

**Завдання А: Перенавчання CNN на Лісові Супутникові Знімки**

```
Базова архітектура Бушина (2023):
  Input:  RGB + Near-IR канали супутника (Sentinel-2: 10 м/піксель)
  Conv1:  32 фільтри 3×3 → ReLU → MaxPool
  Conv2:  64 фільтри 3×3 → ReLU → MaxPool
  Dense:  512 → 6 класів

Нові класи для Silken Net (замість "згорілих полів"):
  0: Healthy forest (NDVI > 0.6)
  1: Stressed forest (NDVI 0.3–0.6, посуха / шкідники)
  2: Fire / burned area (активна пожежа або свіжо горіле)
  3: Clear-cut / illegal logging (раптова втрата крони)
  4: Reforestation / young growth (NDVI < 0.3 але зростає)
  5: Non-forest (сільгосп, забудова, вода)
```

**Завдання Б: Синтез Macro + Micro — Корелятор «Супутник ↔ Анкер»**

Ключова наукова цінність: якщо CNN на супутнику бачить «стрес» у зоні — і одночасно `delta_t` анкерів у тій же зоні падає — це **causal linkage**, придатний для Scopus Q1:

```
pipeline:
  1. Sentinel-2 tile (100×100 км) → CNN inference → stress_map[lat][lon]
  2. Anchor telemetry (delta_t, vcap) → spatial aggregation за GPS координатами
  3. Corr(stress_map, delta_t_mean) → p-value < 0.01 → causal link
  4. Blockchain: satellite_hash + anchor_cluster_hash → Chainlink Oracle → KlimaDAO

Deliverable: SCC token ціна підтверджується dual-source верифікацією (ground truth + satellite)
```

**[LIVE ✅] dClimate FIRMS — Термальний Шар NRT як Ground Truth для Class 2 «Fire»**

З PR #223 (commit 575ed53) `Dclimate::VerificationService` інтегровано з NASA FIRMS (VIIRS Suomi NPP, 375 м, NRT-затримка ~3 год) через dClimate API. При кожному `fire_detected` EwsAlert система виконує реальний HTTP GET до `DCLIMATE_BASE_URL/v4/geo/grid-history/firms_nrt_global-area_v2` та отримує FRP (Fire Radiative Power, МВт) і рівень довіри детекції — це точний ground truth для Class 2 CNN Бушина:

```
dClimate FIRMS → Class 2 CNN labeled samples:
  fire_confirmed   (FRP ≥ 10 МВт + confidence ≥ 50%) → labeled "Fire / burned area"
  clear_sky_no_fire (ясне небо, термоаномалій немає) → labeled "Healthy / Stressed" (Class 0/1)
  obscured_by_clouds (cloud_cover > 70%)             → виключається (як SCL cloud masking у Sentinel-2)

dclimate_ref = "dclimate:firms:{satellite}:{timestamp}:{nonce}" → аудит-трейл кожного sample
Пайплайн: EwsAlert → DclimateVerificationWorker → VerificationService → FIRMS API → labeled_fire_event
```

Бушину доступний **готовий live pipeline** замість ручної розмітки: кожен верифікований EwsAlert автоматично стає labeled sample. VIIRS (375 м) виявляє точкові термоаномалії значно точніше, ніж Sentinel-2 (10 м) оптичний канал, і ці дані вже надходять у PostgreSQL через `alert.satellite_status` + `alert.dclimate_ref`.

**🌿 [Mongabay/Delgado 2026] Macro-Micro Verification — Чому Sentinel-2 NDVI недостатньо**

Стаття Delgado et al. Різниця проявляється лише у **звуковому ландшафті** (dawn/dusk піки активності фауни), який супутник принципово не реєструє.

Для Бушина це означає не критику CNN-підходу, а **завершення повної кільцевої архітектури верифікації**:

```

  → "Це зелено?" (NDVI, EVI, SAVI)
  → ймовірнісна карта здоров'я лісу

  ⚠️ Обмеження: монокультура pine = захищений мішаний бір
                на однаковий зелений піксель

Micro layer  (TinyML soundscape — 1 дерево = 1 STM32):
  → "Тут є ЖИТТЯ?" (5-class CNN: silence/wind/cavitation/chainsaw/FAUNA)
  → dawn/dusk fauna_activity_index 0–63 → AiInsight#biodiversity_trend
  
  Перевага: інструментально розрізняє функціональну екосистему від
            мертвої посадки (стаття Delgado довела це на 119 ділянках)

Synthesis  (Спільно з Любченком §1.8 — GA + Random Forest):
  Сurated_carbon_credit = NDVI_health × biodiversity_score

    NDVI=high & fauna=low  → "Підозрюваний green-washing" → no-mint
```

#### 🟣 Вектор 2: BSP-Кластеризація IoT-Графу (Модуль 07)

**Контекст: Великий ліс = тисячі анкерів; хто з ким спілкується?**

Поточна прошивка використовує flat TTL-mesh: кожен анкер намагається передати пакет будь-якому сусіду з достатнім зарядом. При тисячах вузлів — це неефективно: занадто багато broadcast, collision, та марне витрачання заряду на далекі хопи.

Праця Бушина _«Програма реалізації алгоритму BSP для кластеризації соціальних мереж»_ (2015) дає **готовий алгоритм** для структурування складних графів на ієрархічні кластери.

**Суть BSP-підходу для IoT:**

```
Традиційна кластеризація (K-Means, DBSCAN):
  Групує вузли за схожістю атрибутів (наприклад, vcap ≈ 3.2 В)
  → Проблема: фізична відстань та топологія не враховуються

BSP (Business System Planning) — адаптація для IoT-графу:
  Вузли: анкери G(V, E)
    V = {anchor_i: (GPS_lat, GPS_lon, vcap_i, delta_t_i)}
    E = {edge(i,j): якщо RSSI(i,j) > -110 dBm}  [фізичний LoRa зв'язок]

  BSP-кластеризація:
    1. Побудувати матрицю суміжності A[i][j] = RSSI(i,j) × vcap_weight(j)
    2. BSP-розбиття: мінімізувати cut edges між кластерами (слабкі зв'язки)
       при обмеженні: розмір кластеру ≤ MAX_CLUSTER (наприклад, 50 анкерів)
    3. Обрати cluster_head = argmax(vcap) у кожному кластері → Queen-лідер
    4. Солдати → лише cluster_head → Queen → Backend
```

**Завдання А: Статична BSP-Кластеризація при Розгортанні**

- Алгоритм первинного розбиття лісу на кластери за картою RSSI + GPS координатами
- Deliverable: JSON конфігурація кластерів → прошивається у EEPROM Soldier при провізіонінгу
- Порівняння з поточним flat-mesh: симуляція → мінімізація packet-hop count та collision rate

**Завдання Б: Динамічна Рекластеризація при Відмовах**

> **⚠️ Архітектурна корекція (2026-05-28): глобальний BSP НЕ може виконуватись на Soldier.** BSP-розбиття потребує **глобального знання графу** (матриця суміжності `A[i][j]` всіх вузлів). Soldier (STM32WLE5JC) бачить лише своїх **1-hop LoRa-сусідів** — він фізично не має повного графу лісу, тож «on-device greedy BSP» архітектурно некоректний. Розподіл обчислень:
> - **Глобальний BSP → Backend** (повна карта RSSI+GPS усіх анкерів) АБО **Queen** (топологія її кластера у CIFO EdgeCache, 50 слотів за DID). Queen/Backend перераховує кластери і **через OTA downlink надсилає кожному Soldier його `cluster_id` + `role` (head/node)**.
> - **На Soldier лишається лише ЛОКАЛЬНЕ рішення** — не BSP, а простий greedy-failover: коли вузол чує `CLUSTER_DISSOLVE` від свого head (vcap < поріг), він локально перемикається на найкраще-чутний альтернативний head серед тих, кого реально чує по LoRa (max RSSI×vcap), і чекає підтвердження ролей від Queen/Backend через OTA.

- Тригер: `vcap_cluster_head < 1.8 В` → head розсилає `CLUSTER_DISSOLVE` beacon
- Локальний failover на Soldier: вибір найкраще-чутного сусіднього head (greedy, 1-hop, < 1 KB RAM) — тимчасовий, до OTA-перепризначення
- Глобальний BSP-merge: Queen/Backend перераховує кластери з повної топології → OTA push `cluster_id`+`role`

#### 🟤 Вектор 1: Petri Net PN-Модель Rails Моноліту (Модуль 08)

**Контекст: Коли тисячі дерев одночасно надсилають телеметрію — хто кого блокує?**

Ruby on Rails з сервером Puma (multi-threaded) + Sidekiq workers (multi-process) + PostgreSQL connection pool — це класична багатопотокова система, де **deadlock між threads** або **вичерпання DB pool** може повністю зупинити інгестію телеметрії. Особливо критично при target-деплойменті на Akash, де Kubernetes-pod може мати нестабільний мережевий зв'язок, а timeout конфігурації не очевидні.

> **Контекст Akash (06_02, TRL 4):** Реального деплою на Akash ще не виконувалось через BLOCKER-1 (Cloud SQL недоступний з Akash — за межами GCP VPC) та BLOCKER-2 (Sidekiq відсутній у SDL). PN-модель дозволяє верифікувати архітектуру **до** вирішення цих блокерів — щоб при переході на Akash система гарантовано залишалась deadlock-free.

Дослідження Супруненко по комбінованому підходу до імітаційного моделювання ПЗ з паралелізмом дозволяють побудувати **математично строгу PN-модель** цієї системи.

**Завдання А: Побудова PN-Моделі Sidekiq + Puma + PostgreSQL**

```
Компоненти PN-моделі Rails моноліту Silken Net:

Places (ресурси та стани):
  p1: HTTP request queue (CoAP → Rails API endpoint /api/v1/telemetry)
  p2: Puma thread pool (config.puma threads: 3 per worker, WEB_CONCURRENCY workers)
  p3: PostgreSQL connection pool (pool: 5 per worker per DB у database.yml)
  p4: Sidekiq job queue "uplink" (priority 1 — найвищий, UnpackTelemetryWorker)
  p5: Sidekiq job queue "alerts" (priority 2, EwsAlertWorker)
  p6: Sidekiq job queue "web3_critical" (priority 6, MintingWorker)
  p7: Active DB transaction (INSERT INTO telemetry_logs)
  p8: Completed telemetry record
  p9: External RPC node state (Polygon/Solana/Celo — Alchemy/Infura latency/429
      Rate Limit) — НАЙКРИТИЧНІШИЙ bottleneck Web3-інфраструктури (NEW 2026-05-28)

Transitions (операції):
  t1: accept_request (HTTP → Puma thread)
  t2: acquire_db_connection (Puma → PostgreSQL pool)
  t3: enqueue_sidekiq (Rails controller → uplink queue)
  t4: process_telemetry (UnpackTelemetryWorker → DB write)
  t5: trigger_ews (EwsAlertWorker → alerts queue)
  t6: mint_scc (MintingWorker → web3_critical queue)
  t7: call_rpc_node (MintingWorker/Oracle → зовнішня RPC-нода; може блокуватись
      на latency/429 — токен «зависає» у p9)

Верифікація:
  - Reachability analysis: чи може p3 (DB pool) вичерпатись при 1000 паралельних requests?
  - Deadlock detection: чи є стан де t2 та t4 одночасно очікують p3 (DB connection)?
  - Boundedness: чи обмежена p4 (uplink queue) при 10,000 nodes × 60s = 167 pkt/s ingress rate?
  - 🔴 Каскадний збій через RPC (p9): якщо Polygon RPC відповідає з 429/latency
    на 5 хв — чи НЕ виникає deadlock? Інваріант, який треба ДОВЕСТИ:
      (а) t7 (RPC-виклик) виконується ТІЛЬКИ після ЗВІЛЬНЕННЯ p3 (DB connection
          НЕ утримується через зовнішній HTTP-виклик — класична anti-pattern);
      (б) черга web3_critical (p6) гарантовано BOUNDED (backpressure, не росте
          безмежно при недоступній ноді);
      (в) t7 має exponential backoff + circuit breaker → token повертається у
          p6 без вичерпання Puma/Sidekiq/DB ресурсів.
    Тобто збій блокчейн-ноди НЕ повинен зупиняти інгестію телеметрії (p1→p8).
```

#### 🟤 Вектор 2: Метод Згортки для Управління State Explosion (Модуль 08)

**Контекст: Повний Rails моноліт = мільярди станів → аналіз неможливий без редукції**

Проблема state explosion: повна PN-модель Rails моноліту з 36+ Sidekiq workers, 82 API ендпоінтами (→ `04_03`), 25+ моделями та multi-DB PostgreSQL матиме **астрономічну кількість комбінацій станів** — класична проблема верифікації складних систем.

Супруненко розробила унікальний **метод згортки (Convolution Method)**: лінійні ділянки PN-моделі без критичних властивостей (local deadlock, race condition, queue boundedness) **згортаються** в один абстрактний transition — розмірність моделі зменшується у десятки разів.

**Алгоритм застосування до Rails:**

```
Крок 1: Identify "linear sections" (безпечні, ненасичені pipeline ділянки)
  Приклад: HTTP accept → Puma thread → serialize JSON → enqueue Sidekiq
  Ця ділянка є детермінованою, без shared resources → безпечна для згортки

Крок 2: Verify no critical properties in section
  - Жодного shared place (p3 DB pool не торкається)
  - Жодного inhibitor arc (no conditional branching)
  - Жодного merge transition (один input → один output)

Крок 3: Apply convolution → single abstract transition T_ingest
  Замість 5 transitions + 4 intermediate places → 1 transition T_ingest
  Розмірність: -4 places, -4 transitions (для кожного воркера)

Крок 4: Analyze reduced model → find deadlocks, races, unbounded places
  Тепер reachability graph керований → аналіз займає хвилини, не дні
```

**Deliverable:** Верифікований звіт «Rails 8.1 monolith is deadlock-free and queue-bounded under 10,000 concurrent IoT connections» → включити до технічної документації Silken Net + наукова публікація.

#### 🟢 Вектор 3: Теорія Прийняття Рішень та Data Mining для Edge AI (Модуль 06)

**Контекст: STM32WLE5JC як автономний агент**

Кожен анкер є **автономним агентом**, що приймає рішення в умовах жорсткого дефіциту енергії. Поточна логіка `soldier/main.c` — проста: зібрав дані → запакував → TX. Але LoRa TX споживає ~15 мА × 100 мс = 1500 мкДж, тоді як добовий EBFC-бюджет ≈ 5000 мкДж. Кожна зайва передача — 30% добового бюджету.

**Завдання А: Теорія прийняття рішень для оптимізації LoRa TX**

```c
/* Модель автономного рішення Осауленка для soldier/main.c */

/* Критерій прийняття рішення про TX на основі multi-attribute utility: */

typedef struct {
  float u_energy;     // корисність з точки зору енергії: vcap / vcap_threshold
  float u_data;       // корисність даних: |delta_t - delta_t_prev| / sigma_noise
  float u_time;       // корисність часу: elapsed_since_last_tx / max_tx_interval
  float u_network;    // корисність мережі: rssi_last_rx / rssi_threshold
} DecisionUtility_t;

/* Адитивна нормалізована функція корисності (weights від Осауленка):
   W_ENERGY + W_DATA + W_TIME + W_NET == 1.0f  (інваріант) */
float compute_utility(DecisionUtility_t *u) {
  const float W_ENERGY = 0.40f;  // найважливіший критерій
  const float W_DATA   = 0.30f;  // зміна сигналу
  const float W_TIME   = 0.20f;  // не мовчати >30хв
  const float W_NET    = 0.10f;  // якість каналу
  /* static_assert: сума ваг == 1.0 (перевіряється компілятором) */
  _Static_assert((int)((0.40f + 0.30f + 0.20f + 0.10f) * 100) == 100,
                 "Utility weights must sum to 1.0");
  return W_ENERGY * u->u_energy
       + W_DATA   * u->u_data
       + W_TIME   * u->u_time
       + W_NET    * u->u_network;
}

/* Рішення: TX якщо utility > threshold.
   Початкова оцінка 0.55 — підлягає калібруванню на польових даних
   50+ анкерів (Підгрупа В); цільовий показник: скорочення TX на 30-40%
   при втраті пакетів < 5%. */
#define TX_UTILITY_THRESHOLD 0.55f  /* [initial estimate, to be calibrated] */
```

**Перевага:** Замість TX кожні 15 хв незалежно від умов — **адаптивний TX**: коли є енергія + новий сигнал + не мовчав довго + хороший канал. Оцінка: скорочення TX на 30–40% → подовження циклу автономності вдвічі.

**Завдання Б: Data Mining для backend телеметрії Lorenz Attractor**

```
Вхідні дані:
  telemetry_logs: delta_t (float), vcap (float), temp (float),
                  lorenz_z (float), tinyml_class (int)
  Обсяг: ~1000 анкерів × 96 вимірів/добу = 96,000 рядків/добу
  Горизонт: 5 років = 175,200,000 рядків (планетарний масштаб)

Методи Data Mining (Осауленко):
  Кластеризація (k-means / DBSCAN):
    → автоматичне виявлення "аномальних кластерів" дерев:
      група А: нормальний метаболізм (baseline Lorenz Z ∈ [20, 40])
      група Б: стрес (Z < 15, vcap_charge_slow)
      група В: критичний стрес (Z < 8, temp > 45°C → пожежна загроза)

  Асоціативні правила (Apriori):
    → виявлення: якщо (delta_t_trend < -15% за 7 днів) AND
                       (tinyml_class == "drought") AND (cluster == B)
      THEN: P(критичний стрес за 14 днів) > 0.87
    → автоматичне правило для EWS Alert + Parametric Insurance trigger

  Регресійний аналіз (часові ряди):
    → прогноз delta_t на 30 днів вперед для кожного анкера
    → вхід для Proof of Growth: growth_points = f(delta_t_trend)
    → динамічне коригування ваг у Multi-Attribute Utility (feedback loop)
```

#### 🟢 Вектор 1: Генетичні Алгоритми для Оптимізації Backend ML (Модуль 04\_02)

**Контекст: InsightGeneratorService та ML-модель лісового стресу**

`InsightGeneratorService` (04_02) виконує добову агрегацію телеметрії та формує `AiInsight` через ML-модель `silken_forest.marshal` — евристичну модель stress_index. Ця модель потребує оптимізації ваг (порогових значень delta_t, lorenz_z, temp) для різних лісових екосистем. Стандартний gradient descent застрягає у локальних мінімумах через нерегулярність біологічних часових рядів.

> **Архітектурна примітка:** `delta_t` — це **вимірюваний** показник (час між пробудженнями MCU: `current_time - last_wakeup_timestamp`), а не прогнозований. Soldier вимірює delta_t безпосередньо через `HAL_GetTick()`. Mruby VM на MCU виконує bio_contract.rb (Lorenz Attractor) — замінювати його нейромережею означає зміну фундаментальної архітектури bio-contract. Тому GA-оптимізація застосовується до **backend** InsightGeneratorService, а не до on-device mruby VM.

**Підхід Любченка (публікація 2022) — Backend Optimization:**

```
Генетичний алгоритм для оптимізації ваг stress_index моделі:

Хромосома:
  chromosome = [w_delta_t, w_lorenz_z, w_temp, threshold_critical, threshold_stressed]
  де w_* — вагові коефіцієнти ознак для stress_index [0.0..1.0]

Фітнес-функція:
  f(chromosome) = F1-score(stress_classification vs ground_truth)
  ground_truth: ручна розмітка 500 "відомо здорових" та "відомо стресових" дерев

Еволюція (50 поколінь × 100 хромосом = 5000 оцінок):
  Відбір: tournament selection (k=5)
  Схрещування: uniform crossover (p_cross=0.8)
  Мутація: gaussian mutation (σ=0.05 per weight)
  Елітизм: топ-5 хромосом переходять без змін

Навчання (Akash GPU кластер):
  $ akash deploy --image silknet/ga-backend-trainer:latest
  → output: optimal_stress_weights.json
  Деплой: Rails config/ml_weights.yml → rake silken_net:reload_ml_weights

Результат: InsightGeneratorService з оптимізованими порогами → вища точність EwsAlert
  Baseline (евристика): F1 ≈ 0.72
  GA-оптимізація:       F1 ≈ 0.85+ (цільова метрика)
```

#### 🟢 Вектор 3: Master of Logic — Мінімізація Edge AI та Верифікація Solana (Модуль 06, 07)

**Контекст: Master of Logic — де він справді цінний (і де ні)**

Логіка прийняття рішення про LoRa TX на MCU — це кон'юнкція гейтів:

```
Поточна логіка (firmware v1, soldier/main.c):
IF (vcap > VCAP_TX_MIN)
AND (delta_t_changed)
AND (time_since_last_tx > MIN_TX_INTERVAL)
AND (tinyml_alert OR normal_schedule)
THEN TX

Це вже мінімальна форма: кожен гейт незалежний (заряд / новизна даних /
duty-cycle / причина), жоден не надлишковий. Спокуса «мінімізувати» цей вираз
у коротшу ДНФ є хибною — див. корекцію нижче. Реальна цінність Master of Logic
для Silken Net — НЕ у firmware boolean-tweaking, а у формальній верифікації
guard-логіки смарт-контрактів (де помилка коштує мільйони).
```

> **⚠️ Корекція (2026-05-28): попередній приклад «мінімізації» був математично хибним і вилучений.** Він стверджував еквівалентність
> `vcap_ok && delta_changed && time_ok && (alert || sched)` ⇔ `vcap_ok && (delta_changed || time_ok || alert)`.
> Це НЕ еквівалентні функції: контрприклад `vcap=1, delta_changed=1, time_ok=0, alert=0` → перший вираз = 0 (TX заборонено, бо не минув MIN_TX_INTERVAL), а «оптимізований» = 1 (TX!). «Оптимізація» **зламала б бізнес-логіку** — передача відбулась би занадто рано, до закінчення інтервалу. До того ж таблиця істинності мовчки відкидала 5-ту змінну `sched`.
>
> **Реальний стан:** логіка TX — це **кон'юнкція гейтів** (усі мають виконатись): `vcap_ok ∧ delta_changed ∧ time_ok ∧ (alert ∨ sched)`. Це вже мінімальна форма — кожен гейт незалежний (заряд, новизна даних, duty-cycle, причина), жоден не є надлишковим, тож скорочувати нічого. Для 4–5 булевих змінних мінімізація ДНФ **не дає виграшу для прошивки**: реальна вартість — це обчислення операндів (`vcap`, `delta_t`, `elapsed`, `tinyml_class`), а не `&&`/`||` між уже готовими булями; компілятор (GCC `-O2`/`-Os`) і так оптимізує короткозамкнені вирази на рівні AST. Тому окрема firmware-задача «мінімізації умов пробудження» має ~нульову цінність і вилучена (попередня оцінка «0.2 мкДж/рік → тисячі кВт·год» була некоректним перебільшенням).
>
> **Куди справді спрямувати Master of Logic:** на **формальну верифікацію guard-логіки смарт-контрактів** (нижче), де логічна діра коштує мільйони, а не на firmware boolean-tweaking.

**Верифікація логіки смарт-контрактів (Polygon Solidity + концептуальна Solana):**

> **Примітка:** Поточна реалізація мінтингу SCC — на **Polygon** через Solidity контракт `SilkenCarbonCoin.sol` (директорія `contracts/`). Solana використовується лише для USDC мікро-винагород (`Solana::MintingService`). Нижче — концептуальна ілюстрація застосування Master of Logic до логіки мінтингу (незалежно від мережі).

```
Логіка мінтингу SCC (Polygon, реалізована в BlockchainMintingService):

Guard clauses перед мінтингом:
  require: verified_by_iotex? (ZK-proof верифікація)
  require: oracle_status_fulfilled? (Chainlink callback)
  require: hadron_kyc_status == "approved" (KYC/Compliance)
  require: growth_points >= 10_000 (Proof of Growth threshold)

Перевірка Master of Logic:
  P1: growth_points >= 10000
  P2: verified_by_iotex == true
  P3: oracle_status == "fulfilled"
  P4: hadron_kyc_status == "approved"
  Висновок C: mint 1 SCC

  Питання: чи С слідує з P1 AND P2 AND P3 AND P4?
  Master of Logic: побудова CNF → резолюція → перевірка логічного слідування
  Результат: "Так, C є логічним наслідком P1, P2, P3, P4 — без суперечностей"

  Додатково: перевірка на повноту (чи є "сліпі зони" де мінтинг неможливий
              при коректних даних?) → виявлено та виправлено перед деплоєм.
```

## 🔬 4. Валідація гіпотези «Лоренц Z ↔ здоров'я» (Ground-Truth Protocol) [Lorenz de-risk]

**Проблема:** ланцюг Z-атрактора → `stress_index` → slashing **елегантний, але емпірично недоведений**. Потрібен ground-truth, щоб (а) підтвердити/спростувати предиктивність Z, (б) калібрувати ML-`stress_index`, (в) безпечно виставити slashing-пороги. Cross-ref [`05_05 §7`](05_05_Slashing_and_Risk_Policy).

**Дизайн (ЧНУ — UNI.9 Карапетян Data Science + UNI.5 Гусак + bio-hub UNI.13a):**
- **Когорта:** 20–30 дерев (Черкаський бір), SilkenNet-анкер + **незалежний ground-truth**: еталонний sap-flow сенсор (незалежний від EBFC `delta_t`), дендрометр (приріст), періодичний NDVI/leaf-area, експертний бал стану + події смертності/хвороби.
- **Тривалість:** ≥1 вегетаційний сезон (захопити стрес-події: посуха, шкідники).
- **Збір:** щоденні `stress_index` + компоненти (`Z`, `sap_flow`, `acoustic`, `temp`, `vcap`, **`RH`/`VPD`** (BME280, `02_01 §3.4`)), `growth_points`, ground-truth.
- **Аналіз** (backend-харнес `SilkenNet::LorenzValidationService` — ✅ реалізовано, `app/services/silken_net/`, 12 specs):
  1. Кореляція `stress_index` ↔ ground-truth decline (Spearman ρ).
  2. **Incremental value Z:** чи додає Z предиктивність ПОНАД прямі сигнали (sap_flow)? Якщо ні → демоут Z до **DCI-only**.
  3. Agreement device bio_status (Z-derived) vs експертний бал (Cohen's κ).
  4. ROC детекції стресу + false-positive rate (slashing-safety).
  5. **VPD-confounder:** частка sap_flow-drops, пояснених погодою (high VPD) vs хворобою — валідує False-Slashing guard (`05_05 §6`, BME280 `02_01 §3.4`).
- **Критерії приймання (proposed):** ρ(stress_index, decline) ≥ 0.6; Z дає incremental ΔAUC > 0.05 над sap_flow-baseline (інакше Z = лише DCI); FPR < 5% на операційному порозі.
- **Вихід:** калібровані ваги ML-`stress_index` + heuristic + slashing-пороги (DAO-tunable, BIZ.4); рішення про роль Z (predictive vs DCI-only).

> Це закриває найбільший науковий ризик проєкту: без цього доказу bio-частина стоїть на гіпотезі. Лоренц-DCI (anti-fraud) лишається валідним **незалежно** від результату — навіть якщо Z демоутиться до DCI-only, fraud-детекція не страждає.
