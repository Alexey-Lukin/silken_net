# 08_05: ЧІПБ — Інтеграція Пожежної Безпеки та Параметричного Страхування

## 🎯 Мета

Формалізація академічної та прикладної співпраці з **Черкаським інститутом пожежної безпеки імені Героїв Чорнобиля (ЧІПБ)** Національного університету цивільного захисту України (НУЦЗУ) за чотирма напрямами:

1. **Валідація тригерів параметричного страхування** — наукове обґрунтування порогових значень `ParametricInsurance` смарт-контрактів (`critical_fire`, `extreme_drought`, `insect_epidemic`) для децентралізованих страхових пулів (Etherisc DIP)
2. **Протоколи фізичного реагування (SOP)** — розробка стандартних операційних процедур для арбористів та лісників при отриманні `EwsAlert` від кіберфізичної мережі
3. **Предиктивне моделювання поширення вогню** — інтеграція моделей поширення пожежі з телеметрією `delta_t` та `bio_status` для підвищення точності раннього попередження
4. **Актуарне обґрунтування блокчейн-оракулів** — науково-юридична база для визначення порогів слешингу та виплат USDC через Etherisc

ЧІПБ — єдиний в регіоні заклад, що поєднує **інженерію пожежної безпеки**, **аварійно-рятувальну техніку** та **практичний досвід ДСНС**. Три попередні академічні партнери (ЧНУ — фізико-хімічна верифікація хардверу; ЧНУ ФОТІУС — кіберфізична валідація firmware/backend; ЧДТУ — Data Science, RF-верифікація, акустика) покривають повний цикл від анкера до блокчейну, але **жоден з них не має компетенції у реальному пожежогасінні, оцінці ризиків природних катастроф та протоколах фізичного реагування ДСНС**. ЧІПБ закриває цю критичну прогалину — перетворює цифровий алерт на легітимну дію в реальному світі.

> **Контекст:** Silken Net генерує алерти автономно (`PANIC_TTL=5` при chainsaw detection, `fire_detected` EwsAlert, `critical_fire` ParametricInsurance trigger). Але без валідованих SOP та наукового обґрунтування тригерів ці алерти залишаються «цифровим шумом». ЧІПБ перетворює їх на **юридично та технічно обґрунтовані сигнали** для диспетчеризації ДСНС, страхових виплат та судової експертизи.

### 1.1. Биченко Артем — Диспетчеризація та Інтеграція з ДСНС

**Посада (потребує верифікації):** Науковець кафедри пожежної безпеки, ЧІПБ
**Науковий ступінь (потребує верифікації):** Кандидат технічних наук
**Спеціалізація:** Автоматизація систем пожежогасіння, алгоритми диспетчеризації, інтеграція IoT-систем з оперативними протоколами ДСНС

**Точка перетину зі Silken Net:**

Silken Net генерує два типи аварійних сигналів, які потребують конверсії в легітимні диспетчерські команди:

1. **PANIC_TTL=5 пакет** (`firmware/soldier/main.c:45`) — Soldier детектує бензопилу (TinyML acoustic class 3: `chainsaw`, `acoustic_events` > поріг) та підвищує TTL аварійного пакету з DEFAULT_TTL=3 до PANIC_TTL=5. Цей пакет проходить через LoRa mesh з пріоритетом і тригерить **виключно** `EwsAlert.alert_type = :vandalism_breach` (незаконна вирубка — сигнал для лісової охорони / поліції, НЕ для пожежних підрозділів).

   > **⚠️ Критично (виправлено 2026-05-28):** Акустичний клас `chainsaw` НЕ повинен тригерити `:fire_detected`. Бензопила — це маркер вандалізму/вирубки, а не пожежі; маршрутизація її на `:fire_detected` спричинила б помилковий виклик ДСНС (марний виїзд пожежної техніки на лісоруба → штраф, втрата довіри). `:fire_detected` вимагає **окремої комбінації фактів**: `temperature_c > поріг` + аномалія `delta_t` (стрес-десикація дерева) + супутникове підтвердження (`dClimate Cosmic Eye`, FRP). Жоден акустичний клас сам по собі пожежу не підтверджує.

2. **EwsAlert → EmergencyResponseService** (`app/services/emergency_response_service.rb`) — при `severity_critical? && alert_type_fire_detected?` система автономно:
   - Відкриває `water_valve` на 4 години (14400 сек, розбито на chunks по MAX_COMMAND_DURATION=3600)
   - Активує `fire_siren` на 1 годину
   - Команди з `priority: :high`, TTL 15 хвилин, idempotency через UUID

**Проблема:** Ці автономні дії відбуваються **без інтеграції з ДСНС**. Система Silken Net вмикає сирени та клапани, але не сповіщає реальні пожежні підрозділи. Потрібен **мост між цифровим алертом та диспетчеризацією ДСНС**.

**Конкретний R&D-запит:**

### 1.2. Ротар Василь — Стандартні Операційні Процедури (SOP) для Лісників

**Посада (потребує верифікації):** Науковець кафедри пожежної безпеки, ЧІПБ
**Науковий ступінь (потребує верифікації):** Кандидат педагогічних наук, доцент
**Спеціалізація:** Розробка навчальних програм, інструкцій та регламентів дій для служб цивільного захисту, методика підготовки рятувальників

**Точка перетину зі Silken Net:**

Silken Net оперує в лісах, де кінцевими виконавцями дій є **форестери (роль `User.role = :forester`)** та **патрулі**. Система надсилає їм EwsAlert через Turbo Streams (`broadcast_new_alert → Alerts::Row`, `ews_live_feed`), але **відсутні формалізовані інструкції: що саме робити, коли на дашборді з'являється червоний алерт**.

Поточний стан: `EwsAlert.alert_type` має 7 типів. **Розподіл за компетенцією (виправлено 2026-05-28):** ЧІПБ (НУЦЗУ) — це аварійно-рятувальна служба, а не біологи/ентомологи. Тому Ротар (ЧІПБ) розробляє SOP **лише для аварійно-безпекових подій**; біологічні SOP (посуха, шкідники, передстресова ентропія) делегуються **ЧНУ Біо-Хабу (Спрягайло, Гаврилюк)** — див. [`08_01`](08_01_University_R_and_D_Protocols).

**Зона компетенції ЧІПБ (SOP Ротара + Биченка):**

| `alert_type` | Поточна автоматика | SOP (ЧІПБ) |
|---|---|---|
| `fire_detected` (3) | `water_valve` 4 год + `fire_siren` 1 год | SOP: евакуація, позначення периметру, координація з ДСНС (завдання Биченка) |
| `vandalism_breach` (2) | Лише сповіщення | SOP: огляд капсули, протокол заміни Soldier-вузла / деінсталяції в місці (завдання Несена) |
| `seismic_anomaly` (4) | `seismic_beacon` 30 хв | SOP: перевірка стабільності ґрунту, оцінка ризику зсувів |
| `system_fault` (5) | Лише сповіщення | SOP: діагностика шлюзу, заміна Gateway, перевірка LoRa connectivity |

**Зона компетенції ЧНУ Біо-Хаб (делеговано, [`08_01`](08_01_University_R_and_D_Protocols)):**

| `alert_type` | Поточна автоматика | SOP (ЧНУ Біо-Хаб, НЕ ЧІПБ) |
|---|---|---|
| `severe_drought` (0) | `water_valve` OPEN 2 год | SOP: інспекція ґрунтової вологи, перевірка кореневої системи, оцінка CODIT — потребує дендролога/фізіолога рослин |
| `insect_epidemic` (1) | `water_valve` OPEN 1 год | SOP: візуальна ідентифікація шкідника, відбір проб, карантинна зона — потребує ентомолога |
| `entropy_anomaly` (6) | Лише сповіщення | SOP: плановий огляд кластера, збір ґрунтових/біопроб, калібрація сенсорів — потребує біоценолога |

### 1.3. Куліца Олег — Предиктивне Моделювання Поширення Вогню

**Посада (потребує верифікації):** Науковець кафедри, ЧІПБ
**Науковий ступінь (потребує верифікації):** Кандидат технічних наук
**Спеціалізація:** Моделювання динаміки пожеж, фізика горіння лісових матеріалів, прогнозування поширення вогню

**Точка перетину зі Silken Net:**

Silken Net фіксує ранні ознаки пожежонебезпеки через два канали:

1. **`delta_t` (час заряду іоністора)** — ключовий біофізичний сигнал. При спеці та посусі метаболізм дерева (транспірація, ксилемний потік) сповільнюється → EBFC генерує менший струм → `delta_t` зростає → `bio_status = :stress`.

   > **⚠️ Важливо (виправлено 2026-05-28):** `delta_t` відображає **гідратацію самого дерева** (глибинний ксилемний потік), а НЕ вологість поверхневої лісової підстилки. Це принципово різні fuel-шари: ~90% низових пожеж починаються в сухій підстилці (листя/хвоя/мох), яка пересихає за один спекотний вітряний день незалежно від того, що глибококоренева сосна ще тримає вологу. Тому `delta_t` НЕ є проксі вологості підстилки. Натомість `delta_t` — це проксі **вологості живого пального (Live Fuel Moisture Content, LFMC) крони**: десикація дерева знижує LFMC хвої/листя → підвищує **займистість крони** → це маркер переходу низова → **верхова (crown) пожежа** — найкатастрофічнішого сценарію. Вологість поверхневої підстилки покривається супутниковими даними dClimate (NDVI/LST/опади), а не `delta_t`.

2. **`temperature_c` + `acoustic_events`** — підвищення температури + аномальна акустика (кавітація ксилеми при екстремальній спеці, acoustic class 2: `cavitation`) → комплексний сигнал "сухий ліс".

### 1.4. Зобенко Наталія — Актуарне Обґрунтування Блокчейн-Оракулів

**Посада (потребує верифікації):** Науковець кафедри, ЧІПБ
**Науковий ступінь (потребує верифікації):** Кандидат технічних наук
**Спеціалізація:** Оцінка ризиків, техногенна безпека, кількісний аналіз ризиків промислових та природних катастроф

**Точка перетину зі Silken Net:**

Silken Net використовує **параметричне страхування** — автоматичну виплату при досягненні заданих порогових значень (без людського арбітражу). Це реалізовано через:

1. **ParametricInsurance** (`app/models/parametric_insurance.rb`) — AASM: `active → triggered → paid → expired`
2. **Etherisc DIP Oracle Mode** — зовнішні USDC-виплати через децентралізований страховий пул на Polygon
3. **Oracle Consensus** — `required_confirmations` незалежних AI-джерел для підтвердження катастрофи
4. **Cosmic Eye (dClimate)** — супутникова верифікація (`satellite_status_verified?`) як другий фактор

**Проблема:** Поточні пороги (`threshold_value`, `required_confirmations`, `FIRE_FRP_THRESHOLD_MW = 10.0 MW`, `FIRE_CONFIDENCE_THRESHOLD = 50%`) встановлені **евристично, без актуарного обґрунтування**. Для юридичної валідності страхових виплат USDC потрібен науковий розрахунок.

> **⚠️ Принцип тригерів виплат (виправлено 2026-05-28):** Тригери параметричних виплат за **фізичні збитки** (пожежа, вандалізм) ПОВИННІ базуватися на об'єктивних апаратних фактах + супутнику, а НЕ на похідних хаотичної динаміки (`z_value` / `divergence Z`). Підстави:
> 1. **`divergence Z` НЕ є мірою збитку.** Це fraud-detection метрика (`FRAUD_DEVIATION_THRESHOLD = 30%`), що порівнює device-Z vs server-Z на фізичних сенсорах (sap_flow / temperature) для виявлення підробки телеметрії. Дерево у природному стресі (високий `stress_index`) ≠ згоріле дерево.
> 2. **`divergence Z` у проді ≈ 0.** Після [FW.7] серверний і прошивковий Z **бітово ідентичні** (Float64 IEEE 754, верифіковано 50 000 parity-тестами) — тобто це НЕ «шум флоат-округлення», а навпаки строго детермінований 0. До того ж raw device-Z у production-пакеті взагалі не передається ([FW.31]), тож тригер на ньому був би мертвим.
>
> **Коректні тригери фізичних збитків:** (a) масова втрата зв'язку вузлів кластера (вузли фізично знищені = згоріли), (b) екстремальна `temperature_c` на вузлах, що вижили, (c) супутникове підтвердження Fire Radiative Power (`dClimate` FRP ≥ `FIRE_FRP_THRESHOLD_MW`). `stress_index` / `z_value` лишаються лише для **біологічних** тригерів (drought/pest prediction), не для виплат за фізичну руйнацію.

**Спеціалізація:** Інженерія рятувального обладнання, механіка з'єднань, проєктування спеціалізованих інструментів

**Точка перетину зі Silken Net:**

**Тризонний коаксіальний анкер** ([`01_01`](01_01_Coaxial_Gyroid_Topology_and_PEEK)) Ti-6Al-4V + PEEK (загальна довжина ~80–120 мм, пористість гіроїдної анодної секції 65%) **вживляється в деревину** методом Flush Mount step drilling ([`01_04 §3`](01_04_CODIT_and_Xylemointegration)).

> **⚠️ Засаднича корекція (2026-05-28): анкер НЕ витягується — він постійний за дизайном.** Через 2–4 роки жива тканина (калюс + заболонь) **проростає у 65% макропори гіроїда** — це і є мета ксилемоінтеграції ([`01_04`](01_04_CODIT_and_Xylemointegration)), а не побічний ефект. Додатково: annular barbs мають **храпову (ratchet) геометрію** — легко увійти, неможливо вийти; DIN 471 retaining rings + press-fit Ti-PEEK-Ti замикають зони; CODIT-калюс інкапсулює фланець. **Спроба «вирвати» тризонну збірку = вирвати армований титаном шмат стовбура → дерево гине.** Тому концепція «екстрактора анкера» фізично хибна. Правильна модель — два окремі сценарії:
> - **Заміна електроніки (upgrade/fault):** змінюється лише **капсула Soldier**, під'єднана через 2-пінове Pogo Pin Blind Mate ([`02_02`](02_02_Blind_Mate_Pogo_Pin_Interface)). Анкер (Zone 1 + Zone 2) лишається в дереві недоторканим.
> - **Виведення з експлуатації (decommissioning in place):** для мертвого дерева чи вандалізму — електроніку та O-ring знімають, фланець Zone 3 зрізають врівень із корою, канал герметизують. Інертні Ti (Zone 1) + PEEK (Zone 2) лишаються **назавжди** як стерильний мінералізований «сучок» (титан і PEEK біоінертні, не токсичні для дерева).

Сценарії обслуговування:

| Сценарій | Тригер у системі | Стан CODIT | Дія |
|----------|-----------------|------------|------|
| Заміна Soldier (hardware upgrade) | `system_fault` EwsAlert, Tree.state → `:maintenance` | Будь-яка | Зняти/поставити капсулу через Pogo-pin; анкер лишається |
| Дерево загинуло | `bio_status = :deceased`, Tree.state → `:decommissioned` | Фаза 3-4 (зріла) | Decommission in place: зняти капсулу, зрізати фланець, герметизувати |
| Вандалізм / фізичне пошкодження | `vandalism_breach` EwsAlert | Будь-яка | Огляд; за потреби заміна капсули або decommission in place |
| Плановий апгрейд всього кластера | OTA неможливий (зміна hardware) | Будь-яка | Масова заміна капсул (анкери лишаються) |

## 🌐 3. Міжуніверситетська Синергія: ЧІПБ ↔ ЧНУ ФОТІУС ↔ ЧДТУ

### 3.1. Матриця Перетину

| # | Домен | ЧІПБ (08_05) | ЧНУ ФОТІУС (08_02) | ЧДТУ (08_04) | Тип зв'язку |
|---|-------|-------------|---------------------|--------------|-------------|
| **I** | **Параметричне страхування** | Зобенко: QRA, юридичне обґрунтування threshold_value | Порубльов + Онищенко: теорія перколяції (q_c), Monte Carlo (→ стаття 21, 08_03) | Карапетян: Weibull/Pareto збитків, basis risk copula (задачі #41-44) | **Послідовний**: ФОТІУС → q_c → ЧДТУ → актуарна модель → ЧІПБ → QRA + юрид. обґрунтування |
| **II** | **Предиктивна пожежна модель** | Куліца: delta_t → fire_spread_rate, FWI | Косенюк: Kalman Filter delta_t (< 200 байт RAM) | Карапетян: STL декомпозиція delta_t, SARIMA прогноз (задачі #1-2) | **Паралельний**: ФОТІУС фільтрує сигнал → ЧДТУ аналізує тренд → ЧІПБ будує fire model |
| **III** | **SOP + Mesh надійність** | Ротар + Биченко: SOP, ДСНС протоколи | Порубльов: TTL-flood relay надійність G(V,E,P), PANIC_TTL=5 валідація | — | **Комплементарний**: ФОТІУС математично валідує TTL → ЧІПБ визначає SOP на базі цієї надійності |
| **IV** | **Акустична детекція + реагування** | Биченко: dispatch protocol (chainsaw → vandalism_breach; fire_detected — окрема комбінація фактів) | Ярмілко: SPI/DMA TinyML pipeline | Базіло + Бондаренко (ПМКТ): валідація фононної лінзи, калібрувальний датасет | **Послідовний**: ЧДТУ ПМКТ → hardware → ФОТІУС → firmware → ЧІПБ → реагування |
| **V** | **Заміна капсули / decommission in place** | Несен: інструмент заміни капсули + виведення з експлуатації (анкер постійний) | — | — | **Незалежний**: механіко-біологічна задача ЧІПБ, з консультацією ЧНУ біо-хабу (Спрягайло) щодо біоінертності залишених Ti+PEEK |

- Права на комерційну експлуатацію системи (монетизація SCC/SFC)
- Доступ до production API, blockchain ключів та raw production телеметрії
- Права на ліцензування технології або моделей третім сторонам
- AES-256 ключі шифрування (HardwareKey)
