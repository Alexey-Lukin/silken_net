# Промт: Memory Housekeeping (догляд за персистентною пам'яттю)

> **Як використовувати:** встав цей файл (або «виконай `.claude/prompts/memory_housekeeping.md`») коли власник просить упорядкувати / почистити / структурувати персистентну пам'ять (`…/memory/MEMORY.md` + `*.md`). Це **дім** методу; skill `memory-maintenance` лише посилається сюди. Спілкуйся українською. Канонічний **формат** пам'яті (frontmatter, типи user/feedback/project/reference, Why/How-to-apply, `[[name]]`-лінки, один факт = один файл) живе в системному промті — тут його НЕ дублюємо, лише застосовуємо.

---

## 🎯 Місія

Тримати пам'ять **чистою, структурованою й без дублів** — але **БЕЗ АМНЕЗІЇ**. Індекс має бути тонким (гачки), деталь — у файлах; відкриті дії — у трекері (`00_07`), а не лише в пам'яті. Покращувати, а не видаляти цінне.

**Дух роботи (цитати власника, 2026-06-13):**
- «живе цінне не удаляти, краще якісно таке покращити.»
- «повиносити ще сміття з памяті, але акуратно, спокійно і впевнено, **нам не треба амнезії**.»
- «Мені головне щоб **не удалилось те що треба**.»
- «все що ми знаходимо по дорозі що треба робити, **то не губи**.»
- «якщо було щось в памяті що ще **робити, перевіряти** … і його **нема в 00_07** — то краще туди занести.»
- «поструктурувати, повидаляти дуплікацію … **глибоко** досліди, проаналізуй як краще. Дуже уважно.»

> ⚠️ **Залізне правило конфлікту:** коли «прибрати сміття» свариться з «не загубити потрібне» — **перемагає збереження**. Сумніваєшся → лишай. Звітуй чесно, а не вигадуй видалення.

## 🔢 Порядок (по кроках, не поспішаючи)

### 1. Інвентаризація + цілісність (ПЕРЕД будь-якими змінами)
- Список усіх файлів: розмір(байти)/рядки/тип. Знайди **викиди** (один файл у рази більший — кандидат на внутрішнє тоншання, але див. крок 4).
- **1:1 index↔files:** кожен `- [..](file.md)` у `MEMORY.md` → існуючий файл; кожен файл (крім `MEMORY.md`) → має рядок в індексі. **Жодного broken-pointer чи orphan.**
  ```bash
  for fn in $(grep -oE '\]\((\w+)\.md\)' MEMORY.md | tr -d ']()'); do [ -f "$fn" ] || echo "BROKEN: $fn"; done
  for f in *.md; do [ "$f" = MEMORY.md ] && continue; grep -q "($f)" MEMORY.md || echo "ORPHAN: $f"; done
  ```

### 2. Індекс = ТІЛЬКИ гачки
- `MEMORY.md` — один рядок на пам'ять: `- [Title](file.md) — короткий гачок`. Деталь живе у **файлі**.
- Якщо гачок розрісся у стіну тексту (історія/деталь) — це сміття В ІНДЕКСІ. **Перед** тоншанням **переконайся**, що ця деталь реально є у файлі (grep по ключових токенах/раундах), і лише тоді обріж гачок до 1-2 речень + «деталі у файлі». (Прецедент: гачок 7861→786 символів після перевірки, що R6-R12 у файлі.)

### 3. Структура по типу (reorder VERBATIM, нуль-втрата)
- Згрупуй `MEMORY.md`: `## 👤 User` / `## 🛠 Feedback` / `## 📚 Reference` / `## 📦 Project`. Велику секцію (>~15) під-групуй (`### …`).
- Роби **скриптом-reorder** (рядки переставляються байт-у-байт + заголовки), НЕ переписуй гачки руками. Класифікуй за префіксом імені файлу (`user_`/`feedback_`/`reference_`/`project_`).
- **Доведи нуль-втрату:** `diff <(grep '^- \[' BACKUP|sort) <(grep '^- \[' MEMORY.md|sort)` → `IDENTICAL`.

### 4. Прибрати сміття — але verify-before-delete (no amnesia)
- **Сміття** = справді мертве: дубльована-в-індексі деталь, стейл-статус, що вже resolved, editorial-шум. **НЕ сміття** = уроки, рішення, відкриті айтеми, «чому», `[[links]]`, наукова провенанс.
- Тест на видалення: *чи спричинить втрата амнезію (зникне потрібний факт/урок/рішення/відкритий пункт)?* ТАК → лишай. НІ → можна прибрати.
- **Великий історичний файл (campaign-history тощо) — це дім-деталей за дизайном.** Його вага — норма (він поглинає деталь, щоб індекс був тонкий). НЕ потрошити без явної згоди власника; уроки вплетені в механіку — різати ризиковано. Запропонуй конкретну стару секцію на стиснення, не гати весь запис.

### 5. Дублікація (рідкісна, якщо є `[[links]]`)
- Пам'яті мають **посилатися** одна на одну через `[[name]]`, а не повторювати зміст. Реальний дубль зазвичай = **index-vs-file** (крок 2).
- Перевір крос-файл: чи campaign/огляд RESTATE-ить спеціалізовану пам'ять verbatim? Якщо лінкує `[[…]]` — це референс, не дубль. Два РІЗНІ факти однієї категорії (напр. дві DFT-поради) — **не дубль**, не зливай заради косметики.

### 6. Action-items → 00_07 (щоб пережили будь-яке тоншання)
- Пройди проєктні пам'яті на відкриті **to-do / to-check / follow-up / pending / residual / awaiting**.
- Для кожного: чи є воно в `00_07`? (`grep` по темі/ID). Багато вже там (напр. IP→UNI.3, partner→UNI.*, reliability→E.*).
- **Якщо НЕ в 00_07** — додай туди коректним item'ом (правильна §-секція за канон-домом; `section-home` guard вимагає, щоб meta-ref модуля = секція). Потім **встав у пам'ять рядок `Tracked in 00_07: <ID>`** — щоб видно було, що не загубиться.
- Зовнішні треди (партнери/нейминг/рішення) теж лічаться як action-items.

### 7. Стейл-гачки + дрібні правки
- Звір кожен гачок з поточним станом файлу; онови ті, що розійшлися (зроблені задачі, перенумеровані ID).

### 8. Інструментарій і безпека
- Для **точкової заміни довгого рядка** (Edit не зматчить 7000-символьний old_string) — Ruby `File.readlines`/`lines[i]=…`/`File.write`, з `abort unless lines[i].include?("очікуваний-маркер")`. Зроби `cp BACKUP` перед і `diff` після.
- Пам'ять лежить у `~/.claude/projects/…/memory/` — **поза git репо**; коміти не потрібні. Тим уважніше — немає `git revert`, лише твій backup.

## 🧠 Durable-уроки
- **Чистка добре-доглянутої пам'яті = де-bloat + структура + стейл-фікси, НЕ масове видалення.** Так само, як «не вигадуй переноси» у SSOT-кампанії.
- **Verify-before-delete і для пам'яті** (`[[feedback_verify_canon_before_delete]]`): деталь має жити в **ДОСТУПНОМУ домі** (файл/канон-доки/00_07/інша памʼять/код), перш ніж зрізати її з індексу/гачка. ⚠️ **git-історія — НЕ дім** (founder 2026-06-14: «в гіт історію не часто дивляться»): «воно є в git» саме по собі НЕ виправдовує видалення потрібного — потрібне має лишатись там, куди реально дивляться.
- **No-volatile у пам'яті теж** (`[[feedback_no_volatile_counts]]`): гачок не має тримати лічильники, що дрейфують.
- **Verify-before-delete = READ, не лише grep** (SESSION-5, 2026-06-14 — ледь не амнезія). Перед тим як обрізати роздутий гачок, крок 2 каже «переконайся, що деталь є у файлі (grep)» — але **grep дає FALSE-negative** на unicode-токенах (β/ρ, ρ-relative, кирилиця) і на складних `\|`-alternations у `for`-циклі: позначив живі standing-lessons як «HOOK-ONLY», хоча вони були у файлі. Якби я довірився — зрізав би потрібне. **Для CRITICAL-verify читай сам файл** (він малий — дім факту); grep лише для першого наближення, не як остаточний доказ присутності. Якщо обрізаєш дубль-СТАТУС (items-список, що 100% у файлі) — безпечно; якщо чіпаєш lessons/«чому» — READ.
- **Date/shipped/session-чистка по одному файлу: голий stamp ≠ демонстрація** (founder-прохід 2026-06-24). Типовий шум, що осідає в memory = дати-провенанс (`Caught/Learned/established <date>:`), closed-shipped-маркери (`Shipped/Done … <hash> … closed` — git тримає), session-приклади. ⚠️ Але **session-приклад буває ДВОХ видів:** голий date/shipped-stamp = шум (прибрати); **демонстрація-багу/пастки = DURABLE** (parallel-edit `||`-glue, `c275120` bad-commit, `/ready` force_ssl) — вона несе техзнання, видалити = амнезія. Прибирай дату/shipped-обгортку, демонстрацію ЛИШАЙ; дату-В-ПРИКЛАДІ (ілюстрація формату, якого уникати — напр. `# fix (2026-06-06)`) роби generic (`(YYYY-MM-DD)`), не стирай. Founder-gate «не поудаляй лишнього» → SCAN-класифікуй (шум vs durable) і показуй кандидатів ПЕРЕД чисткою, чисти по ОДНОМУ файлу (не batch), `structure_sql`/`zsh_bash_gotchas` = надто щільні, відкласти.
- **Велика merge/консолідація надщільного history-файлу (founder-прохід 2026-06-27): «merge+dedup» ≠ «скоротити»; grep ≠ presence-proof; verify-actual-state.** Надщільний `project_ssot_campaign_history` стиснуто/злито приблизно вдвічі за серію founder-вказівок (per-block ×2/2.5/3 → потім merge-кластери: §Round-handoffs+§Timeline → §Campaign-ledger; 8 module-iters → 1; 5 R22-followups → 1; 16 SESSION-блоків → 1 §Deep-cement). **🔴 (1) «merge + dedup» ≠ «скоротити»** (founder спинив мене серед merge module-iters — я почав компресувати): зливаючи N блоків КОНТЕНТ кожного лишай *verbatim*, схлопуй лише СТРУКТУРУ (N headers → 1 + теги `[S2]`/`[M01]`) + прибирай *справжній* дубль (recurring-уроки → одна «Shared method» нота + `→ §Durable`-pointers). Merge зберігає; компресія = окрема операція з окремою вказівкою. **🔴 (2) grep = FALSE-negative-машина на markdown/unicode → presence-verify ЛИШЕ READ-ом** (re-bit 3× за сесію; розширює SESSION-5 β/ρ/cyrillic-урок на `**bold**`-між-словами (`** **`), backtick навколо токена (`` `_appendix_` ``), «лапки», case `Same`≠`same`): grep-`0` ≠ амнезія — підтверди READ-ом (або grep під-токен БЕЗ спецсимвола) перш ніж вірити що контент зник чи лишився. **🔴 (3) verify АКТУАЛЬНИЙ стан файлу, не памʼять «що нібито зробив»** — SESSION-14+15 пропустилися в ранній партії, яку я вважав done; `wc -w` рядка викрив їх повними, founder спіймав → перед «готово» перечитай/перевір ціль. **🔴 (4) big-file playbook:** (a) cross-cutting-уроки → read-first `§Durable` ПЕРШ (anti-amnesia), тоді трим/merge; (b) Ruby span-replace межами по УНІКАЛЬНОМУ маркері (НЕ `[[link]]`/спільний токен, що зустрічається раніше — presence-guard тоді коректно abort-нув і врятував від не-того-span) + `cp`-backup + post-verify set-diff guard-імен/distinctive-токенів; (c) leading-`\n` glue-bug кусає на row-removal → boundary-grep ПІСЛЯ кожної структурної правки (спіймав злиття `01_03).### Iter-4`); (d) зберігай round→guard provenance (§Guard-set на нього вказує); (e) format-residue після merge = orphan `^>$` + no-blank-before-`#` → scan+fix наприкінці.
- **Founder-мандат «скоротити / там є сміття» (НЕ merge) → багато-прохідне ТОЧКОВЕ де-блоут за критерієм «не-інформації» (founder-прохід 2026-06-27, той самий `project_ssot_campaign_history` далі → −49% сукупно за ~5 проходів).** Доповнює р.83 (там «merge≠скоротити»; тут founder ЯВНО хоче скоротити): 🔴 (1) **founder «ще є сміття» ПІСЛЯ твого «mostly clean / це межа» = валідний сигнал, не похибка** (5× за сесію — його ж «все ідеально = підозріло», обернене на тебе); не захищай попередній прохід, шукай ІНШИЙ зріз. 🔴 (2) **НЕ пропорційно** (founder: «пропорційно не удаляй») — рівномірний телеграф КОЖНОГО рядка = ПОМИЛКА (founder спинив); ріж ТОЧКОВО: 0 у щільному (§Durable-уроки/guards), багато де густо води. 🔴 (3) **«не-інформація» — калібруй на РЕАЛЬНИХ зразках З ФАЙЛУ** (founder має чіткий критерій у голові; абстрактне питання марне, multiselect зі зразками-рядками — влучний): клас = мета-наратив про мій процес (`didn't trust ✅` / `flag too HARSH` / `instinct WRONG`) · одноразові tooling-трюки (grep-механіка) · routine finding-переліки чий ДІМ деінде (00_07 §🗄️ / canon) · повторні мантри (дублі §Durable) + голі metrics.
