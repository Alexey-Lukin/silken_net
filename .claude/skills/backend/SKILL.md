## Gotchas Not Obvious From Docs

1. **RBAC prefix** — `enum :role, {investor, forester, admin, super_admin}, prefix: true` → `role_admin?`, НЕ `admin?`; ролі «patrol» НЕ існує. Authz = boolean-OR іменованих ролей, не числовий ранг, і ВСІ предикати живуть у моделі: `User#forest_commander?` · `#admin_or_above?` · `#super_admin?` · `#access_level`. ⚠️ Формула «admin ∪ super_admin» має ОДИН дім — `User#admin_or_above?` (з 2026-07-31); доти вона стояла пʼятьма копіями, і греп за цілим виразом бачив лише три — форми з отримувачем між операндами (`user&.role_admin? || user&.role_super_admin?`) він пропускає. Не плодь шосту: `authorize_admin!`, `ApplicationPolicy` і роле-фільтри компонентів кличуть саме її. ⚠️ НЕ плутай з `#organization_admin?` (`role_admin? && organization_id`) — super_admin під неї НЕ підпадає. Той самий prefix-патерн на всіх enum'ах (`status_resolved?`, `action_type_repair?`; `oracle_status_*` → CLAUDE §6).
2. **IDOR sibling-guard** — write-ендпоінт із клієнтським FK ЗОБОВ'ЯЗАНИЙ звірити його проти **`acting_organization!`** (НЕ `current_user.organization` — див. #19): існуючий-але-чужий → 404 (`RecordNotFound`), відсутній → fall-through у модельну 422. Зразки: `ProvisioningController#register` (cluster_id), `MaintenanceRecordsController#verify_maintainable_within_organization!`. Новий ендпоінт — дзеркаль їх. 🔴 **FK з ТІЛА запиту — окремий підклас, і всі наші сторожі до нього сліпі за побудовою** (гейти дивляться на `:id`-маршрут та імʼя стріму). Єдиний відомий порушник — `Codex::CitationsController` — закритий [SEC.26] 2026-07-30, але шукай цю форму в кожному новому write-ендпоінті: `authorize` над КЛАСОМ нічого не каже про ціль. 🔴 **І форма фіксу тут інша, ніж у зразків вище — знай обидві.** Зразки резолвлять ціль, ТОДІ звіряють (`return if target.nil?` → 422, чужий → 404): це навмисно розрізняє «нема» і «чуже». Де такого розрізнення не треба, дешевше **скоупити сам резолвер** — мапа citable-типів віддає `org.trees`/`org.clusters`/`AiInsight.for_organization(org)`, і `find` по ній гасить existence-oracle побічним ефектом форми, без другої перевірки. 🔴 **Для DELETE вісь може бути НЕ ціллю:** у цитат це **автор** (`created_by_user_id`, NOT NULL), бо ціль знищується без FK-каскаду, і скоуп по ній зробив би осиротілий запис невидалимим — мітигація вдарила б по власнику, не по атакеру. Гард ставиться **перед** `authorize` (404, не 403). Канон — [`04_05`](../../../docs/04_05_Codex_Lore_Module.md) ADR-CDX-11.
3. **M2M-токен = повний org-admin scope** — `m2m_auth#create` видає `api_access` першого org-admin'а будь-якому Ed25519-довівшому пристрою; звуження = відкритий SEC.16 (`00_07`). Replay-guard = Redis `SET NX` на `SHA256(sig)`, TTL 600 c, + SolidCache-fallback при Redis-down.
4. **`session[:ps]` salt-stamp (SEC.16)** — `establish_session` (ЄДИНА точка логіну, обидва шляхи) ставить `password_salt.last(10)`; `authenticate_user!` звіряє; `change_password` оновлює ЛИШЕ ініціатора (guard `session[:user_id]==current_user.id`) + `destroy_all` інших Session. Крадений cookie гасне на password-change. 🔴 **Звіряльників ТРИ, не два — третій поза `BaseController`** (SEC.25 Ф1, 2026-07-28): `ApplicationCable::Connection#connect` читає ту саму сесію (`cookies.encrypted[session_options[:key]]`, ключі РЯДКОВІ — серіалізатор `:json`) і робить ту саму звірку, щоб зміна пароля гасила й відкритий WebSocket, а не лише HTTP-сесію. ⚠️ **Третій — `LocalesController#remember_choice_for_signed_in_user`**: він успадковує `ApplicationController` (СЕСТРУ, не предка `BaseController`), тож `current_user` там немає й звірка написана власною копією. **Міняєш форму стемпа — міняй усі ТРИ** (`base_controller` · `locales_controller` · `application_cable/connection`): розходження означає, що один шлях переживає ревокацію, яку інший уже застосував. Джерело переліку — `rg -n password_salt app/` із відсіюванням прози, не пам'ять. ⚠️ І знай наявну крихкість, перш ніж «оптимізувати» порівняння: `password_salt` віддає `nil` без `password_digest`, а `nil.to_s.last(10)` = `""`, тож для користувача без пароля обидва боки згортаються в порожній рядок і перевірка істинна — fail-OPEN, симетричний в обох місцях, сьогодні недосяжний (сесія вимагає логіну паролем) → `00_07` SEC.16.
5. **Webhook-HMAC fail-closed патерн** (`oracle_callbacks` / `helium_sos`) — skip auth → HMAC-SHA256 над **raw body** (`X-Chainlink-Signature` / `X-Helium-Signature`); секрет відсутній у `production?` АБО `WEB3_STRICT_MODE=="true"` → **raise SecurityError** (dev/test = warn-bypass). Новий inbound-webhook — клонуй цей патерн, не Bearer.
6. **Idempotency-Key** на `POST actuators/:id/execute`: JSON без ключа → **400** (НЕ 422); pending-команда → 409 — **крім override** (`STOP`/`EMERGENCY_*`, [ARCH.58]: інакше оператор не подасть аварійну зупинку саме тоді, коли в черзі щось є); cache-write їде `rack.response_finished` (Puma 7+) — вужча лямбда-сигнатура мовчки скипає запис.
7. **DID не приходить від клієнта** — provisioning деривує його з 24-hex silicon UID (murmur3-fmix32, FW.54). `Tree::DID_FORMAT` = `SNET-XXXXXXXX`, Gateway = `SNET-Q-XXXXXXXX`; `tree.peaq_did` = зовнішній `did:peaq:0x…` (пише `PeaqRegistrationWorker`, модельної format-валідації НЕМА).
8. **HardwareKey: довжина за ТИПОМ ВЛАСНИКА** (`detect_owner_kind` — колонки device_type нема): 32 hex = AES-128 Tree-LoRa · 64 hex = AES-256 Gateway-CoAP. HKDF-SHA256 info-strings (точні): `"silken-aes-128-lora-key"` · `"silken-aes-256-device-key"` · `"silken-aes-128-broadcast-key"` (KEYB) · `"silken-ed25519-iotex-v1"`; без `PROVISIONING_MASTER_KEY` → `SecurityError` (fail-closed).
9. **Dual-Key Grace** — `previous_aes_key_hex` живе до першого uplink'а на новому ключі (`clear_grace_period!`); `rotate!` при живому grace → `RotationPendingError`. Tree-ротація = FW.17 ratchet за ENV `FW17_RATCHET_DOWNLINK_ENABLED` (default OFF); Gateway = random + ФІЗИЧНИЙ re-provision (key-downlink'а не існує).
10. **`Gateway#online?` динамічний** — `last_seen_at >= (config_sleep_interval_s * 1.2).seconds.ago`, жодного фіксованого порогу; SQL-двійник `scope :online` через `make_interval`. Міняєш логіку — міняй обидва.
11. **Партиційні моделі декларують `self.primary_key = "id"`** (`TelemetryLog`/`GatewayTelemetryLog`/`BlockchainTransaction`) — інакше `.id` повертає масив. Тримається на ВСІХ партиційних моделях, вкл. `Codex::Match` (був єдиним холдаутом із композитним AR-PK — вирівняно ARCH.56; DB-PK лишається композитним `(id, created_at)`, це вимога Postgres і її НЕ треба «виправляти»).
12. **Auditable [ARCH.57]** — хук = `after_update_commit if: :saved_change_to_X?`, НІКОЛИ AASM `after_all_transitions` (файрить ДО персистенції + сліпий до raw `update!` — обґрунтування `04_01 §7`). Wire-sites (число НЕ фіксуємо — дрейфує; джерело = `rg -n 'record_audit_trail!' app` **мінус проза** — `-l` дає на два файли більше за сайти: сам concern і `organizations_controller`, де слово стоїть у коментарі про те, ЧОМУ там натомість синхронний `AuditLog.create!`): User-role · NaasContract · ActuatorCommand · SystemParameter · HardwareKeyService · BlockchainBurningService · **Organization** (`stream_epoch_rotated` — відкликання виданих імен Turbo-стрімів, [SEC.25 Ф3]). Без актора → WARN-skip (дію не валимо, але й сліду нема — ops-рецепт мусить створити `oracle_executioner`); `archive: false` default (chain-only).
13. **FactoryBot reuse-ідіома** — `Tree.after_create` авто-створює wallet + device_calibration (has_one) → фабрики реюзають через `initialize_with`; фабрика, що create-ить другий запис, б'ється об unique-index (ARCH.56).
14. **`EwsAlert#message` — це РЕНДЕР, а не колонка** (I18N.1, 2026-07-26). У БД лежать `message_key` + `message_params` (jsonb); колонки `message` НЕМА, метод збирає фразу з `alerts.messages.*` у момент показу (fail-open на невідомий ключ, `nil` за порожнього; presence-валідація сидить на `message_key`). Писати алерт — лише ключем: `EwsAlert.create!(… message_key:, message_params:)` / `escalate_field_audit!(cluster:, message_key:, message_params:)`. 🔴 Два правила, кожне куплене багом: **параметр несе ВИМІР, ніколи фрагмент фрази** (інакше локалізована рамка дістає незмінну середину — «Slashing blocked (дерево SNET-…)» англійцю), і **умовний фрагмент усередині рядка стає ДРУГИМ КЛЮЧЕМ, а не булевим параметром** (в іншій мові він може стояти в іншому місці речення). Свідомий виняток — сирий текст ЧУЖОГО виключення (`%{error}`): він не локалізується жодною схемою. 🔴 І найгостріше: **не дедуплікуй алерти по тексту** — `treasury/monitor_service` робив `where("message LIKE …")`, тобто фраза була ключем; такий запит ламається ТИХО (перестає знаходити → алерт сипле щоцикла). Дедуп іде по `message_key` + `message_params ->> '…'`.
15. **MaintenanceRecord Evidence Protocol** — фото обов'язкові ЛИШЕ для `repair`+`installation` (`skip_photo_validation: true` = системні записи); `biomass_extraction` вимагає `biomass_yield_kg > 0` → `EcosystemHealingWorker` (**async** `after_create_commit`, черга critical, НЕ inline) → `declare_deceased!` + `PuroEarthPassportWorker` (після commit; необоротний on-chain CORC). Статус дерева removed/deceased далі тригерить слешинг (money → `web3-pipeline`). Мутації запису = автор-або-admin, і дім цього правила — **`MaintenanceRecord#mutable_by?(actor)`** (не приватний метод контролера, як було): його читають ОБИДВА гарди й компонент, тож копії формули не існує. ⚠️ Предикат про організацію мовчить свідомо — приналежність тримає асоціативний скоуп у викликача, тобто запис МУСИТЬ приїхати з org-скоупленого запиту. 🔴 **Шляхів мутації ДВА, і другий — вкладений `maintenance_record_photos#destroy`**: він мутує той самий запис (видаляє фотодокази `purge_later` — незворотно й поза `Auditable`, [SEC.28]), і гарда автора не мав зовсім, бо коміт, що закрив «Forester #2 within the same org» на `edit`/`update`/`verify`, до нього не дійшов. Рефлекс ширший за цей випадок: **питай не «чи гардований цей контролер», а «хто ще мутує цей ЗАПИС» — і відповідь шукай у вкладених `resources`, не у файлі, який правиш.** Ranger-економіка → `00_07` E.20 (deferred Phase 2).

16. **Актуатор у стані `active` мовчки вбиває нові накази** [ARCH.58]. `ActuatorCommand#dispatch_to_edge!` (`after_commit on: :create`) кличе `actuator.ready_for_deployment?`, а той вимагає `idle?` → команда стає `failed` через `update_columns` (повз AASM), і **API вже віддав `202 accepted`**. Три наслідки, кожен куплений багом: (а) `create!` на активному актуаторі в спеці — це не «команда в черзі», а труп, тож фікстури мусять народжуватись, доки актуатор ще `idle`; (б) аварійний `STOP` тому був неможливий за конструкцією — тепер `priority_override?` минає і цей гейт, і 409-гард контролера, а деривація «це override?» живе ОДНОГО разу в `ActuatorCommand.override_payload?`; (в) гейт стереже лише МОМЕНТ СТВОРЕННЯ, тож живий pending опиняється на активному актуаторі щонайменше чотирма шляхами, і лише один із них — обхід колбеків: `insert_all` аварійного `EmergencyResponseService`; override від оператора; власний STOP sweep'а; **і звичайна людська команда, створена на ще-idle актуаторі** — її не активує ніхто, а `by_priority` (`priority DESC`) пропускає поперед неї EWS-чанки, які актуатор і вмикають. Похідне правило: питай «у якому СТАНІ рядок може опинитись», а не «яким шляхом його створили». Ширше: сам гейт — артефакт push-ери; під poll-семантикою [FW.60] наказ просто чекає в `.pending`, а строк життя дає `expires_at` (якого команда від контролера НЕ отримує).

17. **`insert_all` може створити рядок, який НЕ ВМІЄ ПОМЕРТИ** [ARCH.75]. Він обходить валідації, тож у БД лягає запис, що не проходить власну модель — і далі **кожен** шлях через `save`/`save!` (AASM-подія, `update!`, навіть `fail!`-перехід «прибрати сміття») кидає `RecordInvalid`. Рядок не можна ні провести далі, ні термінувати; TTL-прибирання теж не працює, бо воно теж перехід. Реальна ціна тут: `EmergencyResponseService` ріже тривалість за власною константою й не питає `actuator.max_active_duration_s` (сіди: клапан 300 с, сирена 120 с проти чанків по 3600) — і **одна пожежна тривога назавжди вбивала весь downlink-poll шлюза**: coap-демон виняток ловить (`rescue StandardError`) і йде далі, але `reply` лишається непризначеним — `socket.send` не відбувається, тож разом із CMD мертві ratchet, OTA-hint і time-sync. Два рефлекси: (а) пишеш `insert_all` — сам відповідай за інваріанти, які модель більше не перевіряє (особливо ті, що залежать від ІНШОГО запису, як safety envelope); (б) виносити такий рядок можна лише `update_columns`, і ARCH.57-ланцюг тоді закривається ручним викликом — так само, як це робить `dispatch_to_edge!`, хоч у нього причина інша (він обходить валідації, щоб не крутити колбеки, а не тому, що рядок непersистовний).

18. **A cached per-tenant value needs the org in the KEY, not only in the query — and the key is the half that gets forgotten** [SEC.16, 2026-07-28]. `BaseController#ews_alert_count_cached` feeds the sidebar's «Threat Alerts» badge, i.e. it renders on **every** dashboard page — the most widely distributed tenant fact in the app. It ran `EwsAlert.unresolved.count` under the global key `"ews_alert_count_unresolved"`, so every authenticated viewer of every org saw the whole platform's unresolved count (measured: own 1, badge 4). 🔴 The two halves are **independent defects with independent mutations**: with a scoped query under a shared key, whoever warms the cache serves their number to everyone else for the TTL. So when you add a cached helper here, scope both, and write the example so it calls org A *before* org B — a key collision is invisible until something is already cached. ⚠️ And the spec that hid this for as long as it existed stubbed `EwsAlert.unresolved` and asserted the stub's own value: a tautology in which the missing scope could not be expressed at all. Nil-org returns 0, never a global sum (fail-closed, and aligned with the acting-organization contract that shipped later — `04_03 §3.1`).

26. 🔴 **`error` (однина) і `errors` (множина) — це ДВА різні контракти, і ключ відповіді сам називає, яка гілка відповіла** [TEST.10, 2026-08-03]. `render_validation_error(record)` віддає `{ errors: [ …full_messages ] }` — **масив**, лише для провалу валідації моделі. Явні guard-гілки контролера (невалідний UID, зайнятий UID, чужий `cluster_id`) віддають `{ error: "…" }` — **рядок**. Тобто ключ = безкоштовний дискримінатор гілки, і саме тому `json["errors"] || json["error"]` у спеці — не «зручний хедж», а **знищення єдиного сигналу**: приклад провізії з назвою «missing family» місяцями падав на UID-guard'і й ніхто цього не бачив (фікстура давала 11 символів проти `DidDerivation::UID_HEX_FORMAT` на 24 hex). **Пиши пін на ТОЧНИЙ ключ і додай `not_to have_key` на сусідній** — тоді два приклади стають взаємними мутаціями й гілку не переплутати. Ширше: сама лише перевірка статусу тут не дискримінує, бо обидві гілки віддають `422`.
