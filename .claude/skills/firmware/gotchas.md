1. **Shared peripheral, per-operation reconfig: restore the baseline — and make sure a baseline EXISTS.** Named instance: Queen MUST call `Restore_ECB_Mode()` after every CBC operation, else subsequent LoRa decrypts silently fail (wrong KeySize + wrong key in CRYP). The class is wider than CRYP — it has bitten in **three different shapes**, and the breakage always lands on the NEXT user of the peripheral, never on the caller who reconfigured. Check all three whenever a peripheral has more than one caller (CRYP · Radio · SPI1 · ADC · DMA):
   - **(a) configured, never returned** — the original SEC.8/FW.16 ECB↔CBC, plus CCM width-units (`MX_CRYP_Restore_From_CCM` puts the width-units back to WORD and re-runs `MX_CRYP_Init` — DataType 32B + ambient key; gotcha 7.1). ⊕ The silicon self-test is a caller too (2026-09-28): `Ccm_Run_Self_Test` left BYTE width-units and dangling B0/Header behind, so the sym KAT that runs next in POST measured a config the shipping path never uses. It now cleans up after itself, POST re-runs `MX_CRYP_Init()` between the two, and `test_ccm_selftest.c` pins the hygiene. CRYP-specific home: `03_05 §7`.
   - **(b) nothing to restore TO** — ✅ **closed 2026-09-11 [FW.61]**, and the shape is worth keeping because it is the one a restore-reflex cannot reach. Baseline LoRa modulation used to be set by **no call at all**, so the peripheral carried whatever the last writer left. `RadioInit` is not a baseline: it programs timers/IRQ and `SUBGRF_SetTxParams(RFO_LP, 0, …)` — the **low-power PA at 0 dBm** — while SF/BW/CR/preamble/CRC stay unwritten, and `SubgRf.RxContinuous` stays `false`, which silently turns the Queen's always-on listener into RX-single. **A driver default is not a baseline; only an explicit call is.** ⊕ **Completeness of a baseline is judged by the list of what a FOREIGN mode can change, not by the argument list of the restoring call** (FW.61, 2026-09-11): the sync word is an argument of neither TX- nor RX-config, so no check of the call form names it — yet the LoRaWAN detour writes the public word 0x3444 via `SetPublicNetwork(true)`, and `RadioSetModem` rewrites it only when `Current != Previous`, which `Radio.Init` leaves equal. Same class, second instance on the same detour: the MAC re-binds the driver's single events pointer, so the return path re-binds it with `Radio.Init(&radio_events)` before anything else (`02_05 §6.1` Hard Rule, step 3). The doc home of the NUMBERS is `03_05 §2.1` (`00_06 §2.3` registry); the compiler's declared MIRROR is `firmware/common/lora_phy.h` (pure profile) + `lora_phy_apply.h` (`Lora_Phy_Apply_Sync_Word` · `Lora_Phy_Apply_Tx/Rx` — the single seam both firmwares and `make -C firmware/test lora_phy` call). ⚠️ The two setters share ONE pair of driver structs, but TX-before-RX is a convention; the ONE load-bearing order is `Lora_Phy_Apply_Sync_Word()` FIRST (boot and after the LoRaWAN detour) — it calls SetModem inside and restores what the detour left in the register (why → the header of `lora_phy_apply.h`). `RadioSend` rewrites payload length per frame.
   - **(c) a partial restore reads as a complete one** — ✅ **closed by construction in the same pass, and that is the point**: the panic-TX restore used to re-set ONE of six `SetTxConfig` arguments (preamble) and pass a private `LORA_PANIC_*` quartet for the rest, correct only because that quartet happened to equal canon. Those defines are gone; PANIC now differs from baseline in exactly one argument, because there is only one place the other twelve are written. **Whenever you see a "restore" that names fewer arguments than the call it undoes, the fix is not to widen the restore but to remove the second copy of the defaults.** ⚖️ **A gate on «does every call site use the shared constants» was measured and REFUSED** (FW.61, 2026-09-11): the class has 4 instances, and `00_05 §5` says treat instances; the carrier is that no second defaults set exists in the tree any more (`LORA_PANIC_*` removed). Price, said aloud: a new private set of defaults handed to a bare `Radio.SetTxConfig` in a `main.c` would redden nothing — the `lora_phy` lane scans `main.c` only for a bare `Radio.Send(`. ⊕ **2026-09-24 the seam grew a second variable argument, and it is a different kind** (⚖️ FW.61): TX power became a per-ROLE constant (`LORA_PHY_TX_POWER_DBM_SOLDIER` 14 ⊥ `_QUEEN` 10 — the Queen's ERP ceiling with her 5-dBi antenna), passed like `rx_continuous`. 🔴 Both constants are `int8_t`, so a Queen call site handed the Soldier's constant compiles clean: the `_Static_assert` in `lora_phy.h` judges the VALUE of `_QUEEN`, never WHICH constant a call site picks, and the host pin judges the seam's form, not `main.c` (a declared blindness, gate deliberately not built — the class is small, `00_05 §5`; the other declared blindness of the same pin, `fixLen`⟷`payloadLen` neighbour zeros, is declared in `test_lora_phy.c` itself). A new `Lora_Phy_Apply_Tx` caller — read its role off the file it sits in, and grep `TX_POWER_DBM_` in the diff before you push. ⊕ **The PA has a SECOND path the seam never sees — the LoRaWAN MAC** (ARCH.34, 2026-10-10): the Queen's Helium detour does not call `Lora_Phy_Apply_Tx` at all; LoRaMac computes the conducted power itself as `floor(MaxEIRP − 2·index − AntennaGain)` from REGION defaults (16.0 EIRP, 2.15 dBi), so at its index 0 it would have flown +13 dBm conducted — ERP 15.85 dBm with the real 5-dBi antenna, past the NKEK ceiling itself — while every assert stayed green — the assert judges `_QUEEN`, and nothing read the MAC. `helium_mac.c` now hands the MAC the real gain in BOTH MIB slots (an OTAA join resets the live slot from the DEFAULT one — set only the live one and the join silently restores 2.15) and derives the index from `LORA_PHY_TX_POWER_DBM_QUEEN`; the pin is the stub radio's `SetTxConfig` in `make -C firmware/test helium_mac_smoke`, i.e. the power the MAC actually hands the driver, not a constant. Before trusting «the power is pinned», ask which stacks write `SetTxConfig` — a vendored MAC is a writer too, and `SetTxContinuousWave` is a third path: its certification package (FPort 224, on by default in EU868) takes power straight from a downlink, so the detour switches that port off.

1c. **Retransmit is UPLINK-only — the downlink poll has none, so a lost 2.05 is recovered only by the `cmd=` echo cursor, never by a CoAP retry (FW.63).** `Flush_Cache_To_Rails` increments `coap_mid` ONCE and retries the same PDU inside `for (retry < COAP_MAX_RETRIES)` — a genuine same-MID CON retransmit. `Queen_Poll_Downlink` does the opposite: `coap_mid++` on **every** attempt and `return`s on an empty reply, and `Sim7070_Udp_Fetch` is a one-shot `CAOPEN→CASEND→CADATAIND→CARECV→CACLOSE` with no internal retry. So a lost 2.05 on the downlink poll is **never re-requested** at the CoAP layer; the order survives only because the `cmd=` echo re-serves it (below). Rails' `CoapGate::REPLY_CACHE` is real but only dedups a *duplicated datagram*. ⚠️ **No retransmit does not make the MID cache safe:** `coap_mid` lives in the Queen's RAM and the cache slot has no TTL, so after a reboot the same number can arrive carrying a DIFFERENT question (since FW.60 the MID restarts from HRNG, so the collision is chance, not rule — and every request also carries a fresh nonce `n=`). Serving the cache there answers someone else's poll and silently swallows the live pending command. Today `CoapGate::REPLY_CACHE` is keyed on a request FINGERPRINT (route + query): match → `poll_duplicate`, mismatch → `poll_mid_collision` + fresh derivation. The transferable half: **a cache keyed on a counter that its writer resets is keyed on nothing** — ask what zeroes the key, not just what increments it. Two reflexes: (a) **never generalise one CoAP tract's reliability onto the other** — that is exactly how the false claim entered three docs and two code comments; (b) the OTA leg shows the correct shape — a LOST reply leaves `g_ota_fetch_next_ch` standing, and a REJECTED package (transit CRC) no longer stalls the campaign: every conversation takes the next MISSING package from the cursor, wrapping around (`Ota_Fetch_Next_Missing`, `firmware/queen/ota_window.h`), a completed body is never re-fetched (a body package after completion is a duplicate, not a new campaign — only a changed `fw` in the hint dawns one), delivery is declared when the assembly is COMPLETE (body + full trailer) AND belongs to the campaign being fetched (the hint dawn binds it — `Ota_Campaign_Delivered`), never when the window is live, and a 4.xx reply clears `g_ota_fetch_pending` (FW.60, ⚖️ delegated 2026-10-09, `03_02 §4а`); CMD's equivalent cursor is the `cmd=<token>` echo (below). ⚠️ **CMD's cursor is the echo:** Rails does only `dispatch!` at build time; `acknowledge!` waits for `observe_delivered_command!` to see a `cmd=<token>` echo from Queen (`g_last_acked_cmd_token`, mirroring `fw=`) on a later poll, so a lost 2.05 now re-serves the same envelope instead of losing the order — `Cmd_Dedup_Check` makes the redelivery safe. Design-justification (why echo over blind re-delivery or a documented open-loop) → `03_02 §4а`; state and chronicle → `00_07` FW.63. ⚠️ **And the echoed token is the LAST colon-field, never «the 3rd colon» (FW.60, 2026-09-10):** an `ACTION:value` payload shifted the old window onto ACTUATOR_ID, so the echo never matched `idempotency_token` and an EXECUTED command died by TTL as `failed` — the dedup hash stayed self-consistent, which is exactly why nothing noticed. Locator = pure header `firmware/queen/cmd_token.h` (host-pinned, mutation-verified); Rails forbids a colon in ACTION (`ActuatorCommand::ALLOWED_PAYLOAD_FORMAT`), so both ends agree by construction — do not reintroduce a colon-counting parser.

3. **`Load_AES_Key()` must run BEFORE `MX_CRYP_Init()` — reversed, CRYP silently uses a zeroed key.** Both files follow this order but it's easy to break during refactoring. ⊕ Precisely: the LAST `MX_CRYP_Init()` before any field crypto must follow the key load — the `CCM_SELFTEST` build runs the POST with one `MX_CRYP_Init()` BEFORE the keys (FW.69, 2026-10-09: the KATs set their own keys, and `Load_AES_Key` on an empty key page resets the board), then re-inits after `Load_*`.
4. **Cold-TX deferral: at low temperature the Soldier skips TX entirely, so never assume every wake cycle emits a packet** — the FW.10 winter ESR guard against brownout (its Vcap half is degenerate in the field — gotcha 9). ⊕ One exception, by delegated verdict (2026-10-10, `03_01 §1.8а`): the CCM temperature sentinel `ADC_TEMP_UNMEASURED_C` (−128, an ADC failure) TRANSMITS — the Vcap half is always true on the VDDA rail (gotcha 9), so the conjunction would otherwise silence exactly the frame that reports a failed temperature read.
5. **StatusByte layout is post-FW.29 — `[PanicFlag:1 | Status:2 | GrowthPoints:5]`, and status 3 means vm_error, never tamper** — packet byte 10 = `[PanicFlag:1 (bit7) | Status:2 (bits6..5) | GrowthPoints:5 (bits4..0)]`; firmware packs `(status << 5) | growth_points`, backend unpacks `(byte & 0x1F) * 2`. `Status` now has 4 values (0 homeostasis / 1 stress / 2 anomaly / 3 **vm_error** — [SLASH-1 P0, 2026-07-05] status=3 is written ONLY by `BIO_STATUS_VM_ERROR`; mruby `pack_status_byte` returns 0..2; physical tamper rides PANIC_FLAG, NOT the status bits — backend side → #10). Normal frames force bit7=0 (`lora_payload[10] &= ~PANIC_FLAG_BIT`); panic frames set it. Canon: `03_04 §4.4` Status-byte + `03_01 §8`.

A new writer (a debug setter, a direct `HAL_RTC_SetTime`) goes through it; gossip writes the calendar not at all. ⚠️ The carrier is a grep in the `soldier` target of `firmware/test/Makefile`: it reds unless `main.c` calls the function exactly once with the same state and the verbatim seam, on any other writer of the `delta_t` base, on any `Wall_Calendar_Set(` call or call through the seam, on DST/SynchroShift/SmoothCalib/LL_RTC/`RTC->TR|DR` writers, and on `HAL_RTC_Set*` beyond two outside comment lines. It is a carrier against ACCIDENTAL regression, not a boundary against a deliberate edit: a call inside another function or under `#if 0`, and a writer outside `main.c` (a CubeMX `MX_RTC_Init` that sets the time), it does not see.

17. **A mutation probe on the host lane can run the PREVIOUS binary, because make judges MTIME and not CONTENT — so force the target with `make -C firmware/test -B <target>`** [HW.31, 2026-09-26; widened HW.16, 2026-10-01]. 23. **A power mode or HAL call taken from an app note, a forum or another STM32 family may not exist on WL — and a grep of the vendored tree can still hit its name** [FW.54, 2026-10-05]. ⊕ The same holds for a CONSTANT: `ADC_VREFINT_CAL_MV` stood at 3000 — the L4/G4 calibration voltage — while WL calibrates `VREFINT_CAL` at Vref+ = 3.3 V (`VREFINT_CAL_VREF` in the vendored `stm32wlxx_ll_adc.h`), so every VDDA read came out ~9 % low (FW.50, 2026-10-10); now a `_Static_assert` in `firmware/soldier/main.c` ties ours to the vendor's. The canon carried «STOP2 RTC-only 300 nA» (via a `PWR_CR1` bit `RRSTP`) as a ratified scenario input until the primary source refuted it: WL has neither `STOP2_RTC_ONLY` nor `RRSTP`, and SRAM2 retention (`PWR_CR3` `RRS`) acts only in Standby (`03_01 §1.10`). The L4 name `HAL_PWREx_DisableSRAM2ContentRetention` even appears in `firmware/extern/stm32wlxx-hal-driver/Inc/Legacy/stm32_hal_legacy.h` (an older macro aliased to it), while WL's `firmware/extern/stm32wlxx-hal-driver/Inc/stm32wlxx_hal_pwr_ex.h` declares `HAL_PWREx_EnableSRAMRetention` / `HAL_PWREx_DisableSRAMRetention` and no `…SRAM2ContentRetention`. **Reflex: before writing a HAL call or citing a mode, find the DECLARATION in the vendored `stm32wlxx_hal_*.h` headers (or the bit in `firmware/extern/cmsis-device-wl/Include/stm32wle5xx.h`) and the current in DS13105 — a name hit in `Legacy/` proves nothing — then build the gated branch on `hal_check_ccm` (gotcha 13).** ⊕ **The opposite trap is quieter — the name EXISTS on WL and compiles, but MEANS something else** [FW.46, 2026-10-09]: the Soldier armed its brownout reflex (ARCH.21) with `PWR_PVDLEVEL_7` under the comment «Поріг 2.2V», and every lane stayed green for months. On WL (as on L4) level 7 is not a threshold at all — `stm32wlxx_hal_pwr.h` calls it «External input analog voltage (compared internally to VREFINT)», DS13105 lists only VPVD0..VPVD6 and gives no WLE5 pin a PVD_IN function; 2.2 V is VPVD1 = `PWR_PVDLEVEL_1`. A compiler cannot catch this class, and neither can the declaration-check above: **read the doc comment of the CONSTANT next to its `#define`, and match the value to the DS13105 table, not to the comment beside the call.** Found by writing the real body (the mini image), not by reading the call — the same pass found the cycle reading two ADC channels with no channel selection.

24. **On the cycle the radio sleeps in ONE place — the first statement of Phase 5 (`phase5_kenosis:`; the PVD callback is the only other site) — and every path into low power must pass it; a `goto` past it or a TX after it leaves the radio in STDBY_RC, 0.7 mA against 140 nA of sleep, and `Set_Sleep` is accepted only from Standby, so a live receiver ignores it** [FW.54 · FW.10 · FW.27-B, 2026-10-07]. Found the hard way: the frost `goto phase5_kenosis` (FW.10), the low-vcap skip of the Phase 4.5 listen block and the FW.27-B OTA re-request TX all reached STOP2/Standby with the radio awake (DS13105 Rev 12, Table 28: Standby with RC 13 MHz — 0.7 mA · Sleep warm start — 140 nA · cold start — 50 nA), while a code comment claimed «Далі Фаза 5 гасить радіо» and Phase 5 had no radio call at all. The RX window is only a software timer — `RxTimeout` is NULL on the Soldier and the hardware timeout is ≈ 65 s — and `Set_Sleep` is accepted ONLY in Standby (RM0461 Rev 11 §4.8.3; `SUBGRF_SetSleep` does not standby first), so the receiver is stopped explicitly with `Radio.Standby()` at the end of the window and before the PVD sleep; before that fix the normal path most likely slept with the receiver live (4.82 mA). The carrier is mechanical: `make -C firmware/test standby_wake` requires `Radio.Standby();` after any `Radio.Rx(` / `Radio.StartCad(` before the label, `Radio.Sleep();` as the first statement after it, no `Radio.*` / `Lora_Phy_*` call until the STOP2 entry in either branch, and `Radio.Standby();` → `Radio.Sleep();` in the PVD callback. ⚠️ Its ceiling: it reads text, so a radio call inside another function — or a late radio IRQ after the sleep (every HAL SUBGHZ command — the IRQ status read included — runs `SUBGHZ_CheckDeviceReady` in `firmware/extern/stm32wlxx-hal-driver/Src/stm32wlxx_hal_subghz.c`, which pulses NSS and wakes a sleeping radio, and `radio.c` answers `IRQ_RX_DONE` / `IRQ_HEADER_ERROR` / `IRQ_CRC_ERROR` with `SetStandby(STDBY_RC)`; dormant until the radio IRQ glue lands with board-freeze) — it does not see. **Reflex: adding a TX, a `goto` or an early exit anywhere in the cycle — the radio must still reach the Phase 5 sleep in Standby, and nothing may wake it after.**

25. **A byte of the CCM plaintext has MORE THAN ONE WRITER — the panic path packs its own literals into the same 14 bytes the telemetry path fills, so re-homing a byte is an audit of every call site of `Soldier_Build_CCM_LoRa_Packet` and of every backend reader of that byte, not an edit of one `Pack_*` helper** [FW.59 / wire-rev2.2, 2026-10-08]. Measured on the slot package: the recommendation moved the SEC.20 contract report into byte 11 after reading only the telemetry call in `firmware/soldier/main.c`, while the CCM panic call writes `0xFF` («код паніки») into that same byte — after the move every panic frame would have decoded as `reverted` and raised a critical `firmware_reverted` alert, and nothing in the host suite would have reddened, because each path is tested alone. The same byte also carries a SENTINEL with a consumer of its own (`0xFE` → `apply_time_uncertain_sentinel!` in `app/services/telemetry_unpacker_service.rb`), and the diag byte has a parser that reads any new bit as the old field (`threshold_invalid`). The read-only adversary found all three; the recommendation's author found none. **Reflex: before a wire byte changes meaning, list its WRITERS (`grep -n "Soldier_Build_CCM_LoRa_Packet(" firmware/soldier/main.c` — telemetry and panic) and its READERS (unpacker · sentinel handlers · alert dispatch), and ask of each sentinel value which consumer branches on it — the layout table in `lora_ccm.h` names one writer per byte and is silent about the rest.** Home of the ratified layout and its consumer list — `docs/03_05` §2.1 ledger (wire-rev2.2) and the implementation leg `00_07` FW.66.

26. **Sleeping from INSIDE an interrupt with WFI wakes only on an interrupt that can PREEMPT it — at the highest priority nothing can, so the board sleeps until reset** [FW.69, 2026-10-09]. The brownout reflex (`HAL_PWR_PVDCallback`, called from the PVD IRQ at priority 0) entered STOP2 with `PWR_STOPENTRY_WFI` while its comment promised «until the voltage rises»; the voltage rise is the SAME IRQ, already active, so it could never wake it, and IWDG is frozen in STOP2 by the conveyor. ⚠️ **The first fix was wrong too, and the way it was wrong is the transferable part:** `SEVONPEND` + WFE turns a TRANSITION into pending into an event, not the pending STATE — a rise that lands before the first WFE leaves the IRQ pending with no event, `SEV; WFE; WFE` swallows one that lands in the window, and whether the SAME active IRQ re-pending counts as an event at all the architecture does not promise. **The form that holds: don't sleep IN the handler — sleep on EXIT from it.** Save state, set a coma flag, set LPMS=STOP2 + SLEEPDEEP + `HAL_PWR_EnableSleepOnExit()`, and return: a rise during the body tail-chains into the same IRQ, a later rise preempts the sleep as an inactive interrupt, and the callback seeing «not below threshold while in coma» resets; any other interrupt (a future WUT) runs and drops back to sleep, so no reset loop. Under sleep-on-exit every OTHER enabled handler runs while the thread is frozen at an arbitrary point (a radio IRQ would wake the radio and could leave HAL_SUBGHZ stuck BUSY), so mask them all in the NVIC for the coma — except the wake IRQ, whose pending bit you must not clear. In thread mode (the boot path) sleep-on-exit never fires and there is no tail-chain either: call the callback, then `for (;;) { if (!PVDO) NVIC_SystemReset(); __WFI(); }` — a rise that lands before the coma flag is set is consumed by the PVD IRQ, and a bare WFI loop would then sleep on a healthy rail forever (third adversary round, 2026-10-09). Two companions: act only on the falling edge (`PWR_FLAG_PVDO`), and arm the PVD AFTER the DR restore with EXTI/NVIC pending cleared — the callback writes RAM state into DR. **Reflex: before any low-power entry, ask which context you are in; in handler mode, name the interrupt that will wake you, check it can preempt you, and check it cannot go pending before you arm the sleep.**
