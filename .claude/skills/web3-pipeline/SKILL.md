1a. 🔴 **A monitoring read that MUTATES what it reports is not a probe — and both circuit breakers in this tree had exactly that** [ARCH.84, 2026-08-14]. `Web3::ResilientClient#provider_health` and `Web3::HttpClient#circuit_status` both called the *mutating* `provider_available?`, which on an elapsed cooldown zeroes the failure count, deletes `@circuit_opened_at` and rewrites the Prometheus gauge. **So opening the health panel half-opened real breakers** — two operators looking at the dashboard changed RPC routing by the act of looking, and the gauge they were reading recorded their own visit. Fixed as a PAIR per class: pure `provider_reachable?` (report) ⊥ mutating `provider_available?` (dispatch only — `available_urls` / `check_circuit!`, because only the dispatcher has standing to *try* a provider). ⚠️ Keep the branches mirrored rather than shared: the transition must fire ONLY on «cooldown elapsed», never on the two early `true`s (circuit closed · desync guard) — collapsing them into one condition is exactly what makes the transition arbitrary. 🔴 **The tracker item named ONE class; there were two** — the second was reachable only by reading `provider_available?`'s *callers*, not by grepping the item's own vocabulary. **Reflex for any «probe / status / health» method: read what it CALLS, not what it is named — and ask whether the call writes.** 🔴 **And the refactor's own sting, worth more than the fix: removing the side effect left the MECHANISM untested.** Coverage dropped below the floor and named the branch — the half-open transition in `HttpClient` had no test of its own; the only thing exercising it in the whole suite was the monitoring call, i.e. the defect. **So when you strip a side effect out of a reader, ask whether that effect was the mechanism's ONLY exerciser — if it was, the fix ships the mechanism without a net, and nothing says so except a coverage floor you might not be watching.** ⚠️ Two smaller traps met on the way: duplicating the decision into a pure/mutating PAIR doubles a dead defensive branch (keep one home for the decision, the sibling holds only the transition condition), and a `&&` whose second operand is always true where it is reached is an uncoverable branch by construction.

2. **manual_review state** — `BlockchainTransaction` AASM has a `manual_review` state = DOUBLE-SPEND GUARD. tx_hash exists but outcome unknown → funds locked until manual check. Don't auto-resolve. 🔴 **But the state is OVERLOADED, and `BLOCKCHAIN_MANUAL_REVIEW_DEPTH` cannot tell the two apart** [ARCH.82, 2026-08-14]: an INS.2 reserve-gate HOLD parks a payout here too, and that is *policy working as designed* (reconcile the event, maybe raise the threshold) — the opposite response to a double-spend limbo (funds possibly lost). One signal answering two questions is a measurement substitution, so the HOLD carries its OWN counter (`silkennet_insurance_reserve_hold_total{reason}` + `sn-alert-insurance-reserve-hold`). ⚠️ `:eval_error` is NOT counted — that branch re-raises for Sidekiq retry, and counting it would page an operator for a network blip disguised as halted issuance. **Reflex: before reading a depth gauge as an incident signal, list every writer that parks a row in that state.**

18. 🔴 **`wallets.balance` is a GROSS lifetime counter — the mint never debits it, and anything deciding "how much can be minted" must read `available_balance`** [ARCH.94, 2026-08-12]. `lock_and_mint!` only increments `locked_balance`; converted points stay locked **forever by design** (`04_01 §6` E.66 — "сконвертовано назавжди, finalize не потрібен"), and `release_locked_funds!` fires on the FAILURE path only (`fail` event + rollback service). So `available_balance = balance − locked_balance` is the only quantity that means "still convertible". 🔴 **The defect this bought, and why it is the most confusable invariant on the money path:** `EvaluateTreeBatchWorker` sized the mint from `balance` while `lock_and_mint!` gates on `available_balance` — after the first mint `locked ≥ threshold > balance mod threshold` holds forever, so **every wallet minted exactly once and then raised on every later cycle**, swallowed by `rescue StandardError` into a counter (job returns SUCCESS, no retry, no DeadSet, mint SLO stays 100 % because the wallet never enters its denominator). The mirror lived in `TokenomicsEvaluatorWorker#eligible_wallets` (`where("balance >= ?")`), which re-selected the dead wallet hourly forever. ⛔ **Do NOT "fix" this by releasing the lock on `confirmed`** — measured: that yields **+50 % over-emission** (3 SCC on 20 000 credited points instead of 2), because `balance` is gross and releasing makes the same points mintable twice.
