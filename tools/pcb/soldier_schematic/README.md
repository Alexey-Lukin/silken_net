# HW.56 — the Soldier's schematic, written by code (power path · MCU without the RF path)

The node's schematic is generated by `build_schematic.rb`, the same way `tools/pcb/*` generate boards: the agent writes and checks it without a window, the human opens the same file in KiCad. Ruling, tools and their limit (no vendor model of the power path) — [`02_01 §7`](../../../docs/02_01_Hardware_Architecture_and_BOM.md); state and open legs — [`00_07`](../../../docs/00_07_Action_Plan_Tracker.md) HW.56.

## What is here

| File | Role |
|---|---|
| `build_schematic.rb` | the source — generates everything below (AGPL-3.0-or-later, like all tooling); its header says where every number comes from and what the schematic does NOT prove |
| `soldier.kicad_sch` | the root sheet: one block per sheet below — ⛔ none of the `.kicad_sch` files is edited by hand: edit the generator and rebuild |
| `soldier_power.kicad_sch` | sheet `power` — the power path: BQ25570 with its dividers, the VSTOR clamp (position 14), the Vcap-sense switch (position 23) |
| `soldier_mcu.kicad_sch` | sheet `mcu` — the STM32WLE5CC without the RF path: supply and decoupling, SMPS, HSE from the TCXO, LSE, NRST, SWD pads |
| `silkennet.kicad_sym` | the project symbol library: symbols corrected against their datasheets (the BQ25570 — two pin types per SLUSBH2G; the STM32WLE5CC — five pin types per DS13105) and symbols KiCad does not ship, built from the datasheets' pin tables (TLV840N…PL · TPS22860 · the NT2016SF TCXO; the DMN2990UFA reuses KiCad's NMOS drawing, renumbered to the pads of `tools/pcb/hw12_dmn2990ufa_breakout`) |
| `sym-lib-table` | the project library table — stock libraries through `${KICAD10_SYMBOL_DIR}`, ours through `${KIPRJMOD}`, so the schematic does not depend on the user's global table |
| `soldier.kicad_pro` | a minimal project file, so KiCad opens the folder as a project — generated every run and judged by `--check`, because ERC rule severities live in it |

The sheets form one hierarchy on purpose: a KiCad global label joins nets only inside one project, so two separate files with matching labels would join nothing — and one board takes one netlist.

The design outputs are hardware design and fall under **CERN-OHL-S-2.0** by the zone map in [`/NOTICE`](../../../NOTICE); KiCad's S-expressions have no comment syntax, so they carry no per-file tag.

## Rebuild and check

```bash
ruby tools/pcb/soldier_schematic/build_schematic.rb           # regenerate + ERC + PDF + SPICE netlist into out/
ruby tools/pcb/soldier_schematic/build_schematic.rb --check   # the same, and red if the committed files lag the generator
```

Any Ruby works (no bundle); KiCad 10 is looked up in `~/Applications/KiCad`, or through `KICAD_CLI` and `KICAD_SYMBOL_DIR`. ⚠️ Rebuild with the same KiCad version as the image CI pins (`KICAD_IMAGE` in `.github/workflows/cad_smoke.yml`): the schematic embeds copies of the stock symbols, so another version's libraries make the committed files «stale» in CI on a correct tree. Upgrading KiCad is one commit — rebuild locally with the new version and move that digest.

The run is red on any ERC violation (all severities, both sheets — ERC runs on the root), on a failed PDF or netlist export, on a capacitor value written with a bare `F` (SPICE reads it as femto), and on any pin whose net in KiCad's own exported netlist differs from the net the generator intended. That last check is what makes drawing safe: the generator keeps the intended connections (pin → net) apart from the drawing (wires, labels, ground symbols), so a wire that touches the wrong pin, or a label renamed to another existing net — which ERC cannot see, since no label is left dangling — turns the run red with the pins named.

A mistake in the *intended* connections changes both halves at once, so two more checks judge the intent itself:

- **parts the datasheet requires** — every row of `MCU_PARTS` (decoupling, SMPS, TCXO and LSE parts, NRST capacitor, each with its datasheet page) and every SWD pad must be in KiCad's netlist: a capacitor dropped from the drawing turns the run red even though intent and drawing agree;
- **pin function** — the MCU pin map names the silicon function a net needs (SWDIO · SWCLK · I2C1_SCL · OSC32_IN · VDDTCXO …), and that function must be among the alternates of *that* pin in KiCad's symbol (ST's data, checked against DS13105 Tables 20/21): swapped PA13/PA14 turn red even when intent and drawing are swapped alike.

One ERC rule is switched off in the generated `.kicad_pro`: `isolated_pin_label`, because the sheet boundary (RF path, I²C1, console) and the GPIOs still «open» are single-pin labels by design. A stricter check replaces it: a single-pin net that is not a declared boundary (`LONE_PIN_NETS`) turns the run red.

The drawing form (ground symbols, dividers as wired ladders, parallel capacitors on a shared rail, IC pins as stub + label) is a delegated ruling in [`02_01 §7`](../../../docs/02_01_Hardware_Architecture_and_BOM.md); on a dense IC a global label sits on a longer stub, so its frame clears the neighbouring local labels. `out/` is ignored by git — it is rebuilt.

The divider resistors are not typed into the generator: it reads them from the table in [`02_03 §5`](../../../docs/02_03_BQ25570_MPPT_Nano_Power.md) with the same parser `tools/firmware/bq25570_dividers.rb --check-canon` uses to judge that table, so the schematic cannot drift from the canon as long as `--check` runs — and CI runs it whenever one of its inputs changes (job `schematic` in `.github/workflows/cad_smoke.yml`). Part numbers are not copied either: each part's `BOM` field points to its position in [`02_01 §3.1`](../../../docs/02_01_Hardware_Architecture_and_BOM.md); where a value names a part number that is still a candidate (the clamp, position 14), it says «(кандидат)».

The MCU sheet holds only the pins the canon already gives a home ([`03_01`](../../../docs/03_01_Firmware_Lifecycle_and_DMA.md), pin budget): SWD, I²C1, console, TCXO, LSE, and PA0 left unconnected as a reserve. Every other GPIO carries a global label `<pin>_OPEN` until the `.ioc` pin map (FW.46). That is also why the two nets the Vcap-sense switch shares with the MCU (`VCAP_SENSE_EN`, `VCAP_ADC`) do not reach an MCU pin yet: the canon leaves that pin to layout and the `.ioc`. `VOUT` does — it is the global label that feeds VDD, VDDA, VDDRF, VDDSMPS and VBAT. The RF path (position 19) is not drawn: its pins leave the sheet as labels, because the publication terms of the ST note it would copy have not been read yet.

## Opening it in KiCad

Open `soldier.kicad_pro` from the main KiCad window and start the Schematic Editor from there; the two sheets are blocks on the root. After a rebuild, use File ▸ Revert to see the new version. Do not save over the files from KiCad: the next rebuild overwrites them.
